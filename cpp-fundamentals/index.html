0.回答框架：怎么答才”经得起追问”

字节面试官的习惯是顺着一个点往下钻三到五层，直到你答不出来为止。所以回答不要一次把知道的全倒出来，而是分层：

  1. 一句话定义（是什么）。
  2. 设计动机（为什么需要它，解决了什么问题）。
  3. 实现机制（编译器 / 运行库 / 操作系统各做了什么）。
  4. 边界与陷阱（什么时候会出错，怎么排查）。
  5. 主动引出下一层（“这里其实还涉及到……”），把追问方向引到你熟的地方。

复杂度、线程安全、异常安全，是三个可以对任何 C++ 问题追加的通用维度，面试官答不出别的追问时就会问这三个，提前准备。

1.内存管理

1.1 进程内存布局

是什么：一个 C++ 程序运行时，虚拟地址空间从低到高大致分为：

区域 内容 生命周期 备注
.text 机器指令 进程 只读、可执行、可在进程间共享
.rodata 字符串字面量、const 全局常量 进程 只读，写入触发 SIGSEGV
.data 已初始化的全局 / 静态变量 进程 占可执行文件体积
.bss 未初始化或零初始化的全局 / 静态变量 进程 不占文件体积，加载时清零
堆 heap malloc / new 分配 手动管理 向高地址增长，brk 控制边界
mmap 区 动态库、大块 malloc、文件映射、线程栈 各异 位于堆和栈之间
栈 stack 局部变量、参数、返回地址、保存的寄存器 函数调用期 向低地址增长，主线程默认 8MB（ulimit -s）

追问链

  • 局部 static 变量放哪？ .data 或 .bss，和全局变量一样，只是作用域受限。C++11 起首次执行到定义处才初始化，且线程安全（编译器插入 guard 变量 + 原子检查，即 __cxa_guard_acquire）。
  • const int x = 10; 全局放哪？ 通常 .rodata。若被取地址或 extern，编译器必须分配存储；否则可能直接被常量折叠进指令，不占内存。
  • 字符串字面量能修改吗？ char* p = "abc"; p[0] = 'x'; 是未定义行为，实际会 SIGSEGV，因为在 .rodata。char a[] = "abc"; 是把字面量拷贝到栈上，可以改。
  • 栈溢出怎么发生？ 递归过深或大数组局部变量（如 int a[1<<20]）。栈底有 guard page，触碰它就 SIGSEGV。解决：改堆分配、改迭代、ulimit -s 或 pthread_attr_setstacksize。
  • 为什么栈比堆快？ 栈分配只是移动 rsp 寄存器一条指令，释放随函数返回自动完成，局部性好、缓存友好；堆要走 allocator 的查找、分裂、合并、加锁。
  • 线程栈在哪？ 主线程栈由内核创建；其他线程栈由 pthread_create 用 mmap 分配，默认 8MB，位于 mmap 区。所以线程多了要注意虚拟地址空间消耗（32 位尤其明显）。

1.2 malloc / free 的底层（glibc ptmalloc2）

为什么要懂：字节会直接问”malloc 底层怎么实现”、“free 怎么知道要释放多大”、“频繁 malloc 小对象有什么问题”。

两条系统调用路径

  • 小于 M_MMAP_THRESHOLD（默认 128KB，且会随释放的大块动态上调，最高 32MB）：从堆上分配，堆不够时调 brk/sbrk 把堆顶上移。
  • 大于阈值：直接 mmap 一块匿名内存，free 时 munmap 立刻还给内核。

chunk 结构（64 位）

+------------------+
| prev_size        |  前一个 chunk 空闲时才有意义
+------------------+
| size | A | M | P |  本 chunk 大小（含头），低 3 位是标志：
+------------------+  A: 非主分配区  M: 由 mmap 分配  P: 前一个 chunk 在使用中
| user data ...    |  <- malloc 返回的指针指向这里
|                  |
+------------------+
  • chunk 头是 prev_size(8) + size(8) 共 16 字节，malloc 返回的 p 指向头之后。所以 free(p) 用 p - 8 读 size 字段、p - 16 定位 chunk 起始，这就是”free 怎么知道大小”的答案。
  • 最小 chunk 32 字节，返回地址 16 字节对齐。malloc(1) 实际占 32 字节，这是”小对象浪费”的来源之一。
  • 空闲 chunk 的 user data 区被复用为双向链表指针 fd/bk，所以 use-after-free 读到的”垃圾”往往是指针值。

空闲块管理（bins）

结构 大小范围（64 位） 特点
tcache（glibc ≥ 2.26） ≤ 1032 字节，每线程 64 个桶，每桶最多 7 个 无锁，最快，LIFO 单链表
fast bins ≤ 128 字节 单链表，LIFO，不合并，相邻空闲块不会立刻合并
unsorted bin 任意 free 后先放这里，下次 malloc 时再归类
small bins < 1024 字节，62 个，每个精确一种大小 双向循环链表
large bins ≥ 1024 字节 按大小范围分桶，桶内有序
top chunk 堆顶剩余 所有 bin 都不满足时从这里切

分配流程：tcache → fast bin → small bin → 遍历 unsorted bin（顺手归类）→ large bin → top chunk → 不够则 brk 扩堆或 mmap。

释放流程：小块进 tcache / fast bin；否则检查前后 chunk 是否空闲，合并后放 unsorted bin；若合并后紧邻 top chunk 就并入 top；top 超过 M_TRIM_THRESHOLD（128KB）时调 brk 收缩还给内核。

追问链

  • 多线程下 malloc 怎么保证线程安全？ 每个 arena 一把锁；线程首次 malloc 时尝试获取一个 arena，拿不到就新建（数量上限 8 × 核数）。tcache 是线程私有的，小分配完全无锁。
  • 内存碎片是什么，怎么减少？ 外部碎片：空闲块总量够但不连续。内部碎片：对齐和最小 chunk 造成的浪费。减少办法：对象池 / slab（同大小对象复用）、内存池预分配大块自己切、使用 tcmalloc / jemalloc（按 size class 分级、线程本地缓存、更好的合并策略）、避免长生命周期对象和短生命周期对象交错分配。
  • free 之后内存为什么没还给操作系统？ 只有 top chunk 超阈值时才 trim；中间的空闲块无法 trim，只能等合并。所以 RSS 不降是正常的，不一定是泄漏。
  • tcmalloc 和 ptmalloc 的区别？ tcmalloc 按 size class（约 88 级）分配，每线程有 ThreadCache，中央有 CentralFreeList 和 PageHeap，小对象无锁，大对象按页（8KB）管理，用 span 描述连续页，用 pagemap（radix tree）从地址反查 span，所以 free 也不需要 chunk 头。
  • malloc(0) 返回什么？ 实现定义。glibc 返回一个最小 chunk 的有效指针，可以 free。
  • calloc 和 malloc 的区别？ calloc 会清零。对大块 mmap 分配，内核给的页本来就是零页，calloc 可以跳过 memset，所以有时比 malloc + memset 快。

1.3 new / delete 与 malloc / free

区别表

new / delete malloc / free
层次 C++ 运算符，可重载 C 库函数
类型 返回具体类型指针，编译器算大小 返回 void*，手工传字节数
构造 / 析构 调用 不调用
失败 抛 std::bad_alloc（nothrow 版本返回空） 返回 NULL
数组 new[] / delete[] 配对 无区分
底层 operator new 默认调 malloc 直接分配

new 表达式的三步

未定义行为 / 伪代码，不保证可编译
T* p = new T(args);
// 等价于：
void* raw = operator new(sizeof(T));   // 1. 分配原始内存，失败抛 bad_alloc
T* p = static_cast<T*>(raw);
new (p) T(args);                        // 2. placement new：在 raw 上构造
// 若构造函数抛异常，编译器会自动调 operator delete(raw)，不会泄漏

delete p 则是先调 p->~T()，再 operator delete(p)。

追问链

  • new 出来的对象用 free 释放会怎样？ 析构函数不会被调用，若 T 持有资源就泄漏；若类重载了 operator new 走的是别的分配器，free 直接 crash；即使是默认实现，也属于未定义行为。
  • delete[] 怎么知道数组有多少个元素？ 对有非平凡析构函数的类型，new[] 会在数组前面多分配 8 字节存放元素个数（cookie），delete[] 读它逐个析构。对 int 这类平凡类型不存 cookie，delete[] 只是 free。所以 new[] 配 delete 对 int 数组”碰巧”没事，对 std::string 数组一定崩。
  • operator new 失败后做什么？ 先调用 std::set_new_handler 设置的处理函数（可以释放缓存后重试），处理函数为空才抛 bad_alloc。
  • placement new 有什么用？ 内存池、std::vector 在预留空间上构造元素、在共享内存上构造对象。用完要手动调 p->~T()，不能 delete。
  • 为什么要重载 operator new？ 自定义分配策略（内存池）、统计与追踪泄漏、对齐（C++17 有 std::align_val_t 重载）。类内重载是隐式 static 的。
  • new 一个对象和在栈上定义一个对象，除了位置还有什么区别？ 生命周期、异常安全（栈对象由 RAII 保证析构）、性能、以及多态需要（基类指针指向堆上派生类对象）。

1.4 常见内存错误与排查

错误 表现 排查
内存泄漏 RSS 持续增长 valgrind memcheck、-fsanitize=leak、tcmalloc heap profiler
悬垂指针 / use-after-free 随机崩溃、读到脏数据 -fsanitize=address（ASan）几乎必抓
double free glibc 直接 abort：“double free or corruption” ASan、gdb backtrace
越界写 破坏相邻 chunk 头，通常在下一次 malloc/free 时崩 ASan、MALLOC_CHECK_=3
栈溢出 SIGSEGV，backtrace 极深 gdb bt、ulimit -s
返回局部变量地址 值被后续调用覆盖 编译器警告 -Wreturn-local-addr
未初始化读 结果不确定 valgrind、-fsanitize=memory（MSan，仅 clang）

追问链

  • 段错误怎么定位？（字节三面原题）开 core dump（ulimit -c unlimited），gdb ./bin core，bt 看栈，frame N 切帧，info locals。若栈被打坏 bt 不可信，用 ASan 重跑；若是 release 无符号，用 addr2line -e bin 地址。线上环境看 dmesg 拿崩溃地址。
  • ASan 原理？ 编译器在每次内存访问前插桩，检查 shadow memory（每 8 字节应用内存对应 1 字节 shadow）；malloc 被替换，释放的内存进隔离区暂不复用，两侧加 redzone。开销约 2 倍时间、2 到 3 倍内存。
  • valgrind 原理？ 动态二进制翻译，在虚拟 CPU 上执行并跟踪每个字节的可寻址性和已初始化性。慢 20 到 50 倍，但不需要重新编译。

1.5 RAII 与智能指针

RAII 是什么：Resource Acquisition Is Initialization。把资源的生命周期绑定到栈对象的生命周期上，构造获取、析构释放。析构函数在作用域退出时一定执行，无论是正常返回、break、还是异常传播，这是 C++ 异常安全的基石。std::lock_guard、std::fstream、智能指针都是 RAII。

unique_ptr

  • 独占所有权，不可拷贝，可移动。
  • 默认删除器下 sizeof(unique_ptr<T>) == sizeof(T*)，零开销。传入函数指针作为删除器会变成 16 字节，传入无状态 lambda 或函数对象仍是 8 字节（空基类优化）。
  • unique_ptr<T[]> 特化调用 delete[]。
  • release() 放弃所有权返回裸指针，reset() 释放并可接管新指针，get() 只借用。
#include <memory>
#include <cstdio>
struct FileCloser { void operator()(FILE* f) const { if (f) fclose(f); } };
using FilePtr = std::unique_ptr<FILE, FileCloser>;
FilePtr openFile(const char* path) { return FilePtr(fopen(path, "r")); }
static_assert(sizeof(FilePtr) == sizeof(FILE*), "stateless deleter is free");

shared_ptr

内存布局：一个 shared_ptr 对象是两个指针，16 字节。一个指向被管理对象，一个指向控制块。控制块里有：强引用计数、弱引用计数、删除器、分配器、（make_shared 时）对象本身。

shared_ptr<T>            控制块 (heap)
+-----------+           +------------------+
| T* ptr    |---------->| T object         |  (make_shared 时对象内嵌在这里)
| ctrl*     |---------->| strong_count     |
+-----------+           | weak_count       |
                        | deleter          |
                        | allocator        |
                        +------------------+

为什么需要两个计数：strong 归零时析构对象，weak 归零时才释放控制块。weak_ptr 要能在对象已销毁后仍安全地查询 expired()，所以控制块必须比对象活得久。

make_shared vs shared_ptr<T>(new T)

make_shared shared_ptr(new T)
分配次数 1 次（对象和控制块一起） 2 次
缓存局部性 好 差
异常安全 天然安全 C++17 前 f(shared_ptr(new T), g()) 中 g 抛异常可能泄漏
自定义删除器 不支持 支持
私有构造函数 不能用 能用
内存释放时机 对象内存要等所有 weak_ptr 消失才释放（因为和控制块一体） 对象独立释放

线程安全语义（高频追问）

  • 控制块的引用计数是原子操作，所以多个线程各自持有不同的 shared_ptr 副本指向同一对象，并发拷贝 / 析构是安全的。
  • 同一个 shared_ptr 对象被一个线程写（reset、赋值）、另一个线程读，是数据竞争。C++20 提供 std::atomic<std::shared_ptr<T>>。
  • 被管理的对象 T 本身的线程安全由 T 自己负责，shared_ptr 不管。

循环引用

#include <memory>
#include <iostream>
struct Node {
    std::shared_ptr<Node> next;
    std::weak_ptr<Node>   prev;       // 若这里也是 shared_ptr，a 和 b 互相持有，计数永远不为 0
    ~Node() { std::cout << "~Node\n"; }
};
int main() {
    auto a = std::make_shared<Node>();
    auto b = std::make_shared<Node>();
    a->next = b;
    b->prev = a;                       // weak 不增加强计数
    // 离开作用域：a 计数 1→0 析构，其成员 next 析构使 b 计数 1→0 析构。正确打印两次 ~Node
}

判断原则：所有权方向用 shared_ptr（父持子），反向观察用 weak_ptr（子看父）；观察者模式中被观察者对观察者也用 weak_ptr。

weak_ptr 用法：lock() 返回 shared_ptr（对象已销毁则为空），必须用返回值而不能用 expired() 后再操作，因为两步之间对象可能被别的线程释放。

enable_shared_from_this

  • 问题：类内部拿 this 构造一个新 shared_ptr 会产生第二个控制块，双重释放。
  • 方案：继承 enable_shared_from_this<T>，它内部持有一个 weak_ptr<T>，shared_ptr<T> 的构造函数检测到这个基类时会给 weak 赋值。shared_from_this() 就是 weak.lock()。
  • 陷阱：在构造函数里调用 shared_from_this() 会抛 bad_weak_ptr，因为此时还没有任何 shared_ptr 接管它；对象必须由 shared_ptr 管理，栈对象调用它同样抛异常。
#include <memory>
#include <functional>
#include <vector>
struct Session : std::enable_shared_from_this<Session> {
    std::vector<std::function<void()>> callbacks;
    void start() {
        // 回调里延长自身生命周期，避免异步回调时 this 已被销毁
        auto self = shared_from_this();
        callbacks.push_back([self] { /* use self->... */ });
    }
};

手写 shared_ptr（字节高频手撕）。要点：拷贝加计数、析构减计数并在归零时销毁、赋值用 copy-and-swap 一次处理自赋值与异常安全、计数用原子、删除器用类型擦除藏进控制块。

#include <atomic>
#include <utility>
#include <iostream>
template <class T>
class SharedPtr {
    struct Ctrl {                                  // 控制块：强/弱计数分开，weak 要能在对象死后仍查 expired
        std::atomic<long> strong{1}, weak{1};      // weak 初始 1：所有 shared 合起来算一个 weak 引用
        virtual void dispose() = 0;                // 销毁被管对象
        virtual ~Ctrl() = default;
    };
    template <class D>
    struct CtrlImpl : Ctrl {                       // 类型擦除：删除器类型只活在这里，不进 SharedPtr 的模板参数
        T* p; D d;
        CtrlImpl(T* p_, D d_) : p(p_), d(std::move(d_)) {}
        void dispose() override { d(p); }
    };
    T* ptr_ = nullptr;
    Ctrl* ctrl_ = nullptr;

    void incStrong() const { if (ctrl_) ctrl_->strong.fetch_add(1, std::memory_order_relaxed); }
    void decStrong() {
        // release：保证本线程此前对对象的写，对最后那个执行 dispose 的线程可见
        if (ctrl_ && ctrl_->strong.fetch_sub(1, std::memory_order_acq_rel) == 1) {
            ctrl_->dispose();
            if (ctrl_->weak.fetch_sub(1, std::memory_order_acq_rel) == 1) delete ctrl_;
        }
    }
public:
    SharedPtr() = default;
    template <class D = void(*)(T*)>
    explicit SharedPtr(T* p, D d = [](T* q){ delete q; })
        : ptr_(p), ctrl_(p ? new CtrlImpl<D>(p, std::move(d)) : nullptr) {}

    SharedPtr(const SharedPtr& o) : ptr_(o.ptr_), ctrl_(o.ctrl_) { incStrong(); }
    SharedPtr(SharedPtr&& o) noexcept : ptr_(o.ptr_), ctrl_(o.ctrl_) { o.ptr_ = nullptr; o.ctrl_ = nullptr; }
    ~SharedPtr() { decStrong(); }

    SharedPtr& operator=(SharedPtr o) noexcept { swap(o); return *this; }   // copy-and-swap：自赋值与异常安全一次解决
    void swap(SharedPtr& o) noexcept { std::swap(ptr_, o.ptr_); std::swap(ctrl_, o.ctrl_); }

    T* get()  const noexcept { return ptr_; }
    T& operator*()  const noexcept { return *ptr_; }
    T* operator->() const noexcept { return ptr_; }
    explicit operator bool() const noexcept { return ptr_ != nullptr; }
    long use_count() const noexcept { return ctrl_ ? ctrl_->strong.load(std::memory_order_relaxed) : 0; }
    void reset() { SharedPtr().swap(*this); }
};

struct Res { int id; explicit Res(int i) : id(i) { std::cout << "ctor" << id << " "; } ~Res() { std::cout << "dtor" << id << " "; } };
int main() {
    {
        SharedPtr<Res> a(new Res(1));
        std::cout << a.use_count() << " ";           // 1
        { SharedPtr<Res> b = a; std::cout << a.use_count() << " "; }   // 2
        std::cout << a.use_count() << " ";           // 1
        SharedPtr<Res> c(new Res(2));
        c = a;                                       // Res2 在这里析构
        std::cout << "| " << a.use_count() << " ";   // 2
    }
    std::cout << "\n";
    bool called = false;
    { SharedPtr<int> d(new int(5), [&](int* p){ called = true; delete p; }); }
    std::cout << "自定义删除器被调用: " << called << "\n";
}

面试时如果时间紧，可以只写强计数版本（去掉 Ctrl 的虚函数和 weak 计数），然后主动说明”完整版还需要 weak 计数和删除器类型擦除”，把追问引到自己熟的地方。

为什么减计数用 acq_rel 而加计数用 relaxed：加计数只需原子性，不需要与其他内存操作建立顺序；减到 0 的那个线程要销毁对象，必须能看见其他线程此前对对象的所有写，所以需要 acquire 语义，同时自己的写也要对后来者可见，所以是 release —— 合起来就是 acq_rel。

追问链

  • shared_ptr 能管理数组吗？ C++17 起 shared_ptr<T[]> 支持，之前要自己传 default_delete<T[]>。
  • 为什么不用 auto_ptr？ 拷贝语义是转移所有权，放进容器会出错，C++17 已删除。
  • 智能指针有开销吗？ unique_ptr 零开销；shared_ptr 拷贝有原子加减，跨核竞争时缓存行来回失效，热路径上尽量传引用或 const shared_ptr&，不要按值传。
  • 什么时候用裸指针？ 不拥有所有权的观察、与 C 接口交互、性能敏感且生命周期显然的场合。C++ Core Guidelines：裸指针表示”不拥有”。
  • shared_ptr 怎么做到删除器类型不出现在模板参数里？ 类型擦除：控制块是一个带虚函数的基类，shared_ptr<T>(p, deleter) 构造时生成一个派生控制块类型，把 deleter 存在里面。这也是它和 unique_ptr 的关键区别。

1.6 内存对齐

为什么要对齐：CPU 按字长访问内存，未对齐访问在 x86 上慢（可能跨两个缓存行），在 ARM 等平台直接总线错误；原子操作要求对齐；SIMD 指令要求 16/32 字节对齐。

规则（面试口述版）

  1. 每个成员的偏移量必须是该成员对齐值的整数倍（默认对齐值 = 成员大小，不超过 #pragma pack(n)）。
  2. 结构体总大小必须是最大成员对齐值的整数倍。
  3. 结构体的对齐值 = 最大成员对齐值。
#include <cstdint>
#include <cstddef>
struct A { char a; int b; char c; };          // 1 + 3(pad) + 4 + 1 + 3(pad) = 12
struct B { char a; char c; int b; };          // 1 + 1 + 2(pad) + 4 = 8，调整顺序省 4 字节
struct C { char a; uint32_t b; uint8_t c; uint64_t d[0]; };  // 字节三面原题
// a(1) pad(3) b(4) c(1) pad(7) = 16。d 是柔性数组不占空间，但把整体对齐提升到 8
static_assert(sizeof(A) == 12 && sizeof(B) == 8 && sizeof(C) == 16);
static_assert(alignof(C) == 8);
#pragma pack(push, 1)
struct P { char a; int b; };                  // 5，无填充
#pragma pack(pop)
static_assert(sizeof(P) == 5);
struct alignas(64) CacheLine { int x; };      // 强制 64 字节对齐，用来避免 false sharing
static_assert(sizeof(CacheLine) == 64);

追问链

  • 柔性数组有什么用？ 变长消息头：struct Msg { uint32_t len; char data[]; }，一次 malloc(sizeof(Msg) + n) 得到头和数据连续的内存，内核和网络协议栈大量使用。C99 标准写法是 data[]，data[0] 是 GNU 扩展。
  • 什么是 false sharing？ 两个线程频繁写的变量落在同一个 64 字节缓存行，导致缓存行在核间来回失效。解决：alignas(64) 或填充，把热点变量隔开。
  • 空类大小为什么是 1？ 保证两个不同对象地址不同，数组元素能区分。派生类继承空基类时可以做空基类优化（EBO），基类不占空间。
  • #pragma pack(1) 的代价？ 访问成员可能变慢，某些平台崩溃；取成员地址后交给要求对齐的函数（如原子操作）会出错。仅在协议解析等确实需要时使用。

2.指针与引用

2.1 指针 vs 引用

维度 指针 引用
本质 一个存地址的变量，自身有地址和大小 对象的别名，语言层面不是对象
可否为空 可以 nullptr 必须绑定有效对象（悬垂引用是 UB，不是”空”）
可否重绑定 可以 初始化后不可改指向，r = x 是给被引对象赋值
多级 int** 没有”引用的引用”（引用折叠是模板推导规则，不是二级引用）
算术 p + 1 按类型大小前进 不支持
sizeof 指针大小（8） 被引对象大小
作为参数 需判空，调用方要取地址 语义清晰，调用方直接传对象

引用底层怎么实现：编译器通常用一个 const 指针实现，函数参数传引用时汇编里传的就是地址。但标准不要求引用占存储，例如 int& r = x; 在同一作用域内编译器往往直接把 r 替换成 x，不产生任何指针。所以”引用就是指针”这句话在面试里要说成”编译器一般用指针实现引用，但语言层面引用不是对象，没有自己的地址和大小”。

追问链

  • 什么时候必须用指针？ 需要表示”没有”（可空）、需要改变指向（链表遍历）、需要放进容器（vector<int&> 不合法，用 reference_wrapper 或指针）、与 C 接口交互。
  • 函数参数选 T、const T&、T&& 还是 T*？ 小的平凡类型（int、指针、string_view）按值；只读大对象用 const T&；要拿走所有权用按值 + std::move（或 T&&）；可空用指针或 optional。
  • 返回引用什么时候安全？ 返回参数引用、成员引用、静态对象引用安全；返回局部变量引用是 UB（gcc 会警告，值在栈被复用后变化）。

2.2 值类别与移动语义

三种基本值类别

  • lvalue：有身份、不能被移动。变量名、*p、返回左值引用的函数调用、字符串字面量。
  • prvalue：无身份、能被移动。字面量 42、a + b、按值返回的函数调用、lambda 表达式。
  • xvalue：有身份、能被移动。std::move(x)、返回 T&& 的函数调用、std::move(obj).member。

glvalue = lvalue + xvalue（有身份）；rvalue = prvalue + xvalue（能被移动）。

右值引用 T&&：只能绑定右值。设计目的是让编译器能区分”可以被掏空的临时对象”和”还要继续用的对象”，从而实现移动语义与完美转发。

std::move 到底做了什么：什么都不做，只是一个类型转换。

#include <type_traits>
template<class T>
constexpr std::remove_reference_t<T>&& my_move(T&& t) noexcept {
    return static_cast<std::remove_reference_t<T>&&>(t);
}

它把参数转成 xvalue，从而让重载决议选中移动构造 / 移动赋值。真正”移动”的是移动构造函数的实现（接管指针、把源置空）。

#include <utility>
#include <cstddef>
#include <algorithm>
class Buffer {
    char* data_ = nullptr; size_t size_ = 0;
public:
    explicit Buffer(size_t n) : data_(new char[n]), size_(n) {}
    ~Buffer() { delete[] data_; }
    Buffer(const Buffer& o) : data_(new char[o.size_]), size_(o.size_) { std::copy(o.data_, o.data_ + size_, data_); }
    Buffer(Buffer&& o) noexcept : data_(o.data_), size_(o.size_) { o.data_ = nullptr; o.size_ = 0; }  // 接管 + 置空
    Buffer& operator=(Buffer o) noexcept { swap(o); return *this; }   // copy-and-swap 同时处理拷贝赋值与移动赋值
    void swap(Buffer& o) noexcept { std::swap(data_, o.data_); std::swap(size_, o.size_); }
};

追问链

  • 移动构造为什么要 noexcept？ std::vector 扩容时若移动构造可能抛异常，为了保证异常安全会退化成拷贝（std::move_if_noexcept）。没写 noexcept，你的移动构造在 vector 里根本用不上。
  • 被移动后的对象是什么状态？ 标准库保证”有效但未指定”（valid but unspecified）：可以析构、可以赋新值，但不要读它的值。自己写的类应保证被移动后至少能安全析构。
  • 对 const 对象 std::move 会怎样？ 变成 const T&&，匹配不到 T&& 的移动构造，静默退化为拷贝。这是常见的性能陷阱，尤其是 const 成员或 lambda 的 const 捕获。
  • return std::move(local); 对不对？ 错。它会阻止 NRVO（具名返回值优化），把一次零拷贝变成一次移动。直接 return local; 编译器会先尝试省略拷贝，不行再隐式当作右值移动。
  • 什么是 RVO / NRVO / 拷贝省略？ RVO：return T(...) 直接在调用方的返回槽上构造，C++17 起强制。NRVO：T t; ...; return t; 编译器把 t 直接放在返回槽上，非强制但主流编译器都做。前提是只有一个返回路径且返回的是同一个局部变量。
  • 移动比拷贝一定快吗？ 不一定。int、std::array、SSO 范围内的短 std::string 移动和拷贝代价相同；只有持有堆资源的类型移动才有优势。

2.3 万能引用与完美转发

引用折叠规则：& & → &，& && → &，&& & → &，&& && → &&。只有两个都是右值引用才得到右值引用。

万能引用（转发引用）：形如 T&& 且 T 是被推导的模板参数（或 auto&&）。传左值时 T 推导为 X&，折叠后参数类型是 X&；传右值时 T 推导为 X，参数类型 X&&。

#include <utility>
#include <string>
#include <vector>
struct Widget { std::string name; explicit Widget(std::string n) : name(std::move(n)) {} };
template<class T, class... Args>
T make(Args&&... args) {
    return T(std::forward<Args>(args)...);   // 左值仍是左值，右值仍是右值
}
void demo() {
    std::string s = "abc";
    Widget w1 = make<Widget>(s);              // Args = std::string&，拷贝 s
    Widget w2 = make<Widget>(std::move(s));   // Args = std::string，移动 s
    (void)w1; (void)w2;
}

std::forward 做了什么：forward<T>(x) 就是 static_cast<T&&>(x)。T 是左值引用时折叠成左值引用，T 是非引用时得到右值引用。它和 move 的区别是：move 无条件转右值，forward 有条件地还原原始值类别。

追问链

  • vector<T>::emplace_back 为什么比 push_back 好？ emplace_back(args...) 用完美转发在容器内存上直接构造，省一次临时对象的构造和移动。push_back(T&&) 至少要一次移动。但对已有对象两者等价，且 emplace_back 会执行隐式转换，可读性略差。
  • T&& 什么时候不是万能引用？ vector<T>::push_back(T&&) 中 T 是类模板参数不是函数推导的，它就是普通右值引用。const T&& 也不是。
  • 为什么不能对同一个万能引用参数 forward 两次？ 第一次可能已经把它移走了。

2.4 const 的全部用法

#include <string>
const int a = 1;                 // 常量，必须初始化
int b = 2;
const int* p1 = &b;              // 底层 const：不能通过 p1 改 *p1，p1 本身可以改指向
int* const p2 = &b;              // 顶层 const：p2 不能改指向，可以改 *p2
const int* const p3 = &b;        // 两者都不能改
int const* p4 = &b;              // 与 p1 完全等价，const 在 * 左边就是底层
struct S {
    mutable int cache = 0;
    int v = 0;
    int  get() const { ++cache; return v; }          // const 成员函数：this 是 const S*，只能改 mutable 成员
    int& ref()       { return v; }
    const int& ref() const { return v; }             // 按 const 重载，const 对象调用返回 const 引用
    const std::string& name() const& { return n_; }  // 引用限定符：左值对象返回引用
    std::string        name() &&     { return std::move(n_); }  // 右值对象直接移出
private:
    std::string n_;
};

记忆法：从右往左读。const int* p：“p 是指针，指向 int，int 是 const”。int* const p：“p 是 const，是指针，指向 int”。

字节原题：const int& func(const char* p) const 中三个 const 的含义：返回一个不能通过它修改的引用；参数指向的字符不能改；成员函数不修改对象状态。

追问链

  • const 和 #define 的区别？ const 有类型、有作用域、编译器检查、可调试、可取地址；#define 是预处理文本替换，无类型无作用域，不出现在符号表，宏展开可能有副作用（#define SQR(x) x*x）。C++ 中优先 constexpr / const / inline 函数。
  • const 变量能改吗？ 通过 const_cast 去掉 const 后写入，若对象本身定义为 const 是 UB（可能放在只读段或被常量折叠）；若对象本身非 const、只是通过 const 引用访问，则合法。
  • constexpr 和 const 的区别？ const 是”运行期不可修改”，constexpr 是”编译期可求值”。constexpr 变量隐含 const；constexpr 函数在参数是常量时编译期求值，否则退化为普通函数。
  • const 成员函数中修改成员的合法途径？ mutable（用于缓存、锁、统计计数）、通过指针成员修改指向的对象（const 只作用于指针本身）。
  • 顶层 const 在函数签名中被忽略：void f(int) 和 void f(const int) 是同一个函数，重定义报错；但 void f(int*) 和 void f(const int*) 是重载。

2.5 四种类型转换

转换 检查时机 用途 失败行为
static_cast 编译期 数值转换、上行转换、有关联类型间转换、void* 与 T* 下行转换不检查，错了是 UB
dynamic_cast 运行期 多态类型的下行 / 交叉转换 指针返回 nullptr，引用抛 std::bad_cast
const_cast 编译期 添加 / 去除 const / volatile 修改本身 const 的对象是 UB
reinterpret_cast 编译期 位模式重新解释：指针 ↔︎ 整数、不相关指针类型 无检查，几乎总是平台相关

dynamic_cast 底层：要求源类型有虚函数（多态）。通过对象的 vptr 找到 vtable，vtable 前面有 type_info 指针，运行库沿继承链比对 type_info，还要用 vtable 中的 offset-to-top 调整 this 指针（多继承）。开销大约几十到几百 ns，在热路径上应用虚函数或 type tag 替代。

#include <iostream>
#include <cstring>
#include <cstdint>
#include <typeinfo>
struct Base { virtual ~Base() = default; virtual const char* who() const { return "Base"; } };
struct Derived : Base { const char* who() const override { return "Derived"; } int extra = 1; };
struct Other  : Base { const char* who() const override { return "Other"; } };

int main() {
    Derived d;
    Base* pb = &d;                                   // 上行转换：隐式，不需要 cast

    // dynamic_cast：运行期查 vtable 里的 type_info，失败指针给 nullptr、引用抛 bad_cast
    if (auto* pd = dynamic_cast<Derived*>(pb)) std::cout << "dyn 成功 " << pd->extra << " ";
    Other o; Base* po = &o;
    std::cout << "dyn 失败→" << (dynamic_cast<Derived*>(po) == nullptr) << " ";
    try { (void)dynamic_cast<Derived&>(*po); } catch (const std::bad_cast&) { std::cout << "引用版抛 bad_cast\n"; }

    // static_cast：编译期，下行不检查。你确知动态类型时才用，快但错了是 UB
    auto* fast = static_cast<Derived*>(pb);
    std::cout << "static 下行 " << fast->who() << " ";
    std::cout << "typeid " << (typeid(*pb) == typeid(Derived)) << "\n";   // 1，typeid 也走 vtable

    // const_cast：只有当对象本身非 const 时，去掉 const 后写入才合法
    int v = 1; const int& cr = v;
    const_cast<int&>(cr) = 2;                        // 合法：v 本身不是 const
    std::cout << "const_cast " << v << " ";          // 2
    // const int ci = 1; const_cast<int&>(ci) = 2;   // UB：对象本身是 const

    // reinterpret_cast：位模式重解释。float/int 互看要用 memcpy，直接转引用违反严格别名
    float f = 1.0f; uint32_t bits;
    std::memcpy(&bits, &f, sizeof bits);             // 正确做法（C++20 可用 std::bit_cast）
    std::cout << "float 位模式 0x" << std::hex << bits << std::dec << "\n";  // 0x3f800000
}

追问链

  • 为什么 C 风格强转不好？ 它会按 const_cast → static_cast → static_cast + const_cast → reinterpret_cast 顺序尝试，你不知道最终发生了什么，且无法 grep。
  • static_cast 下行转换什么时候安全？ 你能从别的途径确认动态类型时（如 tag 字段），此时比 dynamic_cast 快。
  • 上行转换需要 cast 吗？ 不需要，派生类指针可以隐式转成基类指针。多继承时编译器会自动调整偏移。
  • reinterpret_cast<float&>(int_var) 合法吗？ 违反严格别名规则，是 UB。正确做法是 memcpy 或 C++20 std::bit_cast。

2.6 空指针调用成员函数（字节高频输出题）

未定义行为 / 伪代码，不保证可编译
class C {
public:
    // int a;
    void func() { printf("hello\n"); }
};
C* c = nullptr;
c->func();          // 通常能正常打印

分析：非虚成员函数在编译期就确定地址（在 .text 段），调用时只是把 c 作为隐藏参数 this 传进去。函数体没有解引用 this，所以不会崩。标准上这是 UB，但主流编译器的行为如上；面试要先说 UB，再说实际会怎样。

2.8 lambda 与 std::function

lambda 是什么：编译器生成的一个匿名类（闭包类型）的对象，捕获的变量是成员，函数体是 operator()。每个 lambda 表达式类型唯一。

#include <functional>
#include <memory>
#include <vector>
int lambda_demo() {
    int x = 1, y = 2;
    auto byVal = [x]() { return x; };            // 拷贝 x 进闭包，后续改 x 不影响
    auto byRef = [&y]() { return y; };           // 存 y 的引用，y 析构后调用是悬垂
    auto mut   = [x]() mutable { return ++x; };  // 默认 operator() 是 const，改捕获需 mutable
    auto init  = [p = std::make_unique<int>(3)]() { return *p; };  // 初始化捕获（C++14），可移动进不可拷贝对象
    auto gen   = [](auto a, auto b) { return a + b; };            // 泛型 lambda，operator() 是模板
    int (*fp)(int) = [](int v) { return v * 2; };                 // 无捕获 lambda 可转函数指针
    std::function<int()> f = byVal;                               // 类型擦除，可存任意可调用对象
    return byVal() + byRef() + mut() + init() + gen(1, 2) + fp(3) + f();
}

std::function 的实现要点：类型擦除。内部持有一个指向”可调用对象包装”的基类指针（或小对象优化缓冲区），包装类是模板派生类，虚函数 invoke。开销：一次间接调用、可能一次堆分配（大于 SBO 缓冲区，libstdc++ 为 16 字节时）。热路径上优先用模板参数接收可调用对象，或用 C++23 的 move_only_function / 自写 function_ref。

追问链

  • lambda 捕获 this 的陷阱？ [this] 捕获的是裸指针，对象析构后回调还在就是悬垂。异步场景用 [self = shared_from_this()] 或 [weak = weak_from_this()]。
  • [=] 与 [&] 默认捕获选哪个？ 立即调用的局部 lambda 用 [&]；会逃逸出作用域（存起来、发给线程）的用 [=] 或显式列出，禁止默认按引用捕获。
  • lambda 与函数对象、函数指针的性能差异？ lambda 和手写函数对象一样可以被内联；函数指针和 std::function 是间接调用，通常不能内联。std::sort 传 lambda 比传函数指针快，就是这个原因。
  • lambda 的 sizeof？ 无捕获为 1；有捕获则是捕获成员的大小之和（按对齐）。

3.2 虚函数机制（必考，要能画图）

vptr 与 vtable

  • 有虚函数的类，编译器为每个类生成一张虚函数表（vtable），放在 .rodata，表项是虚函数地址。
  • 每个对象头部（Itanium ABI 下偏移 0）有一个指向本类 vtable 的指针 vptr，所以 sizeof 多 8 字节。
  • 调用 p->f() 编译成：读 p 的 vptr → 取 vtable 中 f 对应槽位（编译期确定的索引）→ 间接调用。
struct Base    { virtual void f(); virtual void g(); int x; };
struct Derived : Base { void f() override; virtual void h(); int y; };

  Derived 对象                      Derived 的 vtable（.rodata，每个类一份）
  +----------+                     +---------------------+
0 | vptr     |------+              | offset_to_top = 0   |  多继承调整 this 用
  +----------+      |              +---------------------+
8 | x        |      |              | typeinfo* (Derived) |  dynamic_cast / typeid 用
  +----------+      |              +=====================+  <-- vptr 指向这里
12| y        |      +------------->| &Derived::f         |  slot 0，覆盖了 Base::f
  +----------+                     | &Base::g            |  slot 1，直接继承
                                   | &Derived::h         |  slot 2，派生类新增
                                   +---------------------+

注意 vptr 指向的是"第一个函数槽"，offset_to_top 和 typeinfo 在它前面（负偏移）。

可以用指针算术把这张表挖出来验证：

#include <iostream>
#include <cstddef>
// 用指针算术把虚表挖出来，证明“对象头部是 vptr、表项是函数地址”。
// 这段代码依赖 Itanium ABI 布局，是演示用途，不是可移植代码。
struct Base {
    virtual void f() { std::cout << "Base::f "; }
    virtual void g() { std::cout << "Base::g "; }
    int x = 1;
};
struct Derived : Base {
    void f() override { std::cout << "Derived::f "; }   // 覆盖 slot 0
    virtual void h() { std::cout << "Derived::h "; }    // 新增 slot 2
    int y = 2;
};
using Fn = void(*)(void*);

int main() {
    Derived d;
    // 注意都是 16：Base 是 vptr8 + x4 + 尾部填充 4，Derived 的 y 直接复用了这 4 字节填充
    std::cout << "sizeof(Base)=" << sizeof(Base) << " sizeof(Derived)=" << sizeof(Derived) << "\n";  // 16 16
    // 对象首 8 字节就是 vptr：把对象地址当 void** 解引用，拿到的就是虚表首地址
    void** vptr = *reinterpret_cast<void***>(&d);
    auto off = [&](const void* m) { return reinterpret_cast<const char*>(m) - reinterpret_cast<const char*>(&d); };
    std::cout << "x 偏移=" << off(&d.x) << " y 偏移=" << off(&d.y) << "\n";   // 8 12（0..7 是 vptr）
    // 依次调用虚表的 slot 0/1/2
    for (int i = 0; i < 3; ++i) reinterpret_cast<Fn>(vptr[i])(&d);
    std::cout << "\n";                                  // Derived::f Base::g Derived::h
    // 同类型对象共享同一张表；不同类型的表不同
    Derived d2; Base b;
    std::cout << "同类共表 " << (*reinterpret_cast<void***>(&d) == *reinterpret_cast<void***>(&d2))
              << " 异类异表 " << (*reinterpret_cast<void***>(&d) != *reinterpret_cast<void***>(&b)) << "\n";  // 1 1
}

这段同时演示了 §3.4 说的尾部填充复用：Base 是 vptr(8) + x(4) + 填充(4) = 16，Derived 的 y 正好落在那 4 字节填充里，所以 sizeof(Derived) 仍是 16，而不是 16 + 4。

vptr 何时设置：在每一层构造函数体执行前由编译器插入的代码设置为当前层的 vtable，析构时同样逐层回退。这解释了两道经典题：

  1. 构造函数里调用虚函数：调到的是当前构造层的版本，不是最终派生类的版本，因为派生部分还没构造，vptr 还指向基类表。
  2. 析构函数里调用虚函数：同理，~Base 里调 f() 得到 Base::f，因为派生部分已析构，vptr 已回退。

多继承下的布局：有几个带虚函数的基类就有几个 vptr。派生类指针转成第二个基类指针时要加偏移；第二基类的 vtable 里覆盖函数的表项指向一段 thunk，thunk 先调整 this 再跳到真正的函数。这就是 vtable 里 offset_to_top 的作用。

追问链

  • 为什么构造函数不能是虚函数？ 虚调用依赖对象里的 vptr，而 vptr 是构造函数设置的，构造之前对象还不存在，没有 vptr 可查。语义上构造函数的任务就是创建确定类型的对象，不存在”根据动态类型选择构造函数”。要”虚构造”用工厂方法或 clone() 虚函数。
  • 为什么析构函数常常需要虚？ 通过基类指针 delete 派生类对象时，非虚析构只调 ~Base，派生部分的资源泄漏，且这是 UB。规则：类打算被多态使用（有任何虚函数）就把析构声明为虚。反之不打算做基类的类不要加虚析构，避免多 8 字节和失去平凡性。
  • 静态成员函数为什么不能虚？ 没有 this，没法查 vptr。
  • 模板成员函数为什么不能虚？ vtable 大小必须在类定义时确定，而模板成员可以实例化出无限多个版本。
  • 内联函数能虚吗？ 语法上可以。通过对象直接调用（静态类型已知）时编译器能内联；通过指针 / 引用调用时必须查表，不能内联。所以”虚函数不能内联”是不准确的。
  • 虚函数调用比普通调用慢多少？ 一次内存读 vptr、一次读表项、一次间接跳转，无法内联、分支预测可能失败。大约几 ns，热循环里几百万次才有感觉。真正的代价是阻止内联导致的优化损失。
  • final 和 override 的作用？ override 让编译器检查确实覆盖了基类虚函数（防止签名写错变成新函数）。final 禁止进一步覆盖或继承，编译器据此可以把虚调用去虚化（devirtualization）为直接调用。
  • 纯虚函数与抽象类：virtual void f() = 0; 使类不能实例化。纯虚函数可以有定义（Base::f() {}），派生类可显式调用，常用于提供默认实现。纯虚析构函数必须有定义，否则链接失败。
  • 虚函数表存在哪？ .rodata（只读数据段），每个类一份，进程内共享。
  • typeid 和 dynamic_cast 用什么信息？ vtable 中的 type_info 指针。没有虚函数的类 typeid 是编译期静态类型。

3.3 构造与析构

构造顺序：虚基类（按声明深度优先、从左到右）→ 直接基类（按声明顺序）→ 成员（按声明顺序，与初始化列表顺序无关）→ 构造函数体。析构完全相反。

#include <iostream>
struct A { A() { std::cout << "A "; } virtual ~A() { std::cout << "~A "; } };
struct M { M() { std::cout << "M "; } ~M() { std::cout << "~M "; } };
struct B : A { M m; B() { std::cout << "B "; } ~B() override { std::cout << "~B "; } };
int main() { { B b; } std::cout << "\n"; }   // 输出：A M B ~B ~M ~A

析构中调用虚函数的输出题（字节一面原题，完整分析）

#include <iostream>
using namespace std;
class A {
public:
    virtual void F() { cout << 1 << endl; }
    void CallF() { F(); }
    virtual ~A() { CallF(); F(); }
};
class B : public A {
public:
    void F() override { cout << 2 << endl; }
    ~B() override {}
};
class C : public B {
public:
    void F() override { cout << 3 << endl; }
    void CallF() { F(); A::CallF(); }    // 隐藏了 A::CallF（非虚函数不构成覆盖）
    ~C() override { CallF(); }
};
int main() {
    A* p = new C();
    p->CallF();     // 静态类型 A，CallF 非虚 → A::CallF → F() 虚调用，动态类型 C → 3
    delete p;       // 虚析构 → ~C 先跑：C::CallF → F() 此时对象仍是 C → 3；A::CallF → F() → 3
                    // 然后 ~B 空；然后 ~A：CallF → A::CallF → F()，此时 vptr 已回退为 A → 1；F() → 1
    return 0;       // 输出 3 3 3 1 1
}

默认成员函数与 Rule of 0/3/5

  • 编译器可生成：默认构造、析构、拷贝构造、拷贝赋值、移动构造、移动赋值。
  • 声明了任意一个拷贝操作或析构，编译器就不再隐式生成移动操作（退化为拷贝）。声明了移动操作，拷贝操作被隐式删除。
  • Rule of 3：自定义了析构、拷贝构造、拷贝赋值中的任一个，通常三个都要写（说明类在手动管理资源）。
  • Rule of 5：C++11 起再加移动构造、移动赋值。
  • Rule of 0：用智能指针和标准容器管理资源，一个都不写，最推荐。

拷贝构造 vs 拷贝赋值：拷贝构造作用于尚未存在的对象（T b = a;、传值参数、按值返回），拷贝赋值作用于已存在的对象（b = a;）。T b = a; 是拷贝初始化，不是赋值。

深拷贝 vs 浅拷贝：默认拷贝是逐成员拷贝，指针成员只拷地址，两个对象指向同一块内存，析构时 double free。持有裸资源的类必须自己实现深拷贝，或者用 unique_ptr 让编译器禁止拷贝。

explicit：禁止单参数构造函数（以及 C++11 起的多参数列表初始化）参与隐式转换。std::vector<int> v = 10; 因为 explicit 而不合法，避免了歧义。单参数构造函数默认都应加 explicit，除了确实想要隐式转换的（如 std::string 从 const char*）。

追问链

  • 拷贝赋值为什么要处理自赋值？ a = a 时若先释放自己的资源再从”源”拷贝，源已经被释放。copy-and-swap 天然免疫，且提供强异常安全（拷贝失败时原对象不变）。
  • 为什么拷贝赋值要返回 T&？ 支持链式 a = b = c，且与内建类型行为一致。
  • = default 和不写有什么区别？ = default 显式要求编译器生成，即使你声明了其他特殊成员函数；同时它保留平凡性（trivial），而用户自定义的空实现不是平凡的，会影响 memcpy 优化和 is_trivially_copyable。
  • = delete 的其他用法？ 删除特定重载防止隐式转换：void f(int); void f(double) = delete; 这样 f(1.0) 报错。
  • 委托构造函数：T(int a) : T(a, 0) {}，一个构造函数调另一个，减少重复。

#include <cstdint>
struct Empty {};                                    // 1
struct V { virtual ~V() = default; };               // 8：只有 vptr

struct D2 { Empty e; int x; };                      // 8：作为成员的空类占 1 字节 + 对齐

追问链

  • 为什么空类不是 0 字节？ 两个不同对象必须有不同地址，Empty arr[2] 才能区分元素。
  • sizeof(Derived) 一定大于等于 sizeof(Base) 吗？ 是，派生类包含完整基类子对象。但基类的尾部填充可以被派生类成员复用（尾部填充重用），所以不一定是”基类大小 + 成员大小”。
  • 为什么成员函数不占对象空间？ 函数代码在 .text，所有对象共享，调用时通过 this 区分。只有虚函数需要一个 vptr 来做运行期分发。

3.5 多继承与虚继承

菱形继承问题：D : B, C，B : A，C : A，D 里有两份 A，访问 d.x 歧义，A 的构造函数跑两次。

虚继承：B : virtual A，C : virtual A，D 中只有一份 A，由最底层派生类 D 负责构造 A（B、C 构造函数中对 A 的初始化被忽略）。实现上 B、C 子对象里不再直接内嵌 A，而是通过 vtable 中的 vbase_offset 找到共享的 A 子对象，所以访问虚基类成员多一次间接寻址。

struct A { int x = 1; };
struct B : virtual A { int b = 2; };
struct C : virtual A { int c = 3; };
struct D : B, C { int d = 4; };
int diamond() { D d; return d.x; }    // 不再歧义。sizeof(D) 在 x86-64 通常为 40（两个 vptr + 4 个 int + 对齐）

追问链

  • 虚继承的代价？ 每个虚继承的类多一个 vptr（即使没有虚函数），访问虚基类成员多一次查表，对象布局复杂，static_cast 从虚基类下行转换不允许（只能 dynamic_cast）。
  • 什么时候用多继承？ 主要是继承多个纯接口类（只有纯虚函数的抽象类），像 Java 的 interface。多个带实现的基类容易产生菱形和二义性。
  • std::iostream 就是菱形虚继承：istream 和 ostream 都虚继承 ios_base。

追问链

  • 为什么返回类型不能作为重载依据？ 调用表达式可以不使用返回值，编译器无法据此选择。
  • 协变返回类型：基类虚函数返回 Base*，派生类覆盖可返回 Derived*，仍算覆盖。clone() 常用。
  • 重载决议顺序：精确匹配 → 提升（char→int、float→double）→ 标准转换（int→double、派生指针→基类指针）→ 用户定义转换 → 省略号。有二义性就报错，而不是随便挑一个。
  • 名字查找先于重载决议：这就是隐藏的原理。编译器先在 Der 作用域找到 f，找到了就停止，不再看 Base，然后在 Der::f 的候选里做重载决议。

3.7 静态多态与 CRTP

模板实现的编译期多态：没有 vptr，没有间接调用，可内联，但每种类型生成一份代码（代码膨胀），且只能在编译期确定类型。

#include <iostream>
template<class Derived>
struct Shape {
    double area() const { return static_cast<const Derived*>(this)->areaImpl(); }  // 编译期"虚函数"
};
struct Square : Shape<Square> { double s = 2; double areaImpl() const { return s * s; } };
struct Circle : Shape<Circle> { double r = 1; double areaImpl() const { return 3.14159 * r * r; } };
template<class T> void print(const Shape<T>& s) { std::cout << s.area() << "\n"; }
int crtp_demo() { print(Square{}); print(Circle{}); return 0; }

运行期多态 vs 编译期多态怎么选：容器里要装异构对象、插件式扩展、跨动态库边界，用虚函数；类型在编译期已知、追求零开销（数值库、策略模式）用模板。std::variant + std::visit 是第三条路：闭集类型、值语义、无堆分配。

追问链

  • CRTP 的其他用途？ 给派生类注入通用功能（如 enable_shared_from_this、对象计数、操作符生成）、静态接口检查。
  • 模板会导致代码膨胀怎么缓解？ 把与类型无关的部分抽到非模板基类（vector<T*> 共享 vector<void*> 实现的思路）、extern template 显式实例化。

3.8 运算符重载与友元

不能重载的运算符：.（成员访问）、.*（成员指针访问）、::（作用域解析）、?:（三目）、sizeof、alignof、typeid。原因是这几个要么作用于名字而非值（.、:: 的左边是标识符，不是可求值的对象），要么由编译器在编译期求值（sizeof、alignof），重载它们等于让语言的基本语义可被用户改写，无法保证任何代码的可读性。同理，重载不能改变优先级、结合性、操作数个数，也不能发明新符号 —— 这些是语法层面的信息，在重载决议发生之前就已经被解析器定死了。

成员 vs 非成员

运算符 位置 原因
=、[]、()、-> 必须成员 标准强制。它们语义上与对象的身份强绑定，允许非成员会让「赋值」这类操作可以被外部随意劫持
<<、>> 必须非成员 左操作数是 std::ostream，你无权往标准库的类里加成员
双目 + - * / == < 推荐非成员 保证对称性，见下
单目 ++ -- ! * -> 推荐成员 只作用于自身，没有对称性问题，写成成员能直接访问私有成员

对称性问题（这是选非成员的真正原因）：成员函数的左操作数必须是 this，编译器不会对它做隐式转换。所以 operator+ 写成成员时，money + 2 能编译（2 隐式转成 Money），但 2 + money 不能 —— int 里没有这个成员函数。写成非成员后两个参数地位平等，都能走隐式转换，两种写法就都成立了。

#include <iostream>
class Money {
    long cents_;
public:
    Money(long c) : cents_(c) {}                    // 故意不 explicit，允许 2 → Money
    long cents() const { return cents_; }

    Money& operator+=(const Money& o) { cents_ += o.cents_; return *this; }

    Money& operator++()    { ++cents_; return *this; }          // 前置：返回自身引用
    Money  operator++(int) { Money old = *this; ++cents_; return old; }  // 后置：int 是哑元

    friend std::ostream& operator<<(std::ostream& os, const Money& m);   // 需要读私有成员
};

// 非成员 + 复用成员 +=：逻辑只写一处。按值收 lhs，它正好充当累加器，省一次拷贝
inline Money operator+(Money lhs, const Money& rhs) { lhs += rhs; return lhs; }
inline bool  operator==(const Money& a, const Money& b) { return a.cents() == b.cents(); }
inline bool  operator!=(const Money& a, const Money& b) { return !(a == b); }

std::ostream& operator<<(std::ostream& os, const Money& m) { return os << m.cents_ << "分"; }

int main() {
    Money m{100};
    std::cout << m + 5 << " " << 5 + m << " ";   // 105分 105分：非成员才让 5 + m 成立
    std::cout << m++ << " " << m << " ";         // 100分 101分：后置返回的是旧值副本
    std::cout << ++m << "\n";                    // 102分
}

operator[] 要成对重载：T& operator[](size_t) 与 const T& operator[](size_t) const。只写非 const 版本，const 对象和 const& 参数就无法下标访问；只写 const 版本则无法赋值。去重的经典写法是让非 const 版转发给 const 版：return const_cast<T&>(static_cast<const C&>(*this)[i]); —— 这里 const_cast 是安全的，因为对象本身确实非 const，只是我们临时加 const 去复用实现（C++23 的 deducing this 可以彻底消除这段样板）。

友元

  • friend 授予某个函数或类访问私有 / 保护成员的权限。声明写在类内任意访问区都一样，因为它授予的是别人的权限，不是自己的成员，所以 public: / private: 对它无意义。
  • 不可继承：父类的友元不是子类的友元。原因是子类可能有父类作者完全不知道的新私有成员，自动放行等于让基类作者替派生类作者做了不该做的决定。
  • 不可传递：朋友的朋友不是朋友。同理，A 信任 B 不代表 A 信任 B 信任的人，否则封装的边界会随依赖链无限扩散。
  • 单向：A 声明 B 为友元，只是 B 能看 A，A 看不了 B。
  • 典型用途：operator<<、需要同时访问两个类内部的二元操作、单元测试类。
  • 关于「破坏封装」：友元其实是把类接口的一部分显式写在类内声明出来。它可控、可见、可审计，比为了让外部函数能访问而把成员改成 public 严格得多 —— 后者是对所有人开放，前者只对点名的那一个开放。

追问链

  • 后置 ++ 为什么返回值而不是引用？ 因为它要返回的是自增前的旧值，而旧值只存在于函数内的局部副本 old 里；返回引用就是返回一个即将析构的局部对象的引用，必然悬垂。这也是循环里推荐 ++it 的原因：后置版无法避免构造一份副本，而这份副本在 for 里根本没人用。
  • operator<< 为什么不能写成成员？ 成员函数的左操作数固定是 this。写成 Money 的成员，调用就得写成 m << std::cout，参数顺序是反的。而要写成 std::ostream 的成员，你得去改标准库的类 —— 没这个权限。所以只能是非成员，再用 friend 或公有接口拿数据。
  • 重载 &&、||、, 有什么坑？ 内建版本保证短路求值和求值顺序；一旦重载，它们退化成普通函数调用，而函数调用的所有实参在进入函数体前都必须求值完毕，短路和顺序保证同时消失。调用者看着还是 a && b，行为却变了，所以基本不要重载。
  • operator-> 为什么能「链式穿透」？ 标准规定 x->m 在 x 是类对象时展开为 x.operator->()->m；如果返回的还是类对象，就继续对结果调 operator->，递归直到得到裸指针再做成员访问。智能指针正是靠这条规则，只写一层 operator-> 就实现了 p->member。
  • C++20 的 <=> 解决了什么？ 手写六个关系运算符（< <= > >= == !=）不仅重复，还极易出现不一致（比如 < 和 == 用了不同字段），而不一致的比较器喂给 std::sort 是 UB。auto operator<=>(const T&) const = default; 让编译器按成员声明顺序生成一套必然自洽的比较，== 再单独默认生成一个（因为相等常有比三路比较更快的短路实现，如先比 size）。

4.STL

4.1 总览

六大组件：容器、算法、迭代器、仿函数（函数对象）、适配器（stack/queue/priority_queue、迭代器适配器、函数适配器）、分配器。设计核心是泛型 + 迭代器解耦：算法只依赖迭代器接口，不依赖容器。

五类迭代器（字节原题）

类别 能力 典型容器
输入 Input 只读、单遍、++ istream_iterator
输出 Output 只写、单遍、++ ostream_iterator、back_inserter
前向 Forward 可读写、多遍、++ forward_list、unordered_*
双向 Bidirectional 前向 + -- list、map、set
随机访问 Random Access 双向 + +n、[]、比较 vector、deque、array、原生指针

C++20 增加 Contiguous（连续存储）。算法根据迭代器类别选择实现，例如 std::distance 对随机访问是 O(1)，对其他是 O(n)；std::sort 要求随机访问，所以 list 有自己的 sort 成员。

4.2 vector

内存模型：三个指针 begin、end、cap（或一个指针 + 两个 size_t），sizeof(vector) == 24。元素在堆上连续存放。

扩容机制

  • 容量不足时分配新块，把旧元素移动（移动构造 noexcept 时）或拷贝过去，释放旧块。
  • 增长因子：libstdc++ 是 2 倍，MSVC 是 1.5 倍。
  • 为什么是常数倍而不是加常数：摊还分析。倍增下 n 次 push_back 总拷贝次数是 n + n/2 + n/4 + … < 2n，摊还 O(1)。每次加 k 个则是 O(n²/k)。
  • 为什么 1.5 比 2 可能更好：2 倍时前面所有释放块的总和 1 + 2 + 4 + … + 2^(k-1) = 2^k - 1 < 2^k，永远装不下新块，旧内存无法复用；因子小于黄金分割 1.618 时，之前释放的块之和才可能容纳下一次分配。

push_back 复杂度分析（字节三面原题）：不扩容 O(1)；扩容那一次 O(n)；摊还 O(1)。

reserve vs resize

reserve(n) resize(n)
改变 只改 capacity 改 size（同时可能改 capacity）
构造元素 不构造 多出来的部分值初始化（或用给定值）
之后 v[i] i < size 才合法，reserve 后直接 v[5] 是 UB 合法
用途 已知数量，避免多次扩容 需要立即有 n 个可用元素

[] vs at()：[] 不检查越界（UB，Debug 模式下部分实现有断言）；at() 检查，越界抛 std::out_of_range。性能敏感用 []，边界不可信用 at()。

迭代器失效规则

操作 失效范围
push_back / insert 引发扩容 全部迭代器、指针、引用
insert 未扩容 插入点及之后
erase 被删点及之后（end() 也失效）
clear 全部
reserve 若容量改变则全部

遍历中删除的正确写法

#include <vector>
#include <algorithm>
void erase_demo(std::vector<int>& v) {
    for (auto it = v.begin(); it != v.end(); ) {
        if (*it % 2 == 0) it = v.erase(it);   // erase 返回下一个有效迭代器
        else ++it;
    }
    // 更好：erase-remove 惯用法，O(n) 一次搬移
    v.erase(std::remove_if(v.begin(), v.end(), [](int x) { return x % 3 == 0; }), v.end());
    // C++20：std::erase_if(v, pred);
}

追问链

  • vector<bool> 有什么特殊？ 是特化，按位存储，operator[] 返回代理对象而非 bool&，不能取地址，不满足容器要求。需要真 bool 数组用 vector<char> 或 deque<bool>。
  • emplace_back 和 push_back 的区别？ emplace_back 完美转发参数原地构造；push_back 先构造临时再移动 / 拷贝。传已有对象时一样。
  • shrink_to_fit 一定生效吗？ 非强制请求，实现可以忽略。要确保释放用 vector<T>(v).swap(v)。
  • clear 会释放内存吗？ 不会，capacity 不变。
  • vector 里存指针还是对象？ 对象：局部性好、少一次间接。指针：元素大、需要多态、需要稳定地址（被别处引用）时用。
  • vector<T> 的 T 需要满足什么？ 可移动构造或可拷贝构造；resize 需要可默认构造。
  • vector 和数组的区别？ 动态大小、自动管理内存、知道自身大小、可作为值传递和返回、可放进其他容器。开销是多 16 字节和一次间接。

4.3 deque、list、forward_list

deque：分段连续。一个中控数组（map）存指向多个定长缓冲区（libstdc++ 512 字节）的指针。两端 push 都是 O(1)，随机访问 O(1) 但要两次寻址（先算在哪个块）。中间插入 O(n)。push_back/push_front 会让迭代器失效但引用和指针不失效（元素不搬家），这一点和 vector 不同。用途：std::queue 和 std::stack 的默认底层、滑动窗口。

list：双向链表，每个节点 prev/next + 数据，节点独立分配。插删 O(1) 且不影响其他迭代器；不支持随机访问；sizeof 节点开销 16 字节 + 分配器开销；缓存不友好。splice 可以 O(1) 把节点从一个 list 移到另一个，LRU 就靠它。

forward_list：单链表，只有 next，省 8 字节，只能 insert_after/erase_after，没有 size()（保持 O(1) 操作的纯粹性）。

追问链

  • 什么时候 list 比 vector 快？ 频繁在中间插删且已持有迭代器、元素巨大且拷贝昂贵、需要迭代器长期稳定。其他情况几乎总是 vector 更快，即使是”中间插入”，vector 的 memmove 在 n 不大时也常胜过 list 的指针跳转和缓存缺失。
  • 为什么 list::size() 是 O(1)？ C++11 起要求。代价是 splice 部分区间时要遍历计数。

4.4 map / set：红黑树

红黑树五条性质

  1. 节点是红或黑。
  2. 根是黑。
  3. 叶子（NIL）是黑。
  4. 红节点的两个孩子都是黑（不能有连续红）。
  5. 任一节点到其所有后代叶子的路径含相同数量的黑节点。

由 4 和 5 推出：最长路径不超过最短路径的 2 倍，高度 ≤ 2·log₂(n+1)，查找 O(log n)。插入删除通过最多 O(log n) 次变色和最多 3 次旋转恢复性质（插入最多 2 次旋转，删除最多 3 次）。

为什么 map 用红黑树而不是

候选 为什么不选
AVL 平衡更严格，查找略快，但插删旋转更多。map 读写混合，红黑树综合更优。Linux 内核、Java TreeMap、C++ STL 都选红黑树
跳表 需要随机数，空间 O(n log n) 常数更大，STL 要求确定性和最坏复杂度保证。Redis 用跳表是因为区间遍历和实现简单
B / B+ 树 为磁盘 IO 优化（大节点、少层数），内存中缓存行利用率高但实现复杂；数据库索引用它
哈希 无序，无法 lower_bound / 范围遍历，最坏 O(n)，迭代器随 rehash 失效

map 特性

  • operator[] 在 key 不存在时插入默认值并返回引用，所以 if (m[k] == 0) 会污染 map，只读查询用 find / count / at / C++20 contains。
  • 迭代器按 key 有序，erase 只让被删元素的迭代器失效，插入不使任何迭代器失效（节点不搬家）。
  • lower_bound(k) 第一个 ≥ k，upper_bound(k) 第一个 > k，equal_range 两者。
  • 自定义 key 需要提供 operator< 或比较器，比较器必须是严格弱序（<= 是错的）。
  • 节点大小：颜色 + 3 指针 + pair，约 40 字节 + 数据。

追问链

  • map 的 key 能修改吗？ 不能，iterator 指向 pair<const K, V>。要改 key 得 erase 再 insert，或 C++17 extract 改后 insert 节点句柄（不重新分配）。
  • multimap / multiset：允许重复 key，equal_range 取一组，count 是 O(log n + k)。
  • std::set 怎么实现 O(log n) 删除第 k 大？ 标准 set 不支持按秩访问，需要 GNU 的 __gnu_pbds::tree 或自己维护子树大小（order statistic tree）。
  • map 和 unordered_map 怎么选？ 需要有序遍历、范围查询、key 没有好哈希、对最坏情况敏感（防哈希碰撞攻击）时用 map；纯点查且量大用 unordered_map。

4.5 unordered_map：开链哈希

结构（libstdc++）：一个桶数组（bucket_count 个指针），所有元素在一条单链表上，桶指向该桶第一个元素的前驱，这样 erase 不需要双向链表。每个节点缓存 hash 值（可选）。

关键参数

  • 负载因子 load_factor = size / bucket_count，默认 max_load_factor = 1.0。
  • 超过则 rehash：桶数增长到下一个质数（约 2 倍），所有元素重新挂链。rehash 是 O(n)，所以单次 insert 最坏 O(n)，摊还 O(1)。
  • reserve(n) 预先分配桶，避免多次 rehash。

迭代器失效：rehash 使所有迭代器失效，但指针和引用不失效（节点不搬家，只是重新挂链）；erase 只使被删元素失效。

哈希冲突的解决方法对比

方法 原理 优点 缺点
链地址法（STL） 同桶元素链表 删除简单、负载可 > 1 节点分配开销、缓存不友好
开放寻址：线性探测 冲突就查下一格 缓存友好、无额外分配 聚集（primary clustering）、删除需墓碑、负载 > 0.7 性能急降
开放寻址：二次探测 / 双重哈希 步长平方或第二个哈希 减少聚集 实现复杂，表大小需质数
Robin Hood / Swiss Table（absl） 线性探测 + 元数据字节 + SIMD 分组探测 极快，缓存友好 实现复杂
再哈希 / 扩容 负载高时重建 控制链长 一次性 O(n) 停顿

为什么桶数取质数：哈希值 h % n 时若 n 是 2 的幂，只用到 h 的低位，低位分布差（如指针地址、步长为偶数的 key）就会大量冲突；n 是质数时每一位都参与。取 2 的幂的实现（Java HashMap、absl）会先对 h 做一次扰动混合再取低位，用位运算代替取模。

追问链

  • 怎么给自定义类型做 key？ 特化 std::hash<T> 或传哈希函数对象，同时提供 operator==。组合多个字段时用 h1 ^ (h2 << 1) 或 boost::hash_combine（乘一个大奇数再异或），单纯异或会让 (a,b) 和 (b,a) 冲突。
  • unordered_map 的最坏复杂度？ O(n)：所有 key 哈希到同一桶。对外部输入做 key 时存在哈希洪水攻击，防御是随机种子哈希（如 SipHash）。
  • 怎么实现线程安全的哈希表？（字节原题）分段锁：桶分成若干段，每段一把 shared_mutex，读用 shared_lock，写用 unique_lock；rehash 时要拿全局锁或做渐进式 rehash（Redis 做法：两张表同时存在，每次操作搬一个桶）。无锁方案：CAS 链表头插入 + 标记删除，实现难度高。
  • 遍历 unordered_map 顺序稳定吗？ 不保证，依赖实现和插入历史，不同进程可能不同，不要依赖。
  • std::hash<std::string> 用什么算法？ libstdc++ 用 MurmurHash2 变体（_Hash_bytes），对 int 等整型则是恒等映射。
  • unordered_map<int,int> 每个元素占多少内存？ 节点：next 指针 8 + pair 8 + 可选缓存 hash 8 + malloc 头 16 ≈ 32 到 40 字节，再加桶数组，比 vector<pair> 大好几倍。

4.6 适配器与堆

  • stack / queue 默认基于 deque，priority_queue 默认基于 vector + std::make_heap / push_heap / pop_heap。
  • priority_queue 默认 less<T> 是大顶堆。小顶堆用 greater<T>，或自定义比较器 lambda + decltype。
  • 堆操作：push 上滤 O(log n)，pop 把末尾换到顶再下滤 O(log n)，make_heap 从 n/2 开始下滤 O(n)。
  • priority_queue 不支持修改元素优先级；需要 decrease-key 时用 set 或懒删除（Dijkstra 常用：出堆时发现已过期就跳过）。

4.7 string

SSO（短字符串优化）：std::string 对象内部有一个小缓冲区，短字符串不堆分配。libstdc++（GCC 5 起）容量 15 字节，sizeof(string) == 32；libc++ 容量 22 字节，sizeof == 24。所以短 string 移动和拷贝代价相同，且 data() 指向对象内部，移动后原来的 data() 指针失效。

COW 的废弃：GCC 4 时代用写时拷贝（引用计数共享缓冲区），C++11 要求 operator[] 返回的引用在其他操作前保持有效、且多线程下不能有隐藏共享，COW 需要原子引用计数还容易出错，因此被 SSO 取代。这也是 GCC 5 换 ABI（_GLIBCXX_USE_CXX11_ABI）的原因之一。

追问链

  • c_str() 和 data() 区别？ C++11 起都保证以 \0 结尾，等价。返回指针在 string 被修改或析构后失效。
  • string 拼接的复杂度？ += 摊还 O(len)，同 vector；a + b + c 产生多个临时，C++11 移动语义缓解，性能敏感用 reserve 后 append，或 absl::StrCat。
  • string_view（C++17）：指针 + 长度，不拥有，零拷贝切片，作只读参数替代 const string&（还能接收 const char* 不构造 string）。陷阱：不保证 \0 结尾，不能传给 C API；不能指向临时对象超过其生命周期。
  • std::string 和 char* 相互转换的开销？ string(const char*) 要 strlen + 拷贝；c_str() 免费。

4.8 算法库要点

  • std::sort：introsort。快排为主（三数取中），递归深度超过 2·log₂n 时切堆排序保证 O(n log n) 最坏，区间长度 ≤ 16 时用插入排序。不稳定。要求随机访问迭代器。
  • std::stable_sort：归并排序，有足够缓冲区时 O(n log n)，否则原地归并 O(n log² n)。稳定。
  • std::nth_element：快速选择，平均 O(n)。
  • std::partial_sort：堆，O(n log k)。
  • 比较器要求：严格弱序。用 <= 会在相等元素上 UB（可能越界或死循环）。
  • std::lower_bound / upper_bound / binary_search：要求有序，O(log n)；对非随机访问迭代器比较 O(log n) 但移动 O(n)。
  • std::unique：只移除相邻重复，先排序；返回新逻辑末尾，需配合 erase。

考察点集中在三处：扩容策略、未初始化内存上的构造/析构、移动的 noexcept 约束。写的时候要主动说出为什么用 operator new 而不是 new T[n]（后者会默认构造所有元素）。

#include <memory>
#include <utility>
#include <stdexcept>
#include <iostream>
template <class T>
class Vector {
    T* data_ = nullptr;
    size_t size_ = 0, cap_ = 0;

    // 关键点：只有 T 的移动构造是 noexcept 才敢移动。否则搬到一半抛异常，
    // 旧缓冲区已被掏空、新缓冲区不完整，无法回滚 —— 这就是 vector 的强异常保证要求。
    static void relocate(T* dst, T* src, size_t n) {
        if constexpr (std::is_nothrow_move_constructible_v<T>)
            for (size_t i = 0; i < n; ++i) ::new (dst + i) T(std::move(src[i]));
        else
            for (size_t i = 0; i < n; ++i) ::new (dst + i) T(src[i]);       // 拷贝，抛了旧的还在
    }
    void grow(size_t want) {
        size_t ncap = cap_ ? cap_ * 2 : 1;                                  // 倍增 → push_back 摊还 O(1)
        if (ncap < want) ncap = want;
        T* nd = static_cast<T*>(::operator new(ncap * sizeof(T)));          // 只分配，不构造
        relocate(nd, data_, size_);
        for (size_t i = 0; i < size_; ++i) data_[i].~T();
        ::operator delete(data_);
        data_ = nd; cap_ = ncap;
    }
public:
    Vector() = default;
    ~Vector() { clear(); ::operator delete(data_); }
    Vector(const Vector& o) { reserve(o.size_); for (size_t i = 0; i < o.size_; ++i) push_back(o.data_[i]); }
    Vector(Vector&& o) noexcept : data_(o.data_), size_(o.size_), cap_(o.cap_) { o.data_ = nullptr; o.size_ = o.cap_ = 0; }
    Vector& operator=(Vector o) noexcept { swap(o); return *this; }
    void swap(Vector& o) noexcept { std::swap(data_, o.data_); std::swap(size_, o.size_); std::swap(cap_, o.cap_); }

    void reserve(size_t n) { if (n > cap_) grow(n); }
    void push_back(const T& v) { if (size_ == cap_) grow(size_ + 1); ::new (data_ + size_) T(v); ++size_; }
    void push_back(T&& v)      { if (size_ == cap_) grow(size_ + 1); ::new (data_ + size_) T(std::move(v)); ++size_; }
    template <class... Args>
    T& emplace_back(Args&&... a) {                                          // 完美转发，原地构造，省一次临时对象
        if (size_ == cap_) grow(size_ + 1);
        ::new (data_ + size_) T(std::forward<Args>(a)...);
        return data_[size_++];
    }
    void pop_back() { data_[--size_].~T(); }
    void clear() { for (size_t i = 0; i < size_; ++i) data_[i].~T(); size_ = 0; }

    T& operator[](size_t i) { return data_[i]; }                            // 不检查，UB
    T& at(size_t i) { if (i >= size_) throw std::out_of_range("Vector::at"); return data_[i]; }
    size_t size() const { return size_; }
    size_t capacity() const { return cap_; }
    T* begin() { return data_; }  T* end() { return data_ + size_; }        // 裸指针就是合法的随机访问迭代器
};

struct Tracked {
    int v; Tracked(int x) : v(x) {}
    Tracked(const Tracked& o) : v(o.v) { ++copies; }
    Tracked(Tracked&& o) noexcept : v(o.v) { ++moves; }
    static inline int copies = 0, moves = 0;
};
int main() {
    Vector<int> v;
    for (int i = 0; i < 5; ++i) v.push_back(i * i);
    for (int x : v) std::cout << x << " ";
    std::cout << "| size=" << v.size() << " cap=" << v.capacity() << "\n";  // 0 1 4 9 16 | size=5 cap=8
    try { v.at(99); } catch (const std::out_of_range& e) { std::cout << "at 越界: " << e.what() << "\n"; }

    Vector<Tracked> t; t.reserve(4);                                        // 预留后扩容不再发生
    for (int i = 0; i < 4; ++i) t.emplace_back(i);
    std::cout << "emplace 拷贝=" << Tracked::copies << " 移动=" << Tracked::moves << "\n";  // 0 0
    t.emplace_back(4);                                                      // 触发一次扩容 → 4 次移动
    std::cout << "扩容后 拷贝=" << Tracked::copies << " 移动=" << Tracked::moves << "\n";   // 0 4
}

要能回答的追问

  • 为什么用 ::operator new + placement new，而不是 new T[cap]？ new T[cap] 会立刻默认构造 cap 个元素，而 capacity 之外的槽位应该是未构造的原始内存；而且 T 可能根本没有默认构造函数。
  • 扩容时为什么要判 is_nothrow_move_constructible？ 若移动可能抛异常，搬到一半失败时旧缓冲区已被掏空、新缓冲区不完整，无法回滚，就破坏了强异常保证。标准库用 std::move_if_noexcept 做同样的事 —— 这就是”移动构造必须写 noexcept“的根本原因，上面的 Tracked 用例实测出扩容时是 4 次移动 0 次拷贝，把 noexcept 去掉就会变成 4 次拷贝。
  • emplace_back 返回引用有什么用？ C++17 起返回新元素的引用，可以直接链式使用，省一次 back()。
  • 迭代器为什么可以直接用 T*？ 裸指针天然满足随机访问迭代器的全部要求。真实实现用包装类是为了类型安全和调试期检查。

// 1. 自定义分配器：统计分配量。STL 容器通过 allocator 与内存分配解耦
template <class T>
struct CountingAlloc {
    using value_type = T;
    static inline size_t bytes = 0;
    CountingAlloc() = default;
    template <class U> CountingAlloc(const CountingAlloc<U>&) {}
    T* allocate(size_t n) { bytes += n * sizeof(T); return static_cast<T*>(::operator new(n * sizeof(T))); }
    void deallocate(T* p, size_t n) { bytes -= n * sizeof(T); ::operator delete(p); }
    template <class U> bool operator==(const CountingAlloc<U>&) const { return true; }
    template <class U> bool operator!=(const CountingAlloc<U>&) const { return false; }
};

// 2. 给自己的容器写迭代器：把五个 traits 声明齐，算法库才认得它
template <class T>
class Ring {
    std::vector<T> buf_;
public:
    explicit Ring(std::initializer_list<T> xs) : buf_(xs) {}
    class iterator {
        T* p_ = nullptr;
    public:
        using iterator_category = std::random_access_iterator_tag;   // 决定算法走哪条实现
        using value_type        = T;
        using difference_type   = std::ptrdiff_t;
        using pointer           = T*;
        using reference         = T&;
        iterator() = default;
        explicit iterator(T* p) : p_(p) {}
        reference operator*() const { return *p_; }
        iterator& operator++() { ++p_; return *this; }
        iterator  operator++(int) { auto t = *this; ++p_; return t; }
        iterator& operator--() { --p_; return *this; }
        iterator  operator+(difference_type n) const { return iterator(p_ + n); }
        difference_type operator-(const iterator& o) const { return p_ - o.p_; }
        bool operator==(const iterator& o) const { return p_ == o.p_; }
        bool operator!=(const iterator& o) const { return p_ != o.p_; }
    };
    iterator begin() { return iterator(buf_.data()); }
    iterator end()   { return iterator(buf_.data() + buf_.size()); }
};

int main() {
    {
        std::vector<int, CountingAlloc<int>> v;
        for (int i = 0; i < 100; ++i) v.push_back(i);
        std::cout << "峰值分配 " << CountingAlloc<int>::bytes << " 字节，容量 " << v.capacity() << "\n";
    }
    std::cout << "全部释放后 " << CountingAlloc<int>::bytes << " 字节\n";   // 0

    Ring<int> r{3, 1, 2};
    std::cout << "distance=" << std::distance(r.begin(), r.end()) << "\n";  // 3，随机访问 → O(1)
    for (int x : r) std::cout << x << " ";

}

  • 有状态分配器的坑：两个容器的分配器不相等时，swap/移动赋值的行为由 propagate_on_container_* 决定，可能退化成逐元素拷贝。
  • 迭代器五件套（iterator_category/value_type/difference_type/pointer/reference）少一个，std::iterator_traits 就萃取不到，算法会编译失败。iterator_category 决定算法选哪条实现：上面 std::distance 因为标了 random_access_iterator_tag 走的是 O(1) 的 last - first，若标成 forward_iterator_tag 就会退化成 O(n) 逐个 ++。

#include <iostream>
struct ListNode {
    int val; ListNode* next;
    explicit ListNode(int v) : val(v), next(nullptr) {}
};

// 1. 反转：三指针。画图确认 next 先存下来，否则断链
ListNode* reverse(ListNode* head) {
    ListNode* prev = nullptr;
    while (head) { ListNode* nxt = head->next; head->next = prev; prev = head; head = nxt; }
    return prev;
}

// 2. 找中点：偶数长度返回后一个中点（K 个一组、排序链表都按这个约定）
ListNode* middle(ListNode* head) {
    ListNode *slow = head, *fast = head;
    while (fast && fast->next) { slow = slow->next; fast = fast->next->next; }
    return slow;
}

// 3. 判环 + 找入口：相遇后一个指针回头，同速再走必在入口相遇
ListNode* cycleStart(ListNode* head) {
    ListNode *slow = head, *fast = head;
    while (fast && fast->next) {
        slow = slow->next; fast = fast->next->next;
        if (slow == fast) {                       // 有环
            for (slow = head; slow != fast; ) { slow = slow->next; fast = fast->next; }
            return slow;
        }
    }
    return nullptr;                                // 无环
}

// 4. 合并两个有序链表：dummy 头省掉“第一个节点”的特判
ListNode* merge(ListNode* a, ListNode* b) {
    ListNode dummy(0); ListNode* tail = &dummy;
    while (a && b) { ListNode*& pick = (a->val <= b->val) ? a : b; tail->next = pick; tail = pick; pick = pick->next; }
    tail->next = a ? a : b;
    return dummy.next;
}

// 5. K 个一组翻转：先探测够不够 k 个，再翻转区间，再接回
ListNode* reverseKGroup(ListNode* head, int k) {
    ListNode dummy(0); dummy.next = head; ListNode* groupPrev = &dummy;
    while (true) {
        ListNode* probe = groupPrev;
        for (int i = 0; i < k && probe; ++i) probe = probe->next;
        if (!probe) break;                         // 不足 k 个，保持原序
        ListNode* groupStart = groupPrev->next;
        ListNode* nextGroup  = probe->next;
        probe->next = nullptr;                     // 断出这一段
        groupPrev->next = reverse(groupStart);     // 翻转后头变成 probe
        groupStart->next = nextGroup;              // 原来的头成了尾，接回去
        groupPrev = groupStart;
    }
    return dummy.next;
}

static ListNode* build(std::initializer_list<int> xs) {
    ListNode dummy(0); ListNode* t = &dummy;
    for (int x : xs) { t->next = new ListNode(x); t = t->next; }
    return dummy.next;
}
static void print(ListNode* h) { for (; h; h = h->next) std::cout << h->val << (h->next ? "->" : "\n"); }

int main() {
    print(reverse(build({1,2,3,4,5})));                 // 5->4->3->2->1
    std::cout << middle(build({1,2,3,4}))->val << "\n"; // 3（偶数取后中点）
    print(merge(build({1,3,5}), build({2,4,6})));       // 1->2->3->4->5->6
    print(reverseKGroup(build({1,2,3,4,5}), 2));        // 2->1->4->3->5
    ListNode* c = build({1,2,3,4}); c->next->next->next->next = c->next;   // 4 指回 2
    std::cout << "环入口 " << cycleStart(c)->val << "\n";                   // 2
    std::cout << "无环 " << (cycleStart(build({1,2})) == nullptr) << "\n";  // 1
}

为什么快慢指针能找到环入口：设头到入口距离 a，入口到相遇点 b，环长 L。相遇时慢走 a+b，快走 a+b+kL，且快是慢的两倍，得 a+b = kL，即 a = kL - b。所以从头走 a 步，和从相遇点走 kL-b 步，会同时到达入口。这个推导要能在白板上说出来。

5.2 哈希表设计（手写要点）

  1. 哈希函数：整数用乘法哈希或 Fibonacci hashing（乘 0x9E3779B97F4A7C15 取高位）；字符串用 FNV-1a / MurmurHash；目标是均匀、快、雪崩性好。
  2. 冲突处理：链地址法简单可靠；开放寻址（线性探测）缓存友好但要处理墓碑与负载上限。
  3. 扩容：负载因子超过阈值（链地址 1.0，开放寻址 0.7）时桶数翻倍，全部重哈希。渐进式 rehash 可避免停顿。
  4. 删除：链地址直接摘节点；开放寻址不能真删（会断开探测链），用墓碑标记，插入时可复用墓碑。
  5. 线程安全：分段锁；或每桶一把自旋锁；读多写少用 shared_mutex。

// 开链哈希表：桶数组 + 每桶一条链。面试手撕的最小可用版本
template <class K, class V, class Hash = std::hash<K>>
class HashMap {
    struct Entry { K k; V v; };
    std::vector<std::list<Entry>> buckets_;
    size_t size_ = 0;
    float maxLoad_ = 1.0f;
    Hash hash_;

    size_t idx(const K& k, size_t n) const { return hash_(k) % n; }
    void rehash(size_t n) {
        std::vector<std::list<Entry>> nb(n);
        for (auto& b : buckets_)
            for (auto& e : b) {
                size_t i = idx(e.k, n);
                nb[i].push_back(std::move(e));      // 重新挂链：节点搬桶，但元素地址变了（因为 list 节点被 move）
            }
        buckets_.swap(nb);
    }
public:
    explicit HashMap(size_t n = 8) : buckets_(n) {}

    V* find(const K& k) {
        for (auto& e : buckets_[idx(k, buckets_.size())]) if (e.k == k) return &e.v;
        return nullptr;
    }
    void put(const K& k, V v) {
        if (V* p = find(k)) { *p = std::move(v); return; }
        if (static_cast<float>(size_ + 1) > maxLoad_ * buckets_.size())
            rehash(buckets_.size() * 2);            // 负载因子超阈值 → 翻倍重哈希，单次 O(n)，摊还 O(1)
        buckets_[idx(k, buckets_.size())].push_back(Entry{k, std::move(v)});
        ++size_;
    }
    bool erase(const K& k) {
        auto& b = buckets_[idx(k, buckets_.size())];
        for (auto it = b.begin(); it != b.end(); ++it)
            if (it->k == k) { b.erase(it); --size_; return true; }   // 链地址法删除很简单：摘节点
        return false;
    }
    size_t size() const { return size_; }
    size_t bucket_count() const { return buckets_.size(); }
};

int main() {
    HashMap<int, std::string> m;
    for (int i = 0; i < 20; ++i) m.put(i, "v" + std::to_string(i));
    std::cout << "size=" << m.size() << " buckets=" << m.bucket_count() << "\n";  // 20 32
    std::cout << *m.find(7) << " " << (m.find(99) == nullptr) << "\n";            // v7 1
    m.put(7, "new7"); std::cout << *m.find(7) << "\n";                            // new7
    std::cout << m.erase(7) << " " << (m.find(7) == nullptr) << " size=" << m.size() << "\n";  // 1 1 19
}

加线程安全：把上面的 buckets_ 切成 N 段，每段一把 std::shared_mutex，段号 hash(k) % N。读路径 shared_lock，写路径 unique_lock；rehash 需要按固定顺序拿全部段锁（避免死锁），或者改用 Redis 的渐进式 rehash（新旧两张表并存，每次操作顺手搬一个桶，避免一次性 O(n) 停顿）。

struct DSU {
    std::vector<int> p, r;
    explicit DSU(int n) : p(n), r(n, 0) { std::iota(p.begin(), p.end(), 0); }
    int find(int x) { while (p[x] != x) { p[x] = p[p[x]]; x = p[x]; } return x; }   // 路径减半
    bool unite(int a, int b) {
        a = find(a); b = find(b);
        if (a == b) return false;
        if (r[a] < r[b]) std::swap(a, b);
        p[b] = a; if (r[a] == r[b]) ++r[a];
        return true;
    }
};

#include <vector>
#include <queue>
#include <iostream>
#include <climits>
using Graph = std::vector<std::vector<int>>;                 // 邻接表：g[u] = u 的邻居

// BFS 无权最短路。要点：入队时就标记 visited，否则同一点会被重复入队
std::vector<int> bfs(const Graph& g, int s) {
    std::vector<int> dist(g.size(), -1);
    std::queue<int> q; q.push(s); dist[s] = 0;
    while (!q.empty()) {
        int u = q.front(); q.pop();
        for (int v : g[u]) if (dist[v] == -1) { dist[v] = dist[u] + 1; q.push(v); }
    }
    return dist;
}

// DFS 三色判环：0 白未访问，1 灰在栈中，2 黑已完成。遇到灰点 = 有后向边 = 有环
static bool dfsCycle(const Graph& g, int u, std::vector<int>& color) {
    color[u] = 1;
    for (int v : g[u]) {
        if (color[v] == 1) return true;
        if (color[v] == 0 && dfsCycle(g, v, color)) return true;
    }
    color[u] = 2;
    return false;
}
bool hasCycle(const Graph& g) {
    std::vector<int> color(g.size(), 0);
    for (size_t i = 0; i < g.size(); ++i) if (!color[i] && dfsCycle(g, i, color)) return true;
    return false;
}

// 拓扑排序（Kahn）：入度 0 入队；出队数 < V 说明有环
std::vector<int> topoSort(const Graph& g) {
    std::vector<int> indeg(g.size(), 0), order;
    for (size_t u = 0; u < g.size(); ++u) for (int v : g[u]) ++indeg[v];
    std::queue<int> q;
    for (size_t i = 0; i < g.size(); ++i) if (!indeg[i]) q.push(i);
    while (!q.empty()) {
        int u = q.front(); q.pop(); order.push_back(u);
        for (int v : g[u]) if (--indeg[v] == 0) q.push(v);
    }
    return order.size() == g.size() ? order : std::vector<int>{};   // 空 = 有环
}

// Dijkstra 堆优化：小顶堆存 (dist, node)，懒删除处理过期项
std::vector<long long> dijkstra(const std::vector<std::vector<std::pair<int,int>>>& g, int s) {
    std::vector<long long> d(g.size(), LLONG_MAX);
    using P = std::pair<long long,int>;
    std::priority_queue<P, std::vector<P>, std::greater<P>> pq;
    d[s] = 0; pq.push({0, s});
    while (!pq.empty()) {
        auto [du, u] = pq.top(); pq.pop();
        if (du > d[u]) continue;                                     // 过期项，跳过
        for (auto [v, w] : g[u])
            if (d[u] + w < d[v]) { d[v] = d[u] + w; pq.push({d[v], v}); }
    }
    return d;
}

追问链

  • BFS 和 DFS 怎么选？ 要最短路 / 最少步数用 BFS；要遍历所有路径、判环、回溯用 DFS；图很深用 BFS 防栈溢出；图很宽用 DFS 省内存。
  • BFS 的空间复杂度？ O(最大一层宽度)，二叉树最坏 O(n/2)。DFS 是 O(深度)。
  • 双向 BFS：从起点和终点同时扩展，相遇即停，把 O(b^d) 降为 O(b^(d/2))，单词接龙类题必提。
  • A*：Dijkstra + 启发函数，f = g + h，h 不高估时最优。

5.5 LRU 与 LFU 设计

LRU：哈希表 + 双向链表。哈希表负责 O(1) 定位节点，双向链表负责 O(1) 调整顺序 —— 两者缺一不可，这是这道题的核心答案。

#include <unordered_map>
#include <iostream>
// 自己串双向链表（面试更能体现对指针的掌控；用 std::list + splice 也可以，见下方追问）
class LRUCache {
    struct Node {
        int k, v; Node *prev = nullptr, *next = nullptr;
        Node(int k_, int v_) : k(k_), v(v_) {}
    };
    int cap_;
    Node *head_, *tail_;                       // 哨兵，省掉所有头尾特判
    std::unordered_map<int, Node*> mp_;

    void remove(Node* n) { n->prev->next = n->next; n->next->prev = n->prev; }
    void pushFront(Node* n) {                  // 头部 = 最近使用
        n->next = head_->next; n->prev = head_;
        head_->next->prev = n; head_->next = n;
    }
public:
    explicit LRUCache(int cap) : cap_(cap), head_(new Node(0,0)), tail_(new Node(0,0)) {
        head_->next = tail_; tail_->prev = head_;
    }
    ~LRUCache() { for (Node* p = head_; p; ) { Node* n = p->next; delete p; p = n; } }
    LRUCache(const LRUCache&) = delete;             // 手管裸指针 → Rule of 3，禁掉拷贝最省事
    LRUCache& operator=(const LRUCache&) = delete;

    int get(int key) {
        auto it = mp_.find(key);
        if (it == mp_.end()) return -1;
        remove(it->second); pushFront(it->second);  // 命中 → 提到头部
        return it->second->v;
    }
    void put(int key, int value) {
        auto it = mp_.find(key);
        if (it != mp_.end()) { it->second->v = value; remove(it->second); pushFront(it->second); return; }
        if (static_cast<int>(mp_.size()) == cap_) { // 满了 → 淘汰尾部
            Node* victim = tail_->prev;
            remove(victim); mp_.erase(victim->k); delete victim;
        }
        Node* n = new Node(key, value);
        pushFront(n); mp_[key] = n;
    }
};

int main() {
    LRUCache c(2);
    c.put(1,1); c.put(2,2);
    std::cout << c.get(1) << " ";     // 1，此时顺序 1,2
    c.put(3,3);                       // 淘汰 2
    std::cout << c.get(2) << " ";     // -1
    c.put(4,4);                       // 淘汰 1
    std::cout << c.get(1) << " " << c.get(3) << " " << c.get(4) << "\n";  // -1 3 4
}

追问链

  • 为什么必须是双向链表？ 淘汰时要删尾节点，删除需要它的前驱。单链表找前驱是 O(n)，就退化了。
  • 为什么用两个哨兵节点？ 省掉”链表为空”“删的是头/尾”这些特判，把出错概率最高的边界代码消掉。面试时主动说这一点是加分项。
  • 能用 std::list 吗？ 可以，unordered_map<K, list<pair<K,V>>::iterator> + list::splice(begin, lst, it) 把节点 O(1) 挪到头部。代码短很多，但面试官往往想看你自己控制指针，最好两种都能写。
  • 为什么 mp_.erase(victim->k) 要用节点里存的 key？ 因为从链表尾拿到的是节点，反查哈希表需要 key。这就是节点里必须存 key 而不只存 value 的原因，是这道题最常见的漏点。
  • 并发怎么做？ 分片：按 hash(key) % N 切成 N 个独立的 LRU，每片一把锁，把锁竞争降到 1/N。单片内部 get 也会改链表，所以读也要拿写锁，不能用读写锁优化。
  • 怎么支持过期时间？ 节点加 expireAt 时间戳，get 时惰性判断已过期就当未命中并删除；再配一个后台线程定期抽样清理（Redis 的做法）。

LFU：key → (value, freq) 哈希 + freq → 双向链表 哈希 + minFreq。访问时把节点从 freq 链表移到 freq+1 链表；淘汰时删 minFreq 链表的尾。全部 O(1)。难点在维护 minFreq：只有当某次访问使旧 freq 链表变空、且旧 freq 恰好等于 minFreq 时，minFreq 才 +1；插入新 key 时直接置 minFreq = 1。

追问链

  • auto 为什么要丢弃顶层 const 和引用？ 因为 auto 复用的是模板实参推导规则，而按值传参本来就是拷贝 —— 拷贝出来的新对象是否 const、是否是引用，与源对象无关。const int& r = x; auto a = r; 推出 int，正是「我拿一份副本」的语义。要保留就写 auto&、const auto& 或 decltype(auto)。
  • decltype(x) 和 decltype((x)) 为什么不一样？ 前者作用于标识符，得到声明类型 int；后者 (x) 是表达式，而 x 作为表达式是左值，规则规定对左值表达式推出 T&，于是得到 int&。这条区别是 decltype(auto) 完美返回的基础，也是常见坑：多写一层括号就从返回值变成返回引用。
  • nullptr 到底解决了什么？ NULL 通常是 0 或 0L 的宏，类型是整数，所以 f(int) 和 f(char*) 同时存在时 f(NULL) 会选中整数版本，与直觉相反。nullptr 的类型是独立的 std::nullptr_t，能隐式转任意指针但不能转整数，重载决议因此唯一确定。
  • constexpr 和 const 的区别？ const 只承诺「不通过这个名字修改」，值可以来自运行期（const int n = rand(); 合法）；constexpr 要求编译期就能求出值，因此才能用作数组长度、模板实参、case 标签。constexpr 函数则是「允许在编译期求值」，实参不是常量时它照样退化为普通运行期函数。
  • 移动构造为什么必须加 noexcept？ vector 扩容时要把旧元素搬到新内存。若移动构造可能抛异常，搬到一半失败就既回不去（旧内存已被移空）也走不下去，无法提供强异常保证；所以标准库用 move_if_noexcept，检测到移动可能抛就退化为拷贝。少写一个 noexcept，扩容性能可能从 O(n) 次移动变成 O(n) 次深拷贝。
  • enum class 比 enum 好在哪？ 传统 enum 的枚举值会泄漏到外层作用域（两个 enum 各有一个 Red 就冲突），且能隐式转 int（if (color == 3) 这种无意义比较编译得过）。enum class 有独立作用域、不隐式转换，把这两类错误变成编译错误。

6.2 static 的五种用法（字节原题）

  1. 函数内局部静态变量：只初始化一次，生命周期到进程结束，存 .data/.bss；C++11 起初始化线程安全（编译器生成 guard 变量 + __cxa_guard_acquire）。
  2. 全局 / 命名空间作用域静态变量与函数：内部链接，仅本翻译单元可见，避免符号冲突。C++ 推荐用匿名命名空间。
  3. 类静态成员变量：所有对象共享，不占对象大小，类外定义（C++17 可 inline static 类内定义）。
  4. 类静态成员函数：无 this，只能访问静态成员，可作为回调函数指针。
  5. static 修饰的类内常量：static constexpr int N = 10; 编译期常量，可用于数组大小。

编译器层面：局部 static 变量在汇编里就是一个带 guard 字节的全局符号，函数每次进入检查 guard；静态成员变量就是一个带类名修饰的全局符号。

追问链

  • 局部 static 的线程安全是怎么做到的？ 编译器为它生成一个 guard 变量，进入函数时先原子检查 guard：未初始化则调 __cxa_guard_acquire 上锁初始化，已初始化则直接跳过。C++11 之前标准没规定这一点，所以老代码里的「懒汉单例」需要自己加双检锁；C++11 之后 Meyers 单例（函数内 static T inst;）本身就是线程安全的最简写法。
  • 为什么推荐匿名命名空间而不是 static？ 两者都给符号内部链接，但 static 修饰的类型无法作为模板实参（C++11 前），而匿名命名空间对类型、模板、变量、函数一视同仁，语义统一。此外匿名命名空间里的符号仍有唯一名字，调试时能看到，static 的则更难定位。
  • 类静态成员变量为什么要类外定义？ 类内的是声明，不分配存储；类定义通常在头文件里被多个 TU 包含，若类内即定义就会产生多重定义违反 ODR。类外定义放在唯一一个 cpp 里，保证全程序只有一份。C++17 的 inline static 用 inline 的 ODR 豁免解决了这个问题，才允许类内初始化。
  • 静态成员函数为什么能当回调函数指针，普通成员函数不能？ 普通成员函数有隐藏的 this 参数，其类型是 R (C::*)(Args)，与 C 风格的 R (*)(Args) 根本不是一种类型，也无法在没有对象的情况下调用。静态成员函数没有 this，签名与普通函数完全一致，所以能直接传给 C API。

6.3 inline、extern、volatile、explicit、mutable

  • inline：C++ 中真正的作用是允许多重定义（ODR 例外），让函数 / 变量（C++17）能定义在头文件里被多个 TU 包含；是否内联展开由编译器决定，inline 只是提示。类内定义的成员函数隐式 inline。
  • extern：声明而不定义，告诉编译器符号在别处；extern "C" 关闭 C++ 名字修饰以便与 C 链接。
  • volatile：禁止编译器把变量缓存在寄存器或优化掉读写，每次访问都真的读写内存。用于硬件寄存器、信号处理中的标志。不提供原子性和内存序，多线程同步用 atomic，不要用 volatile。
  • explicit：见 3.3。
  • mutable：允许在 const 成员函数中修改该成员，用于缓存和互斥锁。

追问链

  • inline 既然不保证内联，那关键字还有什么用？ 它真正的作用是 ODR 豁免：允许同一个函数 / 变量在多个 TU 中出现定义，链接器把重复符号合并成一份，从而使函数能定义在头文件里。是否展开是优化器根据函数体大小、调用频率、是否递归自行决定的，跟这个关键字没有必然联系。
  • volatile 为什么不能用于多线程同步？ 它只做一件事：禁止编译器把该变量缓存进寄存器或优化掉冗余读写。但它不保证原子性（v++ 仍是读-改-写三条指令，可被中断）、不建立内存序（不阻止 CPU 乱序执行，也不发出任何缓存一致性屏障）。多线程需要的恰恰是后两者，所以必须用 atomic。volatile 的正当用途只有内存映射硬件寄存器和信号处理函数里的 sig_atomic_t 标志。
  • mutable 为什么不算破坏 const 语义？ const 成员函数承诺的是逻辑上不改变对象的可观察状态，而不是物理上一个字节都不动。缓存计算结果、给 const 的读操作加互斥锁，都不改变对象对外表现出的值，却必须写成员 —— mutable 就是为这类「物理写、逻辑只读」的场景准备的。滥用它去改真正的业务字段才是破坏 const。
  • extern "C" 到底改了什么？ 只改名字修饰方式，让编译器按 C 规则生成符号（add 而不是 _Z3addii），使 C 代码能链接到。它不改变调用约定之外的任何 C++ 特性，但因为 C 符号不含参数类型，被它包住的函数不能重载 —— 两个重载会生成同名符号，链接冲突。

6.4 模板基础

  • 函数模板参数推导：只推导，不做隐式转换（max(1, 2.0) 失败）。可显式指定 max<double>(1, 2.0)。
  • 特化与偏特化：类模板可偏特化，函数模板只能全特化（要”偏特化”用重载）。
  • SFINAE / enable_if / C++20 concepts：根据类型特征启用重载。
  • 可变参数模板：template<class... Args> void f(Args&&... args)，递归展开或 C++17 折叠表达式 (args + ...)。
  • 模板为什么要放头文件？（字节原题）编译器实例化模板时需要看到完整定义；放 cpp 里，其他 TU 只有声明，链接时找不到实例化符号。例外：显式实例化 template class Vec<int>; 放在 cpp，头文件 extern template class Vec<int>;，仅适用于类型集合已知的情况。
  • 两阶段查找：模板定义时检查非依赖名，实例化时检查依赖名。所以 typename T::type 需要 typename 消歧义。

追问链

  • SFINAE 和 if constexpr 怎么选？ 要在重载集之间做选择（不同函数、不同返回类型）只能用 SFINAE / concepts；在一个函数体内部分支用 if constexpr，可读性好得多，且未选中的分支不会被实例化（所以可以写只对某些类型合法的代码）。
  • std::enable_if 放哪？ 推荐放模板参数默认值位（std::enable_if_t<cond, int> = 0），放返回类型会让函数签名难读，放函数参数会污染接口。
  • 为什么函数模板不能偏特化？ 标准如此。需要”偏特化”的效果就写重载，编译器的重载决议本身就能处理；或者把逻辑转发给一个可偏特化的类模板。
  • 模板报错为什么这么长？ 实例化链一层层展开。缓解手段：static_assert 提前给出人话错误、C++20 concepts 在约束层就报错、拆小模板。

6.5 异常

  • throw 后栈展开，沿途局部对象析构（RAII 保证资源释放），匹配到 catch 停止。
  • 异常安全三级：基本保证（不泄漏、对象仍有效）、强保证（失败则状态不变，copy-and-swap）、不抛保证（noexcept）。
  • 析构函数不要抛异常：栈展开中再抛就 terminate。析构隐式 noexcept。
  • 异常的开销：零开销模型下不抛时几乎无成本（只是表驱动），抛出时很慢（微秒级），不要用异常做控制流。
  • 为什么很多 C++ 项目禁用异常：二进制体积、可预测性、与 C 代码混用、历史遗留。Google 风格禁用，改用错误码 / StatusOr / expected。

#include <vector>
#include <stdexcept>
#include <iostream>
#include <cstring>

// 异常安全三级的具体对照
class Widget {
    char* buf_; size_t n_;
public:
    explicit Widget(size_t n) : buf_(new char[n]), n_(n) { std::memset(buf_, 0, n); }
    ~Widget() { delete[] buf_; }
    Widget(const Widget& o) : buf_(new char[o.n_]), n_(o.n_) { std::memcpy(buf_, o.buf_, n_); }

    // 反例：基本保证都做不到。new 抛异常时 buf_ 已被 delete，对象处于悬垂状态
    Widget& badAssign(const Widget& o) {
        delete[] buf_;
        buf_ = new char[o.n_];              // 这里抛 → buf_ 是野指针，析构时 double free
        n_ = o.n_; std::memcpy(buf_, o.buf_, n_);
        return *this;
    }
    // 强保证：先在临时上做完所有可能抛异常的操作，最后用 noexcept 的 swap 提交
    Widget& operator=(const Widget& o) {
        Widget tmp(o);                      // 抛了就抛了，*this 一个字节都没动
        swap(tmp);                          // noexcept，不会失败
        return *this;                       // tmp 析构掉旧资源
    }
    void swap(Widget& o) noexcept { std::swap(buf_, o.buf_); std::swap(n_, o.n_); }
    size_t size() const { return n_; }
};

// RAII 是异常安全的地基：无论从哪条路径离开，析构一定执行
struct Guard {
    const char* tag;
    explicit Guard(const char* t) : tag(t) { std::cout << "获取" << tag << " "; }
    ~Guard() { std::cout << "释放" << tag << " "; }
};
void mayThrow(bool t) {
    Guard g("资源");
    if (t) throw std::runtime_error("boom");   // 栈展开时 g 的析构照样跑
    std::cout << "正常路径 ";
}

int main() {
    Widget a(10), b(20);
    a = b;
    std::cout << "强保证赋值后 size=" << a.size() << "\n";      // 20

    try { mayThrow(false); } catch (...) {}
    std::cout << "\n";
    try { mayThrow(true); }
    catch (const std::exception& e) { std::cout << "| 捕获: " << e.what() << "\n"; }

    // 按引用捕获，且从最派生到最基类排列，否则派生类的 catch 永远进不去
    try { throw std::out_of_range("oor"); }
    catch (const std::out_of_range& e) { std::cout << "out_of_range: " << e.what() << "\n"; }
    catch (const std::logic_error&)    { std::cout << "不会到这里\n"; }
}

追问链

  • 为什么 catch 要按引用？ 按值捕获会切片（catch 基类时派生部分被切掉），还多一次拷贝。统一写 const std::exception&。
  • catch 顺序为什么重要？ 按书写顺序匹配，不做最佳匹配。把基类写在前面，派生类的 catch 永远进不去，编译器会警告。
  • 构造函数抛异常，析构函数会调用吗？ 不会 —— 对象没构造完就不算存在。但已构造完的成员和基类子对象会被逆序析构，所以成员用 RAII 就不会泄漏。要在初始化列表里捕获异常得用 function-try-block。
  • noexcept 函数里抛异常会怎样？ 不是编译错误，运行时直接 std::terminate，不做栈展开。

// optional：表达“可能没有值”，替代“返回 -1 / 空指针 / 额外 bool 出参”
std::optional<int> parsePort(std::string_view s) {
    int v = 0;
    for (char c : s) { if (c < '0' || c > '9') return std::nullopt; v = v * 10 + (c - '0'); }
    return v <= 65535 ? std::optional<int>{v} : std::nullopt;
}

// variant：闭集类型的和类型，值语义、无堆分配，是虚函数之外的第三条多态路线
using Value = std::variant<int, double, std::string>;
std::string render(const Value& v) {
    return std::visit([](const auto& x) -> std::string {
        using T = std::decay_t<decltype(x)>;
        if constexpr (std::is_same_v<T, std::string>) return "str:" + x;
        else                                          return "num:" + std::to_string(x);
    }, v);
}

int main() {
    auto p = parsePort("8080");
    std::cout << p.value_or(-1) << " " << parsePort("80x").value_or(-1) << "\n";   // 8080 -1

    std::cout << render(Value{42}) << " " << render(Value{1.5}) << " "
              << render(Value{std::string("hi")}) << "\n";                          // num:42 num:1.500000 str:hi
    Value v = 42;
    std::cout << "index=" << v.index() << " get<int>=" << std::get<int>(v) << "\n"; // 0 42

    // 结构化绑定：拆 pair / tuple / 聚合体
    std::map<std::string, int> m{{"a", 1}, {"b", 2}};
    for (const auto& [k, val] : m) std::cout << k << "=" << val << " ";
    std::cout << "\n";
    auto [q, r] = std::div(17, 5);
    std::cout << "17/5=" << q << " 余 " << r << "\n";                                // 3 2

    // if 带初始化语句：把变量作用域限制在 if 内
    if (auto it = m.find("a"); it != m.end()) std::cout << "找到 " << it->second << "\n";

    std::string s = "hello world";
    std::string_view sv(s);
    std::cout << sv.substr(6) << " 长度 " << sv.size() << "\n";                      // world 11

    m.try_emplace("a", 99);          // 已存在 → 不覆盖

}
  • optional：把”可能没有值”编进类型，替代魔数返回值和出参 bool。注意 value() 在空时抛 bad_optional_access，operator* 不检查。
  • variant：闭集类型的和类型，配 std::visit 做穷尽分派。相比虚函数：值语义、无堆分配、类型集合固定；相比 union：类型安全、自动管理析构。
  • string_view：只读参数首选，能同时接 std::string、const char* 和字面量且零拷贝。两个坑：不保证 \0 结尾（不能直接喂 C API），以及绝不能指向已析构的临时对象。
  • 结构化绑定：拆 pair/tuple/聚合体，遍历 map 时 for (const auto& [k, v] : m) 比 it->first 清楚得多。
  • if / switch 带初始化语句：把变量作用域收紧到分支内。
  • try_emplace / insert_or_assign：避开 map::operator[] “不存在就插入默认值”的副作用；try_emplace 在 key 已存在时不构造 value，比 emplace 少一次无用构造。
  • if constexpr、折叠表达式、类模板参数推导（CTAD）：见 §6.4。

7.编译与链接

四个阶段

  1. 预处理：展开 #include、宏替换、条件编译，输出 .i。g++ -E。
  2. 编译：词法、语法、语义分析，优化，生成汇编 .s。g++ -S。
  3. 汇编：生成目标文件 .o（ELF，含 .text、.data、符号表、重定位表）。g++ -c。
  4. 链接：合并各 .o 的段，符号解析（未定义符号找定义），重定位（填地址）。输出可执行文件或库。

静态链接 vs 动态链接

静态 .a 动态 .so
时机 链接期把代码拷进可执行文件 运行时由 ld.so 加载
体积 大 小
内存 每个进程一份 代码段多进程共享
更新 重新链接 替换 .so 即可，但有 ABI 兼容风险
性能 直接调用 通过 PLT / GOT 间接跳转，首次调用延迟绑定
依赖 无运行时依赖 依赖地狱，ldd 查看

PIC 与 GOT/PLT：动态库被加载到任意地址，代码必须是位置无关的。全局数据访问通过 GOT（全局偏移表）间接；函数调用通过 PLT 跳到 GOT 表项，首次调用触发解析器填表（延迟绑定），之后直接跳。

常见链接错误

  • undefined reference：声明了没定义、忘了链接库、C/C++ 混用没加 extern "C"、模板定义放在 cpp。
  • multiple definition：头文件里定义了非 inline 函数或变量、多个 TU 各有一份。解决：inline、static、匿名命名空间、或移到 cpp。
  • 头文件为什么要 include guard / #pragma once：防止同一 TU 内重复包含导致重复定义；它不解决跨 TU 的多重定义，那是 ODR 和 inline 的事。

ODR（单一定义规则）：每个非 inline 函数 / 变量在整个程序中只能有一个定义；inline 函数 / 类 / 模板可以在多个 TU 中定义，但各定义必须一致。模板实例化产生的重复符号被放在 COMDAT 段，链接器去重。

名字修饰（mangling）：C++ 把函数名、参数类型、命名空间、类名编码进符号（如 _ZN3foo3barEi），支持重载和命名空间。nm -C / c++filt 还原。C 没有修饰，所以 C++ 调用 C 函数要 extern "C" 让编译器按 C 方式生成符号。

追问链

  • static 库和 shared 库里的全局变量初始化顺序？ 同一 TU 内按定义顺序；跨 TU 未定义（static initialization order fiasco），解决用函数内局部静态（Meyers 单例）。
  • -O2 做了什么？ 内联、循环展开、常量传播、死代码消除、向量化、尾调用优化等。调试时 -O0 -g，发布 -O2 或 -O3，-Og 兼顾。
  • LTO（链接时优化）：把优化推迟到链接期，能跨 TU 内联。

#include <iostream>
void work(int id, int& acc, std::mutex& m) { std::lock_guard<std::mutex> lk(m); acc += id; }
int main() {
    int acc = 0; std::mutex m;
    std::vector<std::thread> ts;
    for (int i = 1; i <= 4; ++i)
        ts.emplace_back(work, i, std::ref(acc), std::ref(m));   // 陷阱：thread 默认拷贝参数，传引用必须 std::ref
    for (auto& t : ts) t.join();                                 // 不 join 也不 detach → 析构时 std::terminate
    std::cout << "累加 " << acc << "\n";                          // 10

    // 陷阱：detach 后主线程结束，子线程访问的栈变量已销毁。局部对象千万别 detach 后引用
    std::thread([]{ /* 独立任务，不碰外部栈 */ }).detach();

    // thread_local：每线程一份
    static thread_local int tls = 0;
    std::thread a([]{ static thread_local int t = 0; t += 5; std::cout << "线程A tls=" << t << " "; });
    std::thread b([]{ static thread_local int t = 0; t += 7; std::cout << "线程B tls=" << t << "\n"; });
    a.join(); b.join(); (void)tls;                                // 各自 5 和 7，互不影响
    std::cout << "硬件并发数 " << (std::thread::hardware_concurrency() > 0) << "\n";
}

协程：用户态调度的”线程”，切换只保存少量寄存器（几十 ns），一个线程可跑百万协程；阻塞 IO 要配合非阻塞 + 事件循环。有栈协程（libco、goroutine）vs 无栈协程（C++20 coroutine，编译器把函数变成状态机）。

追问链

  • 线程池开多少线程？ CPU 密集型约等于核数（hardware_concurrency()），因为再多也没有空闲核来跑，只会增加上下文切换和缓存抖动；IO 密集型约等于 核数 × (1 + 等待时间/计算时间)，因为线程大部分时间阻塞在 IO 上不占 CPU，需要更多线程才能把核喂饱。公式只用来定初值，真实值必须压测 —— 它假设了所有任务同质，而现实负载往往不是。
  • join 和 detach 为什么必须二选一？ std::thread 析构时若仍 joinable()，标准规定直接 std::terminate()。这是有意为之：默认 join 会让析构函数悄悄阻塞（析构里做长时间等待是灾难），默认 detach 又会让线程访问已销毁的栈对象。两种默认都危险，所以标准强迫你显式表态。C++20 的 std::jthread 选择了「析构自动 join + 配合 stop_token 请求退出」，让 join 语义变得安全可用。
  • detach 之后为什么容易出悬垂？ detach 只是断开了 thread 对象与执行线程的关联，线程本身继续跑。主线程一旦返回，它栈上的局部变量全部析构，而被 detach 的线程若捕获了这些变量的引用或指针，就在访问已释放内存。所以 detach 的线程只能碰堆上的、有独立生命周期的数据（如 shared_ptr 拷贝）。
  • 一个线程崩溃为什么整个进程都挂？ 段错误是发给进程的信号（SIGSEGV），默认行为是终止整个进程，而不是某个线程。更根本的原因是线程共享同一个地址空间：一个线程写坏了堆或全局数据，其他线程随时会踩到，即使不立刻崩也已经不可信。需要故障隔离的场景（浏览器渲染、插件宿主）因此用多进程而不是多线程。
  • 进程间通信哪种最快，为什么？ 共享内存。其他方式（管道、消息队列、socket）都要把数据从发送方用户空间拷进内核缓冲区、再拷到接收方用户空间，至少两次拷贝加两次系统调用；共享内存把同一段物理页映射进两个进程的页表，读写就是普通内存访问，零拷贝零系统调用。代价是它不自带同步，需要自己用信号量或 futex 保护。

#include <mutex>
#include <condition_variable>
#include <queue>
template<class T>
class BlockingQueue {
    std::mutex mtx; std::condition_variable notEmpty; std::queue<T> q;
public:
    void push(T v) {
        { std::lock_guard<std::mutex> lk(mtx); q.push(std::move(v)); }   // 先解锁再 notify，减少被唤醒线程立刻阻塞
        notEmpty.notify_one();
    }
    T pop() {
        std::unique_lock<std::mutex> lk(mtx);
        notEmpty.wait(lk, [this] { return !q.empty(); });   // 谓词循环检查，防虚假唤醒
        T v = std::move(q.front()); q.pop();
        return v;
    }
};

为什么会虚假唤醒：futex_wait 可能被信号中断返回，或 notify_one 与多个等待者的竞争，POSIX 明确允许，所以标准要求用循环检查条件。

追问链

  • lock_guard / unique_lock / scoped_lock 怎么选？ 默认用 lock_guard：它只有一个成员且构造即加锁、析构即解锁，没有任何运行期状态，是零开销的。需要延迟加锁、中途 unlock、转移锁所有权、或配合条件变量时才用 unique_lock —— 它多存一个「是否持有」的标志，cv.wait 必须能在等待期间解锁再重新加锁，所以只接受 unique_lock。一次锁多把互斥量用 scoped_lock（C++17），它内部用 std::lock 的 try-and-backoff 算法，避免固定顺序加锁带来的死锁。
  • notify_one 和 notify_all 怎么选？ 只有当所有等待者等的是同一个条件、且每次只有一个能继续时（典型如队列出队一个元素）才能用 notify_one。如果等待者的谓词不同，notify_one 可能唤醒一个谓词仍为假的线程，它检查后继续睡，而这次通知就永久丢失了 —— 真正该醒的线程还在等。这种情况必须 notify_all，让所有线程自己检查谓词。
  • 为什么建议在锁外 notify？ 持锁通知时，被唤醒的线程第一件事是重新获取那把锁，而锁还在通知者手里，于是它立刻又阻塞一次（hurry up and wait），多了一轮无谓的上下文切换。注意前提：状态修改必须在锁内完成，只把 notify 挪到锁外。
  • 为什么 wait 必须带谓词？ 两个原因。一是虚假唤醒 —— 底层 futex_wait 可能被信号打断而提前返回，POSIX 明确允许，标准因此不保证 wait 返回时条件成立。二是丢失唤醒的补救 —— 谓词版本在进入等待之前先检查一次条件，如果通知发生在你调用 wait 之前，谓词为真就直接不等了。无谓词的裸 wait 这两种情况都会挂死。
  • 互斥锁到底多贵？ 无竞争时就是一次用户态原子 CAS，几十纳秒，根本不进内核。只有 CAS 失败（真的有竞争）才走 futex 系统调用把线程挂起，代价跳到微秒级。所以「锁很慢」的说法不准确，慢的是竞争。推论：临界区要短；但短到只有几十纳秒时，自旋锁反而更划算，因为这时挂起 / 唤醒的开销已经超过忙等本身。

8.3 原子操作与内存序

  • CAS：compare_exchange(expected, desired)：若当前值等于 expected 则写入 desired 返回 true，否则把当前值写回 expected 返回 false。硬件上是 lock cmpxchg（x86）或 LL/SC（ARM）。所有无锁结构的基石。
  • 原子性怎么保证（字节原题）：x86 上对齐的 8 字节以内读写天然原子；RMW 操作用 lock 前缀锁定缓存行（缓存一致性协议 MESI 保证只有一个核能独占修改），不再锁总线。
  • 内存序：relaxed 只保证原子性；acquire（读）/ release（写）配对建立 happens-before，release 之前的写对 acquire 之后的读可见；seq_cst 全局一致顺序，默认，最慢。x86 是强序平台，acquire/release 几乎免费，seq_cst 存储需要 mfence。
  • ABA 问题：CAS 期间值 A → B → A，CAS 误判未变。解决：带版本号的双字 CAS、hazard pointer、epoch 回收。

#include <atomic>

// 1. relaxed 只保证单个变量的原子性，不保证跨变量的顺序
std::atomic<int> data{0};
std::atomic<bool> ready{false};

void producer() {
    data.store(42, std::memory_order_relaxed);
    ready.store(true, std::memory_order_release);   // release：此前的写不会被重排到它之后
}
void consumer() {
    while (!ready.load(std::memory_order_acquire))  // acquire：之后的读不会被重排到它之前
        std::this_thread::yield();
    // acquire 读到了 release 写的值 → 建立 happens-before → 这里一定看得到 42
    assert(data.load(std::memory_order_relaxed) == 42);
}

// 2. CAS 自旋锁：compare_exchange_weak 允许伪失败，所以必须写在循环里
class SpinLock {
    std::atomic_flag flag_ = ATOMIC_FLAG_INIT;
public:
    void lock()   { while (flag_.test_and_set(std::memory_order_acquire)) ; }
    void unlock() { flag_.clear(std::memory_order_release); }
};

// 3. 无锁栈的 push：CAS 循环的标准形态
template <class T>
class LockFreeStack {
    struct Node { T v; Node* next; };
    std::atomic<Node*> head_{nullptr};
public:
    void push(T v) {
        Node* n = new Node{std::move(v), nullptr};
        n->next = head_.load(std::memory_order_relaxed);
        // 失败时 CAS 会把当前 head 写回 n->next，直接重试即可
        while (!head_.compare_exchange_weak(n->next, n,
                   std::memory_order_release, std::memory_order_relaxed)) {}
    }
    bool pop(T& out) {                                  // 注意：这个 pop 有 ABA 与悬垂问题，见下方说明
        Node* old = head_.load(std::memory_order_acquire);
        while (old && !head_.compare_exchange_weak(old, old->next,
                   std::memory_order_acquire, std::memory_order_relaxed)) {}
        if (!old) return false;
        out = old->v; delete old; return true;
    }
};

int main() {
    std::thread t1(producer), t2(consumer);
    t1.join(); t2.join();
    std::cout << "acquire/release 同步 OK\n";

    SpinLock sl; long counter = 0;
    std::vector<std::thread> ts;
    for (int i = 0; i < 4; ++i) ts.emplace_back([&] {
        for (int j = 0; j < 10000; ++j) { sl.lock(); ++counter; sl.unlock(); }
    });
    for (auto& t : ts) t.join();
    std::cout << "自旋锁计数 " << counter << "\n";        // 40000

    std::atomic<long> ac{0};
    ts.clear();
    for (int i = 0; i < 4; ++i) ts.emplace_back([&] {
        for (int j = 0; j < 10000; ++j) ac.fetch_add(1, std::memory_order_relaxed);  // 纯计数用 relaxed 即可
    });
    for (auto& t : ts) t.join();
    std::cout << "原子计数 " << ac.load() << "\n";        // 40000

    LockFreeStack<int> st; int out = 0;
    st.push(1); st.push(2);
    st.pop(out); std::cout << "无锁栈 pop " << out << "\n";  // 2
    std::cout << "int 无锁? " << std::atomic<int>{}.is_lock_free() << "\n";  // 1
}

上面 LockFreeStack::pop 是故意留了坑的版本，面试时要主动指出来：两个线程同时 pop，A 读到 old = head，还没 CAS 就被切走；B 把该节点 pop 并 delete，再 push 回一个地址相同的新节点；A 恢复后 CAS 比较地址发现”没变”而成功，但 old->next 读的是已释放内存 —— 这就是 ABA 叠加悬垂指针。生产级实现要靠 hazard pointer 或 epoch-based reclamation 延迟回收。能说出这一点，比写出一个”看起来能跑”的无锁栈重要得多。

内存序怎么选：纯计数器（如引用计数的增加、统计量）用 relaxed；用一个标志位发布数据用 release/acquire 配对；拿不准就用默认的 seq_cst，先正确再优化。x86 上 acquire/release 几乎零成本（硬件本身就是强序），但在 ARM 上是真实开销，所以在 arm64 服务器上写错内存序更容易暴露。

追问链

  • relaxed 什么时候够用？ 只需要「计数不丢」而不关心与其他数据的先后关系时，比如统计计数器、shared_ptr 的引用计数递增（递增只可能发生在你已经持有一个有效引用的时候，不需要同步任何别的数据）。但引用计数递减必须是 acq_rel 或在归零时补一个 acquire 屏障 —— 因为最后一个减到 0 的线程要执行析构，它必须能看到其他线程在放弃引用之前对对象做的所有写入，否则析构读到的是过期数据。
  • compare_exchange_weak 为什么允许伪失败？ ARM / PowerPC 等平台用 LL/SC（Load-Linked / Store-Conditional）实现 CAS，只要这段期间发生上下文切换、中断，或该缓存行被别的核碰过，SC 就会失败 —— 哪怕值一个字节都没变。weak 把这种失败暴露出来，换取不必生成额外的重试循环指令；因为 CAS 本来就要写在 while 循环里，伪失败无非多转一圈。反过来，如果你只想试一次（不在循环里），必须用 strong，否则会把伪失败误判成「值被改了」。
  • volatile 能替代 atomic 吗？ 不能，而且是两个维度上都不能。原子性：v++ 编译出来仍是读、改、写三条指令，中间可被打断，volatile 只保证这三次访存不被优化掉，不保证它们是一个不可分割的操作。内存序：volatile 不发出任何屏障指令，既不阻止编译器重排周围的非 volatile 访问，也不阻止 CPU 乱序和写缓冲延迟，别的核可能长时间看不到你的写。Java 的 volatile 有内存语义，C++ 的没有，这是最常见的混淆来源。
  • 无锁一定比有锁快吗？ 不一定，高竞争下往往更慢。CAS 失败要重试，多个核反复对同一缓存行做 RMW 会导致缓存行在核间乒乓（每次独占都要让其他核失效），CPU 被烧在重试上；而互斥锁在竞争激烈时会把线程挂起，让出核给别人干活。无锁的真正价值不是吞吐，而是无阻塞保证（某个线程被抢占或崩溃不会永久拖死其他线程）和尾延迟可预测（不会出现持锁线程被换出导致的长尾）。
  • ABA 为什么只在带指针的无锁结构里致命？ 对纯计数器，值从 A 变 B 再变回 A，CAS 认为「没变」在语义上通常无害。但对指针，地址相同不代表指向的还是同一个对象 —— 内存被释放后重新分配很容易拿到同一地址，此时 CAS 成功，而你手里 old->next 读的是已被回收的内存。解决方向都是「让地址不被这么快复用」：带版本号的双字 CAS（地址+计数一起比）、hazard pointer、epoch-based reclamation。

8.4 死锁

四个必要条件：互斥、持有并等待、不可抢占、循环等待。破坏任一即可避免。

实践手段：固定加锁顺序（按地址排序）、std::scoped_lock(m1, m2) 一次锁多把（内部用 try-lock 回退算法）、try_lock + 超时、缩小锁范围、避免在持锁时调用回调 / 未知代码、用锁层级检测工具（TSan、-fsanitize=thread）。

追问链

  • 四个条件里为什么实践中总是破坏「循环等待」？ 另外三个基本动不了：互斥是锁的本质；不可抢占如果强行破坏（随意剥夺别人的锁）会让临界区失去意义；持有并等待要求一次性申请全部资源，在锁的种类由运行期数据决定时根本做不到。只有循环等待可以用一条不影响正确性的纪律消除 —— 全局固定一个加锁顺序，环就形成不了。
  • std::scoped_lock(m1, m2) 凭什么不死锁？ 它不按固定顺序硬锁，而是用 try-and-backoff：先锁住第一把，其余用 try_lock；只要有一把失败，就把已持有的全部释放，然后从失败的那把重新开始。因为不存在「持有 A 等待 B」的状态，循环等待条件不成立。代价是竞争激烈时可能反复回退。
  • 为什么持锁时不能调用回调 / 用户代码？ 你不知道那段代码会做什么。它可能去拿另一把锁（顺序不受你控制，直接构成环）、可能重新调用你的接口造成自死锁、也可能阻塞在 IO 上把你的临界区拖到毫秒级。规避方式是把回调移出临界区：在锁内把需要的数据拷出来，解锁后再调。
  • 递归锁为什么被认为是坏味道？ 它能工作，但它掩盖的是「我不知道调用这个函数时是否已经持有锁」——也就是不变量的边界没想清楚。而且递归锁下，函数返回时对象不一定回到一致状态（外层还在临界区中间），依赖「函数返回即状态一致」的代码会出错。正确做法通常是把函数拆成加锁的公有版和不加锁的私有版。
  • 怎么定位线上的死锁？ gdb -p <pid> 后 thread apply all bt，看哪些线程卡在 __lll_lock_wait / pthread_mutex_lock，顺着栈就能还原出各自持有和等待的锁，环一目了然。事前预防用 TSan（-fsanitize=thread），它维护锁的获取顺序图，即使这次没真的死锁，只要出现了顺序不一致也会报警。

class DCLPSingleton {
    static std::atomic<DCLPSingleton*> inst_;
    static std::mutex mtx_;
public:
    static DCLPSingleton* instance() {
        DCLPSingleton* p = inst_.load(std::memory_order_acquire);    // acquire 配对下面的 release
        if (!p) {                                                    // 第一次检查：无锁快路径
            std::lock_guard<std::mutex> lk(mtx_);
            p = inst_.load(std::memory_order_relaxed);
            if (!p) {                                                // 第二次检查：拿锁后再确认
                p = new DCLPSingleton();
                // release 保证：构造完成的写一定先于指针发布。
                // 少了它，别的线程可能拿到非空指针却看到未构造完的对象。
                inst_.store(p, std::memory_order_release);
            }
        }
        return p;
    }
};

// ---- 线程池：有界队列 + 两个条件变量 + 优雅关闭
class ThreadPool {
    std::vector<std::thread> workers_;
    std::queue<std::function<void()>> tasks_;
    std::mutex mtx_;
    std::condition_variable notEmpty_, notFull_;
    size_t maxTasks_;
    bool stop_ = false;
public:
    explicit ThreadPool(size_t n, size_t maxTasks = 1024) : maxTasks_(maxTasks) {
        for (size_t i = 0; i < n; ++i) workers_.emplace_back([this] {
            for (;;) {
                std::function<void()> task;
                {
                    std::unique_lock<std::mutex> lk(mtx_);
                    notEmpty_.wait(lk, [this] { return stop_ || !tasks_.empty(); });  // 带谓词，防虚假唤醒
                    if (stop_ && tasks_.empty()) return;             // 关闭且排空才退出
                    task = std::move(tasks_.front()); tasks_.pop();
                }
                notFull_.notify_one();
                task();                                              // 注意：在锁外执行，否则池退化成串行
            }
        });
    }
    template <class F>
    auto submit(F f) -> std::future<decltype(f())> {
        auto p = std::make_shared<std::promise<decltype(f())>>();
        auto fut = p->get_future();
        {
            std::unique_lock<std::mutex> lk(mtx_);
            notFull_.wait(lk, [this] { return stop_ || tasks_.size() < maxTasks_; });  // 队列满则阻塞生产者
            if (stop_) throw std::runtime_error("pool stopped");
            tasks_.push([p, f]() mutable { p->set_value(f()); });
        }
        notEmpty_.notify_one();
        return fut;
    }
    ~ThreadPool() {
        { std::lock_guard<std::mutex> lk(mtx_); stop_ = true; }
        notEmpty_.notify_all(); notFull_.notify_all();               // 必须 all，否则有线程永远醒不来
        for (auto& t : workers_) t.join();                           // join 而不是 detach，保证任务跑完
    }
};

int main() {
    std::cout << Singleton::instance().next() << Singleton::instance().next() << " ";  // 12：同一个实例
    std::cout << (DCLPSingleton::instance() == DCLPSingleton::instance()) << "\n";     // 1
    ThreadPool pool(4);
    std::vector<std::future<int>> fs;
    for (int i = 0; i < 8; ++i) fs.push_back(pool.submit([i] { return i * i; }));
    for (auto& f : fs) std::cout << f.get() << " ";
    std::cout << "\n";                                               // 0 1 4 9 16 25 36 49
}

追问链

  • Meyers 单例为什么线程安全？ C++11 起标准要求局部静态变量的初始化是线程安全的：编译器生成一个 guard 变量，首个线程通过 __cxa_guard_acquire 拿锁初始化，其余线程阻塞等待。C++11 之前没有这个保证，才需要双检锁。
  • 双检锁为什么必须用 acquire/release？ new DCLPSingleton() 包含”分配内存 → 构造对象 → 把地址写给 inst_“三步，编译器或 CPU 可能把第三步重排到第二步之前。别的线程在第一次检查处读到非空指针，却拿到一个还没构造完的对象。release 存储保证构造的写不会被重排到发布之后，acquire 加载保证读到指针后能看见那些写。用普通指针 + volatile 是修不好这个 bug 的，volatile 不提供内存序。
  • 单例什么时候是坏味道？ 隐藏依赖、难以单测（无法注入 mock）、析构顺序不可控（跨 TU 的静态对象销毁顺序未定义）。能用依赖注入就别用单例。
  • 线程池任务为什么要在锁外执行？ 持锁执行任务会让整个池退化成串行，这是最常见的实现错误。
  • 队列满了怎么办？ 三种策略：阻塞生产者（上面的 notFull_）、丢弃任务并返回失败、调用方自己执行（caller-runs）。要能说出取舍。
  • 为什么关闭时必须 notify_all 而不是 notify_one？ 所有工作线程都阻塞在 wait 上，只唤醒一个，其余永远醒不来，join 就会死锁。
  • 为什么用 join 而不是 detach？ detach 后主线程退出时子线程可能还在访问已销毁的池成员。析构函数里 join 才能保证任务跑完、资源安全释放。
  • submit 用 shared_ptr<promise> 包一层是为什么？ std::function 要求可拷贝，而 std::promise 只能移动，直接捕获会编译失败。C++23 的 std::move_only_function 可以省掉这层。

class B : public A { public: B() { cout << "B() "; } ~B() { cout << "~B() "; } };

9.3 构造函数中调用虚函数

    virtual void init() { std::cout << "Base::init "; }
    virtual ~Base() = default;
};
struct Derived : Base {
    int v = 42;
    Derived() : Base() { init(); }           // 此时 vptr 已切换到 Derived

};

// 输出：Base::init Derived::init(42)
// 若 Base 构造时能调到 Derived::init，会读到未初始化的 v，所以语言规定构造期间动态类型是当前构造层

9.10 重载决议与隐式转换

#include <iostream>
void f(int)    { std::cout << "int "; }
void f(double) { std::cout << "double "; }
void f(char*)  { std::cout << "char* "; }
void g(long)   { std::cout << "long "; }
void g(void*)  { std::cout << "void* "; }
int main() {
    f(1);        // int：精确匹配
    f(1.0f);     // double：float→double 是"提升"，优于 float→int 的"转换"
    f('a');      // int：char→int 是提升
    f(nullptr);  // char*：nullptr_t 只能转指针类型
    g(0L);       // long：精确匹配
    g(nullptr);  // void*
    // g(0);     // 编译错误：二义性。0 到 long 是整型转换，0 到 void* 是空指针转换，同属"转换"级别
    // f(NULL);  // NULL 是 0 或 0L 的宏，同样落入二义性或意外选中整数版本，这就是 C++11 引入 nullptr 的原因
    std::cout << "\n";
}
// 输出：int double int char* long void*

重载决议排名：精确匹配 > 提升（char/short→int，float→double）> 标准转换（整型转换、浮点整型互转、指针转换、派生→基类）> 用户定义转换 > 省略号。同一级别内有多个候选且互不更优，就是二义性错误，编译器不会随便挑一个。

9.11 求值顺序

9.13 大小端与位域

#include <cstdio>
#include <cstdint>
int main() {
    // 指针法：小端机器把低位字节放在低地址
    uint32_t v = 0x12345678;
    unsigned char* p = reinterpret_cast<unsigned char*>(&v);
    printf("%02X %02X ", p[0], p[3]);   // x86 / ARM 默认小端：78 12；大端机则是 12 78

    // union 法（字节高频原题）：所有成员共享同一块内存起始地址
    union U { uint32_t i; char c[4]; } u{0x01020304};
    printf("%d ", u.c[0]);              // 小端 4（低地址存最低位字节 0x04），大端 1

    // 位域：能压缩空间，但布局是实现定义的
    struct BF { unsigned a : 1; unsigned b : 3; unsigned c : 4; };
    printf("%zu\n", sizeof(BF));        // 4：三个域共挤在一个 unsigned 里
}

为什么会有大小端之分：多字节整数在内存里必须决定「最低位字节放前还是放后」，两种选择在硬件上各有道理 —— 小端做类型截断方便（取低 8 位直接读首字节，不用调整地址），大端做数值比较和人眼阅读方便（内存序即书写序）。标准没有规定，所以它是平台属性。x86、ARM（默认）是小端，早期 SPARC、PowerPC 和网络协议是大端。

追问链

  • 为什么网络传输要转字节序？ TCP/IP 协议族规定网络字节序为大端，而主机可能是小端，双方若各按本地序解释同一段字节，读出的数就不是一个数。所以发送前 htons/htonl、接收后 ntohs/ntohl。这几个函数在大端机上是空操作，所以无脑加上不会有额外代价。C++20 起可以用 std::endian::native 在编译期判断。
  • union 读取非最后写入的成员，标准上合法吗？ 在 C++ 里是未定义行为（C 语言明确允许这种 type punning，C++ 没有跟进），只是所有主流编译器都按你期望的方式实现了，所以代码「能跑」。要写合规代码应该用 std::bit_cast（C++20）或 std::memcpy —— 后者被编译器识别为类型双关的惯用法，-O2 下会优化成一条 mov，零开销。
  • 位域为什么不能用于跨平台的协议解析？ 标准没有规定位域在存储单元内的分配方向（从高位还是低位开始填）、是否允许跨存储单元、以及填充规则，全部是实现定义的。同一份结构体在 GCC/x86 和某个嵌入式编译器上布局可能完全不同。协议解析要手写移位和掩码。
  • 怎么在编译期判断大小端？ C++20 用 if constexpr (std::endian::native == std::endian::little)。C++20 之前没有合规的办法 —— union 法是 UB，reinterpret_cast 法不是常量表达式，所以实践中靠构建系统传宏（__BYTE_ORDER__ / __ORDER_LITTLE_ENDIAN__，GCC 和 Clang 都预定义）。
