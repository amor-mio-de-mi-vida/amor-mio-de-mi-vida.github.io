TL;DR

  • GPU 上的大规模排序几乎都是基数排序（radix sort）：轮数只取决于 key 的位宽，与数据无关；每一轮都由“直方图 → 扫描 → 稳定写出”三个并行原语组成。
  • Bitonic 排序网络的比较顺序事先固定、没有数据相关的分支，适合在共享内存或寄存器里排几百到几千个元素，代价是 \(O(n\log^2 n)\) 次比较。
  • Onesweep 把基数排序每一轮的全局访存从约 \(3n\) 降到约 \(2n\)，办法是用单遍扫描算每个 block 的写出位置，并提前一次算好所有数字位的直方图。
  • Top-K 往往不需要排序：\(k=1\) 是一次归约，小 \(k\) 可以在寄存器里维护候选列表，大 \(k\) 用基数选择逐字节缩小候选范围。
  • LLM 采样里的 top-k 和 min-p 都能化成一个 logit 阈值，top-p 可以用拒绝采样绕开全词表排序，把每步的显存读写从几十倍词表大小降到几倍。

主线定位：① 字节账 · ⑤ 整卡账

排序与 Top-K：减少遍数（①），按数据规模选择并行策略（⑤）。全系列的分析主线是“一个下界 + 五笔账”，见主线篇。

排序在 GPU 程序里出现的地方比想象中多。3D Gaussian Splatting（3DGS）每渲染一帧，都要把每个高斯按它覆盖的屏幕 tile 复制成若干个“高斯—tile”对，再把这些对按 tile 和深度排序 [1]；MoE 模型的路由器要为每个 token 从几百个专家里挑出 top-k；大语言模型每生成一个 token，采样器都要在十几万个 logit 上做 top-k、top-p 或 min-p 截断。这三件事的规模、精度要求和延迟预算都不一样，但都绕不开“排序”或“找出最大的几个”。

本篇回答三个问题：GPU 为什么用基数排序而不是快排；排序的几种基本 kernel（bitonic 网络、一轮基数排序、单遍的 Onesweep）各自怎么写；以及什么时候根本不需要完整排序，用 Top-K 或拒绝采样就够了。本篇大量用到前几篇的原语：归约（第 10 篇）、warp 投票与 shuffle（第 11 篇）、扫描与单遍 decoupled look-back（第 12 篇），这里只在用到时一句话回顾。

GPU 偏爱基数排序：轮数固定，每轮都是规整的并行原语

CPU 上最常用的快速排序（quicksort）在 GPU 上并不好用，原因有三。第一，划分（partition）的每一步都依赖前一步选出的枢轴，递归深度和每层的工作量由数据决定，很难均匀地分给上万个线程。第二，“和枢轴比较、决定往左还是往右”是数据相关的分支，同一个 warp 里的线程会走不同方向，产生分支发散（第 2 篇）。第三，也是最重要的：排序大数组时瓶颈是显存带宽，衡量算法好坏的标准是数据要在显存里来回搬几遍，而基于比较的排序在这一点上吃亏。

Onesweep 论文给过一个具体对比：基于二路归并的 GPU 归并排序排 1,600 万个 32 位 key，大约要扫全局内存 10 遍（一遍先排出有序子列表，再做 9 轮二路归并；按 \(2^{24}/2^9\) 倒推，每个子列表约 32K 个 key）；而 Onesweep 的基数排序只要 5 遍（一遍直方图加 4 轮分桶）[2, §2]。基于比较的排序总工作量是 \(O(n\log n)\)，且很难一次合并很多路来减少遍数；基数排序的工作量是 \(O(n\cdot w/d)\)，其中 \(w\) 是 key 的位宽、\(d\) 是每轮处理的位数，轮数 \(w/d\) 与 \(n\) 和数据分布都无关。

基数排序的另一个优点是每一轮的结构完全固定：统计每个“数字”（digit，key 中连续 \(d\) 位组成的值）出现几次，做一次前缀和得到每个数字的起始位置，再把每个 key 写到它的位置上。这三步正好是 GPU 最擅长的直方图、扫描和分散写出（scatter）。代价是 key 必须能映射成无符号整数，而且映射要保持大小顺序；浮点数怎么做到这一点，见key 的设计。

两种基数排序

LSD（least significant digit first）从最低位的数字排起，每一轮对整个数组做全局分桶，要求每轮稳定（相同数字的 key 保持原来的相对顺序），这样低位排好的顺序才不会被高位打乱。MSD（most significant digit first）从最高位排起，排完一轮后把数组分成 \(2^d\) 个子问题递归处理。GPU 上的通用排序库（如 CUB）主要用 LSD，本篇也以 LSD 为主。

Bitonic 网络：比较的顺序事先固定，适合排小数组

在讲大数组之前，先看小数组。一个 block 里排 1,024 个数（比如一个 tile 内的局部排序、或者 Top-K 的最后整理），数据能完整放进共享内存，这时显存遍数不是问题，需要的是一种所有线程能步调一致执行的算法。排序网络（sorting network）正好满足：它是一串事先确定好的“比较-交换”（compare-exchange）操作，每个操作比较两个位置上的值，按规定方向把较小的放一边、较大的放另一边。哪两个位置比较、往哪个方向交换，都与数据无关。

Bitonic 排序是 Batcher 提出的一种排序网络 [3]。“bitonic 序列”指先升后降（或先降后升）的序列；对一个长度为 \(m\) 的 bitonic 序列，把位置 \(i\) 和 \(i+m/2\) 两两比较交换，就能得到两个长度为 \(m/2\) 的 bitonic 序列，并且前一半的所有值都不大于后一半。重复这一步直到长度为 1，序列就排好了（这一步叫 bitonic merge）。完整的排序从长度 2 开始：相邻两两排成方向交替的有序对，拼起来就是长度 4 的 bitonic 序列；合并后再按交替方向拼成长度 8 的 bitonic 序列……图 1 用 8 个数完整演示了这个过程。

对 \(n=2^m\) 个元素，网络共有 \(m(m+1)/2\) 步，每步 \(n/2\) 次比较交换，总共 \(\tfrac{n}{4}m(m+1)\) 次比较，即 \(O(n\log^2 n)\)。\(n=8\) 时是 6 步、24 次；\(n=1{,}024\) 时是 55 步、28,160 次。比快排的期望 \(O(n\log n)\) 多一个 \(\log n\) 因子，但在 GPU 上这不是重点：每一步的 \(n/2\) 次比较互相独立，可以由 \(n/2\) 个线程同时完成，步与步之间只需要一次同步。

写成 CUDA 代码时，每个线程负责一个位置 \(t\)，它的比较伙伴是 \(t \oplus j\)（\(\oplus\) 是按位异或），方向由 \(t\) 所在的长度为 \(k\) 的段决定：

for (int k = 2; k <= N; k <<= 1) {      // length of runs
  for (int j = k >> 1; j > 0; j >>= 1) {  // partner distance
    int p = t ^ j;
    if (p > t) {
      bool up = (t & k) == 0;           // run direction
      float a = s[t], b = s[p];
      if ((a > b) == up) { s[t] = b; s[p] = a; }
    }
    __syncthreads();
  }
}

这段代码有三点值得注意。第一，两层循环的次数只取决于 \(N\)，与数据无关，所有线程走的是同一条控制流；唯一的分支 p > t 只是让每对中编号小的那个线程干活。第二，每一步之后的 __syncthreads() 是必须的：下一步的伙伴可能在另一个 warp 里。当 \(j<32\) 时伙伴就在同一个 warp 内，可以改用 __shfl_xor_sync 在寄存器里交换，省掉共享内存往返和 block 级同步，这正是第 11 篇讲的蝶形交换。第三，这个写法让一半线程在每一步闲着；更省的写法是每个线程负责一对，用 \(n/2\) 个线程排 \(n\) 个数。

Bitonic 网络的另一个用途是合并：两个已经排好序的段，把其中一个反转后拼起来就是 bitonic 序列，只需最后一个阶段（\(\log n\) 步）就能合并。下文 Top-K 的 warp 级合并也可以用这个办法实现。

什么时候用 bitonic？数据能放进共享内存（每个 block 最多 227 KB，A100 是 163 KB [4]）或寄存器、而且需要所有线程步调一致时。典型场景是 block 内的局部排序、大排序算法的“小段排序”阶段、以及 Top-K 结果的最终整理。数组一大，\(\log^2 n\) 的步数和每步一次全局同步就会让它输给基数排序。

一轮基数排序 = 直方图 → 扫描 → 稳定写出

LSD 基数排序每一轮只看 key 的 \(d\) 位，把数组按这 \(d\) 位组成的数字稳定地分到 \(r=2^d\) 个桶里。并行实现时，数组被切成很多块，每个 block 处理一块，一轮分三步：

  1. 直方图：每个 block 统计自己那块里每个数字出现几次，得到一张 \(r \times B\) 的表（\(B\) 是 block 数）。
  2. 扫描：按“数字优先、block 其次”的顺序对这张表做 exclusive scan，得到“block \(b\) 中数字为 \(q\) 的第一个 key 应该写到输出的哪个位置”。数字优先保证所有数字为 0 的 key 排在数字为 1 的前面；block 其次保证同一数字内，前面 block 的 key 排在后面 block 的前面，这是稳定性在 block 之间的来源。
  3. 稳定写出：每个 key 的输出位置 = 它所在（数字，block）的起点 + 它在本 block 内同数字 key 中的名次。

图 2 用 8 个 8 位 key、2 个 block、每轮 4 位演示一轮。以 key 0x2A 为例：它在 block 0，低 4 位是 A；block 0 中数字 A 的起点是 4，0x2A 是 block 0 里第二个数字为 A 的 key（名次 1），所以写到位置 5。第一轮结束后数组按低 4 位有序；第二轮再按高 4 位做同样的事，由于每轮都稳定，结果按完整的 8 位有序：05 0A 17 1C 25 2A 37 3A（本例由 plots/ref.py 验证）。

第 1 步是带原子操作的直方图：block 先在共享内存里累加私有直方图，再一次性写出（第 8 篇讲过这种私有化）。第 2 步是第 12 篇的扫描。难点在第 3 步：block 内的名次必须稳定，即编号小的线程拿到小的名次，不能用 atomicAdd 抢位置，因为原子操作的执行顺序不确定 [2, §2]。下面的写法用第 11 篇的 warp 投票求名次：对每个可能的数字 \(q\)，__ballot_sync 得到本 warp 中数字为 \(q\) 的 lane 掩码，名次就是掩码里比自己编号小的 lane 数，再加上前面各 warp 中同数字的个数：

// Stable within the block: rank = keys with the same digit in
// lower lanes of my warp + in all earlier warps of my block.
__global__ void scatter(const unsigned* in, unsigned* out,
                        int n, int shift, const unsigned* off) {
  __shared__ unsigned wcnt[TPB / 32][R];
  int t = threadIdx.x, lane = t & 31, w = t >> 5;
  int i = blockIdx.x * TPB + t;
  bool valid = i < n;
  unsigned key = valid ? in[i] : 0u;
  unsigned d = (key >> shift) & (R - 1);
  unsigned below = (1u << lane) - 1u;  // lanes lower than me
  unsigned rank = 0;
  for (unsigned q = 0; q < R; ++q) {
    unsigned m = __ballot_sync(FULL, valid && d == q);
    if (d == q) rank = __popc(m & below);
    if (lane == 0) wcnt[w][q] = __popc(m);
  }
  __syncthreads();
  for (int v = 0; v < w; ++v) rank += wcnt[v][d];
  if (valid) out[off[d * gridDim.x + blockIdx.x] + rank] = key;

这里每个线程只处理一个 key，循环 \(r=16\) 次投票，是为了把逻辑写清楚。实际的库会让每个线程处理多个 key、用更快的 warp 内匹配方法，并把 \(d\) 取得更大。\(d\) 的取舍很直接：\(d\) 越大，轮数 \(w/d\) 越少，显存遍数越少；但桶数 \(2^d\) 越多，每个 block 要维护的计数器、要做的扫描就越多，片上资源和指令数指数增长。CUB 的 LSD 基数排序在历代 GPU 上把每轮的桶数从 16 逐步提高到 128（32 位 key 从 8 轮减到 5 轮），Onesweep 进一步做到了每轮 256 个桶、4 轮 [2, §1–2]。

Onesweep：把每一轮的全局访存从约 3n 降到约 2n

上面的三步写法有一个浪费：直方图那一步要把整个数组读一遍，写出那一步又要读一遍、写一遍。设 \(n\) 是 key 的个数，每一轮的全局访存约为 \(3n\) 次（读、读、写）[2, §1]。对显存带宽受限的排序来说，这多出来的一次读就是三分之一的时间。

Onesweep 的两个观察消掉了这次读 [2, §3]：

  1. 全局直方图与 key 的顺序无关。某一位上每个数字出现几次，不管数组被前面的轮次排成什么顺序都不会变。所以可以在排序开始前读一遍数组，把所有数字位（32 位 key、每轮 8 位，就是 4 个位置）的全局直方图一次算完。
  2. 每个 block 的起点可以在写出的同一遍里算出来。block \(b\) 中数字 \(q\) 的起点 = 全局中数字 \(q\) 的起点 + 前面所有 block 中数字 \(q\) 的个数。后者是一个沿 block 顺序的前缀和，可以用单遍扫描的 decoupled look-back 在线传递：每个 block 先发布自己 256 个数字的计数，再向前查看前驱 block 已发布的值，拿到前缀后立刻写出 [5]。第 12 篇讲的单遍扫描就是这个机制，这里只是同时传递 256 个前缀和。

于是整个排序变成：一遍直方图，加 \(p\) 轮“读一次、写一次”的分桶，总访存约 \((2p+1)n\)；而每轮先算直方图的“两遍式”需要约 \(3pn\)。32 位 key、每轮 8 位时 \(p=4\)，两者之比是 \(12/9\approx1.33\) [2, §3]。表 1 把几种做法放在一起。

论文报告的结果是：在 A100 上排 2.56 亿个随机 32 位 key，速度达到每秒 294 亿个 key，比 CUB 之前的实现快 1.4–1.6 倍，代码已经并入 CUB [2, Abstract, §1]。这是论文作者的实测数据，本系列没有复现。实际写代码时，大数组排序应该直接调用 CUB 的 cub::DeviceRadixSort；理解它内部的三步和 Onesweep 的改进，是为了在需要把排序融合进别的 kernel、或者只需要部分排序时知道该怎么改。

key 的设计：浮点数怎么排、3DGS 怎么用一个 64 位 key 同时排两个字段

把浮点数变成保序的无符号整数

基数排序只认无符号整数。IEEE 754 浮点数的位模式对非负数恰好是保序的：正数越大，作为无符号整数也越大，因为指数位在尾数位之上。负数有两个问题：符号位为 1，作为无符号整数比所有正数都大；而且负数越小（绝对值越大），位模式反而越大。修正的办法是两条规则：非负数只翻转符号位，把它们整体抬到上半区；负数翻转所有位，既把它们放到下半区，又把内部顺序倒过来：

// Negative floats: flip all bits (reverses their order and puts
// them below positives). Non-negative: flip the sign bit only.
// -0.0 sorts just below +0.0; NaNs land beyond +-inf.
__device__ __forceinline__ unsigned float_to_key(float f) {
  unsigned u = __float_as_uint(f);
  unsigned mask = (u >> 31) ? 0xffffffffu : 0x80000000u;
  return u ^ mask;
}

__device__ __forceinline__ float key_to_float(unsigned k) {
  unsigned mask = (k >> 31) ? 0x80000000u : 0xffffffffu;
  return __uint_as_float(k ^ mask);
}

边界情况要心里有数：\(-0.0\) 和 \(+0.0\) 变换后是相邻的两个不同值（\(-0.0\) 在前）；NaN 根据符号位会落在 \(+\infty\) 之上或 \(-\infty\) 之下。如果业务上要求 \(\pm0\) 相等或 NaN 有固定位置，需要在变换前先规范化。降序排序不用另写：把变换后的 key 按位取反即可。CUB 的文档写明它在排序前做的正是这两条变换（正浮点数翻转符号位、负浮点数翻转全部位），降序时再整体取反；不同的是 CUB 把 \(\pm0\) 当作相等的 key，NaN 则按变换后的位模式排 [6]。

key-value 排序与 3DGS 的 64 位 key

实际排序很少只排 key：通常要带着一个 value（原始下标、指针或整条记录）一起移动，叫 key-value 排序。基数排序处理 value 的方式很简单：分桶时 key 去哪，value 就去哪，所以每轮的访存量按 key 和 value 的总字节数算。为了少搬数据，value 一般只放 4 字节下标，排完后再按下标去取完整记录。

如果要按两个字段排序（先按 A，A 相同再按 B），可以把它们拼成一个更宽的 key：A 放高位，B 放低位。3DGS 的光栅化就是这样做的。它把屏幕切成 16×16 像素的 tile，把每个高斯复制到它覆盖的每个 tile 上，再给每个副本一个 64 位 key：低 32 位是投影后的深度，高位是 tile 编号 [1, §6, Appendix C]。一次基数排序之后，同一个 tile 的副本连续排列，并且在 tile 内按从近到远的顺序排好，正好是逐像素 α 混合需要的顺序；再扫描一遍找出每个 tile 的第一个和最后一个副本，就得到每个 tile 要处理的列表 [1, §6]。我们的写法如下：

// High 32 bits: tile id; low 32 bits: depth. Depth is positive
// after near-plane culling, so its raw bits already sort like
// its value. One sort orders by tile, then front to back.
__device__ __forceinline__ unsigned long long
tile_depth_key(unsigned tile, float depth) {
  unsigned long long hi = (unsigned long long)tile << 32;
  return hi | __float_as_uint(depth);
}

深度直接用了浮点位模式而没有做上面的变换，因为经过近平面裁剪后深度都是正数，正浮点数的位模式本身就保序。官方实现里还有一个细节：调用 CUB 排序时只排 key 的低 \(32 + b\) 位，其中 \(b\) 由 tile 总数的最高有效位决定 [7]。tile 数不大时，高 32 位里只有低十几位有用，少排这些位就能少做几轮。以 1920×1080 的画面为例，tile 网格是 120×68，共 8,160 个 tile，用 13 位就能表示；只排低 45 位，每轮 8 位时要 6 轮而不是 8 轮（按 \(\lceil 45/8\rceil\) 计算）。3DGS 光栅化的完整流程放到第 41 篇。

分段排序

另一种常见需求是对很多互相独立的小段各自排序，比如每个请求的候选列表、每一行数据，叫分段排序（segmented sort）。有三种做法：段都很短时，一个 block（甚至一个 warp）负责一段，在共享内存里用 bitonic 网络排；段长差异大时，可以把段号拼到 key 的高位，变成一次全局排序，这正是 3DGS 的 tile 号所起的作用；CUB 也直接提供了 cub::DeviceSegmentedRadixSort，用起点、终点数组描述各段 [8]。

Top-K 往往不需要排序：按 k 的大小选三种做法

很多场景只需要最大的 \(k\) 个元素，不关心其余元素的顺序。这时完整排序是浪费：对一行 \(V\) 个值，只读一遍（\(4V\) 字节）往往就够了。根据 \(k\) 的大小，有三种做法。

\(k=1\)：一次归约

只要最大值和它的下标（argmax），就是第 10 篇的归约：每个线程维护（值，下标）对，warp 内用 shuffle 两两比较，block 内再合并一次。比较时规定“值相等取下标小的”，结果就是确定的。

小 \(k\)：寄存器里的候选列表 + warp 合并

\(k\) 在几十以内时，可以让每个线程在寄存器里维护一个长度为 \(k\) 的降序列表。线程遍历自己负责的元素，遇到比列表末尾大的就插进去。插入写成“每个位置独立决定：取前一个、取新值、还是保持”的形式，这样数组下标在循环展开后都是编译期常量，列表才能留在寄存器里（第 7 篇讲过动态下标会让数组退到局部内存）：

// Insert x into a descending list. After unrolling every index
// is a compile-time constant: v[] and id[] stay in registers.
template <int K>
__device__ __forceinline__ void insert(float (&v)[K],
                                       int (&id)[K], float x,
                                       int i) {
#pragma unroll
  for (int q = K - 1; q > 0; --q) {
    bool shift = v[q - 1] < x, here = !shift && v[q] < x;
    v[q] = shift ? v[q - 1] : (here ? x : v[q]);
    id[q] = shift ? id[q - 1] : (here ? i : id[q]);
  }
  if (v[0] < x) { v[0] = x; id[0] = i; }
}

完整代码：code/pp13-sort-topk/warp_topk.cu 第 15–28 行（未在 GPU 上运行）

各线程扫完后，32 个列表要合并成一个。做法是做 \(k\) 轮 warp 级的 argmax：每个 lane 拿出自己列表的头部，用 shuffle 找出最大的那个，赢家把它写出并弹出头部。值相等时让 lane 号小的赢，结果就与执行时序无关：

template <int L, int ROUNDS>
__device__ void warp_merge(float (&v)[L], int (&id)[L],
                           float* out_v, int* out_i) {
  int lane = threadIdx.x & 31;
  for (int r = 0; r < ROUNDS; ++r) {
    float best = v[0];
    int who = lane;
    for (int o = 16; o > 0; o >>= 1) {
      float b2 = __shfl_xor_sync(FULL, best, o);
      int w2 = __shfl_xor_sync(FULL, who, o);
      if (b2 > best || (b2 == best && w2 < who)) {
        best = b2; who = w2;
      }
    }
    if (lane == who) {
      out_v[r] = v[0]; out_i[r] = id[0];
      pop(v, id);
    }
  }
  __syncwarp();  // make the lanes' writes visible to each other

完整代码：code/pp13-sort-topk/warp_topk.cu 第 44–63 行（未在 GPU 上运行）

一行只读一遍，合并阶段只有 \(k\) 轮、每轮 5 步蝶形比较（每步两次 shuffle），所以这种做法对小 \(k\) 很快。它的代价在寄存器：每个线程要 \(2k\) 个寄存器存值和下标，\(k=32\) 时就是 64 个，会压低 occupancy。\(k\) 再大，就该换下面的方法。代码里用一个 warp 处理一行是为了简单；一行十几万个元素时，实际实现会让一个 block 的多个 warp 先各自得到 top-k，再在共享内存里合并（例如用上文提到的 bitonic 合并）。

大 \(k\)：基数选择

\(k\) 到几百、几千时，可以借用基数排序的思路，但只找“第 \(k\) 大的值”，不排序。这叫基数选择（radix select）。把每个值变成保序的 32 位 key 后，从最高字节开始：统计还在候选范围内的 key 在当前字节上的直方图，从最大的桶往下累加，找到第 \(k\) 大的 key 落在哪个桶；把这个字节固定下来，\(k\) 减去更大的桶里的个数，进入下一个字节。4 轮之后，32 位全部确定，就得到第 \(k\) 大的值本身：

for (int shift = 24; shift >= 0; shift -= 8) {
  for (int b = threadIdx.x; b < 256; b += blockDim.x)
    hist[b] = 0;
  __syncthreads();
  for (int i = threadIdx.x; i < V; i += blockDim.x) {
    unsigned key = float_to_key(row[i]);
    if ((key & pmask) == prefix)      // still a candidate
      atomicAdd(&hist[(key >> shift) & 255u], 1u);
  }
  __syncthreads();
  if (threadIdx.x == 0) {   // walk buckets from the top down
    unsigned acc = 0;
    int d = 255;
    for (; d > 0 && acc + hist[d] < kk; --d) acc += hist[d];
    kk -= acc;              // rank inside the chosen bucket
    prefix |= (unsigned)d << shift;
    pmask |= 255u << shift;
  }
  __syncthreads();
}

每一轮只需要一个 256 个计数器的共享内存直方图，和一次从高到低的累加。拿到第 \(k\) 大的值 \(t\) 之后，再扫一遍，把所有大于 \(t\) 的元素和足够数量的等于 \(t\) 的元素收集出来，就是 top-k 集合（如果需要有序，再对这 \(k\) 个元素做一次小排序）。

图 3 显示了候选范围在每一轮之后剩多少。一个反直觉的现象是：第一轮往往缩得很慢。最高字节由符号位和指数的高 7 位组成，同一数量级的值都落在同一个桶里。对一行服从正态分布的合成 logit，第 50 大和第 1,000 大的值所在的桶，第一轮后都还有两万多个候选；第二轮看到了指数的最低位和尾数的高位，候选立刻降到几十个以内。

这段代码每一轮都把整行重新读一遍，4 轮共读 4 遍。更省的写法是第一轮之后把候选压缩到一块小缓冲区里（第 12 篇的流压缩），后面几轮只读候选。即使不压缩，基数选择的访存量也是固定的几遍，与 \(k\) 无关，这是它适合大 \(k\) 的原因。

MoE 路由：每个 token 选 k 个专家，再数每个专家收到几个 token

MoE 的路由器对每个 token 输出 \(E\) 个专家的打分（例如 \(E=256\)），选出最大的 \(k\) 个（例如 \(k=8\)）。这是“很多行、每行很短”的 top-k，正适合一个 warp 处理一个 token：每个 lane 只拿 \(E/32\) 个分数，列表长度也只需要 \(E/32\)，然后做 \(k\) 轮 warp 合并。选完之后，路由还要统计每个专家分到多少个 token，后续的 token 重排和分组 GEMM 都要用这个计数：

template <int E, int K>
__global__ void moe_route(const float* logits, float* top_v,
                          int* top_e, unsigned* count) {
  constexpr int PER = E / 32;
  float v[PER];
  int id[PER];
#pragma unroll
  for (int q = 0; q < PER; ++q) { v[q] = -FLT_MAX; id[q] = -1; }
  const float* row = logits + (size_t)blockIdx.x * E;
#pragma unroll
  for (int q = 0; q < PER; ++q) {
    int e = q * 32 + threadIdx.x;
    insert(v, id, row[e], e);
  }
  float* tv = top_v + blockIdx.x * K;
  int* te = top_e + blockIdx.x * K;
  warp_merge<PER, K>(v, id, tv, te);
  if (threadIdx.x < K) atomicAdd(&count[te[threadIdx.x]], 1u);
}

这里的计数用了全局原子加，计数结果是确定的（加法满足交换律）。但如果下一步要按专家把 token 重新排列，每个 token 在专家内的位置就不能靠原子操作抢，否则顺序不确定；正确的做法是对计数做一次扫描得到每个专家的起点，再像基数排序的写出一步那样稳定地分配位置。专家打分要不要先做 softmax 或 sigmoid、选出的 \(k\) 个权重要不要重新归一化，取决于具体模型，这里不展开；token 重排见第 18 篇。

LLM 采样：把截断变成阈值，用拒绝采样代替全排序

大语言模型生成每个 token 时，要从词表上的概率分布 \(p_i = \mathrm{softmax}(z)_i\) 中采样（\(z_i\) 是第 \(i\) 个 token 的 logit，\(V\) 是词表大小）。为了避免采到概率极低的 token，常用三种截断规则：

  • top-k：只保留概率最大的 \(k\) 个 token。
  • top-p（nucleus 采样）：按概率从大到小累加，保留累计概率刚达到 \(p\) 的最小集合 [9]。
  • min-p：保留概率不小于 \(p_{\text{base}}\cdot p_{\max}\) 的 token，其中 \(p_{\max}\) 是最大概率，常用 \(p_{\text{base}}=0.05\)–\(0.1\) [10]。

截断之后，在保留的集合上按原概率重新归一化再采样。图 4 用两个合成分布比较了三种规则保留的 token 数：top-k 不论分布形状都保留 50 个；top-p 在平坦分布上保留了三万多个，在尖锐分布上只保留 6 个；min-p 只看最大概率的倍数，两种情况下分别只保留 10 个和 3 个。

朴素做法：softmax、全排序、前缀和

最直接的实现照着定义写：对每行做 softmax，按概率降序做 key-value 全排序，对排好序的概率做前缀和，找到截断位置，把截断外的概率置零，再归一化、采样。FlashInfer 的博客引用的 PyTorch 实现（取自 vLLM 的 sampler）就是这样，并指出这种做法在大词表下被排序的开销拖慢 [11]。我们可以按Onesweep 的公式估算它的显存读写量：一行 \(V\) 个 FP32 logit，key 和下标各 4 字节，按 Onesweep 式的 4 轮基数排序，一遍直方图读 \(4V\) 字节，每轮读写 key 和下标共 \(16V\) 字节，4 轮 \(64V\)，加上前缀和再读一遍 \(4V\)，共 \(72V\) 字节；两遍式排序则是 \(84V\)。这还没算 softmax 和后续掩码、归一化的几遍。

图 5 把几种做法的读写量换算成了时间下限。以 \(V=131{,}072\)、64 行为例，完整排序的下限约 180 μs，单遍 top-k 约 10 μs。这个数值只是带宽下限，但它说明了方向：采样算子的优化目标是减少扫描整行的遍数，而排序恰恰是遍数最多的那一种。

top-k 和 min-p 都是阈值

先看两种不需要累计概率的规则。softmax 不改变顺序，所以 top-k 保留的就是 logit 最大的 \(k\) 个，可以直接在 logit 上用上一节的寄存器 top-k 或基数选择，找出第 \(k\) 大的 logit \(z_{(k)}\) 作为阈值，根本不必先算 softmax。min-p 也是一个阈值，推导只需一行：

\[ \begin{aligned} p_i \ge p_{\text{base}}\,p_{\max} &\iff e^{z_i - z_{\max}} \ge p_{\text{base}} \\ &\iff z_i \ge z_{\max} + \ln p_{\text{base}} \end{aligned} \](1)

其中 \(z_{\max}\) 是最大的 logit。式 (1) 的第一步把两边同除以 \(p_{\max}\)，softmax 的分母随之约掉了。所以 min-p 只需要一次求最大值的归约，就能得到 logit 阈值。有了阈值，采样时只需在 \(z_i \ge\) 阈值的 token 上，按权重 \(e^{z_i - z_{\max}}\) 做一次逆变换采样（对权重做前缀和，找到累计值第一次超过 \(u\cdot\) 总和的位置，\(u\) 是 \([0,1)\) 上的均匀随机数），而这一步本身就是第 12 篇的扫描。

top-p：用拒绝采样绕开排序

top-p 的截断位置取决于“比某个 token 大的所有 token 的概率之和”，看起来非排序不可。FlashInfer 的做法是拒绝采样（rejection sampling）[11]：先在一个包含 nucleus 的候选集合上按原概率采一个 token，检查它是否在 nucleus 里，在就接受，不在就抬高门槛重新采。按博客的描述，可以把思路写成下面的伪代码（这是我们整理的伪代码，不是 FlashInfer 的源码）：

# 伪代码：top-p 拒绝采样的思路
lo = -inf          # 门槛：只考虑 logit > lo 的 token
loop:
    在 {z_j > lo} 上按权重 exp(z_j - z_max) 采样，得到 t
    mass = 所有 z_j > z_t 的 token 的概率之和
    if mass < p:   # 比 t 大的还不够 p，t 在 nucleus 里
        return t
    lo = z_t       # t 及更小的都不在 nucleus 里，抬高门槛

为什么结果是精确的？nucleus 是“概率最大的若干 token”组成的集合，所以门槛 \(lo\) 之上的候选集合始终包含整个 nucleus：被排除的只是比某个已确认不在 nucleus 里的 token 更小的那些。在一个包含目标集合的大集合上按原权重采样，再拒绝目标集合以外的样本，被接受的样本恰好服从目标集合上重新归一化的分布，这是拒绝采样的基本性质。博客作者以 top-k 为例证明了输出分布是精确的，并说其他截断规则可以类似地证明 [11]。

代价是轮数不确定。博客说，单一门槛的版本没有轮数的理论上界，但实际轮数通常很少；后来的双门槛版本每次失败至少把候选区间缩小一半，最坏情况是 \(O(\log(1/\varepsilon))\) 轮，\(\varepsilon\) 是最小的可表示浮点数 [11]。每一轮需要扫描一到两遍候选（一遍采样、一遍算 mass），但全程可以融合在一个 kernel 里，不用排序，也省掉了多次 kernel 启动。博客报告，在 vLLM 的单卡 H100 配置下，这些 kernel 让采样总时间降低了一半以上 [11]，这是作者的实测结果。

“softmax + top-p 融合”也就水到渠成：softmax 需要的最大值和分母，可以用第 17 篇的 online softmax 在一遍里算出；之后的拒绝采样直接用 \(e^{z_j - z_{\max}}\) 作权重、用分母把 mass 换成概率，整个过程不需要把归一化后的概率写回显存。

在 Hopper 与 Blackwell 上：没有为排序专门新增的硬件，变化来自带宽和片上容量

坦白说，就我们核对过的资料，Hopper 和 Blackwell 都没有为排序或 Top-K 新增专门的指令或单元。排序类 kernel 受显存带宽和延迟限制，新硬件带来的变化主要是间接的：

  • 显存带宽：从 A100 80GB 的 2.039 TB/s，到 H100 SXM 的 3.35 TB/s，再到 HGX B200 每卡的 8 TB/s（出处见第 1 篇的参数表）。基数排序和基数选择都是带宽受限的，下限按带宽等比例下降。
  • 共享内存：每个 block 可用的共享内存从 CC 8.0 的 163 KB 增加到 CC 9.0/10.0 的 227 KB [4]。片上能排的 bitonic 段更长，基数排序每个 block 能处理更大的 tile、维护更多的桶计数。
  • cluster 与分布式共享内存（Hopper 起）：一个 cluster 里的 block 可以直接读写彼此的共享内存（第 22 篇）。我们推测它可以用来在相邻 block 之间合并直方图或 top-k 候选，少走一次全局内存，但没有找到公开的排序实现来证实收益。
  • Blackwell Ultra 的指数运算吞吐：Blackwell Ultra 把 SFU 的指数运算吞吐提高到 Blackwell 的约两倍（见第 1 篇的 Blackwell 特性表 [12]）。融合了 softmax 的采样 kernel 要对每个 logit 求指数，可能从中受益；这一点同样没有公开的实测数据。

换句话说，本篇的算法在三代 GPU 上都适用，变化的是参数：每轮位数 \(d\)、每个 block 处理的 tile 大小、寄存器 top-k 的 \(k\) 上限，都需要按各代的片上资源重新调。

面试怎么问

GPU 上为什么常用基数排序而不是快排？

  • 快排的划分依赖数据、递归深度不定，难以均匀并行；比较后往左还是往右是数据相关分支，会造成 warp 发散。
  • 大数组排序受显存带宽限制，衡量标准是显存遍数。基数排序的轮数 \(w/d\) 固定，每轮一读一写（Onesweep）；基于比较的排序要 \(O(\log n)\) 遍。
  • 每轮只用直方图、扫描、scatter 三个规整原语。
  • 追问：基数排序的缺点？（key 必须能保序映射成整数；位宽大时轮数多；桶数 \(2^d\) 受片上资源限制；小数组时固定开销显得大，不如 bitonic。）

LSD 基数排序为什么要求每一轮稳定？怎么在 GPU 上保证？

  • 低位排好的顺序要在高位相同时保留下来，否则低位那几轮白排了。
  • block 之间：扫描按“数字优先、block 其次”的顺序，前面 block 的 key 一定排在前面。block 内：名次按线程编号算，用 warp 投票 + popc，不能用原子操作抢位置。

Top-K 在 \(k=1\)、\(k=50\)、\(k=1000\) 时分别怎么做？

  • \(k=1\)：argmax 归约，warp shuffle 加 block 合并，相等时取下标小的。
  • \(k=50\)：每个线程在寄存器里维护有序列表（下标要是编译期常量），扫完一遍后 warp/block 合并；寄存器压力随 \(k\) 增长。
  • \(k=1000\)：基数选择，逐字节做直方图找到第 \(k\) 大的值，再一遍收集；访存遍数固定，与 \(k\) 无关。
  • 追问：有很多相等的值怎么办？（基数选择找到的是阈值 \(t\)，收集时先取所有大于 \(t\) 的，再从等于 \(t\) 的里按下标顺序补足。）

浮点数怎么做基数排序？

  • 非负数翻转符号位，负数翻转所有位，得到保序的无符号整数；排完再逆变换。
  • 注意 \(\pm0\) 变成两个不同值、NaN 的位置由符号位决定；降序就把变换结果再取反。

3DGS 为什么只排一次就能同时按 tile 和深度排好？

  • key 是 64 位：高位 tile 号、低 32 位深度。排序按整个 key 比较，先比 tile 号，相同再比深度。
  • 深度为正，浮点位模式直接保序，不用变换；只需排到 tile 号的最高有效位，能少几轮。

softmax + top-p 采样怎么融合，怎么避免全排序？

  • 一遍 online softmax 拿到 \(z_{\max}\) 和分母，不写回概率。
  • top-k、min-p 化成 logit 阈值；top-p 用拒绝采样：在门槛以上采样，检查比它大的概率和是否小于 \(p\)，否则把门槛抬到它，重采。结果精确，轮数通常很少。
  • 追问：为什么拒绝采样的结果分布是对的？（候选集合始终包含 nucleus，在超集上按原权重采样再拒绝集合外的样本，接受的样本服从 nucleus 上的重归一化分布。）

  • 没有实测。本文的 CUDA 代码只通过了编译器前端的语法和类型检查，没有在 GPU 上运行。Bitonic、一轮基数排序、基数选择和 warp top-k 的逻辑用 plots/ref.py 等 Python 参考实现核对过，但 CUDA 版本本身没有执行过。
  • 性能数字都不是我们测的。Onesweep 在 A100 上的速度和 FlashInfer 在 H100 上的收益都是论文或博客作者的实测，按原文引用；图 5 是按访存模型算出的带宽下限，忽略了 softmax、启动开销、同步和缓存命中，一个 decode 步的真实耗时通常远高于它。
  • 代码是教学写法。radix pass 每线程只处理一个 key，并在主机上做扫描；基数选择每轮重读整行；warp top-k 一个 warp 处理一行。生产实现（CUB、FlashInfer、各推理框架）都做了多元素每线程、片上压缩、多 warp 合并等优化，本文没有逐一展开。
  • 拒绝采样的伪代码是我们按博客描述整理的，没有对照 FlashInfer 源码；双门槛版本、多种截断规则组合（top-k 与 top-p 同时使用）的细节没有讲。
  • 3DGS 的细节只讲了 key 的设计；预处理、tile 范围识别和光栅化放在第 41 篇。
  • 没有覆盖的排序话题：MSD 基数排序与混合排序、归并排序与 merge path、多 GPU 排序、超出显存的外部排序。

小结

GPU 排序的核心是基数排序：轮数由 key 的位宽决定，每轮是直方图、扫描、稳定写出三个规整的并行步骤；Onesweep 用前置直方图和单遍扫描把每轮压到一读一写。数组小到能放进共享内存时，比较顺序固定、没有分支的 bitonic 网络更合适。key 的设计是排序的一半功夫：浮点数要保序变换，多个字段可以拼进一个宽 key，3DGS 正是靠一个 64 位 key 一次排好 tile 和深度。

很多时候其实不需要完整排序。\(k=1\) 是归约，小 \(k\) 在寄存器里维护，大 \(k\) 用基数选择；LLM 采样中的 top-k 和 min-p 都能化成 logit 阈值，top-p 可以用拒绝采样精确地绕开排序。判断该用哪种方法的标准始终是同一个：一共要把数据从显存里读写几遍。下一篇开始讲方法论：怎样测量这些 kernel 的真实时间，并用 Nsight 找出瓶颈。
