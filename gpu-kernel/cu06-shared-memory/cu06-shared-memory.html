TL;DR

  • 共享内存（shared memory）是 block 内线程复用数据、交换数据、改变访问方向的地方。它很快，但只有在一个 warp 的 32 个请求分散到 32 个不同的 bank 上时才快。
  • 共享内存按 4 字节一个字轮流分到 32 个 bank 上。同一 warp 里访问同一 bank 的不同字要排队，冲突路数等于“最拥挤的 bank 上有几个不同的字”。
  • 等步长访问的冲突路数是步长与 bank 数的最大公约数：奇数步长没有冲突，步长为 bank 数的倍数时最差，按列读一个方形 tile 正是这种情况。
  • 消除冲突有两招：padding（每行多放一个元素）和 XOR swizzle（列号异或行号）。后者不浪费空间，TMA 的 swizzle 模式和 WGMMA、tcgen05 要求的共享内存布局都是它的硬件版本。
  • __syncthreads() 必须被 block 里每个线程都执行到；把它放进只有部分线程会进入的分支，结果是挂起或算错。

主线定位：① 字节账 · ③ 算力账

shared memory tiling 让数据在片上复用（①），swizzle 消除 bank conflict，让操作数按时到位（③）。全系列的分析主线是“一个下界 + 五笔账”，见主线篇。

矩阵转置是理解共享内存最好的例子。转置要把第 r 行第 c 列的元素搬到第 c 行第 r 列：如果读是按行连续的，写就必然按列跳着走，反之亦然。第 5 篇讲过，跳着访问显存会让一次请求拆成很多个 32 字节扇区，带宽掉得很厉害。解决办法是在片上倒一手：先把一个 32×32 的 tile 按行连续地读进共享内存，再按行连续地从共享内存另一个方向读出来写回显存。显存两边都连续了，难点转移到了共享内存里。

Mark Harris 在 2013 年的一篇 NVIDIA 博客里测过这条路上的每一步 [1]。在 Tesla M2050 上，直接转置只有 18.8 GB/s；改用共享内存中转后是 51.3 GB/s；再在共享内存的 tile 每行多加一个元素，变成 99.5 GB/s，接近同一块卡上纯拷贝的 105.2 GB/s。最后这一步只改了一行声明，却让带宽翻了一倍。这篇要回答的就是：那一行声明为什么这么重要，以及怎样一眼看出一段共享内存代码会不会出这种问题。

Harris 的数据来自 Fermi（M2050）与 Kepler（K20c）两代 GPU，绝对数值早已过时；本文只用它说明各个版本之间的相对关系。这些 kernel 在新 GPU 上的表现本文没有实测。

我们先看共享内存的用途和分配方式，再讲清 bank 的规则和判断冲突的方法，接着用转置把 padding 和 swizzle 走一遍，最后看 Hopper 和 Blackwell 怎样把 swizzle 做进了硬件。

共享内存是程序员自己管理的片上缓存

第 1 篇介绍过，每个 SM 有一块 SRAM，按配置划分成 L1 缓存和共享内存。L1 由硬件自动决定缓存什么；共享内存的内容则完全由程序决定，对同一个 block 的所有线程可见，生命周期和 block 一样长。它通常有三种用途：

  1. 数据复用（tiling）：一块数据从显存读一次，在片上被很多线程用很多次。GEMM 是典型：A 的一个 tile 要和 B 的很多列相乘（第 24 篇）。
  2. 线程间通信：一个线程算出的值要给别的线程用，例如归约和前缀和（第 10、12 篇）。
  3. 改变访问方向：像转置一样，显存那边按行连续访问，片上按列取用。

它为什么值得这么麻烦？看一下带宽。共享内存有 32 个 bank，每个 bank 每个时钟周期能交出 32 位 [2]，也就是说一个 SM 的共享内存每周期最多交出 \(32\times4=128\) 字节。以 A100 为例，108 个 SM、1410 MHz 加速时钟，全部 SM 的共享内存合起来每秒最多交出

\[ 108 \times 128\ \text{B} \times 1.41\times10^{9}\ \text{s}^{-1} \approx 19.5\ \text{TB/s} \](1)

约为 A100 80GB 显存带宽（2.039 TB/s）的 9.6 倍。这是假设每个 bank 每周期都满负荷时的上限，由公开参数算出，不是实测。但它给出了量级：只要一个数据在片上被复用几次，就能省下大量显存流量。而“每周期 128 字节”这个上限有一个前提：这 128 字节必须均匀地分在 32 个 bank 上。下面几节都在讲这个前提。

静态、动态与超过 48 KB 的共享内存

共享内存有两种声明方式。静态声明在 kernel 里写 __shared__ float buf[256];，大小在编译时确定。动态声明写 extern __shared__ float buf[];，不写大小，大小在启动时由 <<<grid, block, smem>>> 的第三个参数给出：

// (2) dynamic: size given at launch (3rd <<<>>> argument)
__global__ void dynamic_smem(const float* in, float* out,
                             int n) {
  extern __shared__ float dbuf[];        // size unknown here
  int t = threadIdx.x;
  for (int i = t; i < n; i += blockDim.x)
    dbuf[i] = in[blockIdx.x * n + i];
  __syncthreads();
  for (int i = t; i < n; i += blockDim.x)
    out[blockIdx.x * n + i] = dbuf[n - 1 - i];
}

完整代码：code/cu06-shared-memory/smem_alloc.cu 第 15–25 行（未在 GPU 上运行）

一个 kernel 里所有 extern __shared__ 数组都从同一个地址开始，所以需要多个动态数组时，通常声明一个字节数组，再按偏移量切出各段（完整代码中的 two_arrays）。切的时候要注意对齐：把 float 段放在 char 段后面时，偏移量要是 4 的倍数。

两种声明的一个关键区别是容量上限。编程指南规定：每个 block 使用超过 48 KB 共享内存的 kernel 是架构相关的，必须用动态共享内存，并且要用 cudaFuncSetAttribute 显式开启 [3]：

// more than 48 KB per block: dynamic smem + explicit opt-in
cudaFuncSetAttribute(dynamic_smem,
    cudaFuncAttributeMaxDynamicSharedMemorySize, (int)bytes);
// optional hint: prefer the largest shared-memory carveout
cudaFuncSetAttribute(dynamic_smem,
    cudaFuncAttributePreferredSharedMemoryCarveout,
    cudaSharedmemCarveoutMaxShared);
dynamic_smem<<<1, 256, bytes>>>(in, out, n);

完整代码：code/cu06-shared-memory/smem_alloc.cu 第 45–52 行（未在 GPU 上运行）

第二个属性叫 carveout，表示希望把 SM 的统一数据缓存中多大比例划给共享内存，可以给百分比，也可以给 cudaSharedmemCarveoutMaxShared 等命名值。它只是一个偏好：驱动会把百分比向上取整到受支持的容量，必要时也会选别的配置 [3]。CC 8.0（A100）可选的共享内存容量是 0、8、16、32、64、100、132、164 KB；CC 9.0（H100）在此之外还有 196 和 228 KB；单个 block 最多能用的比每 SM 上限少 1 KB（A100 为 163 KB，H100 为 227 KB），这 1 KB 留给系统使用 [3]。

共享内存用多了会减少一个 SM 能同时驻留的 block 数，这是第 7 篇 occupancy 的话题。本篇只关心单个 block 内部的访问效率。

分配之后，同一 block 的线程就可以通过这块内存交换数据了。但“交换”意味着有人写、有人读，读必须在写之后。这就是 __syncthreads() 的用途，我们在__syncthreads 讲它的规则；先看共享内存最核心的性能问题。

bank 冲突：一个 bank 每周期只能交出一个字

共享内存的地址按 32 位字（4 字节）编号，相邻的字依次放在相邻的 bank 里：字地址为 \(w\) 的数据在第 \(w \bmod 32\) 号 bank [2]。可以把 32 个 bank 想成 32 个并排的窗口，每个窗口每周期只服务一个“字”。一个 warp 发出一条共享内存指令时，32 个线程（下文按 warp 内的编号称为 lane 0–31）各要一个地址：

  • 如果 32 个地址落在 32 个不同的 bank，一个周期就全部完成。
  • 如果有若干个 lane 要访问同一个 bank 里的不同字，这些访问只能一个接一个地进行，这叫 bank 冲突（bank conflict）[2]。
  • 如果多个 lane 访问的是同一个 32 位字，不算冲突：读的时候这个字被广播给所有请求它的 lane；写的时候只有其中一个 lane 的值会写进去，至于是哪一个，没有定义 [3]。

图 1 画了三种最基本的情况。

怎样算冲突路数

把一个 warp 的 32 个地址换成字地址 \(w = \lfloor \text{byte}/4 \rfloor\)，按 \(w \bmod 32\) 分到 32 个 bank；在每个 bank 里数不同的 \(w\) 有几个；所有 bank 中的最大值就是冲突路数，即这条指令要被拆成几次完成。最大值为 1 就是无冲突。

用这个方法看图 1 的中间一行：bank 0 里有字 0（lane 0）和字 32（lane 16），两个不同的字，所以是 2 路冲突。再看一个反例：s[lane / 2] 让 lane 0、1 读字 0，lane 2、3 读字 1……一共只碰到 16 个字，分在 16 个不同的 bank 里，每个 bank 只有一个字，所以是无冲突，虽然每个 bank 都被两个 lane 访问。

步长决定冲突：路数等于 gcd(s, 32)

最常见的访问模式是等步长：lane \(i\) 访问 s[i * s]。它的冲突路数有一个简单的公式。lane \(i\) 的字地址是 \(i s\)，所在 bank 是 \(i s \bmod 32\)。设 \(g = \gcd(s, 32)\)，那么 \(i s \bmod 32\) 只能取 \(32/g\) 个不同的值，32 个 lane 平均分到这些 bank 上，每个 bank 有 \(g\) 个 lane，它们访问的字地址彼此不同。所以

\[ \text{路数}(s) = \gcd(s, 32) \](2)

这个公式解释了很多经验法则：奇数步长和 32 互质，没有冲突；步长 2 是 2 路；步长 32 是 32 路，等于完全串行。图 2 用一个小模拟器（plots/bank_sim.py，实现的就是上面的计数规则）把步长 1 到 32 全部算了一遍，32 位访问的结果和式 (2) 一致。

64 位和 128 位访问

每个线程一次读 float2（8 字节）或 float4（16 字节）时，一个 warp 要 256 或 512 字节，而共享内存每周期最多交出 128 字节，所以这类请求至少要 2 个或 4 个周期——这是从官方的“每 bank 每周期 32 位”直接推出的下界。真正的问题是：哪些 lane 被放在同一个周期里比较冲突？NVIDIA 现行的编程指南没有写。NVIDIA 开发者论坛上的解释是，128 位的请求会被拆成 4 个阶段（新版 Nsight Compute 称为 wavefront），冲突只在同一阶段内计算 [4]。图 2 的蓝、灰两组点就是按“相邻的 16 个 lane（64 位）或 8 个 lane（128 位）一组”的模型算的：连续访问 float2、float4 没有额外冲突，步长 2 仍是 2 倍；但由于每组只有 16 或 8 个 lane，最坏也只有 16 或 8 倍。

旧版编程指南（计算能力 2.x 一节）对 128 位访问有一条“按四分之一 warp 计算、再加 1”的规则，论坛中的回答指出它只适用于那一代硬件 [4]。看到网上引用这条规则时要注意版本。

这里有一个容易被忽略的陷阱：float4 t = s4[lane]; 是一次 128 位访问，没有冲突；而 s4[lane].x 只读每个 float4 的第一个分量，编译器通常只生成 32 位访问，相邻 lane 相隔 4 个字，于是变成 \(\gcd(4,32)=4\) 路冲突。数据在共享内存里怎么摆，和每次取多宽，要一起看。

按列访问 tile：padding 和 XOR swizzle

回到转置。把一个 32×32 的 float tile 声明成 __shared__ float tile[32][32]，元素 \((r, c)\) 的字地址是 \(32r + c\)，所在 bank 是 \(c\)：同一列的 32 个元素全在同一个 bank。一个 warp 沿第 0 列往下读（lane \(i\) 读第 \(i\) 行），就是 32 路冲突。编程指南用的正是这个例子 [2]。有两种办法把同一列的元素错开到不同的 bank。

padding：把声明改成 tile[32][33]，每行多一个不用的元素。元素 \((r, c)\) 的字地址变成 \(33r + c\)，bank 为 \((r + c) \bmod 32\)：每往下一行，bank 号加 1，第 0 列的 32 个元素正好占满 32 个 bank。代价是多用了 \(32 \times 4 = 128\) 字节，并且每行不再是 128 字节对齐的，后面讲到 TMA 和向量化访问时这一点会成为问题。

XOR swizzle：保持 tile[32][32]，但把逻辑上的第 \(c\) 列存到物理上的第 \(c \oplus r\) 列（\(\oplus\) 是按位异或）：

\[ \text{phys}(r, c) = 32r + (c \oplus r), \qquad 0 \le r, c < 32 \](3)

对固定的行 \(r\)，\(c \mapsto c \oplus r\) 是 0–31 的一个排列，所以同一行的元素仍然占满 32 个 bank，按行读写没有冲突；对固定的列 \(c\)，\(r \mapsto c \oplus r\) 也是一个排列，所以同一列的 32 个元素也分到了 32 个不同的 bank。异或的好处是它是自己的逆运算（\((c \oplus r) \oplus r = c\)），读写两边用同一个函数，而且不占额外空间。图 3 把三种布局的 bank 分布画在了一起。

转置的四个版本

现在可以把转置从头写一遍。四个版本都让一个 block 处理一个 32×32 的 tile，block 形状是 32×8，每个线程搬 4 个元素，这是 Harris 博客的配置 [1]。v0 不用共享内存，读 in 按行连续，写 out 按列跳跃。v1 用共享内存中转：

// v1: stage through smem; reading tile[x][y] is 32-way
__global__ void transpose_smem(const float* in, float* out,
                               int n) {
  __shared__ float tile[TILE][TILE];
  int x = blockIdx.x * TILE + threadIdx.x;
  int y = blockIdx.y * TILE + threadIdx.y;
  for (int j = 0; j < TILE; j += ROWS)
    tile[threadIdx.y + j][threadIdx.x] = in[(y + j) * n + x];
  __syncthreads();
  x = blockIdx.y * TILE + threadIdx.x;   // swap block idx
  y = blockIdx.x * TILE + threadIdx.y;
  for (int j = 0; j < TILE; j += ROWS)
    out[(y + j) * n + x] = tile[threadIdx.x][threadIdx.y + j];
}

完整代码：code/cu06-shared-memory/transpose.cu 第 18–31 行（未在 GPU 上运行）

一个 warp 由 threadIdx.y 相同、threadIdx.x 为 0–31 的 32 个线程组成。写 tile 时它们写同一行的 32 个相邻元素，无冲突；读 tile 时 tile[threadIdx.x][...] 让 32 个 lane 读同一列，32 路冲突。显存两边都连续了，冲突却搬进了共享内存。v2 只把声明改成 tile[TILE][TILE + 1]，其余一字不改；v3 不加 padding，改用式 (3) 的下标：

// v3: no padding; column c of row r is stored at c ^ r
__device__ __forceinline__ int swz(int r, int c) {
  return c ^ (r % TILE);
}
// ...
  for (int j = 0; j < TILE; j += ROWS) {
    int r = threadIdx.y + j;
    tile[r][swz(r, threadIdx.x)] = in[(y + j) * n + x];
  }
  __syncthreads();
  x = blockIdx.y * TILE + threadIdx.x;
  y = blockIdx.x * TILE + threadIdx.y;
  for (int j = 0; j < TILE; j += ROWS) {
    int r = threadIdx.x, c = threadIdx.y + j;
    out[(y + j) * n + x] = tile[r][swz(r, c)];
  }

__syncthreads：所有线程都要到场

转置里的 __syncthreads() 必不可少：线程 \((x, y)\) 读的元素是线程 \((y, x)\) 写的，不等所有线程写完就读，会读到旧值。编程指南对它的定义有两层意思：等 block 里所有线程都到达这一点，并且保证这些线程在此之前对共享内存和全局内存的访问对 block 内所有线程可见 [3]。

它有一条容易踩的规则：__syncthreads() 可以写在条件分支里，但条件必须对整个 block 取相同的值，否则代码“很可能挂起或产生意外的结果” [3]。最常见的错误是把它放在边界检查里面：

__global__ void block_sum_bad(const float* in, float* out,
                              int n) {
  __shared__ float s[256];
  int i = blockIdx.x * 256 + threadIdx.x;
  if (i < n) {                 // last block: some threads skip
    s[threadIdx.x] = in[i];
    __syncthreads();           // BUG: not reached by all
    if (threadIdx.x == 0) {
      float acc = 0.f;
      for (int k = 0; k < 256; ++k) acc += s[k];
      out[blockIdx.x] = acc;
    }
  }
}

完整代码：code/cu06-shared-memory/sync_bug.cu 第 5–18 行（未在 GPU 上运行）

当 \(n\) 不是 256 的倍数时，最后一个 block 里有些线程不进分支，屏障到不齐。这个 bug 在测试时常常不暴露（只要 \(n\) 恰好整除就没事），而且其后果是未定义的，不一定是挂起。另外即使不挂起，线程 0 还会读到没被写过的 s[k]。正确的写法是让所有线程都写共享内存（越界的写 0），把屏障放在分支外面：

__shared__ float s[256];
int i = blockIdx.x * 256 + threadIdx.x;
s[threadIdx.x] = (i < n) ? in[i] : 0.f;  // pad, no branch
__syncthreads();                         // all threads

完整代码：code/cu06-shared-memory/sync_bug.cu 第 22–25 行（未在 GPU 上运行）

只在一个 warp 内交换数据时，用 __syncwarp() 或 warp shuffle 就够了，见第 2 篇和第 11 篇。第 15 篇会介绍用 compute-sanitizer 的 synccheck、racecheck 工具发现这类问题。

另一个常见错误方向相反：多轮使用同一块共享内存时（例如循环里每轮装一个新 tile），读完这一轮之后、下一轮写之前也需要一次 __syncthreads()，否则快的线程会覆盖慢的线程还没读完的数据。GEMM 的主循环里每轮通常有两次屏障，原因就在这里（第 24 篇）。

Hopper 与 Blackwell：swizzle 进了硬件

前面的 swizzle 是程序员在下标里手算的。到了 Hopper，数据通常由 TMA 从显存搬进共享内存（第 21 篇），它在搬运时可以直接按某种 swizzle 模式摆放数据。CUDA 编程指南列出了四种模式：不 swizzle、32B、64B 和 128B [3]。它们都以 16 字节为单位重排数据，128B 模式下的规则正是我们熟悉的异或：

\[ \begin{gathered} \text{逻辑位置 } (y, x) \;\longrightarrow\; \text{物理位置 } (y, x') \\ x' = \big((y + \text{offset}) \bmod 8\big) \oplus x \end{gathered} \](4)

其中 \(x\) 是 16 字节块在 128 字节行内的编号（0–7），\(y\) 是行号，offset 由缓冲区地址决定，缓冲区按 1024 字节对齐时为 0 [3]。一个 16 字节块占 4 个 bank，一行 128 字节正好覆盖全部 32 个 bank，所以式 (4) 和式 (3) 是同一个思想，只是粒度从 4 字节变成了 16 字节。图 5 画出了 8×8 个 16 字节块在 128B 模式下的位置。

编程指南用的例子是一个 8×8 的 int4 矩阵转置：不 swizzle 时往转置缓冲区写一列是 8 路冲突，用 128B swizzle 加上 (i % 8) ^ j 形式的下标后冲突消失 [3]。用我们的模拟器检查，8 个 lane 一组、每个 lane 写 16 字节、相邻 lane 相隔 128 字节时，模型给出的也是 8 倍。

对 Tensor Core 来说，swizzle 从“性能优化”变成了“格式要求”。Hopper 的 wgmma 直接从共享内存读操作数（第 1 篇），它通过一个 64 位的矩阵描述符（matrix descriptor）告诉硬件数据是怎么摆的，描述符里专门有两位指定 swizzle 模式；Blackwell 的 tcgen05.mma 的共享内存描述符同样有 swizzle 字段，并多了一种“128 字节 swizzle、32 字节原子性”的模式 [5]。表 2 汇总了这些模式。

这对写 kernel 意味着三件事：

  • padding 不再适用。TMA 和 Tensor Core 都要求按 16 字节块和 128 字节行组织数据，每行多塞 4 字节会破坏这个结构，所以 Hopper 以后的高性能 kernel 几乎都用 swizzle 而不是 padding。
  • 对齐有硬性要求。编程指南建议共享内存缓冲区按 swizzle 的重复周期对齐（128B 模式为 1024 字节），否则要自己计算偏移量 [3]；wgmma 和 tcgen05 的描述符里也专门有一个“base offset”字段处理没对齐的情况 [5]。
  • 布局要在三方之间对上。TMA 写入的 swizzle 模式、描述符里声明的模式、以及 epilogue 线程自己读写共享内存时用的下标，必须是同一种。第 20 篇会用 CuTe 的 layout 代数统一描述它们：PTX ISA 直接用 CuTe 的记号 Swizzle<3,4,3> 表示 128B 模式 [5]，MLC 教程的数据布局一章也专门讲了 swizzle 布局 [6]。

面试怎么问

给代码判几路冲突

这是共享内存最常见的现场题。下面十行来自 conflicts.cu，其中 s 是 float[32*33]，s2、s4 是 float2、float4 数组，c 是 char 数组：

v += s[lane];            // A: stride 1
v += s[2 * lane];        // B: stride 2
v += s[32 * lane];       // C: stride 32 (column of 32x32)
v += s[33 * lane];       // D: stride 33 (column of 32x33)
v += s[7];               // E: everyone reads one word
v += s[lane / 2];        // F: two lanes per word
float2 t2 = s2[lane];    // G: whole float2, consecutive
float4 t4 = s4[lane];    // H: whole float4, consecutive
v += t2.x + t2.y + t4.x + t4.w;
v += s4[lane].x;         // I: one float out of each float4
v += c[lane];            // J: char, consecutive bytes

完整代码：code/cu06-shared-memory/conflicts.cu 第 13–23 行（未在 GPU 上运行）

答案（由 plots/bank_sim.py 验证）：A 无冲突；B 2 路；C 32 路；D 无冲突；E 无冲突（广播）；F 无冲突（两个 lane 共享一个字）；G、H 没有额外冲突（分别需要 2、4 个 wavefront，这是宽度决定的下限）；I 4 路（只读一个分量就退化成步长 4 的 32 位访问）；J 无冲突（32 个字节只占 8 个字）。回答时按“换算成字地址 → 模 32 → 数每个 bank 里有几个不同的字”三步说，比背结论更让面试官放心。G、H 的结论依赖步长与 gcd 的分相模型，最好主动说明这一点。

转置为什么要 +1 padding？还有别的办法吗？

  • tile[32][32] 的同一列都在同一个 bank，按列读是 32 路冲突；tile[32][33] 让每行起点错开一个 bank，同一列分到 32 个 bank。
  • 另一个办法是 XOR swizzle：列号异或行号，不浪费空间，读写用同一个函数；Hopper 以后的 TMA 与 Tensor Core 布局用的都是它。
  • 追问：padding 有什么缺点？（多占空间；每行不再 128 字节对齐，不能配合 TMA 和 128 位向量访问。）

bank 冲突和访存合并有什么区别？

  • 合并（coalescing）说的是全局内存：一个 warp 的地址落在多少个 32 字节扇区里（第 5 篇）；bank 冲突说的是共享内存：一个 warp 的地址在 32 个 bank 上怎么分布。
  • 两者的理想模式不同：对全局内存，32 个 lane 读同一个地址也只要一个扇区；对共享内存，步长 1 和步长 3 一样好，但步长 2 不行。

__syncthreads() 放在 if 里会怎样？

  • 只要条件对整个 block 相同就合法；如果有的线程进、有的线程不进，行为未定义，可能挂起，也可能读到没写完的数据 [3]。
  • 修法：让所有线程都执行屏障，越界线程写一个中性值（0 或 \(-\infty\)）。
  • 追问：__syncthreads() 除了等待还保证什么？（之前的共享内存和全局内存访问对 block 内所有线程可见。）

超过 48 KB 的共享内存怎么用？

  • 必须用 extern __shared__ 动态声明，并用 cudaFuncSetAttribute(..., cudaFuncAttributeMaxDynamicSharedMemorySize, bytes) 显式开启，启动时第三个参数给出大小 [3]。
  • 每 block 的上限比每 SM 的上限少 1 KB（A100 163 KB、H100 227 KB），这 1 KB 系统保留。

局限与未覆盖

  • 64/128 位访问的分相规则不是官方文档。图 2 中蓝、灰两组结果和面试题 G、H 的结论，依赖“64 位按半个 warp、128 位按四分之一 warp 分相”的模型，来自 NVIDIA 开发者论坛的解释和 128 字节/周期的带宽下界，NVIDIA 现行编程指南没有写明，实际硬件可能有不同的合并方式。
  • 没有实测。图 4 是 Harris 在 Fermi/Kepler GPU 上的数据，新 GPU 上的数字会不同；v3（swizzle 版）没有公开的同条件测量。式 (1) 与表 1 由公式和模拟器算出，没有在硬件上验证。代码只通过了 clang 的语法检查。
  • 模拟器只统计 bank 冲突。它不模拟共享内存的流水线延迟、与 L1 的竞争、以及同时发出多条指令的情况。
  • 没有讲的内容。共享内存原子操作的冲突（第 8 篇）、ldmatrix 的 bank 行为（第 19 篇）、分布式共享内存（第 22 篇）、TMA 的具体编程（第 21 篇）、以及 CuTe 对 swizzle 的统一表示（第 20 篇）。

小结

共享内存每周期能交出 128 字节，前提是一个 warp 的请求均匀分在 32 个 bank 上。判断冲突只需要三步：换算成字地址、模 32、数每个 bank 里有几个不同的字。等步长访问的冲突路数是 \(\gcd(s, 32)\)，按列读一个 32×32 tile 正是最坏的 32 路。padding 和 XOR swizzle 都能把一列错开到 32 个 bank；后者不浪费空间，也是 Hopper 和 Blackwell 上 TMA、WGMMA、tcgen05 共同使用的数据布局。用共享内存交换数据时，别忘了每次写和读之间的 __syncthreads() 必须被所有线程执行到。下一篇讲寄存器和 occupancy：共享内存用多了，一个 SM 能同时驻留的 block 就会变少。
