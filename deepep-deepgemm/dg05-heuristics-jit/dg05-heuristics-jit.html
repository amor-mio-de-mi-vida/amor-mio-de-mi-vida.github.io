TL;DR

  • DeepGEMM 不做自动调参（autotuning）：host 侧为每个 GEMM 形状枚举一个小候选集（SM100 的 M 分组只有 1 个候选），逐条淘汰不合法的、按代价模型或字典序排出最优的那一个，全程不碰 GPU。
  • 流水线级数由"共享内存容量减去固定开销，除以每级字节"算出，块越大级数越少——但 SM90 要求至少 3 级（小矩阵至少 4 级），否则候选被淘汰。
  • 配置最终变成一段 C++ 源码串，喂给 DeepJIT 编译；缓存键由 FNV-1a 对"签名 + 编译器版本 + 选项 + hook + 源码（含递归 include）"五段内容的哈希决定，先查内存 map，再查磁盘目录，未命中才真正编译。
  • 局部性域把权重和 SM 各切成两半：localize() 用 MLOPart 子进程在两个域分别 cuMemCreate，再把 fd 导回主进程 cuMemMap；SM 的归属由指针追逐探测的中位延迟决定，之后还要平衡使两域 SM 数相等。

从形状到内核：五步流水线

图 1 画出了从 GEMM 描述到可执行内核的完整路径。它不经过任何 GPU 上的计时循环，也没有搜索算法——所有决策都在 host 侧的 C++ 代码里完成。

五步由 get_best_config 串起来（heuristics/common.hpp 第 18–47 行）：先调 ArchSpec::get_layout_candidates 枚举候选，逐个调 get_layout_info 算代价，用 ArchSpec::compare 选最好的那个；然后依次调 get_storage_config、get_pipeline_config、get_launch_config 把剩下的配置填满。两个架构走同一套函数签名，但候选空间和比较逻辑完全不同。

启发式怎么选配置

SM100 的 M 分组：只有一个候选

SM100 对 M 分组的三种布局（contiguous、PSUM contiguous、masked）的候选集只有一个元素——所有参数在枚举阶段就定死了：

// Always enable swap A/B (and multicasting if possible) for m-grouped GEMMs

    desc.gemm_type == GemmType::MGroupedMasked) {
    const bool swap_ab = true;
    const auto block_n = 128;

    const auto layout = Layout{swap_ab, block_m, block_n, block_k, cluster_m, cluster_n};
    std::vector<Layout> candidates = {layout};
    return candidates;

swap_ab 恒为 true；block_n 固定 128（swap-AB 后它是 UMMA 的 M 维，在 SM100 上只能是 128）；block_m 等于 mk_alignment_for_contiguous_layout()，默认 128、SM100 理论值 256（见上一篇）；cluster_n 在 N 能被 256 整除且 SM 数为偶数时开到 2，否则 1。这意味着 M 分组 GEMM 在 SM100 上不存在配置选择——候选集只有一个元素，compare 根本不会被调用。

SM90 的候选空间：从几百到十几个

这不是一个精确的性能模型，而是一个只含搬运代价的相对量——HBM 带宽和张量核算力对每个候选都一样，因此不建模（代码注释原话）。它考虑两层片上带宽：L2→SMEM 和 L1（SMEM↔寄存器 + 张量核），对每个 tile 估算各层的搬运字节，乘以块数，分别除以带宽常量，取两者最大值，再除以波效率。下面逐步拆解。

带宽常量

代码用两个常量表示全芯片的每周期吞吐（sm90.hpp 第 162–163 行）：

量公式含义
\(B_{\mathrm{L2}}\)min(64 · NSM, 8×10⁶ / 1.3×10³)L2 → SMEM 全芯片吞吐（B/cycle）
\(B_{\mathrm{L1}}\)128 · NSMSMEM ↔ 寄存器 / 张量核（B/cycle）

第一项的两个分支：64 · NSM 是"每个 SM 每周期从 L2 取 64 字节"；8 × 10⁶ / 1300 ≈ 6154 是 L2 自身的聚合带宽上限——SM 数再多也超不过它。以 \(N_{\mathrm{SM}} = 132\) 为例，\(64 \times 132 = 8448\) 被截到 6154，L2 是全局瓶颈。L1 一侧没有截断，\(128 \times 132 = 16896\)。

这两个常量旁的注释只标了单位，没给来源。局限节已说明本文原样引用、不做正确性判断。

每块搬运量：四项

对一个 \((\text{BM}, \text{BN})\) 的输出 tile，沿 K 维做 \(K/\text{BK}\) 次 MMA；代码把搬运量拆成四项（sm90.hpp 第 170–175 行）：

变量公式（字节）层级含义
\(D_{\text{L2,AB}}\)\(K\!\left(\dfrac{\text{BM}}{c_N} + \dfrac{\text{BN}}{c_M}\right)\!s\)L2→SMEMA、B 块；multicast 时 cluster 内共享，流量除以 cluster 大小
\(D_{\text{L1,AB}}\)\(K(\text{BM} + \text{BN})\,s\)SMEM→RF每个 CTA 仍要完整读一遍 SMEM 里的 A、B
\(D_{\text{L1,TC}}\)\(K\!\bigl(\max(64, \text{BM}) + \text{BN}\bigr)\!s + \text{BM}\!\cdot\!\text{BN}\!\cdot\!s_{\text{CD}}\)SMEM↔TCWGMMA 从 SMEM 读 A（至少 64 行）和 B，再把累加器写回 SMEM
\(D_{\text{CD}}\)\(\text{BM}\!\cdot\!\text{BN}\!\cdot\!s_{\text{CD}}\!\cdot\!(1 + [\text{accum}])\)L1↔L2写输出；若 with_accumulation 还要先读旧值

其中 \(s\) 是 A/B 元素字节数（FP8 为 1、BF16 为 2），\(s_{\text{CD}}\) 是输出元素字节数，\(c_M, c_N\) 是 cluster 的 M、N 维。\(\max(64, \text{BM})\) 来自 WGMMA 一次读 64 行——BM = 16 或 32 的小 tile 仍要从 SMEM 读 64 行。

周期估算公式

设一共 \(P\) 个输出 tile（\(P = \lceil M/\text{BM}\rceil \cdot \lceil N/\text{BN}\rceil \cdot G\)，\(G\) 为组数），\(W = \lceil P/N_{\mathrm{SM}}\rceil\) 个波。代码先算每层的全局搬运周期，取较大者，再按波效率放大：

\[ \begin{aligned} C_{\mathrm{L2}} &= (D_{\text{L2,AB}} + D_{\text{CD}}) \cdot P \;/\; B_{\mathrm{L2}} \\ C_{\mathrm{L1}} &= (D_{\text{L1,AB}} + D_{\text{L1,TC}} + D_{\text{CD}}) \cdot P \;/\; B_{\mathrm{L1}} \\ \eta &= P \;/\; (W \cdot N_{\mathrm{SM}}) \\ C &= \max(C_{\mathrm{L2}},\; C_{\mathrm{L1}}) \;/\; \eta \end{aligned} \](1)

波效率 \(\eta \in (0, 1]\)：末波只有 \(P \bmod N_{\mathrm{SM}}\) 个 SM 有活干，效率低于 1 就放大总代价。

当 cluster 大于 1 但波数 \(W = 1\) 时，multicast 没有收益——同一波里每个 CTA 都在干活，没有"别的波可以共享"这回事——代码直接把 \(C\) 设成最大值，相当于淘汰所有 cluster > 1 的单波候选。

数值示例

以 FP8 1D1D 内核（\(s = 1, s_{\text{CD}} = 4, \text{BK} = 128\)）为例，取两个典型候选：BM = BN = 128（cluster 1×1）和 BM = 128, BN = 64（cluster 1×2），\(M = N = 4096, K = 7168, N_{\mathrm{SM}} = 132\)，不累加。表 2 列出各项。

这个例子里第一个候选胜出：128×128 的 L2 流量和 128×64（cluster 1×2）一样（multicast 让 L2 的 A 流量减半，但 tile 少一倍所以总量不变），而 L1 层因为 tile 大、总块数少，反而更低。这也说明 cluster multicast 不总是赢——它减少 L2 流量但不减少 L1 流量，只有当 L2 是瓶颈时才有收益。代码里"单波时禁掉 multicast"是这一权衡的极端情形。

SM100 的比较：六级字典序

SM100 的 compare 走一个完全不同的路径——不算周期，而是按六级字典序排：


static int get_num_tma_store_stages(const GemmDesc& desc, const Layout& layout) {
    // With single-stage TMA stores, each SM keeps at most one bulk store in
    // flight. This paces the store traffic and improves the achieved DRAM
    // throughput when C/D flushes dominate DRAM traffic; it also frees up
    // shared memory for the A/B mainloop and halves the C/D smem read/write
    // footprint. Only enabled for k-grouped GEMMs.
    if (desc.get_mma_kind() == MmaKind::BF16 or layout.swap_ab or
        not is_k_grouped_contiguous(desc.gemm_type))
        return 2;

    const int num_k_blocks_per_group = desc.k / std::max(desc.num_groups, 1) / layout.block_k;
    const int min_k_blocks = desc.cd_dtype != torch::kFloat ? 16 :
                             desc.with_accumulation ? 24 : 32;
    return num_k_blocks_per_group >= min_k_blocks ? 1 : 2;
}

SM100 的 get_layout_info 里 num_cycles 被留成了 0（源码注释标注为 TODO: calculate expected cycles），所以目前所有比较都是离散的、不含任何浮点估算——SM100 还没有周期代价模型。这也解释了为什么 SM100 的 M 分组只给一个候选：候选集只有一个时，六级字典序根本不会被调用。

共享内存与流水线级数

选定 block_m、block_n、block_k 之后，流水线级数 num_stages 由共享内存容量决定：

\[ \text{num\_stages} = \min\!\left(\left\lfloor\frac{\text{smem\_cap} - \text{smem\_ex}}{\text{smem\_stage}}\right\rfloor,\; S_{\max}\right) \](2)

其中 smem_capacity 在 SM90 和 SM100 上都是 232448 字节（227 KiB）。smem_extra 包括 C/D 的写回缓冲、屏障（mbarrier）数组、SF 的额外存储和 tensor map 缓冲；smem_per_stage 是一级流水线里 A、B 块加上各自 SF 块的字节数。上限 kNumMaxStages 在 SM90 上是 16，SM100 上是 32。

如式 (2) 所示，级数取决于分到每级的字节数。图 2 的右图显示了一个直觉上不明显的事实：BF16 的级数可以比 FP8 高。原因是 BF16 的 block_k 只有 64（因为 BF16 元素是 2 字节，\( 128 \times 8 / 16 = 64 \)），而 FP8 的是 128——每级的 A、B 块字节数分别是 \( \text{BM} \times 64 \times 2 \) 和 \( \text{BM} \times 128 \times 1 \)，刚好一样，但 FP8 1D1D 内核还要为每级的 SF-A 和 SF-B 各留一块（smem_sfa_per_stage 和 smem_sfb_per_stage），总开销更大。

三个运行期旋钮

除了形状之外，DeepGEMM 还暴露了三个可以在 Python 侧随时调的控制旋钮（csrc/apis/config.hpp 第 1–49 行）：

tc_util：张量核利用率上限

set_tc_util(x) 把 runtime→tc_util 设成 0–100 之间的整数，默认 0 表示 100%。它被填进 GemmDesc.tc_util，传给每个 host 侧的 launcher，生成的模板参数叫 kTCUtil。在 SM100 内核里这个参数控制 warpgroup::arrive_tc_util（setmaxnreg 指令的等效），意思是"张量核在一个 warp 调度周期里最多使用这么多比例的时间"。不设则不限制。典型用途是把一部分张量核时间让给 TMA 或尾声以提高并行度。

PDL：流水线描述符加载

set_pdl(True/False) 控制 SM100 的 Programmatic Dependent Launch。PDL 让后一个 grid 在前一个 grid 还没完全结束时就开始启动，可以减少两个 kernel 之间的空隙。它是一个 launch 选项而不是编译期选项：DeepJIT 的 LaunchOptions 里有一个 enable_pdl 字段，每次 launch 时传给 CUDA Driver（config.hpp 第 27–31 行）。

确定性模式

use_deterministic_algorithms(True) 把 HeuristicsRuntime.deterministic_algorithms 设成 true（runtime.hpp 第 18–24 行）。目前代码里只有 Mega MoE 和 Mega mHC 读这个开关（第 8 篇、第 9 篇）。普通 GEMM 的启发式不读它——对于非 Mega 内核，确定性由内核本身保证（同一配置、同一输入、同一网格总是给出同一结果），不需要额外旋钮。

DeepJIT：编译缓存与惰性初始化

DeepGEMM 不用 Triton、不用 CuTe 的 Python 前端——它把内核写成 .cuh 模板，在 host 侧用 std::format 把配置拼成一段 C++ 源码，然后调用 DeepJIT 的 jit→compile(tag, source) 编译它 [1]。DeepJIT 是 DeepSeek 开源的一个轻量级 JIT 运行时 [2]，它处理的是"从源码到可执行内核"这一段基础设施。

缓存键：五段内容的 FNV-1a

DeepJIT 的缓存键由五段输入的哈希决定（runtime.hpp 第 42–51 行）：

  1. extra_signature：应用（DeepGEMM）自己提供的依赖签名，包含 CUTLASS 版本号；
  2. 编译器版本信息：NVCC 的版本和路径；
  3. 编译选项展开成的 flags 串；
  4. post hook（DeepGEMM 不用这个功能）；
  5. 源码加上递归展开的 include 文件。

哈希函数是 FNV-1a 的一个变体，用两段 64 位状态并行推进，取出时各做一次 split-mix 终结化再拼成 32 个十六进制字符。图 3 画出了缓存键的构成和查找顺序。

class FNV1a {
public:
    uint64_t state_0 = 0xc6a4a7935bd1e995ull;
    uint64_t state_1 = 0xff51afd7ed558ccdull;

    FNV1a& update(const std::string_view data) {
        const auto update_byte = [&](const uint8_t byte) {
            state_0 = (state_0 ^ byte) * 0x100000001b3ull;
            state_1 = (state_1 ^ byte) * 0x9e3779b97f4a7c15ull;
        };

        // Prefix every update with its length so chained binary inputs have unambiguous boundaries
        const int64_t size = data.size();
        for (int shift = 0; shift < 64; shift += 8)
            update_byte(static_cast<uint8_t>(size >> shift));
        for (const char value: data)
            update_byte(static_cast<uint8_t>(value));
        return *this;
    }

    [[nodiscard]] std::string get_hex_digest() const {
        const auto split_mix = [](uint64_t value) {
            value = (value ^ (value >> 30)) * 0xbf58476d1ce4e5b9ull;
            value = (value ^ (value >> 27)) * 0x94d049bb133111ebull;
            return value ^ (value >> 31);
        };
        return std::format("{:016x}{:016x}", split_mix(state_0), split_mix(state_1));
    }
};

inline std::string get_hex_digest(const std::string_view data) {
    return FNV1a().update(data).get_hex_digest();
}

每段输入先喂自己的长度再喂内容，这样"源码 A + 选项 B"和"源码 AB + 选项空"不会碰撞。最终的 tag.digest 就是磁盘缓存目录名。

磁盘缓存的原子发布

DeepJIT 的磁盘缓存用目录粒度的原子发布：编译产物先写进 tmp/<uuid>，在里面放好 .committed 标记并 fsync，然后对整个目录做一次 rename——如果另一个进程已经抢先 rename 了，当前进程就删掉自己的临时目录、用已有的（disk.hpp 第 52–69 行）。这使得多机、多进程可以共享同一个缓存目录而不互相踩踏。

compiled_dims：不是所有维度都编进内核

DeepGEMM 的大多数 launcher 都接受一个 compiled_dims 字符串参数。当 compiled_dims 包含 'm' 时，\( M \) 被编成编译期常量（模板参数），否则传 0 表示运行期确定。典型用法是训练时 \( M \) 不定而 \( N \) 和 \( K \) 是模型维度：传 "nk" 让编译器为它们生成特化代码，\( M \) 则留到运行期。

set_ignore_compile_dims(True) 让所有维度都不编译——这在 profiling 或形状频繁变化的场景下减少内核变体（runtime.hpp 第 25–31 行）。

惰性初始化

DeepJIT 和 HeuristicsRuntime 都用 deep_jit::LazyInit 包装：第一次使用（解引用 jit->）时才创建对象。这意味着 import deep_gemm 不会立刻碰 CUDA driver，也不会创建缓存目录——只有第一次调用 GEMM 时才会触发一连串初始化。init_jit 在 deep_gemm.__init__ 的 _C.init() 里被调用，它设置 include 路径和环境前缀（runtime/jit.hpp 第 13–25 行），但 Runtime 对象本身要到首次 compile 时才被 lambda 构造出来。

局部性域与 mlopart

Blackwell GPU 有两个"局部性域"（locality domain）：HBM 的一半在物理上离一半 SM 更近，另一半离另一半 SM 更近。如果权重恰好分配在某个 SM 对应的域里，读取带宽更高、延迟更低。这个信息目前不能通过标准 CUDA API 查询——DeepGEMM 用一个叫 MLOPart（Multi-Locality Partitioning）的机制来分配和探测。图 4 画出了整个流程。

localize()：把权重切成两半

代码里 kNumDeviceLocalityDomains 固定为 2，kNumSMsPerTPC 固定为 2（两个 SM 组成一个 TPC，同 TPC 的 SM 在同一个域）。这些常量在 sm100_locality_domain.hpp 和 locality_domain.hpp 里。

Python 侧的 localize(t, dim=-2) 把一个 \( (N, K) \) 的权重张量变成 \( (2, N/2, K) \)，其中切片 0 分配在域 0、切片 1 分配在域 1（locality_domain.py 第 13–22 行）。底层调用的是 empty_per_domain：它用 cuMemAddressReserve 预留一段虚拟地址，然后对每个域分别调 LocalityDomainAllocator::map，而 map 又调 mlopart::create_memory 在指定域做一次 cuMemCreate，拿到 handle 后 cuMemMap 到预留的地址上（locality_domain.hpp 第 44–57 行）。

MLOPart 子进程

CUDA 13.4 以前没有直接指定域的 cuMemCreate 参数。DeepGEMM 的变通方案是启动一个 MLOPart 子进程：它用 nvidia-cuda-mps-control 带 -mlopart 启动一个 MPS 守护，然后在守护下 cuInit（此时看到的两个"设备"各对应一个域），对指定设备做 cuMemCreate，用 cuMemExportToShareableHandle 导出 POSIX fd，再通过 Unix socket 把 fd 传回主进程。主进程用 cuMemImportFromShareableHandle 把它变成自己进程空间里的 handle，然后 map 到预留地址（mlopart.py 第 43–52 行）。

probe：用指针追逐测延迟

权重放好了，还要知道每个 SM 在哪个域。probe_sm_locality_domains 的做法是：在两个域各分配一块探测缓冲区，在里面写入指针追逐链（每 128 字节一跳、连续 32 跳），每个 SM 跑一个 32 线程的 CTA 去追逐，测每跳的周期数取中位值（locality_domain.hpp 第 82–92 行）。排序后延迟最低的那个域就是这个 SM 的"近域"。判定条件还要求远域/近域的延迟比超过 1.25 倍，且同一 TPC 的两个 SM 给出相同结果——不满足则重试最多 5 次，全部不稳定则退回到均匀分配（locality_domain.hpp 第 100–112 行）。

balance：让两域 SM 数相等

物理探测可能给出不均匀的结果（比如 10 个 TPC 在域 0、6 个在域 1）。balance_sm_locality_domains 把多余域的多余 TPC 改判到少数域，使两域各占 \( n_\text{tpc}/2 \) 个 TPC。具体做法是：找出多余域的 TPC 列表，取前 \( n_\text{surplus} \) 个翻转它们的域标签（locality_domain.hpp 第 118–126 行）。被翻转的 TPC 虽然读远域的延迟稍高，但它们能和近域的 SM 共同组成两路 cluster multicast——这在 Mega MoE 里是必须的（第 8 篇）。

局限与未覆盖

  • 没有任何性能数字。本地没有 GPU。图 2 的级数图由 Python 对 get_pipeline_config 的移植算出，横轴是块大小不是耗时；SM90 的 num_cycles 代价模型也是一个相对量（L1/L2 搬运的估计周期），不是实际时间。
  • SM100 的代价模型待实现。sm100.hpp 的 get_layout_info 把 num_cycles 留成了 0，所有比较走的是字典序而非周期估算。
  • SM90 的 L1/L2 带宽常量来源不明。l2_bandwidth_per_cycle 的公式 min(64 * num_sms, 8e6 / 1.3e3) 似乎是经验值，代码里没有注释说明出处。本文原样引用，不做正确性判断。
  • DeepJIT 的 Ascend 后端未读。README 说它支持 CUDA 和昇腾两个后端，本文只看了 CUDA 那条路径。
  • MLOPart 的 MPS 管道细节未展开。子进程用 nvidia-cuda-mps-control -f 启动守护、再用 start_server ... -mlopart 启动服务端，但这两步的具体含义和前提条件（驱动版本、GPU 架构）未在本文中讨论。
  • 指针追逐内核只描述了原理。sm100_locality_domain.cuh 里的实际 device 代码用了 inline PTX 的 ld.global.ca（cache at all levels，即所有缓存层级都参与）加载指针追逐链。.ca 修饰符并不绕过 L2——绕过 L2 需要使用 .cg（cache global）或 .cs（streaming）。此处使用 .ca 意味着探测的是包含 L1+L2 全栈缓存后的访问延迟，而非裸 HBM 延迟。两个域的延迟差异体现的是 HBM 到 SM 的物理距离差异（经过缓存后仍然可观测），而非绕过缓存后的纯 HBM 延迟差异。本文没有展开讨论探测内核的 PTX 细节。
  • compiled_dims 对内核变体数量的影响没有量化。因为变体数取决于项目的实际 (M, N, K) 集合，没有 GPU 环境无法统计。
  • set_block_size_multiple_of 只一句带过。它设置 block_m_multiple_of 和 block_n_multiple_of，影响 SM100 的 block_m/block_n 候选步长（config.hpp 第 42–48 行），但不在本文的覆盖清单里。
