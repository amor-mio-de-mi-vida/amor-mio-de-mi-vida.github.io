TL;DR

  • Hopper 上 DeepGEMM 有两个 FP8 GEMM 内核，叫 1d1d 和 1d2d；分派只看一个数——B 的 MN 方向缩放粒度。
  • FP8 的乘加由张量核完成，但累加器里只装一个 128 宽的 K 块；每块算完都要乘上两个 scale 再加进另一组 FP32 寄存器。
  • 这套“两级累加”的代价是 CUDA 核上的一次乘加，换来的是 scale 可以细到“每 token × 每 128 个通道”。
  • 一个 CTA 被切成两种 warp：一组专门发 TMA，一组专门发 WGMMA；两组用寄存器重分配互相让出寄存器。
  • 生产者和消费者之间只有 full / empty 两组 mbarrier 和一个相位位；cluster 里的两个 CTA 共享同一次 TMA 多播。
  • 两个内核的输出路径完全不同：1d2d 写 BF16、不支持累加；1d1d 写 FP32、必须带累加，用 TMA 的 reduce-add 落盘。

DeepGEMM 库概览：一套 JIT 内核，覆盖三类计算

在进入内核之前，先看 DeepGEMM 作为一个软件库长什么样。它不是通用线性代数库：只做 DeepSeek 模型需要的那几种矩阵乘，但每一种都写了专用内核。内核以 CUDA 头文件的形式放在 deep_gemm/include 下，通过 Python 包 deep_gemm 调用；没有预先编译好的内核，每个内核在第一次被调用时按形状和硬件现场编译并缓存。

从 Python 到 GPU 的路径对所有内核都一样：

  1. Python 调用一个函数，例如 deep_gemm.fp8_gemm_nt(...)。
  2. host 侧的启发式（dg05）根据 M/N/K、SM 数和架构枚举候选块大小，选出一个配置——不在 GPU 上做自动调参。
  3. 配置变成 C++ 模板实参，拼成一段源码，交给 DeepJIT（dg05）：先查内存缓存和磁盘缓存，未命中才真正编译。
  4. 编译得到的 CUfunction 被 launch 到 GPU 上执行。

与 DeepEP 的接口在两处：DeepEP dispatch 输出的展开布局直接是分组 GEMM 的输入（dg04 ↔ ep02）；Mega MoE 把 EP 的 NVLink 通信搬进了 GEMM 内核内部（dg08 ↔ ep07）。

本篇从最基础的 SM90 FP8 内核开始——它是所有其他内核的骨架。理解了它的两级累加和生产者-消费者流水线，后续的 SM100 变体、分组 GEMM 和融合内核就是在同一个骨架上换部件。

把矩阵乘的输入从 BF16 换成 FP8，算力翻倍，麻烦也随之而来：E4M3 只有 8 个二进制位（1 位符号、4 位指数、3 位尾数），一个张量里不同位置的数值动态范围稍有差异，统一用一个缩放系数就会把小的那部分压没。现在的做法是分块缩放（block-wise scaling）：把矩阵切成小块，每块存一个 FP32 的缩放因子（scaling factor，下文简称 scale）。DeepGEMM 在 Hopper 上把 K 方向的块宽固定成 128，内核开头就写死了这一条：DG_STATIC_ASSERT(BLOCK_K == 128, "Only support per-128-channel FP8 scaling")（sm90_fp8_gemm_1d1d.cuh 第 51 行）。

这一个决定把内核的结构全改了。scale 每 128 个 K 换一次，意味着张量核不能一口气把整个 K 维累加完——累加到一半的部分和还没乘上 scale，不同块的部分和不能直接相加。于是 Hopper 内核必须在流水线中间插入一步：每 128 个 K 停一次，把部分和乘上两个 scale，加进另一组寄存器。本文回答三个问题：这一步为什么值得；两个内核（1d1d 与 1d2d）为什么长得不一样；以及围绕它的 warp 特化和流水线是怎么搭的。

本文只读 SM90（Hopper）的两个 FP8 内核。Blackwell 的 tcgen05/TMEM 路线见第 2 篇，scale 的打包与布局见第 3 篇，调度器与分组 GEMM 见第 4 篇，配置启发式见第 5 篇。

约定与 README 一致 [1]：内核算的是 \( D = C + A B^\top \)，输入布局为 NT（A 行主序、B 列主序），SM90 只支持这一种布局。M、N、K 是 GEMM 的三个维度，BM、BN、BK 是一个 CTA 处理的块大小（BK 恒为 128），\( T = \lceil K/128 \rceil \) 是 K 方向的块数，S 是流水线的 stage 数。

30 秒回顾：GPU 上的 GEMM 为什么要分块

矩阵乘 \(D = A \times B\) 的数据量是 \(O(MNK)\)，但 GPU 的片上存储（共享内存，几百 KB）远小于整个矩阵。标准做法是把 \(D\) 切成 \(\text{BM} \times \text{BN}\) 大小的块（tile），每个线程块（CTA）负责一块。对于每个 tile，CTA 沿 K 维度逐段取 A 的 \(\text{BM} \times \text{BK}\) 和 B 的 \(\text{BN} \times \text{BK}\) 子块搬进共享内存，用张量核做乘加，结果在寄存器里累加；K 走完后把累加器写回全局内存。这个"搬一块、算一块、累加"的循环就是 GEMM 内核的骨架。DeepGEMM 在这个骨架上加了两样东西：异步搬运（TMA 硬件单元负责搬，SM 不等）和warp 特化（一部分线程专门发搬运指令，另一部分专门发计算指令）。下面的"两级累加"就是在这个循环的每一步里插入一次额外的缩放操作。

分块缩放逼出了两级累加

先看 scale 本身解决了什么。DeepGEMM 的量化工具函数把 amax 除以 448（E4M3 的最大有限值）当作 scale：sf = x_amax / 448.0（utils/math.py 第 35–37 行）。per_token_cast_to_fp8 对每一行的每 128 列求一个 amax，per_block_cast_to_fp8 对每个 128×128 块求一个 amax。块越小，每个 scale 覆盖的数值动态范围越窄，能保住的有效位数越多。

图 1 的上半部分用一个 CPU 模拟量化了这件事：取 K = 4096 的一对向量，把它们按 128 分成 32 块，第 t 块的 A 乘上 \( g_t \)、B 乘上 \( 1/g_t \)，于是每块对点积的贡献相同，但 A 自身的动态范围被拉开。整行只用一个 scale 时，相对误差随动态范围迅速变差；每 128 个 K 一个 scale 时，误差几乎不随动态范围变化。这正是 FP8 训练里要做分块缩放的理由。

但“每 128 个 K 一个 scale”不能只在最后乘一次。写成公式：把 K 切成 T 个块 \( \mathcal{B}_0,\dots,\mathcal{B}_{T-1} \)，\( \tilde A, \tilde B \) 是量化后的 FP8 码值，\( s^a_{i,t} \) 是 A 第 i 行第 t 个 K 块的 scale，\( s^b_{j,t} \) 是 B 对应的 scale，那么

\[ \begin{aligned} P^{(t)}_{ij} &= \textstyle\sum_{k \in \mathcal{B}_t} \tilde A_{ik}\, \tilde B_{jk} \\ D_{ij} &= \textstyle\sum_{t=0}^{T-1} s^a_{i,t}\, s^b_{j,t}\, P^{(t)}_{ij} \end{aligned} \](1)

式 (1) 的两行就是两级累加：内层的 \( P^{(t)}_{ij} \) 是一个 128-K 块的部分和（partial sum），由张量核算；外层那个带 scale 的求和，scale 随 t 变化，没法并进张量核的累加器，只能在别处做。这就是 DeepGEMM 内核里 accum 与 final_accum 两组寄存器的来历。

仓库里没有解释为什么不干脆把整个 K 累加在张量核里。DeepSeek-V3 技术报告给过一个理由：Hopper 的 FP8 张量核累加保留的尾数位有限，所以他们每 128 个元素把部分和搬到 CUDA 核的 FP32 寄存器上再累加 [2]。这是报告里的说法，不是本仓库代码能证实的内容。

图 1 的下半部分模拟了另一半动机：假设低精度累加器的尾数只有 b 位，比较“整个 K = 4096 都留在这个累加器里”和“每 128 个 K 升到高精度再累加”。两者用的 scale 完全一样，差别只在那条长累加链。b 小到 14 位左右时，一级累加的误差比两级高一个量级以上；b 到 23 位（FP32）时两条线合拢。这是对算术的模拟，不是对某款张量核的建模，也不是实测。

DeepSeek-V3 技术报告 [2] 在 Section 3.3 中给出了更具体的量化证据：他们在 FP8 训练中测试了不同的 promotion interval（把部分和从低精度累加器搬到 FP32 的间隔），发现 interval = 128 时训练损失与 BF16 基线几乎无差——报告称此方案实现了"virtually no loss in accuracy"。interval 选 128 不是随意的：它恰好等于量化分块的 K 宽度，所以每次 promotion 的边界与 scale 的边界对齐，每个部分和 \( P^{(t)} \) 在被乘上 scale 之前就已经是一个完整的量化块的累加结果，不存在"半个块的部分和被截断后再与另半个块的部分和相加"的精度损失。如果 interval 更大（比如 256），一次 WGMMA 累加会跨越两个 scale 边界，scale 必须在两组部分和合并之后才能乘入——此时低精度累加链已经引入的舍入误差会被 scale 放大。interval = 128 是精度与性能的甜点：更小的 interval 增加 CUDA 核上的乘加次数，更大的 interval 牺牲精度。

“1d”和“2d”说的是 scale 张量的形状

DeepGEMM 的 Python 接口用一个三元组 recipe = (gran_mn_a, gran_mn_b, gran_k) 描述缩放粒度：前两个数是 A、B 在 MN 方向上每个 scale 覆盖多少行/列，第三个是 K 方向的粒度。SM90 的默认 recipe 是 {1, 128, 128}（utils/layout.hpp 第 86–90 行）：A 每个 token 一个 scale，B 每 128 个输出通道一个 scale。测试里的 get_recipes 把这套对应关系写得最清楚：

def get_recipes(self, is_wgrad: bool = False) -> Tuple[Tuple, Tuple, Tuple]:
    recipe, recipe_a, recipe_b = None, None, None
    if self.is_legacy():
        recipe = (1, 1, 128) if is_wgrad else None
    else:
        recipe_a = (1, self.gran_k_a)
        recipe_b = (1, self.gran_k_b) if self.is_fp4_b or is_wgrad else (self.gran_k_b, self.gran_k_b)
    return recipe, recipe_a, recipe_b

源码：tests/generators.py 第 60–67 行。

前向和反向的数据梯度用默认 recipe（B 是权重，按 128×128 块量化）；权重梯度（wgrad）用 (1, 1, 128)，因为此时 A 和 B 都是激活/梯度，两边都按“每行每 128 列”量化。于是两个粒度组合对应两个内核：1d1d 指 A、B 的 scale 在 MN 方向都是一维的（每行/每列一个），1d2d 指 A 一维、B 是二维的 128×128 块。图 2 把三种 scale 张量的形状画在一起。

B 的 scale 形状不同，连带着一串约束跟着变。最要紧的是 scale 怎么进共享内存：1d1d 的 SFB 是一个 [N, K/128] 的大张量，每个 stage 要按 BN 取一列，所以它和 A、B 一样走 TMA；1d2d 的 SFB 只有 [N/128, K/128]，一个 tile 从头到尾只需要 \( T \) 个（偶尔 \( 2T \) 个）float，所以干脆由数学 warp 直接从全局内存读进共享内存。表 2 把两个内核的硬约束列齐，这些都是源码里的 DG_STATIC_ASSERT 或 host 断言。

“1d1d 必须带累加”这一条值得多说一句：host 侧断言 c.has_value() and d.scalar_type() == torch::kFloat（sm90_fp8_gemm_1d1d.hpp 第 84 行），内核也静态断言 C/D 只能是 float。原因在尾声：它用 SM90_TMA_REDUCE_ADD_2D 把结果原子地加到 D 上，天生就是“累加进去”，而不是“写下去”。K 分组的权重梯度正好需要这种语义——多个 K 组的结果要落到同一块 D 上。

张量核只负责一个 128-K 块

现在看寄存器里发生了什么。WGMMA（warpgroup matrix multiply-accumulate）是 Hopper 的异步张量核指令：一个 warpgroup（4 个 warp，128 线程）协同发一条指令，从共享内存读 A、B 的描述符，把结果累加到这 128 个线程的寄存器上 [3]。DeepGEMM 用形状 M=64, N=BN, K=32 的 FP8 变体，每个线程持有 kNumAccum = 64 * BN / 128 个 FP32 累加值：

struct FP8MMA {
    // ...
        MMA::fma(desc_a, desc_b, d[Idx]..., (scale_d ? ScaleOut::One : ScaleOut::Zero));
    // ...
    static constexpr int M = 64;
    static constexpr int N = N_;
    static constexpr int K = 32;
    static constexpr int kNumAccum = M * N / 128;
};

源码：mma/sm90.cuh 第 14–30 行（节选）。

关键在 scale_d 这个参数。在 PTX 层面，WGMMA 指令有一个 .scale_d 字段：值为 1 时 D = D + A×B（累加），值为 0 时 D = A×B（覆盖）。DeepGEMM 通过 CUTLASS 的 ScaleOut 枚举控制它——scale_d 为假时用 ScaleOut::Zero，即覆盖累加器而不是累加进去。调用处传的是 K 方向的循环变量 k（sm90_fp8_gemm_1d1d.cuh 第 302–306 行），一个 128 宽的 K 块要发 \( 128/32 = 4 \) 条 WGMMA，第 0 条清零、后 3 条累加。所以 accum[] 里从来只有一个 128-K 块的部分和，正是 式 (1) 里的 \( P^{(t)}_{ij} \)。

等 warpgroup_wait<0>() 确认这 4 条指令完成后，才是第二级：

// Promote with scales
#pragma unroll
for (uint32_t i = 0; i < WGMMA::kNumAccum / 4; ++ i) {
    const float &scale_b_0 = scales_b[i].x;
    const float &scale_b_1 = scales_b[i].y;
    final_accum[i * 4 + 0] += scale_a_0 * scale_b_0 * accum[i * 4 + 0];
    final_accum[i * 4 + 1] += scale_a_0 * scale_b_1 * accum[i * 4 + 1];
    final_accum[i * 4 + 2] += scale_a_1 * scale_b_0 * accum[i * 4 + 2];
    final_accum[i * 4 + 3] += scale_a_1 * scale_b_1 * accum[i * 4 + 3];
}

源码：sm90_fp8_gemm_1d1d.cuh 第 316–325 行。

这四行把 WGMMA 累加器的布局暴露得很清楚。每个线程的 4 个连续累加值覆盖 2 行 × 2 列：第 0、1 个在行 r_0，第 2、3 个在行 r_1 = r_0 + 8，列则是相邻的两个。所以每个线程只需要两个 A 的 scale（scale_a_0/1，按 r_0 = warp_idx * 16 + lane_idx / 4 从共享内存读）和一串 B 的 scale（scales_b[i] 是一个 float2，覆盖那两列）。图 3 把这条链画成一张图。

1d2d 的这一步形状不同。它的 B 每 128 列才换一个 scale，而 BN 可以取到 192，于是一个 tile 可能跨两个 scale 列。内核为此准备了两套 B scale 和一个谓词：常量 kMustUseUniformedScaleB = (BLOCK_K % BLOCK_N == 0)（第 75 行）为真时（如 BN = 128、64）一个 tile 只落在一个 scale 列里，只读 scale_b_0；否则按 num_former_iters 判断每个累加值该用 scale_b_0 还是 scale_b_1（第 329–345 行）。代码注释特意说明，写成谓词选择而不是两个循环，对性能很重要。用符号写出来，两个内核的差别只是 \( s^b \) 的下标：

\[ \begin{aligned} \text{1d1d:}\quad s^b_{j,t} &= \sigma^b_{j,\,t} \\ \text{1d2d:}\quad s^b_{j,t} &= \sigma^b_{\lfloor j/128 \rfloor,\, t} \end{aligned} \](2)

式 (2) 里 \( \sigma^b \) 是内存里的 scale 张量，j 是输出通道号。1d1d 每个线程要为自己负责的每一列取一个 scale，所以 SFB 必须按 stage 流进共享内存；1d2d 每个 tile 只要 \( T \) 或 \( 2T \) 个 float，所以它选了另一条路——让数学 warp 自己去全局内存取：

一个 CTA 里有两种 warp：搬数的和算数的

    cutlass::arch::warpgroup_reg_alloc<kNumMathRegisters>();

源码：sm90_fp8_gemm_1d1d.cuh 第 169–250 行（节选，中间省略约 75 行）。

warpgroup_reg_dealloc / warpgroup_reg_alloc 来自 CUTLASS 的 cutlass/arch/reg_reconfig.h [4]，对应 Hopper 的 setmaxnreg 指令：生产者把自己的寄存器配额降到 40（1d1d 在展开流水线时降到 24），消费者升到 232–248。线程总数由启发式给出：TMA 侧固定 128 线程，数学侧在 BM ≤ 64 时是 128、否则 256（heuristics/sm90.hpp 第 190–200 行）。生产者的寄存器需求很低——它只是在算地址、发指令，而 final_accum 这种东西全在消费者手里，所以这一笔交易很划算。

消费者的寄存器预算可以粗略反推。以 BN = 128 为例：accum 占 kNumAccum = 64 × 128 / 128 = 64 个 FP32 寄存器，final_accum 同大小再 64 个，光这两组就要 128 个。加上 scale 值、循环变量、地址指针、谓词寄存器等控制开销，总量来到 232（1d2d）或 248（1d1d，因为 SFB 也要在寄存器里做索引）。BN 更大时 kNumAccum 线性增长，上限受 SM90 每线程 255 寄存器硬限制约束。生产者那边，24–40 个寄存器够放一组 TMA 描述符地址加循环计数器，展开流水线时降到 24 是因为完全展开后循环变量被消除。

生产者这 128 个线程里真正干活的更少。cute::elect_one_sync() 在一个 warp 里选出一个线程，整个 CTA 的 TMA 都由它发射。TMA（Tensor Memory Accelerator）是 Hopper 的异步拷贝引擎：一个线程提交一次描述符 + 坐标，硬件自己把一个多维块搬进共享内存 [3]。几个 warp 的职责被分得很细：

  • warp kNumMathThreads/32：开头 prefetch 四五个 TMA 描述符，之后在 1d1d 里负责发全部 TMA。
  • warp kNumMathThreads/32 + 1：初始化 mbarrier，然后调 fence_barrier_init() 让异步代理看到初始化结果。
  • 1d2d 里发 TMA 的是 warp kNumMathThreads/32 + 2，注释写明了理由：BLOCK_M == 32 时 warp 0/1 可能还在做 WGMMA（sm90_fp8_gemm_1d2d.cuh 第 169–171 行）。

流水线只有两组 mbarrier 和一个相位位

生产者和消费者之间是一个 S 级的环形缓冲。共享内存被切成 S 份，每份放一个 stage 的 A tile、B tile 和 scale；同步完全靠两组 mbarrier（硬件支持的共享内存屏障对象，可以计数到达次数，也可以计数异步拷贝的字节数）：

#pragma unroll
for (uint32_t i = 0; i < kNumStages; ++ i) {
    full_barriers[i]->init(1);
    empty_barriers[i]->init(kNumTMAMulticast * kNumMathThreads / 32);
}

源码：sm90_fp8_gemm_1d1d.cuh 第 136–140 行。

两个计数值各有来头。full_barriers[i]->init(1)：一个 stage 的“数据到齐”只需要一次到达，因为它是 ClusterTransactionBarrier——生产者用 arrive_and_expect_tx(字节数) 声明这一拍要搬多少字节，硬件在最后一个字节落地时自动触发。empty_barriers[i]->init(kNumTMAMulticast * kNumMathThreads / 32)：一个 stage 被“用完”要等每个数学 warp 都报到一次，cluster 里每个 CTA 都要算一份，所以是 warp 数乘以多播数。生产者循环因此只有四步：

for (uint32_t k_block_idx = 0; k_block_idx < num_k_blocks; ++ k_block_idx) {
    // Wait consumer release
    CUTE_TIE_DECL(get_pipeline(iter_idx ++), stage_idx, phase);
    empty_barriers[stage_idx]->wait(phase ^ 1);
    // ...
    tma::copy<BLOCK_M, BLOCK_K, 0>(&tensor_map_sfa, &full_barrier, smem_sfa[stage_idx], m_idx, sf_k_idx, num_tma_multicast_a);
    // ...
    full_barrier.arrive_and_expect_tx(SMEM_A_SIZE_PER_STAGE + SMEM_B_SIZE_PER_STAGE + SMEM_SFA_SIZE_PER_STAGE + SMEM_SFB_SIZE_PER_STAGE);
}

源码：sm90_fp8_gemm_1d1d.cuh 第 220–236 行（节选，省略三个 tma::copy 与地址计算）。

等 empty、发 TMA、声明字节数，然后下一拍。四个 tma::copy（SFA、SFB、A、B）共用同一个 full barrier，字节数一次性声明，所以消费者等到的是“这个 stage 的四样东西全齐了”。get_pipeline(iter_idx) 返回 {iter_idx % kNumStages, (iter_idx / kNumStages) & 1}：stage 下标和一个相位位。mbarrier 的等待是按相位的——同一个 barrier 对象被反复使用，用一个翻转的比特区分“这一轮”和“上一轮”，生产者等 phase ^ 1、消费者等 phase。1d2d 用的是等价的写法：一个 advance_pipeline 闭包在回绕到 stage 0 时翻转 phase。

两个内核都在 barrier 初始化后、进入主循环前调了 cudaGridDependencySynchronize()，这是 PDL（Programmatic Dependent Launch）的等待点：前一个内核还没写完的数据，要在这里等齐。PDL 的开关见第 5 篇。

S 是算出来的，不是调出来的。启发式按“共享内存总量减去固定开销，除以每 stage 的开销”取整，上限 16（heuristics/sm90.hpp 第 148–188 行）。代入一组具体数字：SM90 的可用共享内存在代码里写死为 232448 字节（第 14 行），取 BM = BN = 128、BF16 输出的 1d2d 内核，固定开销是 D 的缓冲 \( 128\times128\times2 \) 对齐到 1024 得 32768 字节、16 级 barrier 预留 256 字节、SFB 的 \( \lceil 7168/128 \rceil \times 4 = 224 \) 字节（K = 7168），每 stage 则是 A 的 16384 + B 的 16384 + SFA 的 512 = 33280 字节。于是 \( S = \lfloor (232448 - 33248)/33280 \rfloor = 5 \)。同样的块大小换成 1d1d，D 的缓冲变成 FP32 的 65536 字节、每 stage 多出 SFB 的 512 字节，\( S \) 掉到 4。启发式还要求 S ≥ 3（小块要求 ≥ 4），否则这个候选配置直接被丢掉。

最后是多播。当启发式选了 cluster（两个 CTA 绑在一起调度）时，两个 CTA 往往要读同一块 A 或同一块 B。TMA 的多播让一次拷贝同时落进 cluster 内多个 CTA 的共享内存：在 copy_nd 里，多播数大于 1 时只有 cute::block_rank_in_cluster() == 0 的 CTA 发射，掩码是 (1 << num_tma_multicast) - 1（common/tma_copy.cuh 第 77–87 行）。多播方向由 kIsTMAMulticastOnA = cluster_n > 1 决定，调度器还要检查这一行/列是否真的成对（is_tma_multicast_valid），落单的块退回单播。

什么时候启发式会选择用 cluster（从而开启多播）？关键条件在 heuristics/sm90.hpp：只有当 tile 数量足够多（grid size ≥ SM 数的两倍）并且 N 维有至少两块时，才会把 cluster_n 设成 2。这是因为 cluster 把两个 CTA 绑在相邻 SM 上调度，如果 tile 数本来就不够填满所有 SM，cluster 反而限制了调度灵活性。完整的候选筛选规则留给第 5 篇。图 4 把这两件事画在一起。

尾声分两条路：BF16 写回与 FP32 原子累加

一个 tile 的 K 维走完后，final_accum 里是这个 tile 的最终结果，要落到全局内存。两个内核在这里彻底分道。

1d2d 输出 BF16。它先把 FP32 寄存器两两转成 nv_bfloat162，用 STSM（stmatrix，一条把寄存器里的矩阵片段写进共享内存的指令）写进 smem_d，再由少数线程发 SM90_TMA_STORE_2D（batched 时是 3D）。写进共享内存的地址要按 TMA 的 swizzle 模式逐位算出来，那段代码的注释写着“think twice before modifying this”，因为改动会影响指令数（第 383–418 行）；随后 tma_store_fence() 加一个 named barrier，确保共享内存的内容对异步代理可见。

1d1d 输出 FP32，走的是另一条：

// Use TMA store to write back to global memory
if (warp_idx % 4 == 0 and cute::elect_one_sync()) {
    cute::SM90_TMA_REDUCE_ADD_2D::copy(
        &tensor_map_cd, smem_d_0, n_block_idx * BLOCK_N,
        current_group_idx * shape_m + m_block_idx * BLOCK_M + r_0);
    cute::tma_store_arrive();
}

源码：sm90_fp8_gemm_1d1d.cuh 第 344–350 行。

这里没有 STSM——FP32 结果直接用 st.shared 以 float2 写进共享内存——也没有普通的 store，而是 REDUCE_ADD：TMA 把共享内存里的块加到全局内存上。这解释了启发式里那条看起来很奇怪的规则——1d1d 的 store block M 固定为 WGMMA 的 64，注释写着“1D1D kernel will do single warp-group stores”（heuristics/sm90.hpp 第 126–131 行）：每个数学 warpgroup 独立把自己那 64 行加回去，不需要先在共享内存里拼成完整的 BM × BN。另外 1d1d 的 BLOCK_N 候选里特意加了 16 和 24（heuristics/sm90.hpp 第 42–48 行），注释说是为了避开 FP32 输出的 bank 冲突。

两个内核的调度器是同一个：grid 大小等于 SM 数，每个 CTA 在 while (scheduler.get_next_block(...)) 里持续领取 tile（持久化内核），tile 的遍历顺序按 L2 复用做了分组交错。这部分留给第 4 篇，那里还要讲 M 分组、masked 和 K 分组三种布局怎样复用同一个调度器。

局限与未覆盖

  • 没有性能数据。本地没有 GPU，本文不含任何实测。仓库 README 的 News 里有一条“up to 1550 TFLOPS on H800”（README 第 25 行），那是 2025 年 4 月一批优化之后的整体宣称，不是本文两个内核在某个具体形状下的测量值，也不对应本文任何一段代码。图 1 是 CPU 上的 NumPy 模拟，不是内核实测。
  • 两级累加的动机是引用，不是本仓库的结论。“张量核累加精度有限”这一条来自 DeepSeek-V3 技术报告 [2]；本仓库代码只能证实“每 128 个 K 做一次带 scale 的 FP32 promotion”这个事实。图 1(b) 模拟的是算术，参数 b 不对应任何硬件寄存器。
  • CUTLASS 子模块未检出。warpgroup_reg_alloc、ClusterTransactionBarrier、SM90_TMA_*、MMA_64xNx32_F32E4M3E4M3_SS_TN 的实现都在 CUTLASS/CuTe 里，本文只能描述 DeepGEMM 对它们的调用方式和参数，无法给出这些符号的源码链接。“setmaxnreg”“WGMMA 异步、按相位等待”等说法基于 PTX ISA 文档 [3] 与 CUTLASS 的接口语义 [4]，不是本仓库代码里的文字。
  • 启发式只讲到够用。stage 数、BLOCK_N 候选、多播开关的完整规则（包括 num_cycles 那个 L1/L2 周期模型）属于第 5 篇。本文代入的 S = 5 / S = 4 是按公式手算的，没有在 GPU 上验证过选中的配置。
  • 一个未解的疑点。启发式在 m <= 16/32 时会把 BLOCK_M = 16/32 加入候选（heuristics/sm90.hpp 第 23–26 行），而 1d1d 内核静态断言 BLOCK_M % WGMMA::M == 0（WGMMA::M = 64）。1d2d 的断言允许 BLOCK_M < WGMMA::M，1d1d 的不允许。这两处是否真会撞上（取决于 FP32 输出路径下的候选筛选与实际调用形状），我们没有 GPU 可以验证，也没有在仓库里找到相关说明。
  • 没讲的部分：SFA 的 MN-major、TMA 对齐布局怎么来的（第 3 篇）、K 分组内核里 tensormap 在运行时被改写的那段（tensor_map_replace_global_addr_in_smem）、以及 1d2d 的 swizzle 地址计算逐位推导。
