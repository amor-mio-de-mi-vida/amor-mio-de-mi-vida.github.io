TL;DR

  • combine 是 dispatch 的逆操作：读取 dispatch 时保存的 metadata，把 MoE 计算后的 BF16 结果送回源 rank 并归约——token 记录只包含 hidden 和 topk_weights，不携带缩放因子。
  • 归约核心 combine_reduce 有两条路径：当无 bias 且有效 top-k 槽位不超过 2 时，用 nv_bfloat162 直接相加（快路径）；否则走 FP32 累加再转回 BF16（通用路径）。
  • combine 只接受 BF16 输入——这不是偶然限制，而是因为 MoE 专家的输出精度是 BF16，combine 通路不需要搬运 FP8 缩放因子。
  • 归约尾声通过 PDL 接力，对每个原始 token 从各对端缓冲区读取、去重、归约，并能在归约中融合最多两个 bias 张量，避免一次额外的全量读写。

前置知识

了解 dispatch 的数据流和 handle 机制（ep02）。本篇新引入：BF16 快路径归约、FP32 通用归约、bias 融合、combine 与 dispatch 互为转置。

combine 在 MoE 流水线中的角色

上一篇讲了 dispatch 如何把 token 按 top-k 选择发送到拥有对应专家的 rank。MoE 专家计算完成后，结果需要沿 top-k 维度归约并送回源 rank——这就是 combine 的任务。

具体地说，combine 需要做两件事：

  1. 通信：把本 rank 专家计算的结果，按 dispatch 时记录的 src_metadata（源 token 全局索引 + 源 rank/topk 索引），发送到对端的接收缓冲区。
  2. 归约：在接收端，对同一原始 token 的多个 top-k 结果求和（可能附带 gate 权重加权），得到最终的合并输出。

从通信量角度看，combine 的 per-token 记录略小于 dispatch——以 hidden = 7168、FP8、k = 8 为例，dispatch 记录约 7488 字节（hidden + SF + 全部 metadata，对齐后），combine 记录约 7200 字节（hidden + topk_weights，对齐后），差距约 4%。但 combine 的计算量更大——它需要做归约（求和或加权求和），而 dispatch 的发送 warp 只做数据搬运不做计算。这也是为什么 combine 把归约逻辑拆成两个内核，而 dispatch 的拷贝尾声只做展开和填零。注意：如果 dispatch 走 BF16（hidden 翻倍到 14336 字节），dispatch 的记录反而比 combine 更大（约 14464 vs 14400 字节），因为 BF16 dispatch 仍然携带完整的 metadata。

和 dispatch 一样，combine 也分成两个依次执行的内核：

  • combine_impl——主内核。读取 MoE 输出和 dispatch 保存的 metadata，把数据发送到对端缓冲区。
  • combine_reduce_epilogue_impl——归约尾声。通过 PDL 接力，从缓冲区读取各对端发来的数据，做归约（可选融合 bias），写出最终结果。
ep01 提到 dispatch 的反向就是 combine、combine 的反向就是 dispatch。这在代码层面体现为：combine 的 topk_weights 参数只在反向传播时非空——它用来把梯度按 gate 权重加权分回各 top-k 分支。

但 combine 的通信量比 dispatch 小得多。dispatch 的 token 记录包含 hidden + SF + 全部 metadata（topk 索引、权重、源位置、链表）；combine 的 token 记录只有 hidden + topk_weights。我们从 get_combine_token_layout 可以直接看到这个差异：

static layout::TokenLayout get_combine_token_layout(
    const int& hidden, const int& elem_size, const int& num_topk) {
    return layout::TokenLayout(hidden * elem_size, 0, num_topk, false);
}

SF 字节数为 0，with_metadata = false——combine 不搬运缩放因子，也不需要记录源位置（因为它就是在往源位置发数据）。

combine_impl 的三种发送模式

如图 1 所示，combine_impl 遍历 dispatch 接收到的每个 token（即本 rank 参与 MoE 计算的 token），根据展开模式和归约策略选择三种发送模式之一。

模式一：不归约（单槽位）

当展开布局中某个 token 只有一个有效的 top-k 槽位时，不需要归约——直接用 TMA load 把该槽位的 hidden 搬到 smem，再 TMA store 到对端缓冲区。这是最快的路径。

模式二：本地归约

当 kAllowMultipleReduction = true 且有多个有效槽位时，先在本地做归约再发送。代码调用 compute_topk_slots 把有效的 top-k 索引排到数组前部，然后调用 combine_reduce 把多个 BF16 向量归约到 smem 的 TMA 缓冲区里，最后 TMA store 发出。这减少了通信量——发一份归约后的结果，而不是多份原始数据。

模式三：展开全发（expanded send）

当不允许多次归约时（kAllowMultipleReduction = false 且使用展开布局），每个 top-k 槽位的数据分别发送到对端缓冲区的不同位置。归约完全推迟到归约尾声。这种模式下 topk_weights 一定为空（代码中有 EP_DEVICE_ASSERT(topk_weights == nullptr)），因为前向传播不需要加权。

三种模式之后，如果 topk_weights 非空（反向传播），则把权重写到对端缓冲区的 topk_weights 字段。这些权重是 gate 网络输出的 FP32 值，每个 top-k 槽位一个标量，相比 hidden 向量的通信开销可以忽略（8 个 float = 32 字节 vs hidden 的 14336 字节）。最后，对于 RDMA 路径，还需要等待本地 send buffer 的 TMA store 完成后发起 gin.put。

三种模式选定"怎么归约"后，实际的传输路径由网络拓扑决定，逻辑与 dispatch 完全一致：如果目标 rank 是 NVLink 可达的（gin.is_nvlink_accessible），TMA store 直写对端缓冲区，延迟最低；否则先 TMA store 到本地 send buffer，再 gin.put 发起 RDMA 写。混合模式下，节点内走 NVLink，节点间走 RDMA，同一个 token 的不同 top-k 目标可能走不同路径。代码中的分支是编译期常量 kIsScaleupNVLink 加运行时的 dst_ptr != nullptr 检查——NVLink 路径通过 gin.get_sym_ptr 返回非空的对称内存指针，RDMA 路径返回空指针跳过 NVLink store 改走 gin.put。

rank 布局 vs topk 布局

缓冲区的索引维度由 use_rank_layout 在编译期决定：


template <bool kAllowMultipleReduction, int kNumRanks, int kNumTopk>
constexpr bool use_rank_layout() {
    if constexpr (not kAllowMultipleReduction)
        return false;
    return kNumRanks <= kNumTopk;
}

template <bool kAllowMultipleReduction, int kNumRanks, int kNumTopk>
constexpr int get_num_tokens_in_layout() {
    return use_rank_layout<kAllowMultipleReduction, kNumRanks, kNumTopk>() ? kNumRanks : kNumTopk;

源码：deep_ep/include/deep_ep/impls/ep/combine_utils.cuh 第 7–17 行（布局选择逻辑）

当 kAllowMultipleReduction 为真且 rank 数量 \(R \leq k\)（top-k 值）时，使用 rank 索引布局——缓冲区按 rank 维度切分，每个 rank 在缓冲区中占一个槽位。这适用于 rank 数较少的场景（如 8 GPU 节点内做 NVLink 直连），因为每个 rank 可能持有该 token 的多个专家结果，在 combine_impl 中先本地归约再发送（模式二），接收端只需遍历 \(R\) 个槽位。

当 \(R > k\) 时切换到 topk 索引布局——缓冲区按 top-k 维度切分，每个 top-k 槽位占一个位置。此时 rank 数多于 top-k 数，如果按 rank 索引，大部分槽位是空的（一个 token 最多被 k 个 rank 持有）；按 topk 索引更紧凑，归约尾声只需遍历 \(k\) 个槽位。get_num_tokens_in_layout 根据选择返回 \(R\) 或 \(k\)，决定了 BufferLayout 的第一维大小。

combine_reduce 的双路径归约

combine_reduce 是 combine 的计算核心（图 2）。它把多个 BF16 向量（来自不同的 top-k 槽位或不同的 rank）归约到一个目标向量。归约有两条路径，在运行时根据条件选择。

BF16 直加快路径（hadd bypass）

// We use BF16 add as much as possible, as casting is slow
const bool enable_hadd_bypass =
    (bias_0 == nullptr and bias_1 == nullptr) and
    (kNumValidTopk <= 2 or topk_slot_idx[2] < 0);
EP_STATIC_ASSERT(kNumValidTopk > 0, "Invalid top-k");

if (enable_hadd_bypass) {
// ...
    for (int i = 0; i < kHiddenVec / (kUnrollFactor * 32); ++ i) {
        // Read values 0
        const auto slot_0 = topk_slot_idx[0];
        const auto src_base_ptr_0 = get_src_buffer_ptr_func(slot_0);
        vec_t values_0[kUnrollFactor] = {};
        #pragma unroll
        for (int j = 0; j < kUnrollFactor; ++ j) {
            values_0[j] = ptx::ldg_with_ge_pred(
                src_base_ptr_0 + (i * (kUnrollFactor * 32) + j * 32 + lane_idx), slot_0, 0);
        }
// ...
        // Wait buffer releases for the first write
        if (i == 0)
            wait_buffer_func();

        // Reduce into shared memory
        const auto bf162_view_0 = reinterpret_cast<nv_bfloat162*>(values_0);
        const auto bf162_view_1 = reinterpret_cast<nv_bfloat162*>(values_1);
        #pragma unroll
        for (int j = 0; j < kUnrollFactor; ++ j) {
            #pragma unroll
            for (int l = 0; l < kNumElemsPerVec / 2; ++ l)
                bf162_view_0[j * (kNumElemsPerVec / 2) + l] += bf162_view_1[j * (kNumElemsPerVec / 2) + l];
            dst_buffer_ptr[i * (kUnrollFactor * 32) + j * 32 + lane_idx] = values_0[j];
        }
    }

源码：deep_ep/include/deep_ep/impls/ep/combine_utils.cuh 第 67–110 行（节选）

快路径的条件是 enable_hadd_bypass：没有 bias，且有效 top-k 槽位不超过 2（即 topk_slot_idx[2] < 0，意味着第三个槽位无效）。为什么限制在 2 个？BF16 直加只做一次 A + B，结果精度等价于 FP32 加法再截断到 BF16。但如果有 3 个或更多槽位，需要做 (A + B) + C——前一步的 BF16 截断误差会参与下一步的加法，形成误差累积。FP32 累加路径则把所有加法都在 FP32 精度下完成，最后才截断一次，精度更好。所以 2 个槽位是快路径和通用路径在精度上等价的边界。满足时，只需要读两个 BF16 向量，用 nv_bfloat162 的加法直接相加写入 smem——全程不做 BF16→FP32→BF16 的类型转换，节省了转换指令的开销。从指令数角度看，BF16 直加只需 1 条 hadd，而 FP32 累加路径至少需要 3 条指令（BF16→FP32 转换、FP32 加法、FP32→BF16 转换），因此快路径在指令发射上有明显优势。

代码结构是标准的向量化加载模式：每个 lane 处理一个 int4（16 字节 = 8 个 BF16 元素），通过 kUnrollFactor 展开内层循环。ptx::ldg_with_ge_pred 是条件加载——当 slot_idx < 0 时返回全零，避免了分支。

FP32 累加路径

} else {

    for (int i = 0; i < kHiddenVec / (kUnrollFactor * 32); ++ i) {
        // Add bias
        float2 reduced[kUnrollFactor * kNumElemsPerVec / 2] = {};

        #pragma unroll

                values[j] = ptx::ldg_with_ge_pred(

            }

            // Reduce
            const auto bf162_view = reinterpret_cast<nv_bfloat162*>(values);
            #pragma unroll
            for (int j = 0; j < kUnrollFactor * kNumElemsPerVec / 2; ++ j)
                ptx::accumulate(reduced[j], bf162_view[j]);
        }
// ...
        // Cast into shared memory
        #pragma unroll
        for (int j = 0; j < kUnrollFactor; ++ j) {
            vec_t casted_value;
            auto bf162_view = reinterpret_cast<nv_bfloat162*>(&casted_value);
            #pragma unroll
            for (int l = 0; l < kNumElemsPerVec / 2; ++ l)
                bf162_view[l] = __float22bfloat162_rn(reduced[j * (kNumElemsPerVec / 2) + l]);
            dst_buffer_ptr[i * (kUnrollFactor * 32) + j * 32 + lane_idx] = casted_value;
        }
    }

源码：deep_ep/include/deep_ep/impls/ep/combine_utils.cuh 第 111–168 行（节选）

通用路径用 float2 累加器 reduced[]。如果有 bias，先通过 add_bias lambda 把 bias 向量累加进来（ptx::accumulate 是 BF16→FP32 的融合加法，在 SM100 上编译为 add.rn.f32.bf16）。然后逐 top-k 槽位加载 BF16 向量，同样用 ptx::accumulate 累加。最后用 __float22bfloat162_rn 转回 BF16 写入 smem。

两条路径最终都把结果写到 dst_buffer_ptr（smem 中的 TMA 缓冲区），后续由 TMA store 搬到全局内存或对端。

向量类型选择

CombineVecTraits 决定了每次加载/存储的粒度：

    // On SM100+, use `longlong4_t` (32 bytes) if hidden is aligned, otherwise fall back to `int4` (16 bytes)
    // NOTES: we observe some performance degrade with `longlong4_t`, temporarily disable it
    static constexpr bool kUseLonglong4 = false;
    using vec_t = std::conditional_t<kUseLonglong4, longlong4_t, int4>;

    using vec_t = int4;
#endif
};

为什么 combine 只走 BF16

combine 对输入类型有一个硬断言：

EP_HOST_ASSERT(x.is_cuda() and x.is_contiguous());
EP_HOST_ASSERT(x.scalar_type() == torch::kBFloat16);
EP_HOST_ASSERT((x.size(1) * x.element_size()) % sizeof(int4) == 0);

源码：csrc/buffers/ep.hpp 第 814–817 行（节选）

这不仅仅是当前实现的局限——它反映了 MoE 流水线的数据流设计：

  1. MoE 专家输出 BF16：无论 dispatch 发送的是 FP8 还是 BF16，专家内部的计算（GEMM + 激活）输出的是 BF16。所以 combine 的输入天然就是 BF16。
  2. 不需要搬运 SF：既然输入已经是 BF16，就不存在缩放因子需要传输。这就是为什么 get_combine_token_layout 把 SF 字节数设为 0。
  3. 归约精度足够：BF16 的 top-k 归约（典型 k=2 到 8）的精度损失可以接受。快路径直接用 BF16 加法（hadd），通用路径提升到 FP32 再转回——两者的最终输出都是 BF16。从硬件角度看，FP8（E4M3/E5M2）在 GPU 上没有标量加法指令——它只出现在张量核的乘加流水线中。如果要对 FP8 做归约，必须先转为 BF16 或 FP32 再相加，等于白白多一层转换。而 BF16 有原生的 hadd 和 hadd2 指令，归约路径可以直接在 BF16 上操作。
  4. 通信量更小：combine 的 token 记录比 dispatch 小得多。以 hidden = 7168、k = 8 为例，dispatch 的记录约 7360B（hidden + SF + metadata，对齐后），combine 的记录约 7200B（hidden + topk_weights，对齐后）——省掉了 SF 和源 metadata 的传输。

如果未来需要支持 FP8 combine（例如在专家输出端做量化），就需要把 SF 加回 token 记录并修改归约逻辑——代码注释中 launch_combine 里有一句"we don't use num_hidden_bytes due to enable later quantization possibility"，暗示这个扩展在设计考虑之内。

在归约中插入 bias

combine_reduce_epilogue 能在归约中融合最多两个 bias 张量（bias_0 和 bias_1），避免一次额外的逐元素 kernel launch。这两个 bias 是可选参数，在 Python 端调用 combine() 时传入。

bias 的约束在 host 端检查：必须是 2 维、CUDA 连续的 BF16 张量，形状 [num_combined_tokens, hidden]，与输入 x 同 dtype 同形。

在 combine_reduce 中，bias 的融合位置是归约循环之前：

  • 如果 bias_0 != nullptr，先把 bias_0 向量读入 float2 reduced[] 累加器。
  • 如果 bias_1 != nullptr，再累加 bias_1。
  • 然后开始逐 top-k 槽位的归约累加。

这意味着 bias 只加一次——不是每个 top-k 槽位都加。这在数学上等价于 \(\text{output} = \text{bias}_0 + \text{bias}_1 + \sum_{k} \text{expert\_output}_k\)。

注意：有 bias 时必定走 FP32 累加路径，因为 enable_hadd_bypass 的条件之一是 bias_0 == nullptr and bias_1 == nullptr。

两个 bias 槽位的设计动机在源码中没有注释说明。推测可能是为了在 MoE 归约后融合多个残差项（如共享专家输出与主路径残差）——但这只是推测，具体用途取决于上层训练框架的接口约定。从性能角度看，在归约中融合 bias 的好处是显而易见的：如果 bias 在归约之后单独做逐元素加法，需要额外一次对整个 [num_combined_tokens, hidden] 张量的全局内存读写——对 hidden = 7168、BF16 精度、4096 个 token 而言，这是约 56 MiB 的额外 HBM 流量。融合之后，bias 在归约循环里顺便加进去，不产生任何额外的内存事务。

融合 bias 还有一个精度上的影响：因为 bias 先被读入 FP32 累加器，所以 bias 与归约结果的加法在 FP32 精度下进行，最后才转回 BF16。如果 bias 单独做逐元素 BF16 加法，精度会稍差——尤其当 bias 值与归约结果在数量级上有较大差异时，BF16 的 7 位尾数可能无法保留足够的精度。因此融合不仅省了一次 HBM 往返，还顺便提高了精度。

combine_reduce_epilogue：去重、归约与输出

归约尾声（combine_reduce_epilogue_impl，图 3）遍历每个原始 token（num_combined_tokens 个），从各对端写入的缓冲区中读取数据、归约、写出。和 dispatch 尾声一样，它通过 PDL 启动（enable_pdl = true），用 cudaGridDependencySynchronize 等待主内核完成。

归约尾声的内核签名包含大量编译期参数——rank 数、top-k 值、hidden 维度等全部在模板中固化。内核启动前通过 cudaGridDependencySynchronize 等待主内核完成——这是 PDL（Programmatic Dependent Launch）的核心机制：归约尾声由前一个 combine_impl 的 cudaTriggerProgrammaticLaunchCompletion 触发，GPU 调度器自动在主内核退出后启动尾声，省掉了 CPU 端的同步和重新提交开销。

// Utils

值得一提的是归约尾声的启动模型。combine_reduce_epilogue_impl 通过 PDL 由 combine_impl 触发——主内核在所有 token 发送完成、全局屏障通过后调用 cudaTriggerProgrammaticLaunchCompletion。PDL 的核心优势是省掉了 CPU 端的同步：传统模式下 CPU 需要等主内核结束（cudaEventSynchronize 或流回调）后再提交尾声内核，PDL 让 GPU 调度器在主内核完成后自动启动尾声，中间没有 CPU 往返的延迟——对于大规模通信密集的 MoE 推理，这可以节省数十微秒的 CPU 调度开销。

warp 分配采用 SM 优先的交错模式：global_warp_idx = warp_idx * kNumSMs + sm_idx——先铺满所有 SM 各一个 warp，再回来给每个 SM 第二个 warp，以此类推。这保证了尾波（最后一批 token）尽可能均匀分布在所有 SM 上，而不是集中在少数 SM 上造成长尾。源码注释明确写道："Here we prioritize distributing tasks to different SMs to ensure that the last wave is evenly concentrated on each SM"——这对尾延迟至关重要，因为如果最后一波只落在少数 SM 上，其余上百个 SM 就全在空等。SM 优先索引把尾波均匀打散，使每个 SM 只多做一个 token 的归约，极大减少了 tail latency。

每个 warp 处理一个完整 token 的归约：从各对端缓冲区读取 hidden 数据，调用 combine_reduce，再把结果通过 TMA store 写到 combined_x 输出张量。值得注意的是，归约尾声的共享内存布局与 dispatch 尾声不同：这里 smem 按 warp 数量切分（每个 warp 占一个 TMA 缓冲区），而不是像 dispatch 那样按完整 token 记录切分。这是因为归约尾声每次只输出一个 token 的 hidden（不需要搬运缩放因子和 metadata），单个缓冲区远小于 dispatch 的完整记录，所以可以给更多 warp 各分一个独立的缓冲区，提高并行度。

对每个 token 的处理分几步：

for (int token_idx = global_warp_idx; token_idx < num_combined_tokens; token_idx += kNumWarps * kNumSMs) {
    // Preprocess all indices
// ...
    const auto [should_deduplicate, deduplicate_key] = [&]() -> std::pair<bool, int> {
        if constexpr (kUseExpandedLayout and not kAllowMultipleReduction) {
            // Activations are never reduced before
            return {false, 0};
        } else if constexpr (kNumScaleoutRanks != 1 and not kUseExpandedLayout and not kAllowMultipleReduction) {
            // Hybrid mode without expanded layout and multiple reduction. Should deduplicate on a per-rank basis
            return {true, stored_dst_expert_idx >= 0 ? stored_dst_expert_idx / kNumExpertsPerRank : -1};
        } else {
            // Should deduplicate on a per-rank (for non-hybrid mode) or a per-scale-rank (for hybrid mode) basis
            return {true, stored_dst_rank_idx};
        }
    }();
    auto reduce_valid_mask = should_deduplicate ?
        ptx::gather(ptx::deduplicate(deduplicate_key, lane_idx) and stored_dst_rank_idx >= 0) :
        ptx::gather(stored_dst_rank_idx >= 0);
    int topk_slot_idx[kNumTokensInLayout];
    compute_topk_slots(
        topk_slot_idx, reduce_valid_mask,
        [=](const int& idx) {
            return kUseRankLayout ? ptx::exchange(stored_dst_rank_idx, idx) : idx;
        }
    );
// ...
    combine_reduce<kHiddenVec, kUnrollFactor, kNumTokensInLayout>(
        lane_idx, topk_slot_idx, static_cast<combine_vec_t*>(tma_buffer.get_base_ptr()),
        /* Get source base */ [=](const int& slot_idx) {
            return static_cast<combine_vec_t*>(
                comm_buffer.get_rank_buffer(slot_idx).get_token_buffer(token_idx).get_base_ptr());
        },
        /* Wait buffer release */ [=]() {
            ptx::tma_store_wait();
            __syncwarp();
        },
        /* Bias 0 */ bias_0 == nullptr ?
            nullptr : static_cast<combine_vec_t*>(bias_0_buffer.get_token_buffer(token_idx).get_base_ptr()),
        /* Bias 1 */ bias_1 == nullptr ?
            nullptr : static_cast<combine_vec_t*>(bias_1_buffer.get_token_buffer(token_idx).get_base_ptr())
    );
    ptx::tma_store_fence();

    if (ptx::elect_one_sync()) {

去重键选择

去重的目的是避免重复归约同一份数据。去重键的选择取决于模式：

  • 展开布局 + 不允许多次归约：不去重（数据从未被归约过）。
  • 混合模式 + 非展开 + 不允许多次归约：按完整 rank 索引（expert / kNumExpertsPerRank）去重。
  • 默认：按 stored_dst_rank_idx（NVLink 域内的 rank 或 RDMA 域的 scaleout rank）去重。

去重后，compute_topk_slots 用位操作把有效的槽位索引排到数组前部：遍历 mask 的每一位（__ffs 找最低位），从对应 lane 取出索引。

归约与输出

排好的槽位索引传给 combine_reduce，后者从各对端缓冲区读取 hidden 数据、做归约（可带 bias），写到 smem。然后 TMA store 把结果写到 combined_x 输出张量。这里的 TMA store 只需要一条指令就能搬完整个 hidden 向量（典型 7168 × 2 = 14336 字节），比用 warp 级的循环拷贝高效得多——TMA 引擎是独立于 SM 算力的硬件单元，发射后 warp 可以立即处理下一个 token，不需要等待写入完成。

最后，如果需要 combined_topk_weights（反向传播时），从缓冲区的 topk_weights 字段读回并写到输出。这里用了 ptx::match 和 get_master_lane_idx 来找到每个 rank 的主 lane，确保从正确的缓冲区位置读取权重。

局限与未覆盖

  • 本文只覆盖直连模式（num_scaleout_ranks == 1）。混合模式（NVLink + RDMA）下的 combine 有额外的 scale-up warp 和 forward warp，转发路径更复杂，见第 4 篇。
  • topk_weights 的加权归约未覆盖：当 topk_weights 非空时（反向传播），combine_impl 会把权重写到缓冲区随数据传输，但归约尾声中没有用权重做加权求和——权重只是被读回写到输出。加权归约发生在 Python 层面还是别处，源码中没有直接证据。
  • 两个 bias 槽位的设计动机是推测：代码支持 bias_0 和 bias_1 两个独立 bias，但文中关于"可能用于融合多个残差项"是推测，不是代码注释或文档的陈述。
  • SM100 上 longlong4 回退是经验结论：CombineVecTraits 中禁用 32 字节向量的注释只说"observe some performance degrade"，没有给出具体数据或原因分析。
  • use_rank_layout 的条件未详细分析：当 \(R \leq k\) 时用 rank 索引缓冲区，否则用 topk 索引。这个切换的性能动机没有在源码中说明。
  • 通信底座和屏障细节：NCCLGin 的 put、get_sym_ptr、is_nvlink_accessible 等接口见第 5 篇。
  • 没有性能数据：本地没有 GPU，文中没有任何实测或估算的性能数字。
