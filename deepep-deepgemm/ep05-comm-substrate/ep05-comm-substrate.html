通信底座：NCCL Gin、对称内存窗口与内存序

DeepEP 的所有 EP 内核共用一套通信基础设施：NCCLGin 封装了 NCCL 的设备端 Gin API 并根据 team 类型自动选择 NVLink 直写或 RDMA 消息传递；对称内存窗口让同一 NVLink 域的 GPU 用指针直接互访；ptx.cuh 提供了从 acquire/release load/store 到 system-scope fence 的完整内存序词汇。

TL;DR

  • DeepEP 的所有 EP 内核共用一套通信基础设施：NCCLGin 封装了 NCCL 的 Gin API，暴露 put、get、signal/wait_signal、red_add_rel 等操作，并根据 team 类型自动选择 NVLink 直写或 RDMA 消息传递。
  • 对称内存窗口（nccl_window）让同一 NVLink 域的 GPU 能用指针直接读写对端内存——get_sym_ptr 返回 NVLink 映射地址，而对 RDMA 对端返回 nullptr，强制走 Gin 路径。
  • ptx.cuh 提供了完整的内存序词汇：ld_acquire_sys、st_release_sys、red_add_rel_{gpu,sys}、fence_acq_rel_sys、tma_store_fence（即 fence.proxy.async）；屏障层级从 gpu_barrier 到 nvlink_barrier 和 gin_barrier 逐层分派。

构造函数接受 nccl_dev_comm（NCCL 设备端通信句柄）、nccl_window（对称内存窗口）和 qp_idx（QP 编号）。构造时立即初始化三个 team：team_world（全局）、team_lsa（NVLink 域）、team_rail（RDMA 域），并计算本地对称内存基地址 lsa_base_ptr。

如图 1 所示，NCCLGin 暴露的 API 可以分为三类：

  • 数据搬运：put（RDMA 写入对端窗口）、put_value（写入单个值）、get（RDMA 读取对端窗口）。
  • 信号：signal（发送信号到对端的指定 slot）、wait_signal（等待某个 slot 的信号到达指定值，带超时和 trap）、flush/flush_async（刷新 QP 中的待发请求）。
  • 双路径操作：red_add_rel（原子加，NVLink 用 PTX、RDMA 用 Gin signal）、get_sym_ptr（返回对端的对称指针或 nullptr）。

所有带 team 模板参数的方法都通过编译时分派选择具体路径。例如 put<ncclTeamTagRail> 走 RDMA，put<ncclTeamTagLsa> 虽然也调用 gin.put，但实际上走的是 NVLink。这种编译时分派的好处是零运行时开销：模板实例化后每条路径的分支全部被消除，生成的 PTX 只包含对应域类型的指令序列。

值得注意的是 flush 和 flush_async 的区别：flush 是同步操作，等待 QP 中所有挂起的请求完成后才返回；flush_async 只把请求推给 NIC 但不等待完成。屏障实现中通常先 flush 所有 QP（确保数据已发出），再执行 signal/wait 协议。在流水线重叠的场景下——例如混合 dispatch 中 scale-out warp 边发送边预载入下一个 token——用的是隐式的 QP 排序语义而非显式 flush，因为同一 QP 上的请求保证按序完成。

Gin 的序保证：DeepEP 依赖的三条合约

DeepEP 内核的正确性依赖 Gin 的三条隐式序合约（handle.cuh）：

  1. 同 QP 有序交付：同一 QP 上的 put 按发射顺序到达远端。ep02–ep04 的 forward warp 因此不需要每发一个 token 就 flush——只要 tail 信号在数据之后到达即可。
  2. put + remote_action 因果性：gin.put(..., remote_action) 保证 remote_action（如 VASignalAdd 递增 tail）在数据写入对端显存之后才执行。收端看到 tail 增长时，对应的数据保证已就位。
  3. waitSignal 的 acquire 语义：gin.waitSignal(..., memory_order_acquire) 返回时，发端在 signal 之前的所有写入对等待线程可见。这与 PTX 的 ld_acquire_sys 类似但走 NIC 路径，因此能跨节点生效。

put 的实现传入了 cuda::thread_scope_thread（本地序）和 cuda::thread_scope_device（远端序）。本地 scope 为 thread 意味着 put 不对本 GPU 的其他线程提供可见性保证——如果本地线程需要依赖 put 的完成，必须显式 flush（或 flush_async + wait）。远端 scope 为 device 意味着数据到达后对远端整个 GPU 可见，不需要额外 fence。waitSignal 内部用滚动的 shadow 计数器追踪期望值：每次调用递增 shadow 并等待实际信号追上——这让 signal 可以无限复用同一 slot 而不需要重置。

red_add_rel：一个接口，两套实现

red_add_rel 是 DeepEP 通信层中最能体现"双路径"设计的函数。它的语义是"对远端某个地址做原子加，并带 release 语义"，但背后是两套完全不同的实现：

当 get_sym_ptr 返回非空指针（NVLink 可达）时，直接使用 PTX 的 red.release.gpu 或 red.release.sys 做原子加——这是纯硬件操作，延迟极低。当返回 nullptr（RDMA 对端）时，改为发 gin.signal 并附带 ncclGin_VASignalAdd 载荷——这实际上是一条 RDMA 消息，由对端的网卡固件解释执行。

gpu scope 和 sys scope 的选择也有讲究：同一 rank（dst_ptr == sym_ptr）或 Rail team 内（只有同一 rank 才 NVLink 可达）用 red.release.gpu；其他 NVLink 对端用 red.release.sys——因为跨 GPU 的 NVLink 写需要 system-scope 才能对对方 GPU 可见。这个区分不仅仅是正确性问题，还有性能影响：red.release.gpu 只需要刷新本 GPU 的 L2 写缓冲，而 red.release.sys 需要等 NVLink fabric 确认所有远端 GPU 的 L2 都已收到数据。在 8 卡 NVLink 域内，一次 sys-scope release 的延迟大约是 gpu-scope 的 3-5 倍——因此代码在可以用 gpu scope 的地方绝不多用 sys scope。

为什么不总用 Gin？

对 NVLink 对端来说，PTX 原子操作的延迟远低于 Gin 的消息传递路径（后者需要经过 QP、WQE 队列、网卡固件）。DeepEP 的策略是"NVLink 能走就走 NVLink，只在不得已时走 Gin"——put_value 也是同样的逻辑：NVLink 可达时直接 st_relaxed_sys，否则 gin.putValue。

对称内存与窗口

如图 2 所示，"对称内存"（symmetric memory）是 NCCL 提供的一种机制：同一 NVLink 域内的所有 GPU 在各自的显存中分配一块相同大小的区域，用同一个 nccl_window 句柄管理。关键操作是 ncclGetLsaPointer(window, offset, rank)：给定窗口、偏移和目标 rank，返回该 rank 对应位置的 NVLink 直通指针——GPU 可以像访问本地内存一样读写这个指针指向的位置。

NCCLGin 在此之上封装了两个操作：

  • get_sym_offset(ptr)：计算指针相对于本地 lsa_base_ptr 的偏移量。
  • get_sym_ptr<team_t>(ptr, dst_rank_idx)：核心翻译函数。

对于 ncclTeamTagRail，只有同一 rank 才返回原指针（team_rail.rank == dst_rank_idx），否则返回 nullptr——因为 RDMA rail 内没有 NVLink 连接。对于 ncclTeamTagLsa 或 ncclTeamTagWorld，先用 is_nvlink_accessible 判断，然后调用 ncclGetLsaPointer 翻译。

这就是 DeepEP 混合模式的核心抽象：所有内核只需要调用 get_sym_ptr——返回非空就可以直写，返回 nullptr 就走 gin.put 传 offset。直连模式和混合模式的数据路径差异，全部隐藏在这个分支里。

对称内存的分配与约束

对称窗口在 EPBuffer（或 BucketBuffer）的构造函数中一次性创建。Python 端先计算所需字节数（按 2 MiB 对齐，来自 calculate_ep_buffer_size），然后把 NCCL comm 句柄和字节数传给 C++ 运行时，运行时通过 NCCL 的窗口注册接口在每张 GPU 上分配等大的区域。所有 rank 必须传入相同的 num_bytes——否则 get_sym_offset 的偏移翻译会错位。分配后窗口大小不可变：如果需要更多空间，必须销毁并重建 buffer。

窗口内部由 BufferAllocator 做二级规划：它在初始化时按固定对齐粒度（get_num_allocation_alignment()）规划所有张量的偏移，然后一次性物化到窗口存储上。LB（负载均衡）区域与 EP 通信缓冲区分开计数（num_lb_bytes 是独立参数），但由同一运行时管理。这种"大块预分配 + 内部规划"设计避免了运行时动态分配的开销和碎片化，代价是必须在初始化时确定最大通信规模——num_max_tokens_per_rank 和 hidden 决定了缓冲区的上限。

is_nvlink_accessible：域判断的三条分支

get_sym_ptr 的关键前置函数是 is_nvlink_accessible。它根据 team 类型判断目标 rank 是否可以通过 NVLink 直写到达：

__device__ __forceinline__ bool is_nvlink_accessible(const int& dst_rank_idx) const {
    IS_TEAM_LSA({
        return true;
    })

    IS_TEAM_WORLD({
        // TODO(NCCL): optimize this function's cycles
        // return ncclTeamRankIsMember(team_lsa, team_world, dst_rank_idx);
        return team_rail.rank * team_lsa.nRanks <= dst_rank_idx and
               dst_rank_idx < (team_rail.rank + 1) * team_lsa.nRanks;
    })

    IS_TEAM_RAIL({
        // TODO(NCCL): some ranks may be connected by NVLink, e.g., "2 + 2 + 4"
        return team_rail.rank == dst_rank_idx;
    })
}

QP 映射与资源共享

NCCL Gin 的每个通信请求需要绑定一个 QP（Queue Pair）。get_qp_mode 函数根据 SM 数和 QP 数决定映射策略：

  • 只有 1 个 QP：所有 SM 共享，使用 NCCL_GIN_RESOURCE_SHARING_GPU（单 SM 时退化为 CTA）。
  • SM 数 ≤ QP 数：每个 SM 独占若干 QP，按 stride 分配（例如 3 个 SM 和 10 个 QP：SM 0 用 0/3/6/9，SM 1 用 1/4/7，SM 2 用 2/5/8），使用 NCCL_GIN_RESOURCE_SHARING_CTA。
  • SM 数 > QP 数：所有 SM 共享所有 QP，按全局 channel index 取模，使用 NCCL_GIN_RESOURCE_SHARING_GPU。

如果 block 里有 notify warps（kWithNotifyWarps = true），QP 0 预留给 notify warp，数据 channel 从 QP 1 开始分配。完整的映射函数展示了所有分支：

template <int kNumSMs, int kNumQPs, int kNumChannelsPerSM, bool kWithNotifyWarps = false>
__device__ __forceinline__ std::pair<int, ncclGinResourceSharingMode> get_qp_mode(
    const int& sm_idx, const int& channel_in_sm_idx, const bool& is_notify_warp = false) {
    constexpr auto kSharingCTA = NCCL_GIN_RESOURCE_SHARING_CTA;
    constexpr auto kSharingGrid = kNumSMs == 1 ? NCCL_GIN_RESOURCE_SHARING_CTA : NCCL_GIN_RESOURCE_SHARING_GPU;

    // Only one QP
    if constexpr (kNumQPs == 1)
        return {0, kSharingGrid};

    // The notify warp always use 1 SM and 1 QP
    if (is_notify_warp)
        return {0, kSharingCTA};

    // Data channels
    constexpr int kQPStartIdx = static_cast<int>(kWithNotifyWarps);
    constexpr int kNumAvailableQPs = kNumQPs - kQPStartIdx;
    if constexpr (kNumSMs <= kNumAvailableQPs) {
        // A single SM uses an entire QP
        // e.g., 3 SMs and 10 QPs
        // SM 0: 0 3 6 9
        // SM 1: 1 4 7
        // SM 2: 2 5 8
        const int num_qps_in_sm = (kNumAvailableQPs / kNumSMs) + (sm_idx < (kNumAvailableQPs % kNumSMs));
        return {kQPStartIdx + sm_idx + (channel_in_sm_idx % num_qps_in_sm) * kNumSMs, kSharingCTA};
    } else {
        // All SMs share all QPs
        const auto global_channel_idx = sm_idx * kNumChannelsPerSM + channel_in_sm_idx;
        return {kQPStartIdx + (global_channel_idx % kNumAvailableQPs), kSharingGrid};
    }
}

源码：deep_ep/include/deep_ep/comm/barrier.cuh 第 56–86 行（get_qp_mode：QP 分配的三路策略）

第 60 行值得注意：当只有 1 个 SM 时，kSharingGrid 退化为 NCCL_GIN_RESOURCE_SHARING_CTA——因为单 SM 下 GPU scope 和 CTA scope 等价，CTA scope 的同步开销更低。第 79–80 行的 stride 分配确保相邻的 channel 请求落在不同的 QP 上，避免同一 QP 上的请求排队。

QP 的数量直接影响 RDMA 的聚合带宽。每个 QP 对应网卡上的一条独立工作队列，QP 之间可以并行地向不同目标发送数据。如果只有 1 个 QP，所有 RDMA 请求串行排队，带宽受限于单条队列的吞吐。反之，QP 太多也有代价：每个 QP 在 NIC 上占用寄存器和缓冲空间，且网卡的硬件调度器在大量 QP 之间轮询的开销会增加。DeepEP 的分析式配置（第 6 篇）通过拓扑探测和带宽公式自动选择 QP 数量，目标是在网卡的队列深度限制内最大化聚合 RDMA 带宽。

每种 EP 操作（dispatch、combine、hybrid dispatch、hybrid combine）各占两个 tag（tag0 和 tag1），对应该操作在内核执行过程中的两次全局屏障点（通常是数据搬运前和归约前）。kDeviceBarrierTag 和 kKernelBarrierTag 预留给设备级和内核级的初始化屏障。标签不能复用，否则不同阶段的信号会互相干扰——这也是为什么标签按固定值硬编码而非动态分配。

屏障与内存序

如图 3 所示，DeepEP 的屏障层级从高到低：

gpu_barrier：顶层入口

gpu_barrier 是所有 EP 内核调用的顶层屏障。它先执行 tma_store_commit + tma_store_wait 确保所有 TMA store 完成，然后做 cooperative_groups::this_grid().sync() 同步所有 SM。之后根据配置把 scale-up 和 scale-out 屏障分配到不同 SM 并行执行：

  • 都需要（do_scaleup && do_scaleout）：SM 0 跑 scaleup_barrier，SM 1..N-1 跑 scaleout_barrier。代码注释说"这有点 hacky"——因为 scaleout barrier 内部会做一次 flush + grid sync，所以 SM 0 也需要额外的 grid sync 来配合。
  • 只需要一个：所有 SM 跑对应的屏障。

屏障使用预定义的 tag 区分不同调用点：kHybridDispatchTag0/1、kHybridCombineTag0/1 等，避免同一内核中不同阶段的屏障信号互相干扰。

nvlink_barrier：两阶段翻符号

工作原理：所有 rank 对同一个 signal_ptr 做 red_add_rel_sys（原子加 +1 或 -1），然后轮询等待信号值到达目标。phase 0 时加 +1 等待 N（rank 数），phase 1 时加 -1 等待 0——如此交替。counter_ptr 记录当前 phase 和 sign，每次屏障后递增。由于 counter 是 64 位无符号数，需要 2^64 / 10^6 / 3600 / 24 / 365 = 571000 年才会溢出（假设每微秒一次屏障），注释特意说明了这一点。

两阶段翻符号的设计解决了经典的"屏障复用"问题。如果只用单调递增的计数器，连续两次屏障之间可能出现"快 rank 已完成第二次屏障的写入，慢 rank 还在读第一次屏障的值"的竞态。交替加减让两次屏障使用不同的目标值（N 和 0），信号值在两次屏障之间是单调的，因此不需要额外的清零步骤。这比经典的 sense-reversing barrier 更简洁，因为它复用了同一个信号地址。

实现上还有一个细节：第 93-95 行限制只用 1 个 SM 执行 NVLink 屏障（kNumSMs > 1 and sm_idx > 0 时直接返回）。这是因为所有 rank 的屏障写入都落在同一个 signal_ptr 上——如果本地有多个 SM 同时做 red_add_rel_sys，本方 rank 会贡献多次，打破了"每个 rank 贡献 1"的语义。而 gin_barrier 中 flush 阶段则让所有 SM 并行参与（第 148-149 行），因为 flush 操作是幂等的：每个 warp flush 自己负责的 QP，不会重复。

gin_barrier：flush + signal/wait

gin_barrier 用于 RDMA 域（或 World team 的非 NVLink 部分）。它分三步：

  1. Flush 所有 QP：所有 SM 的 warp 并行地 flush 所有已分配的 QP，确保之前的 RDMA 请求都已发出。Flush 操作本身是幂等的——对同一个 QP 多次 flush 等价于一次——因此让所有 SM 都参与只会增加覆盖速度，不会产生竞态。每个 warp 按 warp_idx % num_qps 的轮转方式选择要 flush 的 QP，保证了负载均匀分配。在实践中，QP 的数量通常远少于可用 warp 数，因此大多数 warp 在每个 QP 上只做一次 flush，整个过程在几十个时钟周期内完成。这也是为什么 gin_barrier 的总延迟主要由 signal/wait 决定，而非 flush 阶段——flush 几乎总是在 signal 发出前就已经结束了。因此 flush 的代价可以视为被 signal 的网络往返延迟完全遮盖，对总体吞吐量没有可观测的影响，属于零开销的安全保障措施。
  2. World team fence：如果 team 是 ncclTeamTagWorld，额外调用 ptx::fence_acq_rel_sys()——因为 world team 的屏障可能混合 NVLink 直写和 Gin signal，在发布屏障前需要 system-scope fence 确保 NVLink 写对所有 GPU 可见。这个 fence 是 world team 独有的：LSA team 内所有操作都走 NVLink，NVLink 写入的可见性由 fence.proxy.async 保证；Rail team 内所有操作都走 Gin，Gin 的 flush 已提供了充分的 ordering。只有 World team 混用两条路径，需要一个 system-scope 的全局栅栏来统一它们的内存序。
  3. Signal/wait on QP 0：SM 0 在 QP 0 上向所有 rank 发 signal，然后 wait_signal 等待所有 rank 的信号。

ptx.cuh：内存序词汇表

common/ptx.cuh 是 DeepEP 的 PTX 内联汇编库，提供了 GPU 编程所需的全套内存序原语。按功能分类：

Fence

  • fence_acquire_gpu()：fence.acquire.gpu——确保之前的读取对当前 GPU 可见。
  • fence_acq_rel_sys()：fence.acq_rel.sys——system-scope 的完整内存屏障，用于 world team 的 gin_barrier。
  • tma_store_fence()：fence.proxy.async.shared::cta——TMA（Tensor Memory Accelerator）代理操作的 fence，确保共享内存写入对后续 TMA store 可见。TMA 的异步复制走的是与普通 load/store 不同的"代理"路径，普通的内存序指令（如 __threadfence()）不能保证对 TMA 操作可见，必须用 fence.proxy.async 这条专门的代理 fence。这是 Hopper 引入 TMA 后新增的内存序需求——在 Ampere 及以前的 cp.async 中，共享内存的 arrive/wait 机制隐含了所需的序。

Load / Store

  • ld_acquire_sys<T>(ptr)：ld.acquire.sys.L1::no_allocate——system-scope acquire load，不分配 L1 cache line。这是 forward warp 轮询 tail 的标准操作。
  • st_release_sys<T>(ptr, val)：st.release.sys——发布写入，确保之前的操作对读到此值的线程可见。
  • st_relaxed_sys<T>(ptr, val) / st_relaxed_gpu：宽松写入（no ordering），用于 put_value 的 NVLink 路径。
  • ld_volatile<T>(ptr)：ld.volatile——用于全网格归约的轮询（不需要 acquire 语义，只需要看到最新值）。

原子操作

  • red_add_rel_sys(ptr, val) / red_add_rel_gpu：red.release.{sys,gpu}.global.add——带 release 语义的原子加，是 NCCLGin::red_add_rel 的 NVLink 路径的底层实现。
  • red_add(ptr, val)：red.gpu.global.add——不带 release 的原子加，用于同一 GPU 内的全网格归约。

TMA 操作

  • tma_load_1d：cp.async.bulk.shared::cluster.global——从全局内存异步载入到共享内存，用 mbarrier 跟踪完成。
  • tma_store_1d：cp.async.bulk.global.shared::cta——从共享内存异步写入全局内存。
  • tma_store_commit / tma_store_wait<N>：提交和等待 TMA store 完成。

Warp 级原语

  • deduplicate(value, lane_idx)：用 __match_any_sync 找到所有持有相同值的 lane，只保留 highest lane——dispatch 的去重操作依赖此原语。
  • warp_inclusive_sum / warp_exclusive_sum：warp 内前缀和，用于 notify 阶段的计数聚合。
  • exchange(value, src_lane)：__shfl_sync——从指定 lane 读取值，forward warp 的 round-robin 和 slot 分配都依赖它。

超时机制

comm::timeout_while 是所有轮询操作的包装。它的实现比简单的循环多了两个关键设计：

template <int64_t kNumTimeoutCycles, typename func_t>
__device__ __forceinline__ void timeout_while(const bool& condition, const func_t& func,
                                              int64_t start_clock = 0) {
    // User may share a start clock for multiple waits
    if (start_clock == 0)
        start_clock = clock64();

    while (condition) {
        const bool timeout = clock64() - start_clock >= kNumTimeoutCycles;
        if (func(timeout))
            break;

        if (timeout) {
            // Wait another 1 second to let all threads print information and trap
            start_clock = clock64();
            while (clock64() - start_clock < kNumOneSecCycles) {}
            ptx::trap();
        }
    }
}

源码：deep_ep/include/deep_ep/comm/barrier.cuh 第 30–49 行（timeout_while：超时检测与诊断）

第 34–35 行允许调用者共享一个起始时钟——这在连续做多次 wait_signal 时很重要：如果每次 wait 都重置起始时钟，总超时就是"每次 wait 的超时之和"而非"整段等待的超时"。第 39 行的回调函数返回 true 时可以提前跳出循环（用于条件改变时的 early break）。超时后不会立即 trap，而是先等一秒（kNumOneSecCycles ≈ 2 × 10⁹，假设 GPU 时钟约 2 GHz）——这个等待让同一 grid 内所有已超时的线程都有机会 printf 出诊断信息（rank、期望值、实际值），然后才 ptx::trap() 统一终止内核。如果没有这个等待，先 trap 的线程可能导致 printf 缓冲区被截断。

超时诊断在大规模训练中至关重要。当一个 rank 挂起或网络链路出现问题时，其他 rank 的 forward warps 会在 wait_signal 处卡住，最终触发超时。诊断信息包括当前 rank 的 ID、等待的目标 rank、期望的信号值和实际读到的值——这让运维人员可以快速定位是哪条 NVLink 或 RDMA 链路出了问题。默认超时时间约 60 秒（kNumTimeoutCycles ≈ 120 × 10⁹），足够覆盖正常通信的最大延迟，又不会让故障排查等太久。
