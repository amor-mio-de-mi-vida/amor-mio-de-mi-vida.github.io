TL;DR

  • DeepGEMM 的三种 MoE 分组 GEMM 共用同一套内核；布局之间的全部差别，是一个叫 grouped_layout 的 int 张量存什么，以及调度器怎么读它。
  • contiguous 布局把所有专家的 token 拼成一条 M 轴，每段补齐到 get_mk_alignment_for_contiguous_layout()；于是一个 M 块只会落在一个专家里，内核读该块首行的专家号就能定位权重。
  • PSUM 变体只存每组一个结尾偏移，它和 DeepEP handle 里的 psum_num_recv_tokens_per_expert 是同一张表、同一套“下一组起点 = align(上一组结尾, 对齐值)”的算术。
  • masked 布局把每组的有效行数留在显存里，网格大小只取决于 SM 数而不取决于 token 数，所以整个解码步可以录进 CUDA graph。
  • 内核的网格恒等于 num_sms：每个 CTA 反复调用 get_next_block 自己推下一块，顺序按“每组 8 或 16 个主轴块”的分组主序排——在我们复现的小例子里，一波 SM 触及的 A/B 块行数从 17 降到 10。

前置知识

了解 dg01/dg02 的 GEMM 流水线，以及 ep02 的 token 路由概念。本篇新引入：contiguous/masked/K-grouped 三种布局、grouped_layout 索引表、持久化 tile 调度器（get_next_block）。

混合专家（Mixture of Experts，MoE）层的前向要对每个专家做一次矩阵乘，而每个专家收到的 token 数各不相同、每一步都在变。把它写成一个循环、逐个专家调用 GEMM，会在每次调用上付一次内核启动和一次尾波（tail wave）的代价；写成批量 GEMM 又要求每组形状相同。DeepGEMM 走第三条路：一个内核处理全部专家，并把“哪一行属于哪个专家”压缩成一个小小的整型张量交给内核自己读。

这一篇只讲这个整型张量和吃它的调度器。README 把三种形态分别叫 contiguous、masked 和 K 分组 [1]：前两种切 M 轴，用于前向与激活梯度；第三种切 K 轴，用于权重梯度。第 1 篇与第 2 篇讲过的流水线、warp 特化、UMMA 在这里原封不动；换掉的只有“下一块算什么”。

一套内核，三张索引表

先把约定立清楚。沿用 README 的记号 \( D = C + A B^\top \)：\( A \) 是 \( M \times K \) 的激活，\( B \) 是 \( N \times K \) 的权重，\( D \) 是 \( M \times N \) 的输出。MoE 里专家数记作 \( G \)，于是权重是 \( G \times N \times K \)。tile 大小记作 BM、BN、BK。

README 明确了一条设计约束：只有 M 轴被分组，N 和 K 必须固定，因为 MoE 的各个专家共享同一个形状（README 第 78 行）。这把问题缩小到“M 轴怎么切”，而三种答案对应三张表：

三张表都存进同一个参数位置。枚举 GemmType 列出全部七种（types.cuh 第 13–21 行），其中 MGroupedContiguous、MGroupedContiguousWithPsumLayout、MGroupedMasked 和两种 KGroupedContiguous 就是本文的主角；调度器是一个以 GemmType 为模板参数的结构体，所有分支都在 if constexpr 里，编译期只剩一条。

contiguous：把所有专家拼成一条 M 轴

训练前向和推理预填充时，CPU 知道每个专家收了多少 token，于是可以把它们按专家顺序拼成一个 \( \Sigma M \times K \) 的大矩阵。README 称这是 contiguous 布局，并要求“每个专家段必须对齐到 GEMM 的 M 块大小”（README 第 78 行）。

对齐值是一个全局可调的运行期常量

对齐值不是写死的 128，而是 HeuristicsRuntime 的一个字段，默认 128，可以用 set_mk_alignment_for_contiguous_layout 改；另有一个“理论最小值”查询函数，在 SM100 上固定返回 256，注释说这是因为新支持的 UMMA_N = 256 让对齐值可以固定成 256，对 MoE 的 cast、M 分组和 K 分组算子都更友好（heuristics/runtime.hpp 第 57–64 行）。

这个值同时就是 M 分组 GEMM 的 BM：SM100 的启发式对 M 分组一族直接把 block_m 设成它（sm100.hpp 第 34–46 行），SM90 的候选集也只有它一个（sm90.hpp 第 31–33 行）。“段长对齐到 BM”与“BM 等于对齐值”这两件事合起来，保证一个 M 块永远不会横跨两个专家——这是下面所有索引逻辑成立的前提。

把对齐值调大的代价是 padding 变多：三个专家各 300 / 100 / 520 行时，对齐到 128 要补到 1152 行，对齐到 256 要补到 1536 行。注释提醒 expected_m 很小的工作负载应该直接用 Mega MoE（第 8 篇）。

内核怎么知道这一块属于哪个专家

最朴素的那张表是 m_indices：长度 \( \Sigma M \)，每行一个 int，内容是该行所属的专家号，padding 行填 −1。测试里的构造代码就是这么写的（tests/generators.py 第 395–407 行）。调度器读它的地方只有一行：

} else if constexpr (kGemmType == GemmType::MGroupedContiguous) {
    const auto offset = kWithGroupOffset ? cute::max(0, grouped_layout[m_block_idx * BLOCK_M]) : 0;
    return offset * shape_dim + block_idx * block_size;

源码：scheduler/gemm.cuh 第 151–153 行（节选）

逐项读：m_block_idx * BLOCK_M 是这个 M 块的首行，因为段长对齐到 BM，首行的专家号就是整块的专家号；offset * shape_dim 把它变成一个沿 N 轴的位移。这正是 contiguous 布局的关键——偏移加在权重上，不是加在激活上。内核里 A 用全局 M 索引（kAWithGroupMNOffset 对 contiguous 为 false），而 K-major 的 B 带组偏移，于是 \( G \times N \times K \) 的权重被当成一个 \( (G \cdot N) \times K \) 的大矩阵，offset * shape_n 挑出第 offset 个专家那一段（sm100_fp8_fp4_gemm_1d1d.cuh 第 227–236 行）。

cute::max(0, ...) 处理的是整块都是 padding 的情况：此时表里是 −1，钳到 0 让 TMA 去读专家 0 的权重，地址合法；算出来的结果再由 is_computation_valid（SM90）或零填充契约（SM100）丢掉（scheduler/gemm.cuh 第 296–309 行）。同一张表还被 SM90 的 multicast 合法性检查用到：两个配对 CTA 的 M 块必须属于同一个专家，否则不能广播（第 284–290 行）。

PSUM：同一块显存，另一张表

逐行的表有一个缺点：长度正比于 token 数，而且要么 CPU 现算现拷，要么在 GPU 上写一遍。PSUM 布局把它压成每组一个数。MGroupedContiguousWithPsumLayout 的 grouped_layout 长度是 \( G \)，第 \( i \) 个元素是第 \( i \) 组有效行的结尾偏移；下一组的起点由内核自己算：\( \mathrm{align}(\text{上一组结尾}, \mathrm{BM}) \)。调度器里这段算术是这样的：

while (true) {
    // Within current group
    if (next_block_idx < (current_m_block_cumsum + num_m_blocks) * num_n_blocks)
        break;

    // Move to check the next group
    if (++ current_group_idx == kNumGroups)
        return false;

    // NOTES: `num_m_blocks` varies with the increase of the group index
    last_psum_m = math::align(current_psum_m, BLOCK_M);
    current_psum_m = grouped_layout[current_group_idx];
    current_m_block_cumsum += num_m_blocks;
    num_m_blocks = math::ceil_div(current_psum_m - last_psum_m, BLOCK_M);
}

get_swizzled_block_idx(next_block_idx - current_m_block_cumsum * num_n_blocks, m_block_idx, n_block_idx);

// NOTES: `last_psum_m` is aligned with block M
m_block_idx += last_psum_m / BLOCK_M;

源码：scheduler/gemm.cuh 第 206–225 行（PSUM 分支）

last_psum_m 是当前组的物理起点（上一组结尾对齐上去），current_psum_m - last_psum_m 是当前组的真实行数，除以 BM 向上取整就是这一组占几个 M 块。最后一行把组内 M 块号加回全局偏移——因为 last_psum_m 已经是 BM 的整数倍，这个加法是精确的。拿 图 1 的数字代进去：第 1 组的物理起点是 align(300, 128) = 384，行数 484 − 384 = 100，占 1 个 M 块；第 2 组起点 align(484, 128) = 512，行数 1032 − 512 = 520，占 5 个 M 块。

注意 PSUM 和 m_indices 描述的是同一块显存：两者的段落划分完全一致，只是一个按行记、一个按组记。host 侧的接口也只差一个开关 use_psum_layout，以及 grouped_layout 的长度校验（csrc/apis/gemm.hpp 第 212–220 行）。

这张表就是 DeepEP 递过来的那张

PSUM 不是为了省几 KB 显存才有的。DeepEP 的 dispatch 在关闭 CPU 同步时，本来就会在 GPU 上写出这样一个前缀和：

psum_num_recv_tokens_per_expert: prefix sum of alignment-padded received token counts per local
    expert, shape `[num_local_experts]`. Each expert's count is padded to `expert_alignment`.
    In non-expand mode, this is the inclusive prefix sum. In expand mode, `psum[i]` equals
    the aligned cumulative count of experts before `i` plus the actual (unaligned) token count
    of expert `i` — so `psum[i] - align(psum[i-1], expert_alignment)` recovers the real
    count for expert `i`, and `align(psum[i], expert_alignment)` gives expert `i+1`'s
    starting offset.

源码：DeepEP deep_ep/buffers/ep.py 第 47–53 行（文档字符串节选）

文档字符串里的两条算术——\( \text{psum}[i] - \mathrm{align}(\text{psum}[i-1], a) \) 是真实行数，\( \mathrm{align}(\text{psum}[i], a) \) 是下一组起点——和上面那段 CUDA 一字不差地对应。DeepEP 的 README 把这件事说得更直白：expert_alignment 应当设成分组 GEMM 的 token 对齐值，用 DeepGEMM 时就是 deep_gemm.get_mk_alignment_for_contiguous_layout()（DeepEP README 第 160 行）。换句话说，DeepEP 的展开布局（expanded layout）和 DeepGEMM 的 PSUM contiguous 布局是同一份契约的两端，中间不需要任何重排。展开布局本身的语义见第 1 篇（EP）。

masked：让 CPU 不必知道每个专家收了多少 token

解码时情况反过来：为了把整步录进 CUDA graph，CPU 不能在中途等一次设备同步来读回每个专家的 token 数。README 说得很清楚：开启 CUDA graph、CPU 不知道每个专家收到多少 token 时，提供一个 mask 张量，内核只算有效部分；一个典型用法就是拿 DeepEP 低延迟内核的输出当输入（README 第 84–86 行）。

masked 布局的 \( A \) 是 \( G \times M_\text{max} \times K \)，每组只有前 masked_m[i] 行有效；grouped_layout 就是这个长度为 \( G \) 的计数张量，它住在显存里，host 从不读。调度器按它逐组推进：

if constexpr (kGemmType == GemmType::MGroupedMasked) {
    while (true) {
        // End of the task
        if (current_group_idx == kNumGroups)
            return false;

        // Within current group
        num_m_blocks = math::ceil_div(static_cast<uint32_t>(grouped_layout[current_group_idx]), BLOCK_M);
        const auto current_m_block_cumsum = current_m_cumsum + num_m_blocks;
        if (next_block_idx < current_m_block_cumsum * num_n_blocks)
            break;

        // Move to check the next group
        current_group_idx ++, current_m_cumsum = current_m_block_cumsum;
    }

    get_swizzled_block_idx(next_block_idx - current_m_cumsum * num_n_blocks, m_block_idx, n_block_idx);

源码：scheduler/gemm.cuh 第 188–204 行（masked 分支）

和 PSUM 分支几乎同构，差别只有两处：这里的 num_m_blocks 直接由 masked_m[i] 算出（不用减去上一组结尾），而且 M 块号不加全局偏移——因为每组是独立的一片，组号另外通过 current_group_idx 送进 A、B、D 的地址计算。

为什么这能进 CUDA graph

网格大小在 host 侧就定下来了（见下一节，它恒等于 num_sms），每个 CTA 要做多少次迭代由设备上的 masked_m 决定。token 分布变了，图不用重录，只要把新的 masked_m 写进同一块显存。

那 expected_m 是什么？它不参与正确性，只参与配置选择：host 把它填进 GemmDesc 的 expected_m，启发式用“期望形状”估算波数和末波利用率，从而挑 tile 大小（sm100_fp8_fp4_gemm_1d1d.hpp 第 264–276 行）。实际的 \( M \) 比期望大很多时只会变慢，测试里直接写了这条注释（tests/test_fp8_fp4.py 第 181 行）。配置启发式怎么用这些“期望形状”，是下一篇的内容。

还有一条容易漏掉的事实：PSUM contiguous 也能吃解码场景的输入。测试的 masked 用例里有一个 use_psum_layout 开关，打开时调用的是 m_grouped_fp8_fp4_gemm_nt_contiguous(..., use_psum_layout=True, expected_m_for_psum_layout=expected_m)，输入先被 layout_masked_to_psum 压扁成一条 M 轴（tests/test_fp8_fp4.py 第 201–207 行、generators.py 第 422–432 行）。两者的区别是显存与算力的取舍：masked 要为每组预留 \( M_\text{max} \) 行，PSUM 只预留对齐后的真实总行数；代价是 PSUM 需要上游把 token 真的搬成连续的一条——而这正是 DeepEP 展开布局在做的事。

K 分组：权重梯度把收缩维切开

反向传播里权重梯度的形状是 \( \nabla W_g = X_g^\top \nabla Y_g \)：对每个专家，\( M \)（输出通道）和 \( N \)（输入通道）都固定，变的是参与收缩的 token 数。README 用一句话交代：提供 K 轴分组的 API 给 MoE 权重反向用，M 和 N 必须固定（README 第 80 行）。图 2 画出了它的物理布局：A 和 B 沿同一根 K 轴被切成 \( G \) 段，输出是 \( G \) 个互不相干的 \( M \times N \) 矩阵。

host 侧的注释把两种约定并排写了出来：

// Without PSUM layout, `grouped_layout[i]` is the padded K size of group i;
// With PSUM layout, it is the logical K end, and the group starts at `align(previous_end, k_alignment)`
const int sum_k = check_k_grouped_args(ks_cpu, grouped_layout, num_groups,
                                       use_psum_layout, k_alignment, static_cast<int>(a.first.size(0)));

源码：csrc/apis/gemm.hpp 第 344–348 行（节选）

调度器里对应的两条路径只有十来行：

CUTLASS_DEVICE void get_next_k_group() {
    if constexpr (kGemmType == GemmType::KGroupedContiguousWithPsumLayout) {
        // `grouped_layout[i]` is the psum end offset in K elements.
        const auto next_k_end = static_cast<uint32_t>(grouped_layout[current_group_idx]);
        current_k_start = math::align(current_k_end, kKAlignment);
        current_shape_k = next_k_end - current_k_start;
        current_k_end = next_k_end;
    } else {
        current_k_start += current_shape_k;
        current_shape_k = grouped_layout[current_group_idx];
    }
}

源码：scheduler/gemm.cuh 第 71–82 行

非 PSUM 路径里 grouped_layout[i] 已经是补齐后的长度，所以起点就是前缀和；PSUM 路径里它是逻辑结尾，起点要先对齐。两条路径的 current_k_start 都保证是 kKAlignment 的整数倍，而模板的静态断言要求这个对齐值是 BK（128）的整数倍（第 42–43 行），于是每组的 K 块边界都落在整块上。

缩放因子（scaling factor，SF）另走一套计数。每切换一组，调度器把 current_sf_k_cumsum 加上这一组补齐后的 K 所占的 SF 行数（第 241–243 行），因为 SF 是按组独立打包的，它的前缀和与数据的前缀和不是同一个。SF 的打包格式、以及 PSUM 空隙行怎么跳过，在第 3 篇。

三个历史提交：K 分组最容易溢出

K 分组是三种布局里最容易踩 32 位溢出的：\( \Sigma K \) 是所有专家的 token 总数，乘上 \( M \) 或 \( N \) 很快超过 \( 2^{31} \)。仓库历史里有三个相关提交（可用 git log 在本地仓库查看，它们不在本文钉住的 HEAD 上，因此不附永久链接）：

  • f63d7f2「fix: prevent int32 overflow in k-grouped GEMM size calculations (#226)」：host 侧把 sum_mk、sum_nk、sum_k 一律改成 uint64_t 再做形状断言。
  • bb4424a「Fix sum_k * shape_m overflow」：device 侧补 tensor map 全局地址时，把 sum_k * shape_m 显式 static_cast<uint64_t>。
  • 35c4bc8「fix: k_grouped_fp8_gemm_nt_contiguous crashes with n = 768 on H100 (#238)」：这条不是溢出，而是预取的 tensor map 和当前组对不上——块数少于 SM 数时调度器会跳过若干组，预取好的描述符就指向了错的组，提交里加了 prefetched_next_group_idx 来校验并在不匹配时重建当前组的描述符。

本文钉住的版本已经把 SM90 的 K 分组改成从一块显式分配的 tensor_map_buffer 里取描述符（csrc/apis/gemm.hpp 第 413–417 行），SM100 的 K 分组则走 1D1D 路径；上面三条修复的代码形态都已改变，但它们标出的两类坑——跨组的 64 位地址算术和“持久化调度器会跳过整组”——在今天的代码里依然要守。后者正是下一节的主题。

持久化调度器：网格大小只看 SM 数

所有这些分组内核的网格都是 dim3(config.launch_config.num_sms, 1, 1)，而 num_sms 来自 runtime->get_num_sms()（可被 set_num_sms 覆盖）。也就是说，一个 CTA 对应一个 SM，启动一次就不再变，tile 的数量与网格无关。把 tile 映射到迭代的只有一行：

CUTLASS_DEVICE bool get_next_block(uint32_t& m_block_idx, uint32_t& n_block_idx) {
    const auto next_block_idx = (++ current_iter) * kNumSMs + blockIdx.x;

源码：scheduler/gemm.cuh 第 185–186 行

第 \( t \) 次迭代，blockIdx.x 号 CTA 领到全局块号 \( t \cdot \text{num\_sms} + \text{blockIdx.x} \)。没有原子操作，没有共享队列：每个 CTA 都能独立算出自己的下一块。代价是分组布局下要重新扫描“这个块号落在哪一组”，于是上面那些 while (true) 循环都带着增量状态（current_group_idx、current_m_cumsum、current_k_start …），每次调用只往前推、不回退。

图 3 里还能看到两件事。其一，尾波是不均匀的：18 个块分给 8 个 SM，第 2 轮只有 2 个 SM 在干活。这就是启发式要盯着“末波利用率”的原因。其二，一次迭代里不同 SM 可能在不同的专家上（第 0 轮里 SM 6、7 已经进到专家 1），所以任何“整个 CTA 网格同时换组”的假设都不成立——35c4bc8 修的就是这类假设。

最后一点容易被忽略：持久化内核是 warp 特化的，TMA 加载 warp、UMMA warp、尾声 warp 各自跑一个独立的调度器实例，靠完全相同的递推序列保持一致，而不是靠通信。在 SM100 的 FP8 内核里能看到四处 while (scheduler.get_next_block(...))，分属不同的 warp 角色（sm100_fp8_fp4_gemm_1d1d.cuh 第 217 行等）。这也解释了为什么调度器必须是纯函数式的递推：任何一处分歧都会让生产者和消费者对不上。

分组主序：在两个候选之间选一个

有了全局块号，还要决定它映射到哪个 \( (m, n) \) tile。最朴素的映射是行主序：块号 \( b \) 对应 \( (b \div n_N,\; b \bmod n_N) \)。它的问题是，当 N 方向的块数远多于 SM 数时，同时在跑的一波 SM 会扫过 N 方向很长一段，需要同时装下很多个 B 块行，而 A 只用到一两行。DeepGEMM 改成分组主序：先沿主轴取固定的 \( g \) 个块，在这 \( g \) 列里沿次轴走完，再换下一组。

const auto primary_num_blocks = kIsMulticastOnA ? num_n_blocks : num_m_blocks;
const auto secondary_num_blocks = kIsMulticastOnA ? num_m_blocks : num_n_blocks;
const auto num_blocks_per_group = secondary_num_blocks * kNum1DBlocksPerGroup;
const auto group_idx = block_idx / num_blocks_per_group;
auto first_block_idx = group_idx * kNum1DBlocksPerGroup;
auto in_group_idx = block_idx % num_blocks_per_group;
num_blocks_in_group = min(kNum1DBlocksPerGroup, primary_num_blocks - first_block_idx);
// ...
if constexpr (kIsMulticastOnA) {
    m_block_idx = in_group_idx / num_blocks_in_group;
    n_block_idx = first_block_idx + in_group_idx % num_blocks_in_group;
} else {
    m_block_idx = first_block_idx + in_group_idx % num_blocks_in_group;
    n_block_idx = in_group_idx / num_blocks_in_group;
}

源码：scheduler/gemm.cuh 第 112–143 行（省略了 SM90 专用的 multicast 修正分支）

主轴是哪一根由 kIsMulticastOnA 决定，而它等于 cluster_n > 1（sm100_fp8_fp4_gemm_1d1d.hpp 第 74 行）：在 A 上做 multicast 时分组在 N 轴，否则分组在 M 轴。num_blocks_in_group 对最后一组做截断，所以主轴块数不是 \( g \) 的整数倍也没关系。

\( g \) 怎么定？代码里只有两个候选，而且是编译期常量：

static constexpr uint32_t get_num_1d_blocks_per_group() {
    // Select the best from candidates
    uint32_t num_best_blocks = 0, min_usage = cute::numeric_limits<uint32_t>::max();
    for (const auto candidate: {8u, 16u}) {
        const auto usage = kIsMulticastOnA ?
            candidate * BLOCK_N + math::constexpr_ceil_div(kNumSMs, candidate) * BLOCK_M: // Grouping on N
            candidate * BLOCK_M + math::constexpr_ceil_div(kNumSMs, candidate) * BLOCK_N; // Grouping on M
        if (usage < min_usage)
            min_usage = usage, num_best_blocks = candidate;
    }
    return num_best_blocks;
}

源码：scheduler/gemm.cuh 第 14–26 行

usage 就是上面说的“一波 SM 的 MN 足迹”：一组覆盖 candidate 个主轴块，一波 kNumSMs 个块就铺开 \( \lceil \text{num\_sms} / \text{candidate} \rceil \) 个次轴块，两边各乘上自己的块长相加。这是一个行数之和，不是字节数，所以它只在 A、B 元素宽度相同时才是真正的足迹代理——而分组 GEMM 里 A、B 确实同宽。严格比较 usage < min_usage 意味着平局归 8。表 1 把几组参数代进去，可以看到答案并不固定。

这个”优化”的可选空间只有两个元素，连搜索都算不上。但它的位置很关键：kNum1DBlocksPerGroup 是 Scheduler 的模板参数默认值，意味着它在编译期就固定进了这份内核——图 4 的那张 tile 顺序图在运行时不会再变。真正的运行期配置选择（块大小、级数、multicast、swap-AB）发生在 host 侧，是下一篇的内容。

usage 的具体含义值得用数字感受一下。以 H100（128 SM、L2 约 50 MiB）上 M 轴分组、BM = BN = BK = 128、FP8 为例：g = 8 时一波 SM 覆盖 8 行 A tile 和 ⌈128/8⌉ = 16 行 B tile；在处理一个 K 块时，每行 A 占 128 × 128 × 1 = 16 KiB，所以 A 的工作集 128 KiB、B 256 KiB，合计约 384 KiB。4 级流水线下翻四倍也不到 2 MiB，远小于 L2。关键不在于是否放得下，而在于复用次数：组内的 8 行 A tile 与同一组的 16 行 B tile 两两配对，每行 B tile 被 8 次 M-loop 复用；如果换成行主序，一波 128 个 SM 会展开 128 行不同的 B tile，复用率降到 1。候选集 {8, 16} 本身并非由 L2 容量反推——代码注释只写了 Swizzle for better L2 usages——但它足够小以保证组内复用，又足够大以在次轴方向填满 SM。
