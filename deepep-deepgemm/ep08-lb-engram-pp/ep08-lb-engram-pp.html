冗余专家、Engram 与 PP：
三种点对点搬运原语

EPBuffer 的 lb_* 接口按一张副本表在 NVLink 域内推权重、拉梯度；EngramBuffer 用 RDMA 读按下标从远端表里取行；PPBuffer 用有限的槽位在流水线相邻 rank 间收发张量——三者都绕开了 dispatch/combine 的全对全路径。

TL;DR

  • lb_prefetch_weights 和 lb_reduce_grads 是 NVLink 域内的集合操作：每个 rank 从同一张副本表里挑出“自己的专家被复制到了哪里”，前者把权重推过去，后者把梯度拉回来就地累加。
  • 副本表 redundancy_mapping 是 \([R_{\text{nvl}}, S]\) 的 int32 张量，−1 表示空槽，专家号按域内编号“所有者 × 本地专家数 + 本地序号”，rank 不能在自己的槽里放自己的专家。
  • 冗余权重和梯度必须住在独立的 LB 区：它与 EP 通信区同属一个对称窗口，所以同一偏移就能换算出对端地址，而 EP 区的内容每次 dispatch/combine 都会被覆盖。
  • Engram（实验性）把按层分片的查找表放在各 rank 的 GPU 或 CPU 内存里，fetch 用一个内核发出所有层的 RDMA 读，然后每层给一个等待钩子。
  • PP（实验性）只在环上相邻的两个 rank 之间收发张量，靠固定数量的槽位和 arrival / release 两个计数器做流控。

前置知识

了解 ep01 的 EPBuffer 与 LB 区域布局，以及 ep05 的对称内存窗口。本篇新引入：redundancy_mapping 副本表、Engram 远程取数、PP 流水线收发与流控。

前七篇讲的都是全对全：dispatch、combine 和 Bucket 集合通信，每个 rank 都要和很多 rank 交换数据。DeepEP V2.5 还带了三种形状完全不同的原语 [1]，它们的共同点是点对点：谁和谁通信、搬哪一块，在调用之前就已经由一张表或一组下标决定了。

  • 冗余专家的权重与梯度交换：EPBuffer.lb_prefetch_weights 与 EPBuffer.lb_reduce_grads，是 V2.5 新增的正式接口（README 第 15 行）。
  • Engram 远程取数：EngramBuffer.fetch，用 RDMA 读按下标从远端的表里取行。
  • 流水线并行（pipeline parallelism，PP）收发：PPBuffer.send / recv。

README 明确把 Engram 和 PP 标为实验性功能（README 第 33–41 行），本文对它们的描述只代表当前提交的代码。表 1 先给出三者的横向对比，后面逐个展开。三者都建立在 NCCL Gin 设备端通信与对称内存窗口之上，这些底座的内部机制见第 5 篇，这里只用到两个概念：对称窗口是每个 rank 都以相同布局注册的一段内存，同一偏移在每个 rank 上指向“同一个逻辑位置”；LSA（load/store accessible）团队是能用普通加载/存储指令互相访问显存的 rank 集合，在本文的场景里就是一个 NVLink 域。

一张副本表决定冗余专家放在哪里

MoE 训练与推理里，少数“热”专家收到的 token 远多于平均，所在的 GPU 就成了整层的瓶颈。动态冗余专家的思路是把热专家的权重临时复制到别的 GPU 上，让一部分 token 改去副本那里计算。README 提到两个探索这一方向的工作：MoonEP 研究带动态冗余专家、权重预取和梯度归约的在线规划 [2]；UltraEP 根据门控之后的当前负载规划复制与 token 重路由，并把专家复制限制在 NVLink 域内 [3, 4]。README 说 EPBuffer 暴露的这两个原语就是受它们启发（README 第 330–332 行）。

分工很清楚：规划在库外。使用者自己决定哪个专家复制到哪里、把 token 改路由到选定的副本、管理专家 GEMM；DeepEP 只负责按计划把字节搬到位（README 第 337 行）。计划的载体就是 redundancy_mapping，规则如下（README 第 341–343 行，ep.py 第 866–874 行）：

  • 形状 \([R_{\text{nvl}}, S]\)，\(R_{\text{nvl}}\) 是 NVLink 域内的 rank 数，\(S\) 是每个 rank 的冗余槽数；连续的 CUDA int32 张量，域内每个 rank 上内容完全相同。
  • 第 \(r\) 行第 \(c\) 列表示“域内第 \(r\) 号 rank 的第 \(c\) 个冗余槽放哪个专家”，−1 表示空槽，空槽被跳过。
  • 专家号是域内编号：所有者在域内的 rank 号 × 本地专家数 + 本地序号，取值在 \([0, R_{\text{nvl}}E_\ell)\)。多机 EP 时每个 NVLink 域各有一张表，全局专家号要由使用者换算。
  • 副本只能放到别的 rank 上：一个 rank 的本地专家不能出现在它自己的冗余槽里。域内所有 rank 的本地专家数必须相同。

图 1 是一个 4 卡、每卡 2 个本地专家、2 个冗余槽的例子。热专家 e5 属于 rank 2，表里它出现了两次（rank 0 的槽 0、rank 3 的槽 0），于是有两份副本；rank 0 的槽 1 是 −1。

内核开头，每个 rank 用一次块内前缀和把整张表扫一遍，把“所有者是自己”的条目压缩成任务列表，每条任务记下本地专家序号、目标 rank 和目标槽号：

// Compact local expert exchanges in mapping order
int num_found_tasks = 0;
for (int base = 0; base < kNumRanks * kNumRedundantExperts; base += kNumThreads) {
    const int i = base + thread_idx;
    const int expert_idx = i < kNumRanks * kNumRedundantExperts ? redundancy_mapping[i] : -1;
    const int is_local = expert_idx >= 0 and expert_idx / kNumLocalExperts == rank_idx;
    // ...
    if (is_local) {
        // ...
        tasks[task_idx] = {
            .local_expert_idx = expert_idx % kNumLocalExperts,
            .dst_nvl_rank_idx = i / kNumRedundantExperts,
            .redundant_expert_idx = i % kNumRedundantExperts
        };

源码：layout/ep/eplb.cuh 第 39–54 行（节选）

这段代码说明了副本表各项规则的来由：所有者由“专家号 ÷ 本地专家数”算出，所以专家号必须是域内编号、各 rank 的本地专家数必须相同；表必须在各 rank 上完全相同，否则不同 rank 会挑出互相矛盾的任务；−1 不满足 expert_idx >= 0，自然被跳过。任务列表放在 32 KiB 的共享内存里，每条 12 字节，上限约 2700 条（eplb.cuh 第 21–23 行）。

虽然构建算法在库外，但可以从代码约束推出它必须回答的三个问题。第一，选哪些专家复制：根据 gate 网络输出的 token-to-expert 分配，统计每个专家在当前批次（或近几个批次的滑动窗口）收到的 token 数，选出负载超过均值的热专家。第二，副本放在哪个 rank 上：约束是 rank 不能持有自己的副本（第 46 行），所以必须是别的 rank；贪心策略是每次把最热专家的副本放到剩余容量最多的 rank 上，直到 S 个槽用完或负载均衡达标。第三，token 怎么重路由：复制之后，gate 网络原本指向热专家所有者的 token 中，有一部分要改成指向副本——Mega Gate 的 to_physical_map（第 9 篇）和散列分散公式正是为此设计的。UltraEP [3, 4] 把这三步做成一个在线规划器，在门控后、dispatch 前的间隙内运行，约束条件包括：S 个槽的硬上限、NVLink 域内通信的带宽预算、以及"不值得为只减少几个 token 的专家开一次 prefetch"的成本阈值。MoonEP [2] 的思路类似但增加了跨微批的权重预取调度。DeepEP 本身不涉及这些，它只保证：给定一张合法的 redundancy_mapping，prefetch 和 reduce_grads 能正确搬运。

测试脚本构造副本表的方式也印证了规则：从“除自己以外”的专家里随机抽，再把落在自己区间的编号整体后移一段；生成后断言“一个 rank 绝不持有自己本地专家的副本”（test_prefetch_weights.py 第 62–96 行）。另外两个测试都断言 RDMA 域大小为 1，即只在单个 NVLink 域内运行（同文件第 117 行）。

lb_prefetch_weights：所有者把权重推进对端的冗余槽

前向专家计算开始之前，每个 rank 调用 lb_prefetch_weights(redundant_expert_weights, expert_weights, redundancy_mapping)。expert_weights 是本 rank 的 \([E_\ell, \ldots]\) 原始权重，可以是普通的 CUDA 分配；redundant_expert_weights 是 \([S, \ldots]\) 的目标，必须位于 LB 区。两者都可以是张量序列（最多 16 对，eplb.cuh 第 69 行），这样 FP8 权重和它的缩放因子可以一次搬完，不做任何类型转换。每对张量的尾部形状可以不同，只要“每个专家的字节数”相同且是 32 字节的倍数（README 第 343 行）。

文档与代码的一处差异：README 和 docstring 要求每专家字节数是 get_num_tma_alignment()（32 字节）的倍数；ep.hpp 里 prefetch 的主机端断言检查的是 16 的倍数（第 1014–1018 行），而梯度归约检查的是 32（reduce_grads.hpp 第 41–42 行）。按 README 满足 32 字节最稳妥。

内核（prefetch_weights.cuh 第 49–92 行）分四步：建任务列表；全域入口屏障；搬运；全域完成屏障。搬运按 12 KiB 的块进行（prefetch_weights.hpp 第 29–35 行），每个 warp 独占一块共享内存，用全局原子计数器领取下一块，领取顺序是“张量 → 块 → 任务”。领到之后，源地址与目的地址这样算：

// Locate task and resolve pointers
const auto& [redundant_expert_weights, expert_weights, num_bytes_per_expert] = weights[weight_idx];
const auto& [local_expert_idx, dst_nvl_rank_idx, redundant_expert_idx] = smem_layout.tasks[chunk_idx % num_tasks];
const int64_t chunk_offset = static_cast<int64_t>(chunk_idx / num_tasks) * kNumBytesPerChunk;
num_chunk_bytes = static_cast<int>(min(static_cast<int64_t>(kNumBytesPerChunk), num_bytes_per_expert - chunk_offset));
src_ptr = math::advance_ptr(expert_weights, local_expert_idx * num_bytes_per_expert + chunk_offset);
dst_ptr = gin.get_sym_ptr<ncclTeamTagLsa>(math::advance_ptr(redundant_expert_weights,
    redundant_expert_idx * num_bytes_per_expert + chunk_offset), dst_nvl_rank_idx);
return true;

源码：layout/ep/eplb.cuh 第 127–135 行

源地址是本地普通显存里的原始权重；目的地址是把本 rank 自己的 redundant_expert_weights 指针加上槽偏移，再经 get_sym_ptr 换算成目标 rank 上对应位置的地址。这个换算之所以成立，前提是各 rank 的冗余张量在对称窗口里的偏移完全相同——下一节会回到这一点。数据通路是“TMA 从本地显存载入共享内存，再用 TMA 存储写到对端显存”（prefetch_weights.cuh 第 71–86 行）。块号按任务数取模，相邻的块分给不同的任务，因此同一时刻多个 warp 在向不同的对端写；我们推测这样安排是为了让多条 NVLink 同时忙起来。

两道屏障决定了使用约束。入口屏障保证所有 rank 都已到达（对端的 LB 区可写、上一轮的读者已经读完），完成屏障保证所有推送对接收方可见；docstring 说“融合的屏障使冗余权重在返回的事件被等待时对使用者可见”（ep.py 第 860–864 行）。屏障跨整个 NVLink 域，所以域内每个 rank 都必须调用，包括没有分到任何冗余槽、也没有专家被复制的 rank，否则其他 rank 会在屏障上超时。

调用本身是异步的：内核排在通信流上，先等 previous_event（默认等当前计算流），返回一个 EventOverlap，使用权重前调用 .wait()（ep.hpp 第 1027–1040 行）。num_sms=0 时用一个简单的带宽估算：取 NVLink 带宽分别除以单 SM 的读、写带宽，取较大者向上取偶数（ep.py 第 845–852 行），注释说这个预算与副本表无关，环形流量或 rank 偏斜可能在用满这些 SM 之前就先撞上链路瓶颈。估算用到的带宽常数见第 6 篇。

lb_reduce_grads：同一张表，反方向拉回梯度并就地累加

反向时，副本上算出的梯度要加回原专家。lb_reduce_grads(redundant_expert_grads, expert_grads, redundancy_mapping) 是 prefetch 的镜像：同一张表、同一种任务列表，但数据方向反过来。它的输入限制更严：两个张量都必须是二维 FP32，redundant_expert_grads 为 \([S, D]\) 且位于 LB 区，expert_grads 为 \([E_\ell, D]\)，每个专家的全部参数梯度要压平成一行（ep.hpp 第 1049–1066 行）。

while (iterator.next()) {
    // Load redundant gradients
    ptx::mbarrier_arrive_and_set_tx(mbarrier, iterator.num_chunk_bytes);
    ptx::tma_load_1d(tma_buffer, iterator.dst_ptr, mbarrier, iterator.num_chunk_bytes,
                     /* TODO: why this is faster? */ ptx::L2CacheHint::kEvictNormal);
    ptx::mbarrier_wait_and_flip_phase(mbarrier, phase);

    // Accumulate and release the shared buffer
    ptx::tma_store_reduce_add_f32(static_cast<float*>(iterator.src_ptr), tma_buffer, iterator.num_chunk_bytes);
    ptx::tma_store_commit();
    ptx::tma_store_wait_read<0>();
}

源码：impls/ep/reduce_grads.cuh 第 74–85 行

迭代器与 prefetch 完全相同，只是读写对调：从 dst_ptr（对端冗余槽里的梯度）载入，再用 TMA 的归约存储把它加到 src_ptr（本地 expert_grads）上。块大小是 24 KiB（reduce_grads.hpp 第 30–32 行）。于是每个 rank 只写自己的显存，而远端访问全部是读。这与 prefetch 的“只写远端”形成对照，两者共用同一个任务列表：任务永远由所有者执行。我们的理解是，这样安排让累加发生在本地，免去了跨 NVLink 的原子操作；代码和文档没有直接说明动机。

由此得出 README 列出的几条使用规则（README 第 335 行、第 380 行）：

  • 先播种再归约。它是加法而不是覆盖，调用前要让 expert_grads 装着本地的梯度贡献，或者清零。
  • 冗余梯度不会被清空。归约只读它们，下一次累积前要使用者自己覆盖或清零。测试专门检查了冗余梯度池在归约后保持不变（test_reduce_grads.py 第 198–204 行）。
  • 用前向的同一张表。表不同，梯度就会加到错误的专家上。
  • 累加顺序不固定。同一个专家有多个副本时，几个 warp 可能同时向同一块本地梯度做归约。测试注释写道，这里用的 cp.reduce.async.bulk 是逐元素的原子加，多个副本到达的先后不固定，所以测试特意用 FP32 能精确表示的小整数造数据，以便用 torch.equal 比较（第 23–40 行）。换成真实梯度，结果可能在末位上逐次不同。

README 还提醒了一个容易忽略的时序问题：如果冗余槽在多个层或多个微批之间复用，反向计算之前要把需要的权重重新推一遍——专家的反向要用权重计算输入梯度，而槽里此时可能已经是别的层的专家；同理，在复用梯度槽之前要先完成归约（README 第 380 行）。

冗余张量为什么必须住在单独的 LB 区

构造 EPBuffer 时用 lb_allocation_plan_or_num_bytes 预留 LB 区，参数可以是一个 BufferAllocator 计划，也可以是对齐到 2 MiB 的字节数；0 表示不要 LB 区（ep.py 第 273–276 行）。在 C++ 侧，LB 区紧接在 EP 通信区之后，和它一起作为同一块缓冲区交给通信上下文注册，然后只把后半段暴露给 Python：

// Expose only the LB region; the preceding bytes remain reserved for EP communication.
lb_storage = torch::from_blob(
    context->buffer, {num_buffer_bytes + num_lb_buffer_bytes}, [context = context](void*) {},
    torch::TensorOptions().dtype(torch::kByte).device(torch::kCUDA)
).narrow(0, num_buffer_bytes, num_lb_buffer_bytes);

源码：csrc/buffers/ep.hpp 第 82–86 行；上下文以 num_buffer_bytes + num_lb_buffer_bytes 为缓冲区大小创建，见第 73–77 行

图 2 画出了结果：每个 rank 的对称窗口依次是工作区、EP 通信区、LB 区，各 rank 布局相同。BufferAllocator 在构造之前只记录偏移：

tensor = torch.empty(shape, dtype=dtype, device='meta')
offset = align(self.num_bytes, self.alignment)
self.allocations.append((tensor, offset))
self.num_bytes = align(offset + tensor.nbytes, self.alignment)
return tensor

源码：deep_ep/buffers/allocator.py 第 22–26 行

buffer 建好后，materialize 把这些 meta 占位张量原地换成指向 lb_storage 相应偏移的视图（第 28–36 行，ep.py 第 348–350 行）。对齐常数就是 2 MiB 的分配对齐，所以每个计划中的张量都会被补齐到 2 MiB 的整数倍。

现在可以回答“为什么要单独一块区域”了。理由有三层，前两层可以直接从代码读出，第三层是推断：

  1. 必须在对称窗口里。prefetch 和 reduce 都靠 get_sym_ptr 把本地地址换算成对端地址，只有注册进窗口的内存才能这样寻址；原始权重和梯度只在本地访问，所以可以是普通分配（README 第 339 行）。
  2. 各 rank 偏移必须相同。换算的前提是“我的冗余张量在窗口里的偏移，等于对端冗余张量的偏移”。因此 README 要求计划在 NVLink 域内每个 rank 上形状和分配顺序都相同（第 339 行，docstring 第 273–276 行）。
  3. 不能和 EP 通信区共用。EP 通信区是 dispatch 和 combine 的收发缓冲，每次调用都会覆盖（第 2 篇）；而冗余权重从 prefetch 完成一直要活到对应的专家前向与反向结束，中间必然穿插着同一层甚至别的层的 dispatch/combine。放在一起就会被冲掉。代码注释只说“前面的字节保留给 EP 通信”，这一层动机是我们的推断。

测试把这一点推到极端：只为 LB 原语建 buffer 时，EP 通信区只给了最小的 2 MiB（test_prefetch_weights.py 第 134–139 行），说明两块区域的大小彼此独立。测试结束时还特意先删掉指向 LB 区的视图再销毁 buffer，注释说“冗余专家权重池是 buffer 里的视图，所以先释放它们”（同文件第 224–226 行）。表 2 第一部分给出两个 LB 区的算例。

README 示例里，8 个槽 × 1024 个 BF16 只有 16 KiB，FP32 梯度 32 KiB，但两次分配各补齐到 2 MiB，LB 区共 4 MiB。真实专家的权重通常是几十 MiB，补齐的浪费可以忽略；FP32 梯度则是同参数量 FP8 权重的 4 倍，规划显存时要单独算进去。

Engram（实验性）：按下标从远端表里读行

EngramBuffer 解决的是另一类问题：一张很大的查找表按行分片存在各个 rank 上，每个 token 要按若干个下标取回若干行。README 只给了接口说明：存储可以在 GPU 或 CPU 上，支持多层一起取，用 get_storage_size_hint 和 get_theoretical_config 确定大小与 QP，用 set_config 和 write 填表；fetch(indices) 接受 \([L, T, N]\) 的 int32 下标，返回每层一个完成钩子，用某层数据之前调用对应的钩子（README 第 382–386 行）。它还要求 NCCL 提供 ncclGinOptFlagsWarpGet（第 41 行）。

数据模型

第 \(l\) 层的表在每个 rank 上有 \(n_l\) 行（num_entries_per_layer[l] 是每 rank 的行数），全局行号 \(g\in[0, R\,n_l)\) 的所有者是 \(\lfloor g/n_l\rfloor\)。每个 rank 的存储分片把各层的行首尾相接；本 rank 的接收区则为每层预留 \(T_{\max}\times N\) 行，第 \(t\) 个 token 的第 \(j\) 个条目落在该层的第 \(tN+j\) 行（layout/engram/workspace.cuh 第 23–57 行）。所以 hooks[l]() 返回的是一个 \([T, N\cdot\text{hidden}]\) 的视图，每个 token 的 \(N\) 行被拼成一行。测试的下标生成方式是把全局表等分成 \(N\) 段、第 \(j\) 个条目只从第 \(j\) 段里抽（test_engram.py 第 58–67 行），但接口本身没有这个限制。

存储放在哪由构造参数 use_cpu_rdma_storage 决定，write 用 cudaMemcpyAsync 把每层的表拷进本地分片，GPU 和 CPU 两种情况走同一条代码（engram.hpp 第 109–131 行）。FP8 存储时缩放因子不走 RDMA：write 收到的是全表的缩放因子，每个 rank 只把其中 \(1/R_{\text{nvl}}\) 存进 GPU 缓冲区的尾部，取数时由专门的 warp 经 NVLink 从对应的分片读（第 133–151 行，engram_fetch.cuh 第 208–254 行）。

一次 fetch：一个内核发出全部读请求，每层一个等待钩子

源码：impls/engram/engram_fetch.cuh 第 114–130 行

几个细节。其一，每条 RDMA 读的长度就是一行的字节数 kNumHiddenBytes：测试默认隐藏维 256、BF16，每次读只有 512 字节，所以吞吐受网卡每秒能处理的请求数限制，而不是带宽——这也是下面 QP 估算以“每秒读请求数”为输入的原因。其二，RDMA 对端按 NCCL 报告的 ginMinStride 分组：请求总是发给组内第一个 rank（rdma_peer_rank），但源窗口按条目所有者在组内的序号选 storage_windows[intra_peer_rank_idx]（第 91–107 行）；混合模式下各 rank 的存储通过构造时交换的共享句柄互相可见（engram.py 第 73–77 行），窗口机制见第 5 篇。其三，门铃并不每批都敲：按 flush_depth 均分出的阈值合并请求，最后一批一定敲门铃，然后对每层每个（对端, QP）只做一次 flush_async，把最后一个请求句柄写进 last_gin_requests（第 109–112、173–205 行）。

钩子做的事很简单：在调用时的当前流上启动一个单块小内核，等待该层每个（对端, QP）的最后一个请求完成，然后返回该层的数据视图（FP8 时连同缩放因子）：

源码：csrc/buffers/engram.hpp 第 234–247 行

这样分的意义在于：发请求的内核一结束，当前流就可以继续跑别的计算，RDMA 读在后台完成；第 0 层的计算只需等第 0 层的请求，后面各层的读取可以与它重叠。测试分别按正序和逆序调用钩子验证结果（test_engram.py 第 77–96 行），说明钩子之间没有顺序要求。要注意的是，返回的视图直接指向 buffer 的接收区，下一次 fetch 会覆盖它；这一点 README 没写，是从 torch::from_blob 的用法（第 168–176 行）推出来的。

源码：csrc/buffers/engram.hpp 第 279–294 行（节选）

公式读作：要让网卡以速率 \(\lambda\) 处理读请求，在一个往返时间 \(\tau\) 内就得有 \(\lambda\tau\) 个请求在途（Little 定律）；每个 QP 最多同时挂 16 个读，再平摊到 \(P\) 个对端组上：

\[ N_{\text{QP}} = \left\lceil \frac{\lambda\,\tau}{16\,P} \right\rceil,\qquad \lambda \in \{90, 45\}\ \text{Mpps},\quad \tau = 10\ \mu\text{s} \](1)

\(\lambda\) 和 \(\tau\) 都是代码里的假设常数：网卡支持快速 RDMA 原子操作时 \(\lambda\) 取 90 Mpps，否则 45（engram.py 第 140 行），它们不是实测数据。队列深度从默认的 1024 起翻倍，直到装得下“总请求数 ÷（QP 数 × 对端组数）”；如果需要的深度超过 32768，就改为增加 QP 数，并返回 restrict_rd_atomic=True，构造函数据此把 NCCL_GIN_GDAKI_MAX_QP_RD_ATOMIC 设为 8（engram.py 第 81–86 行）。按式 (1)，表 2 列出了不同 \(P\) 下的 QP 数；测试默认参数（2 层、512 个 token、每 token 24 个条目）在 \(P=4\) 时只需 15 个 QP、深度 1024。

Engram 对显存的要求也和 EP 不同：get_storage_size_hint 返回两个数，GPU 接收区按 \(L\cdot T_{\max}\cdot N\) 行算（FP8 时再加缩放因子分片），存储分片按本 rank 全部行数算（engram.hpp 第 251–271 行）。混合模式下要注册的总字节数可能超过单卡显存，构造函数会相应调大 NCCL_WIN_STRIDE，并用环境变量 EP_NUM_MAX_LOCAL_RANKS 估计每个节点的 rank 数（engram.py 第 61–65 行，README 第 407 行）。

PP 收发（实验性）：环上相邻 rank 之间的有界槽位队列

PPBuffer 提供 send(x, dst_rank_idx) 和 recv(x, src_rank_idx)，README 规定它只在“纯 RDMA 的流水线组”里、相邻 rank 之间使用；构造时用 num_max_tensor_bytes 和 num_max_inflight_tensors 预留收发槽；输入输出必须是连续的 CUDA 张量，指针和大小都 32 字节对齐（README 第 388–390 行）。主机端断言目标或来源必须是环上的前一个或后一个 rank（pp.hpp 第 79–111 行）。代码没有检查“纯 RDMA”：通信上下文以关闭混合模式的方式创建，所有数据都用 Gin 的 RDMA put 发送（第 54–60 行）；我们的理解是，同一 NVLink 域内的两个 rank 用它也许能跑，但不在设计和测试范围内（README 第 101 行说 PP 测试需要纯 RDMA 的组）。

存储布局：四个区，每区若干槽

存储大小是 \(4\times n\times B_{\max}\)，\(n\) 为在途张量上限，\(B_{\max}\) 为对齐到 64 字节的单张量上限（pp.hpp 第 44–49 行）。四个区分别是：收自前一 rank、收自后一 rank、发往前一 rank 的暂存、发往后一 rank 的暂存，每区 \(n\) 个槽，第 \(i\) 次收发用第 \(i \bmod n\) 个槽（pp_send_recv.cuh 第 17–25 行、第 124–130 行）。工作区里为两个方向各维护四个计数器：send_count、recv_count、每个 QP 一个的 arrival、release（layout/pp/workspace.cuh 第 11–18 行）。

对照图 4 的编号：

  1. send 等槽。第 \(i\) 次发送（\(i\) 即 send_count）要等对端已经释放了至少 \(i-n+1\) 个槽，也就是在途的未消费张量少于 \(n\) 个；然后各 SM 分段用 TMA 把 x 拷进本地的发送暂存槽，全网格同步。
  2. send 写对端。用至多 2 个 QP 把暂存槽分段 RDMA 写进对端接收区的同号槽，每段附带一个“给对端的 arrival 计数器加一”的远端动作；某个 QP 没有数据可写时也照样发信号，因为接收方会逐个等每个 QP（第 146–167 行）。QP 数取 min(2, num_allocated_qps)（kernels/pp/pp_send_recv.hpp 第 20–23 行）。
  3. recv 等到达。接收内核等每个 QP 的 arrival 计数都达到 recv_count + 1，再用 TMA 把槽里的数据拷进使用者给的输出张量（第 202–221 行）。
  4. recv 释放。拷完后给发送方的 release 计数器加一，并把本地 recv_count 加一（第 223–233 行）。

这个协议有两个性质值得注意。第一，send 内核在发出 RDMA 写之后就结束，不等对端收到；但因为数据先拷进了暂存槽，内核结束后 x 立即可以被改写。暂存槽本身要等对端 release 之后才会被第 \(i+n\) 次发送复用，而 release 发生在对端拷出之后，这时 RDMA 写必然已经完成。第二，两个内核都排在调用时的当前流上，没有事件和钩子，并在 GPU 上自旋等待；等不到就在 num_gpu_timeout_secs 后打印超时信息。所以发送方连续发出超过 \(n\) 个张量而接收方迟迟不 recv，或者 recv 排在了对端 send 所依赖的计算之前，都会卡住。测试生成随机收发序列时专门让“第 \(i\) 次发送排在第 \(i-n\) 次接收之后”，注释写的就是“避免死锁”（test_pp.py 第 38–43 行）。

按测试默认值（4096×7168 的 BF16 张量、在途 4 个），存储要 896 MiB（表 2），是单个张量的 16 倍，因为四个区各要 4 个槽。如果流水线只沿一个方向传激活、另一个方向传梯度，四个区都会用到；只单向使用时一半空间是闲置的，但接口不提供只开单向的选项。

局限与未覆盖

  • 实验性功能。Engram 和 PP 在 README 中标为实验性（第 33–41 行）。它们的接口、约束和本文描述的实现都可能在后续提交中改变；PP 的“纯 RDMA 组”要求只在 README 中出现，代码不检查。
  • 没有性能数据。本文没有引用任何带宽或时延。各测试脚本会打印 GB/s 与 Mpps，但仓库里没有记录结果；Engram 的 90 / 45 Mpps 与 10 μs 是 QP 估算公式里的假设常数，不是测量值。表 2 的数字是把公式代入参数算出的字节数与 QP 数，第二行的专家形状是我们设定的。
  • 推断。以下是我们根据代码的推断：所有者执行全部任务、归约只写本地，是为了避免跨 NVLink 原子操作；块号按任务数取模是为了让多条链路同时忙；LB 区不能与 EP 区共用的直接原因是 EP 区会被每次通信覆盖；Engram 钩子返回的视图会被下一次 fetch 覆盖；PP 用在 NVLink 域内是否可行。
  • 文档与代码的出入。prefetch 的每专家字节数，README 要求 32 字节倍数而主机端断言只查 16；本文建议按 README。
  • 未覆盖。冗余专家的规划算法与 token 重路由（库外，见 MoonEP / UltraEP）；Gin 的 put/get/信号、对称窗口与 LSA 团队的内部实现（第 5 篇）；屏障的实现；SM 估算用到的带宽常数（第 6 篇）；Engram 在上层模型里的具体用途，仓库没有说明，本文也不做猜测。

小结

三种原语都把“谁和谁通信”交给调用者事先确定，库只负责高效地搬字节。冗余专家交换以一张全域一致的副本表为契约：每个 rank 只执行自己作为所有者的任务，前向把权重写进对端 LB 区的同一偏移，反向从同一位置读回梯度、在本地累加；LB 区独立于 EP 通信区，是因为它既要可被对称寻址，又要在多次 dispatch/combine 之间保持不变。Engram 把大表分片放在各 rank 的 GPU 或 CPU 内存里，用一个内核发出全部层的 RDMA 读，再按层交出等待钩子，让取数与计算重叠。PP 则是相邻 rank 之间一个容量为 \(n\) 的有界队列，用 arrival 和 release 两个计数器保证既不覆盖未读的数据，也不读到未到的数据。
