TL;DR

  • SF 必须是 2 的幂（UE8M0 格式）：4 个 8-bit 指数用位移打包进一个 int32，位移量分别是 >>23、>>15、>>7、<<1。
  • 变换后的 SF 张量是 MN-major 布局：stride(-2)=1、stride(-1)=align(mn,4)，满足 TMA 16 字节对齐。
  • 三个 CUDA 内核覆盖三种场景：SM90 纯转置、SM100 转置 + 打包（支持 PSUM 空隙行）、K 分组打包。
  • PSUM 布局下空隙行写零（安全有限编码）而非 UE8M0 0xFF（NaN），避免 MMA 传播 NaN。
  • K 分组打包中每组独立打包后拼接，尾部不足 4 行用零填充；host 侧用上界 (sf_k + 3*num_groups)/4 分配输出。

为什么缩放因子不能直接用 float32

上一篇介绍了 SM100 上块缩放 MMA 的计算流程：每 32 个 FP8（或 FP4）元素共享一个缩放因子（Scaling Factor，SF），MMA 硬件读取 SF 后自动完成先缩放、再累加的流程。但硬件对 SF 有两条硬性约束：

  1. 格式约束：SF 必须以 UE8M0（8-bit 无符号指数）格式存储，即每个 SF 是 2 的整数次幂，用一个字节表示其指数。
  2. 布局约束：TMA 搬运 SF 到张量内存（TMEM）时要求特定的步幅对齐——MN 方向连续、K 方向的步幅是 16 字节的倍数。

用户侧量化产生的 SF 通常是 float32 张量、K-major 布局（即 stride(-2)=sf_k），不满足上述任何一条。DeepGEMM 因此提供了一条完整的变换流水线：把 float32 SF 转换为 int32 打包的 UE8M0 张量、重排为 MN-major 布局、对齐步幅。这条流水线有两条路径：

  • 自动变换：每次 GEMM 前自动执行，输入 float32，输出打包后的 int32。简单但有重复开销。
  • 预变换：调用方预先调用 get_col_major_tma_aligned_tensor 得到 int32 张量，后续 GEMM 直接使用。适用于权重 SF 等可缓存的场景。

每个 SF 值是 2 的幂：UE8M0 打包

UE8M0 格式

UE8M0（Unsigned, 8-bit Exponent, 0-bit Mantissa）是 DeepGEMM 文档中定义的 SF 格式。一个 UE8M0 值占 8 bit，只存储 IEEE 754 float32 的偏移指数（biased exponent），没有符号位和尾数位。换言之，每个 SF 必须恰好是 2 的整数次幂——float32 的 sign = 0、mantissa = 0，只有 8 位指数有效。

Python 参考实现 ceil_to_ue8m0 把任意 float32 向上取整到最近的 2 的幂：如果尾数不为零，指数加 1。pack_ue8m0_to_int 则将连续 4 个 UE8M0 值视为 4 字节，合并存储为一个 int32： 

def ceil_to_ue8m0(x: torch.Tensor):
    bits = x.abs().float().view(torch.int)
    exp = ((bits >> 23) & 0xFF) + (bits & 0x7FFFFF).bool().int()
    return (exp.clamp(1, 254) << 23).view(torch.float)
# ...
def pack_ue8m0_to_int(x: torch.Tensor):
    assert x.dtype == torch.float and x.size(-1) % 4 == 0
    x_int = x.view(torch.int)
    assert (x_int >= 0).all() and (x_int & 0x7fffff == 0).all()
    return (x_int >> 23).to(torch.uint8).view(torch.int)

CUDA 侧的位移打包

CUDA 内核中的打包逻辑直接操作 float32 的整数视图。4 个 float32 值的指数字段位于 bit [30:23]，通过精心选择的位移量，恰好把 4 个 8-bit 指数拼进一个 32-bit 整数的 4 个字节：

  • values[0] >> 23：指数移到 bit [7:0]
  • values[1] >> 15：指数移到 bit [15:8]
  • values[2] >> 7：指数移到 bit [23:16]
  • values[3] << 1：指数移到 bit [31:24]

这要求每个 values[j] 的 sign bit（bit 31）和 mantissa（bit [22:0]）全为零——正好由 DG_TRAP_ONLY_DEVICE_ASSERT 检查。位移后用 OR 合并，一条 packed |= ... 把 4 个指数无冲突地放进不同字节（图 1 给出了一个完整算例）： 

    values[j] = valid_mn and global_sf_k_idx < SF_K ? ptx::ld_shared(sf_smem_buffer + mn_idx * kSmemSFK + sf_k_idx) : 0;
    // FP32 SFs must have a zero sign and mantissa (only the exponent is packed)
    DG_TRAP_ONLY_DEVICE_ASSERT((values[j] & 0x807fffffu) == 0);
// ...
// Pack and store
uint32_t packed = 0;
packed |= (values[0] >> 23u);
packed |= (values[1] >> 15u);
packed |= (values[2] >>  7u);
packed |= (values[3] <<  1u);
// Write safe finite scale codes for PSUM gap rows; UE8M0 0xff is NaN.

    out[global_sf_k_pack_idx * tma_aligned_mn + global_mn_idx] = packed;

注意第 176 行的三元表达式：当 valid_mn 为 false（该行是 PSUM 空隙行）或 global_sf_k_idx >= SF_K（超出 K 范围）时，values[j] 被设为 0。0 的 float32 表示中指数字段为 0，打包后对应 UE8M0 编码 0x00——这是一个安全的有限值（代表 2^{-127}），而非 NaN。这一设计在 §PSUM 空隙行 一节详述。

MN-major 与 TMA 对齐布局

变换后的 SF 张量是一个 int32 矩阵，shape 为 [packed_sf_k, mn]，其中 packed_sf_k = ceil(sf_k / 4)（每 4 个 UE8M0 打包为一个 int32）。关键的布局约定是 MN-major（图 2）：

  • stride(-2) = 1：MN 方向上元素连续存储。
  • stride(-1) = align(mn, 4)：K 方向的步幅是 mn 向上对齐到 4 的结果，即保证步幅是 4 × sizeof(int32) = 16 字节的倍数——恰好满足 TMA 的 16 字节对齐要求。

为什么选 MN-major？MMA 按 M/N 方向消费 SF：同一条 M（或 N）上的所有 K-tile 共享同一组 SF。MN-major 让同一 M 行的 SF 连续排列，TMA 可以用一次操作搬运一整列 SF 到 TMEM。如果用 K-major，TMA 需要额外的转置步骤。

Host 侧的 check_sf_layout 函数在每次 GEMM 启动前验证这些约束。函数接受一系列参数——mn 维大小、K 维大小、粒度、是否 K 分组——并检查 shape、stride 和 dtype 三个层面： 

// SF layouts
static torch::Tensor check_sf_layout(const torch::Tensor& sf,
                                     const int& mn, const int& k,
                                     const int& gran_mn, const int& gran_k,
                                     const std::optional<int>& num_groups,
                                     const bool& tma_stride_check = false,
                                     const bool& sm90_sfb_check = false,
                                     const std::optional<torch::ScalarType>& type_check = std::nullopt) {
    // Type check
    if (type_check.has_value())
        DG_HOST_ASSERT(sf.scalar_type() == type_check.value());

    // Always do shape checks
    const auto sf_dtype = sf.scalar_type();
    DG_HOST_ASSERT(sf_dtype == torch::kFloat or sf_dtype == torch::kInt);
    DG_HOST_ASSERT(sf.dim() == static_cast<int>(num_groups.has_value()) + 2);
    if (num_groups.has_value())
        DG_HOST_ASSERT(sf.size(-3) == num_groups.value());
    DG_HOST_ASSERT(sf.size(-2) == ceil_div(mn, gran_mn));
    DG_HOST_ASSERT(sf.size(-1) == ceil_div(k, gran_k * (sf_dtype == torch::kFloat ? 1 : 4)));

    // TMA stride checks: TMA aligned and MN-major
    if (tma_stride_check) {
        if (num_groups.has_value())
            DG_HOST_ASSERT(sf.stride(-3) == sf.stride(-1) * sf.size(-1));
        // Check contiguity in the MN direction
        DG_HOST_ASSERT(sf.stride(-2) == 1 or mn == 1);
        const auto compact_stride = get_tma_aligned_size(mn, sf.element_size());
        DG_HOST_ASSERT(sf.stride(-1) >= compact_stride);
        DG_HOST_ASSERT(sf.stride(-1) % 4 == 0);
    }

第 115–119 行检查 shape：SF 张量的维数由是否有 num_groups 决定（K 分组多一个维度），最后两维分别是 ceil(mn / gran_mn) 和 ceil(k / gran_k / pack_factor)。第 122–130 行是 TMA 步幅检查：MN 方向连续（stride(-2)==1，允许 mn==1 时退化）、K 方向步幅至少为 get_tma_aligned_size(mn)（16 字节对齐后的值）、步幅是 4 的倍数。第 133–138 行是 SM90 特有检查：SM90 的 SF 可以是行主序或列主序的连续 float32。这两套检查互斥：SM90 走 sm90_sfb_check，SM100 走 tma_stride_check。

三个变换内核

DeepGEMM 用三个不同的 CUDA 内核覆盖 SF 变换的三种场景（图 3）：

transpose_fp32
SM90 路径。输入是 float32、gran_k=128（单一 K 粒度）。内核只做转置——从 K-major 转为 MN-major——不做 UE8M0 打包，因为 SM90 的缩放 MMA 直接使用 float32 SF。
transpose_and_pack_fp32_into_ue8m0
SM100 路径，输入 contiguous（非 K 分组）。内核同时完成转置和 UE8M0 打包：从 float32 K-major 变为 int32 MN-major。支持 PSUM 布局——当存在分组信息时，内核跳过空隙行（详见下节）。
pack_fp32_into_ue8m0
K 分组路径。输入已经是 MN-major 的 float32 张量（由调用方保证），内核只做打包——不转置。每组独立打包后拼接，支持 PSUM 布局中 K 方向不等长的分组（详见 §K 分组打包）。

Host 侧的派发逻辑在 smxx_layout.hpp 中：先判断输入 dtype——int32 直接验证布局后返回；float32 则根据架构和 K 粒度分流。SM90 走 transpose_fp32；SM100 的 contiguous 输入走 transpose_and_pack；K 分组输入走 pack_fp32_into_ue8m0。

Python 层也提供了 fallback 路径：当 CUDA 内核不可用时，get_col_major_tma_aligned_tensor 使用 ceil_to_ue8m0 和 pack_ue8m0_to_int 完成等价变换。这在测试和调试中非常有用——特别是在没有 SM100 硬件的开发机上验证 SF 变换的正确性。Python fallback 还充当了 CUDA 内核的参考实现：单元测试可以比较两者的输出是否逐位一致，从而验证 CUDA 内核的正确性。

值得注意的是，三种内核的选择不是互斥的——同一次 GEMM 调用中，A 和 B 的 SF 可能走不同的路径。例如在 MoE 分组 GEMM 中，激活的 SF（A 侧）可能是每次调用都不同的（需要自动变换），而权重的 SF（B 侧）是固定的（预变换后缓存）。DeepGEMM 的调用约定允许 A 和 B 分别传入 float32（需变换）或 int32（已变换）的 SF 张量，内核在 host 端通过 dtype 检查自动区分。

SM90 transpose_fp32 的共享内存转置

SM90 的缩放 MMA 直接使用 float32 SF，不需要 UE8M0 打包，因此 transpose_fp32 只做一件事：把 K-major 的 float32 矩阵转置成 MN-major。内核使用经典的 shared-memory 转置模式：先从全局内存按行加载一个 BLOCK_MN × SF_K 的块到 SMEM，再按列写回全局内存。 

template <uint32_t kNumThreads, uint32_t BLOCK_MN, uint32_t SF_K, uint32_t BLOCK_SF_K,
          uint32_t PADDED_SF_K = SF_K + (1 - (SF_K % 2))>
CUTLASS_GLOBAL __launch_bounds__(kNumThreads, 4)
void transpose_fp32(const float* sf, float* out, const uint32_t mn) {
    typedef typename utils::Vectorized<sizeof(float) * SF_K>::vec_t in_vec_t;
    constexpr static uint32_t kNumElemsPerVec = sizeof(in_vec_t) / sizeof(float);
    constexpr static uint32_t kSmemSFK = SF_K < BLOCK_SF_K ? PADDED_SF_K : BLOCK_SF_K + 1;
// ...
    // Shapes and strides
    extern __shared__ float smem_buffer[];
    constexpr auto kNumTMAAlignedElems = static_cast<uint32_t>(16 / sizeof(float));
    const auto num_mn_blocks = math::ceil_div(mn, BLOCK_MN);
    const auto block_mn_idx = SF_K < BLOCK_SF_K ? blockIdx.x : blockIdx.x % num_mn_blocks;
    const auto block_sf_k_idx = SF_K < BLOCK_SF_K ? 0u : blockIdx.x / num_mn_blocks;
    const auto block_sf_k_start = block_sf_k_idx * BLOCK_SF_K;
    const auto in_block_mn = min(BLOCK_MN, mn - block_mn_idx * BLOCK_MN);
    const auto in_block_sf_k = SF_K < BLOCK_SF_K ? SF_K : min(BLOCK_SF_K, SF_K - block_sf_k_start);
    const auto tma_aligned_mn = math::align<uint32_t>(mn, kNumTMAAlignedElems);
// ...
    cudaGridDependencySynchronize();
// ...
    __syncthreads();

    // Store
    #pragma unroll
    for (uint32_t i = threadIdx.x; i < in_block_mn * in_block_sf_k; i += kNumThreads) {
        const auto& sf_k_idx = i / in_block_mn, mn_idx = i % in_block_mn;
        const auto& global_mn_idx = block_mn_idx * BLOCK_MN + mn_idx;
        const auto& global_sf_k_idx = block_sf_k_start + sf_k_idx;
        out[global_sf_k_idx * tma_aligned_mn + global_mn_idx] = ptx::ld_shared(smem_buffer + mn_idx * kSmemSFK + sf_k_idx);
    }

源码：deep_gemm/include/deep_gemm/impls/smxx_layout.cuh 第 10–71 行（SM90 transpose_fp32：向量化读入与转置写出）

第 11 行的 PADDED_SF_K 在 SF_K 为偶数时加 1——这是 shared memory 的经典 bank conflict 回避手法：如果 SF_K 恰好是 32 的倍数，相邻行的同列元素会落在同一个 bank，转置写出时所有线程争抢同一 bank。加一列 padding 后步幅变成奇数，破坏了等步长冲突。读入使用 128-bit 向量化加载（Vectorized 把 sizeof(float) × SF_K 字节映射到最大 128-bit 的 vec_t），单线程一次搬运 4 个 float；写出时线程按转置后的列优先顺序遍历，ptx::ld_shared 从 SMEM 按列读取。

第 36 行的 cudaGridDependencySynchronize 值得注意：它等待前一个 CUDA graph 节点（通常是产出 SF 的量化内核）完成后再读取 SF 全局内存，保证依赖关系在 graph 捕获下正确。这是 CUDA 12 引入的 programmatic-dependent-launch（PDL）机制的一部分——第 5 篇会进一步讨论 PDL。

SM100 transpose_and_pack 的向量化策略

SM100 的 transpose_and_pack_fp32_into_ue8m0 内核复合了转置和打包两步操作。读入阶段与 SM90 类似，使用向量化加载把 float32 从全局内存搬进 SMEM。特别的是，当 SF_K < BLOCK_SF_K（小 K 场景），内核直接把整行读为 uint4（128-bit），跳过 warp/lane 分配的复杂逻辑： 

out = out + static_cast<uint64_t>(blockIdx.y) * tma_aligned_mn * kNumPackedSFK;

// Load FP32 SFs
DG_STATIC_ASSERT(BLOCK_MN % 4 == 0, "Invalid block size");
const auto local_sf = sf + static_cast<uint64_t>(block_mn_idx) * BLOCK_MN * SF_K + block_sf_k_start;
if constexpr (SF_K < BLOCK_SF_K) {
    const auto local_sf_u32 = reinterpret_cast<uint32_t*>(local_sf);
    const auto num_values = in_block_mn * SF_K;
    const auto num_uint4 = num_values / 4;
    #pragma unroll
    for (uint32_t i = threadIdx.x; i < num_uint4; i += kNumThreads) {
        const auto& [x, y, z, w] = reinterpret_cast<const uint4*>(local_sf_u32)[i];
        ptx::st_shared(reinterpret_cast<uint4*>(sf_smem_buffer) + i, x, y, z, w);
    }
// ...
}
__syncthreads();

源码：deep_gemm/include/deep_gemm/impls/smxx_layout.cuh 第 130–159 行（SM100 转置+打包：uint4 向量化读入 SMEM）

第 141 行把 local_sf 视为 uint4* 后一次搬 16 字节（4 个 float32），用 ptx::st_shared 直接写入 SMEM——绕过编译器可能的非对齐存储。非 4 对齐的尾部（第 144–145 行）单独处理。大 K 场景（SF_K ≥ BLOCK_SF_K）回退到 warp-lane 分配：每 warp 一行，lane 内按 kNumElemsPerVec 步长遍历列。

写出阶段是转置和打包的融合：外层循环按 [packed_sf_k, BLOCK_MN] 遍历，每次取 4 个相邻 K 位置的 float32（从 SMEM 按行方向读取），打包成一个 int32 后写到 MN-major 的输出位置。打包公式就是 §UE8M0 打包 中的 4 路位移 OR。

PSUM 空隙行的安全处理

在 M 分组 contiguous GEMM 中，多个专家的 token 按 grouped_layout 排布，但相邻组之间可能存在空隙行（gap rows，图 4）。空隙的成因是对齐：每组的起始地址要对齐到 m_alignment（通常 128），上一组结束到下一组开始之间的行是未初始化的。

例如 grouped_layout=[100, 250, 370]、alignment=128 时：Group 0 占 [0, 100)，Group 1 从 align(100, 128)=128 开始占 [128, 250)，行 [100, 128) 是空隙。

变换内核在启动时先把每组的 MN 范围预算到 shared memory 中，然后定义 is_valid_mn lambda：遍历所有组，检查给定 MN 索引是否落在某组的有效范围内。不在任何组内的行是空隙行： 

if constexpr (kUsePsumLayout) {
    for (uint32_t g = threadIdx.x; g < kNumPsumGroups; g += kNumThreads) {
        const auto end_g = grouped_layout[g];
        group_mn_start[g] = g == 0 ? 0 : math::align(grouped_layout[g - 1], m_alignment);
        group_mn_end[g] = end_g;
    }
    __syncthreads();
}
// ...
// PSUM path skips uninitialized per-group MN gaps without early return.
const auto is_valid_mn = [&](const uint32_t& global_mn_idx) -> bool {
    if constexpr (kUsePsumLayout) {
        bool valid = false;
        for (uint32_t g = 0; g < kNumPsumGroups; ++ g)
            valid |= (global_mn_idx >= group_mn_start[g] and global_mn_idx < group_mn_end[g]);
        return valid;
    } else {
        return global_mn_idx < mn;
    }
};

空隙行的 SF 处理方式值得关注。回顾 §UE8M0 打包 中第 176 行：当 valid_mn 为 false 时，values[j]=0。float32 的 0 的指数字段是 0，打包后得到 UE8M0 编码 0x00。为什么不用 0xFF？因为 UE8M0 0xFF 对应 IEEE 754 的偏移指数 255——这是 float32 中为 Inf/NaN 保留的特殊编码。在块缩放 MMA 的上下文里，硬件将 UE8M0 0xFF 视为 NaN。如果空隙行的 SF 是 NaN，MMA 会传播 NaN 到累加器，污染有效结果。第 187 行的注释明确写道"Write safe finite scale codes for PSUM gap rows; UE8M0 0xff is NaN"。

写 0x00（即 2^{-127}）是安全的：空隙行的数据本身是未初始化的垃圾值，乘以一个极小的 SF 后对累加结果的影响可以忽略——在浮点精度范围内不会影响有效组的结果。具体来说，2^{-127} \approx 5.88 \times 10^{-39}，即使垃圾数据恰好是 FP8 能表示的最大值（约 448），乘积也只有 \sim 2.6 \times 10^{-36}，远低于 BF16 的最小精度粒度。这比另一种常见的做法——把空隙行的数据本身清零、SF 用正常值——更高效，因为清零数据需要额外的全局内存写操作，而只改 SF 的值在打包写出时顺便完成，不产生额外事务。

K 分组打包

K 分组（K-grouped）GEMM 用于权重梯度计算（dgrad），其中 K 维度按专家分组、每组长度不同。与 M 分组不同，K 分组的 SF 已经是 MN-major 的 float32 张量（不需要转置），pack_fp32_into_ue8m0 内核只做打包。

核心挑战是：每组的 sf_k 行数可能不是 4 的倍数——而打包要求 4 个 UE8M0 一组。解决方案是每组独立打包，不足 4 行的尾部用零填充，然后把所有组的打包结果拼接在一起。这意味着输出的 packed_sf_k 等于各组 ceil(group_sf_k / 4) 之和，可能大于整体 ceil(sf_k / 4)。

K 分组打包内核的结构与前两个内核不同：它不使用 SMEM 转置，而是每个 warp 负责一整行打包输出。内核模板的静态断言 BLOCK_PACKED_SF_K == kNumThreads / 32 保证 warp 数等于块内的打包行数——一一对应，无需 warp 间同步。

PSUM 与非 PSUM 路径的关键差异在第 245–249 行：非 PSUM 时 group_k 直接等于 layout_value（每组的绝对长度）；PSUM 时 group_k = layout_value - align(prev_group_end, k_alignment)——需要减去对齐后的前缀，得到该组的实际 K 跨度。

Host 侧分配输出张量时，由于内核运行时才读 psum_layout 的精确值，host 无法提前知道每组的精确大小。因此使用一个安全上界：packed_sf_k = (sf_k + num_groups * 3) / 4——每组最多浪费 3 行填充。这个上界的推导很直观：N 个组各自独立打包，最坏情况下每组的 group_sf_k 对 4 取余为 1（需要 3 行零填充），总共额外 3 × N 行未打包行，打包后增加 ceil(3N/4) 行——但代码用了更宽松的上界 (sf_k + 3N)/4（向上取整），多分配几行比内核越界写入要安全得多。

从实现角度看，这种"宽松上界"策略反映了 GPU 编程中的一个通用原则：在 host 侧浪费几 KiB 的显存远比在 device 侧做复杂的精确计算划算。Host 不知道每个组的 M 维度多大、K 维度的对齐状况如何，如果要精确计算就得复现内核的全部打包逻辑——维护成本高且容易出错。宽松上界把复杂度留给内核，host 只做一次简单的除法和加法。这种设计在 DeepGEMM 的其他地方也能看到，例如 get_num_sf_rows_for_moe 对掩码分组的上界估算采用了类似的思路——都是在精确计算不经济时选择可证明安全的上界，用空间换取实现的正确性、鲁棒性和长期可维护性，避免了脆弱的精确计算。

warp shuffle 缓存与组查找

K 分组打包内核中有一个值得关注的实现细节：grouped_layout（每组的边界信息）是通过 warp shuffle 而非 shared memory 分发的。内核在每个 warp 中让 32 个 lane 各缓存 4 个 layout 值到寄存器，总共覆盖 128 个组（恰好是 kNumGroups 的静态上界）。当 warp 需要查某个组的值时，用 __shfl_sync(0xffffffff, layout_cache[group_idx % 4], group_idx / 4) 从持有该值的 lane 广播到全 warp。

这比读 shared memory 更快的原因有两个。第一，warp shuffle 是寄存器到寄存器的操作，延迟只有一个时钟周期，而 shared memory 读取即使无 bank conflict 也需要约二十个周期。第二，K 分组打包内核不需要 SMEM 做转置（输入已经是 MN-major），如果为了分发 layout 而用 SMEM，就要额外考虑多 warp 之间的同步和 SMEM 空间分配，增加了不必要的复杂度。这种寄存器缓存加 shuffle 广播的模式在 DeepGEMM 的其他变换内核中也有体现——它是一种轻量级的 warp 内数据共享原语，适用于数据量刚好不超过一个 warp 的寄存器总容量（32 个 lane 各持有若干值）的场景。当数据量超过这个阈值时才需要回退到共享内存。

此外，每个 warp 在遍历各组时维护 num_padding_sf_rows 计数器，记录到当前组为止累计的零填充行数。这个计数器在后续的读取阶段用来从 packed_sf_k_idx（打包后的行索引）反推原始 sf_row_idx（未打包的行索引）：sf_row_idx = packed_sf_k_idx * 4 + j - num_padding_sf_rows。如果该行落在 [group_sf_row_start, group_sf_row_end) 之外，则跳过读取、用零向量代替——与 §PSUM 空隙行 中的零填充策略一致。

向量化写出阶段也值得一提：每个 lane 处理 mn 方向上的 4 个连续 int32（以 uint4 为单位），所以 32 个 lane 一次覆盖 128 个 MN 位置。不足 128 对齐的尾部由小于 in_block_mn_uint4 的循环条件自动处理，不需要额外的 mask 逻辑。最终一条 128-bit 对齐写入全局内存，完成从四行 float32 到一行 int32 的打包。

局限与未覆盖

  • 推断：选择 MN-major 布局可能是为了配合 UTCCP 按 128 元素列对齐的消费方式（参见上一篇中 UTCCP 的讨论），但源码中没有注释说明这一设计动机。
  • 未覆盖：fp8_einsum 内部的 SF 置换逻辑（get_col_major_tma_aligned_tensor 之外的路径）、Mega MoE 内核中 UTCCP 的行内转置。
  • 未覆盖：SM90 的 128×128 块缩放（不需要 UE8M0、不打包）的 SF 格式细节——SM90 直接使用 float32 转置后的 SF。
  • gran_k=128 的预打包 int32 路径在 K 分组时不可用（K 分组只支持 gran_k=32），因为 K 分组内核假设输入是 float32。
