TL;DR

  • EPBuffer 的通信区只按 MoE 形状算一次：取 dispatch 与 combine 所需字节数的较大者，再向上对齐到 2 MiB；开 FP8 dispatch 后，决定大小的往往是仍为 BF16 的 combine。
  • 展开布局给每个（token, 本地专家）对一行，按专家分段并补齐到 expert_alignment；它的 GPU 端前缀和与 DeepGEMM 的 PSUM 分组格式逐项吻合。
  • do_cpu_sync=False 时输出按最坏情况分配，有效区间只能从 GPU 上的 psum_num_recv_tokens_per_expert 读出；这就是解码路径的用法。
  • EPHandle 保存了一次路由的全部槽位；拿它重放 dispatch 会跳过计数和 CPU 同步，因此 topk_idx 在 handle 用完之前不能改。
  • dispatch 是一个 0/1 选择矩阵 \(S\)，combine 是它的转置，所以二者在反向中互换角色，并且都能复用前向的 handle。

DeepEP 库概览：四个 Buffer，一套通信底座

在进入代码之前，先看 DeepEP 作为一个软件库长什么样。DeepEP 是一个 Python + CUDA 库，用户在 Python 层创建缓冲区对象、调用通信方法，底层由 CUDA 内核通过 NVLink 或 RDMA 完成实际的数据搬运。

库的核心是四种缓冲区，每种负责一类通信模式（表 1）：

四种缓冲区共用同一套通信底座：NCCL Gin 设备端 API + 对称内存窗口（ep05 详解）。"对称"意味着每个 GPU 在同一偏移处看到的是同一个逻辑位置，内核可以直接用远程指针读写对端显存，不需要经过 CPU。

典型调用流程（以 MoE 前向为例）：

  1. 初始化：创建 EPBuffer，传入 MoE 形状参数（专家数、hidden 维、top-k）→ 库自动计算所需显存并注册对称内存，只做一次。
  2. Gate：模型对每个 token 算出 top-k 专家编号和权重（topk_idx、topk_weights）。这一步不在 DeepEP 里。
  3. Dispatch：调用 buffer.dispatch(x, topk_idx, ...) → token 被送到各专家所在的 GPU，返回展开后的激活张量和一个 EPHandle。
  4. 专家计算：把展开后的激活喂给 DeepGEMM 的分组 GEMM（dg04）→ 每个专家并行计算。
  5. Combine：调用 buffer.combine(expert_output, handle) → 结果按路由权重加权求和，写回每个 token 原来的位置。

反向传播时 dispatch 和 combine 互换角色，并复用前向的 handle，不再重新计算路由。

本篇从 EPBuffer 开始——它是最核心的一个，覆盖了 MoE 的 dispatch 和 combine 两条路径，训练和推理都从它进入。后续七篇逐层深入：ep02–ep04 拆内核，ep05 看通信底座，ep06 看资源估算，ep07–ep08 看其余三种缓冲区。

混合专家（Mixture of Experts，MoE）层在专家并行（expert parallelism，EP）下要做两次全对全通信：分发（dispatch）把每个 token 送到它选中的专家所在的 GPU，合并（combine）把专家输出按路由权重加回 token 原来的位置。DeepEP V2.5 把训练、推理预填充和推理解码用到的这两种通信统一进了一个类 EPBuffer，README 的说法是“高吞吐与低延迟 API 统一成单个 EPBuffer 接口，并提供面向分组专家 GEMM 的展开布局” [1]。

这一篇只讲接口和语义：一个 EPBuffer 占多少显存、dispatch 吐出来的张量长什么样、do_cpu_sync 开关换来了什么、handle 里存了什么、“延迟尾声”到底推迟了哪一步，以及为什么 dispatch 的反向恰好是 combine。内核内部怎样收发，留给第 2 篇（直连 dispatch）、第 3 篇（combine）和第 4 篇（混合模式）。

全文用一个运行例子：单机 8 卡（\(R=8\)）、\(E=256\) 个专家（每卡 \(E_\ell=32\) 个）、每 token 选 \(k=8\) 个专家、隐藏维 \(H=7168\)；训练与预填充时每卡最多 \(T=4096\) 个 token，解码时 \(T=128\)；下游 GEMM 的分组对齐取 DeepGEMM 的默认值 128。

直觉：把 token 送出去，再收回来

在读代码之前，先用一个最简单的画面理解 dispatch 与 combine 的语义。假设有 4 张 GPU，每张各管 2 个专家。某个 token 被 gate 选中了第 3 号和第 7 号专家——第 3 号在 GPU 1，第 7 号在 GPU 3。

  • dispatch：token 的隐藏向量从它所在的 GPU 被复制到 GPU 1 和 GPU 3，各放进一个缓冲区里等待专家计算。方向是"从 token 所在处扇出到多个专家所在处"。
  • combine：两个专家各自产出一个向量后，这些向量按路由权重做加权求和，结果写回 token 所在的 GPU。方向是"从多个专家所在处扇入回 token 原来的位置"。

dispatch 可以看作一个 0/1 的选择矩阵 \(S\)（哪个 token 去哪个专家），combine 就是 \(S^\top\) 加上权重——这就是后面说"二者在反向中互换角色"的原因。理解了"扇出-计算-扇入"这个三拍节奏，下面的缓冲区大小计算和句柄复用就好跟了。

缓冲区按最坏情况一次分配，大小由 dispatch 与 combine 的较大者决定

先看构造。README 建议每个 EP 组创建一个 EPBuffer 并反复复用，所有 rank 必须对 num_max_tokens_per_rank 取同一个值，并且这个容量要覆盖训练、预填充、解码里最大的那一批（README 第 105–109 行）。构造函数的参数分成三组（ep.py 第 242–261 行）：

  • 决定通信区大小的：要么直接给 num_bytes（不含工作区，必须是 2 MiB 的倍数），要么给 MoE 形状 num_max_tokens_per_rank、hidden、num_topk、use_fp8_dispatch，由库来算。
  • 拓扑与算法开关：allow_hybrid_mode（多机时是否走 NVLink + RDMA 两级转发，见第 4 篇）、allow_multiple_reduction（combine 是否允许多次归约，见第 3 篇）、deterministic、prefer_overlap_with_compute（倾向少用 SM）、sl_idx 与 num_allocated_qps（RDMA 服务等级与队列对数量，见第 6 篇）。
  • 生命周期：num_cpu_timeout_secs（默认 300 秒）、num_gpu_timeout_secs（默认 100 秒）、explicitly_destroy，以及专家负载均衡用的独立内存区 lb_allocation_plan_or_num_bytes（见第 8 篇）。
num_allocated_qps=0 时自动取值：允许混合模式时为 65（网卡支持快速 RDMA 原子操作）或 129，否则为 17（ep.py 第 327–335 行）。多出来的那 1 个队列对留给计数用的 notify warp。

静态方法 get_buffer_size_hint 与构造函数调用的是同一个 C++ 函数 calculate_ep_buffer_size（ep.py 第 373–399 行），所以“先问大小、再决定要不要重建”不会和实际分配有出入。README 的 get_buffer 例子正是这样做的：已有 buffer 的 num_bytes 不小于新需求就直接复用（README 第 133–140 行）。这个函数本身做三件事：查拓扑、分别算 dispatch 和 combine 需要的字节数、取较大者对齐到 2 MiB。

const auto [num_rdma_ranks, num_nvl_ranks] = comm::get_physical_domain_size(nccl_comm);
const auto [num_scaleout_ranks, num_scaleup_ranks] = comm::get_logical_domain_size(nccl_comm, allow_hybrid_mode);
const auto is_scaleup_nvlink = num_scaleup_ranks == num_nvl_ranks;
// ...
const auto elem_size = use_fp8_dispatch ? sizeof(__nv_fp8_e4m3) : sizeof(nv_bfloat16);
const auto num_sf_packs = use_fp8_dispatch ? math::ceil_div(hidden, 32) : 0; // An approximation for number of SF packs
const auto num_dispatch_bytes = get_dispatch_buffer_size(
    num_max_tokens_per_rank, hidden, num_sf_packs, num_topk, elem_size,
    num_scaleout_ranks, num_scaleup_ranks,
    is_scaleup_nvlink);
// ...
const auto num_combine_bytes = get_combine_buffer_size(
    num_max_tokens_per_rank, hidden, num_topk,
    num_scaleout_ranks, num_scaleup_ranks,
    is_scaleup_nvlink, allow_multiple_reduction);
// ...
return math::align<int64_t>(std::max(num_dispatch_bytes, num_combine_bytes), kNumAllocationAlignmentBytes);

源码：csrc/buffers/ep.hpp 第 262–282 行（节选）

这里有三个容易忽略的细节。第一，“scale-up 域是不是 NVLink”由逻辑域与物理域是否一致决定：单机时两者都是 8 卡，is_scaleup_nvlink 为真；多机但关掉混合模式时，逻辑 scale-up 域是全部 16 卡，而 NVLink 只连 8 卡，于是为假，直连内核要额外准备一块发送缓冲给 RDMA 用。第二，num_topk=0 是允许的，此时按 32 算（第 259–260 行的注释说很多内核限制 \(k\le 32\)），得到的是偏大的上界。第三，FP8 的缩放因子按每 32 个元素一个 4 字节包估算，代码注释称之为近似；若按 1×128 分块缩放，实际只需要四分之一。

一个 token 槽有多大

dispatch 和 combine 的缓冲区都由“token 槽”拼成。一个槽依次放隐藏向量、缩放因子和元数据，各自对齐到 32 字节（TMA 的对齐要求），总长再对齐到 64 字节（RDMA 的对齐要求）：

num_metadata_bytes(num_topk * (sizeof(int) + sizeof(float)) +
                   (with_metadata ? (1 + num_topk) * sizeof(int) : 0)),
// ...
const auto num_data_bytes = math::align<int>(
    math::align(num_hidden_bytes, kNumTMAAlignmentBytes) +
    math::align(num_sf_bytes, kNumTMAAlignmentBytes) +
    math::align(num_metadata_bytes, kNumTMAAlignmentBytes), kNumRDMAAlignmentBytes);

源码：layout/ep/token.cuh 第 25–37 行（节选）；对齐常数见 compiled.cuh 第 64–69 行

dispatch 槽带完整元数据：\(k\) 个专家号和 \(k\) 个权重（各 4 字节），再加 1 个源 token 全局编号和 \(k\) 个链表下标。代入运行例子：BF16 时隐藏向量 \(7168\times 2=14336\) 字节，元数据 \(8\cdot 8+9\cdot 4=100\) 字节、对齐后 128，合计 \(B_d=14464\) 字节；combine 槽只带 \(k\) 个专家号和权重（64 字节），\(B_c=14400\) 字节。FP8 时隐藏向量 7168 字节，缩放因子按 \(\lceil 7168/32\rceil\times 4=896\) 字节估算，\(B_d=8192\) 字节。

单机直连时，dispatch 的接收区为每个源 rank 预留 \(T\) 个槽，NVLink 写对端不需要发送缓冲；combine 的接收区按 \(\min(R,k)\) 份预留（允许多次归约时）。于是

\[ \text{dispatch} = R\,T\,B_d,\qquad \text{combine} = \min(R,k)\,T\,B_c,\qquad \text{hint} = \operatorname{align}_{2\,\mathrm{MiB}}\big(\max(\text{dispatch},\ \text{combine})\big) \](1)

多机时公式更长（混合模式要给 scale-out 的发送与接收另算，每个 scale-out 对端还要多留 1280 个槽，对应按通道切分时每个通道向上取整的余量；见ep.hpp 第 183–247 行），但思路相同：都是“最坏情况下每个来源可能塞满 \(T\) 个 token”。表 2 把五种配置代进式 (1) 及其多机版本。

表里有两点值得记住。其一，FP8 dispatch 把每个槽从 14464 字节缩到 8192 字节，但 combine 输入必须是 BF16（ep.hpp 第 816 行的断言），所以总大小只从 452 MiB 降到 450 MiB。其二，两机 16 卡时，关掉混合模式反而更费显存：直连 combine 要为 16 个对端各留一份发送区（900 MiB），而混合模式的 scale-out 部分只按 2 个对端预留。

每次 dispatch 和 combine 都会按本次调用的 num_max_tokens_per_rank、hidden、num_topk 重算所需字节数，并断言不超过 num_bytes（ep.hpp 第 543–547 行、第 865–868 行）。所以用 BF16 形状建的 buffer 可以跑同形状的 FP8 dispatch，反过来则可能断言失败。

构造函数实际申请的 GPU 内存比 hint 多两块：前面一块工作区（存放计数、屏障信号等，大小由 EPWorkspaceLayout 决定并对齐到 2 MiB），后面一块可选的 LB 区；另外还有一块映射到设备地址空间的锁页主机内存，供 CPU 读取接收计数（ep.hpp 第 69–91 行）。print_memory_usage() 会分别打印工作区、通信区和 RDMA 存储的大小（base.hpp 第 37–49 行）。

把各层加在一起，一个 EPBuffer 在 GPU 上的总占用可以分解为：

  1. 工作区（EPWorkspaceLayout）：原子计数器、屏障信号、RDMA 队列指针等控制数据。大小由 rank 数和队列对数量决定，对齐到 2 MiB。元素只是 32/64 位整数，相比通信区可忽略。
  2. 通信区：即 get_buffer_size_hint 返回的值，式 (1) 给出公式，表 2 列出了各配置的具体大小。这是占用的大头。
  3. LB 区（可选）：由 BufferAllocator 管理，按 2 MiB 对齐的若干子区拼成，供 redundancy_mapping、梯度缓冲等使用。不传 lb_allocation_plan_or_num_bytes 则不分配。
  4. 锁页主机内存：每个 scale-up 对端各占一小块（存放 num_recv_tokens 和 per-expert 计数），映射到 GPU 地址空间，供 CPU 同步和 notify warp 使用。

print_memory_usage()（base.hpp 第 37–49 行）把工作区、通信区和 RDMA 存储分开报告，是调优显存预算的入口。

生命周期：构造和销毁都是集合操作

V2.5 把原来的 ElasticBuffer 拆成 EPBuffer、EngramBuffer、PPBuffer、BucketBuffer 四个类，共享 BufferBase 的生命周期（README 第 11–16 行）。对使用者有三条约束：

  • 构造结束前，Python 端会 torch.cuda.synchronize() 后做一次 group.barrier()，所以组内每个 rank 都要同时构造（ep.py 第 360–363 行）。
  • destroy() 先在当前流上做一次全组 GPU 屏障“等所有 GPU 上的工作完成”，再释放主机工作区和 NCCL 上下文（ep.hpp 第 102–120 行），同样要求组内同时调用。README 因此要求替换 buffer 前先结束所有未完成的操作。
  • explicitly_destroy=False 时由析构函数代劳；设为 True 却忘了调用，析构时会打印“可能泄漏资源”的提示（base.hpp 第 18–29 行）。测试脚本统一用显式销毁，因为它们会反复重建 buffer。

BufferAllocator 只和 LB 区有关：它先用 meta 张量记下一串对齐到 2 MiB 的偏移，buffer 建好后再把这些占位张量换成指向 LB 区的视图（allocator.py）。细节放到第 8 篇。

展开布局：每个（token, 本地专家）对一行，按专家分段并对齐

dispatch 有两种输出布局。非展开布局下，一个 token 不论选中本 rank 的几个专家，都只占一行；recv_topk_idx 告诉你这一行该交给哪些本地专家（不在本 rank 的位置填 −1），下游要自己再做一次按专家的重排。展开布局（do_expand=True）则直接给每个（token, 本地专家）对一行，并把同一专家的行排在一起，正好是分组 GEMM 想要的“连续布局”。图 1 用一个只有 3 个本地专家、对齐为 4 的小例子画出两者。

展开模式下张量形状也随之改变（ep.hpp 第 671–709 行）：recv_x 是 \([N_{\text{exp}}, H]\)，\(N_{\text{exp}}\) 为各专家对齐后行数之和；recv_topk_weights 变成一维，每行一个路由权重；recv_topk_idx 不再返回（为 None），因为行所在的段已经说明了专家号。每个源 token 的各个副本落在哪一行，记录在 handle 的 recv_src_metadata[:, 2:] 里，combine 靠它把副本找回来。

行号由原子加分配，前缀和兼作计数器

计数在 dispatch 主内核里完成：notify warp 汇总所有源 rank 发来的“每个本地专家收到几个 token”，记下未对齐的真实值，再把计数对齐到 \(a\)（dispatch.cuh 第 203–219 行），最后由一个 warp 写出排他前缀和（第 250–256 行）。于是专家 \(i\) 的段起点 \(s_i=\sum_{j<i}\operatorname{align}(c_j, a)\) 已经对齐。拷贝尾声里，每个到达的 token 对它的每个本地专家做一次原子加，拿到的旧值就是它的行号：

// Calculate target indices in the tensor
constexpr int kMetadataStride = 2 + kNumTopk;
int dst_tensor_idx = -1;
if (not kDoExpand and ptx::elect_one_sync()) {
    dst_tensor_idx = i;
} else if (kDoExpand and kCachedMode and lane_idx < kNumTopk) {
    // Cached expand mode: read pre-computed dst_tensor_idx from metadata
    dst_tensor_idx = recv_src_metadata[i * kMetadataStride + 2 + lane_idx];
} else if (kDoExpand and not kCachedMode and dst_expert_idx >= 0) {
    dst_tensor_idx = atomicAdd(psum_num_recv_tokens_per_expert + dst_expert_idx, 1);
}

源码：impls/ep/dispatch_copy_epilogue.cuh 第 113–123 行

这一步一石二鸟：原子加之后，psum_num_recv_tokens_per_expert[i] 从段起点 \(s_i\) 变成了 \(s_i+c_i\)，即“前面各专家对齐后的累计行数，加上本专家的真实行数”。EPHandle 的文档把这条性质写得很明白：\(\text{psum}[i]-\operatorname{align}(\text{psum}[i-1],a)\) 是专家 \(i\) 的真实行数，\(\operatorname{align}(\text{psum}[i],a)\) 是专家 \(i{+}1\) 的起点（ep.py 第 47–53 行）。在图 1 中，计数 \(c=(5,2,3)\)，起点 \((0,8,12)\)，尾声结束后 psum 为 \((5,10,15)\)；非展开模式下同一个张量则是对齐后计数的包含前缀和 \((8,12,16)\)（ep.hpp 第 711–720 行）。

常见误解

psum 在 dispatch 主内核结束时还只是起点，要等拷贝尾声的原子加做完才变成上面说的“起点 + 真实计数”。在延迟尾声模式下，这意味着必须先 wait() 再读 handle 里的 psum。

为什么要对齐，以及它和 DeepGEMM 的关系

分组 GEMM 以 \(BM\) 行为一块切 M 轴，如果某个专家的段跨进了下一个专家的块，一个 tile 就要同时乘两套权重。DeepGEMM 的做法是要求每个专家段对齐到块大小 [2]：README 说连续布局里“每个专家段必须对齐到 GEMM 的 M 块大小，即 get_mk_alignment_for_contiguous_layout()”（DeepGEMM README 第 76–78 行）。这个值默认是 128，可以用 setter 改；在 SM100 上，get_theoretical_mk_alignment_for_contiguous_layout 返回 256（runtime.hpp 第 12–18 行、第 57–64 行）。DeepEP 的 README 因此建议把 expert_alignment 设成前者（README 第 160 行）。

对齐值 \(a\) 的选择是显存浪费与 GEMM 效率之间的权衡。每个有 \(c_i\) 个 token 的专家段被补到 \(\operatorname{align}(c_i, a)\) 行，最坏浪费 \(a{-}1\) 行。\(E_\ell\) 个本地专家共浪费至多 \((a{-}1)\cdot E_\ell\) 行，乘以 BF16 隐藏向量的行宽即为额外显存：运行例子中 \(a=128,\;E_\ell=32\) 时最坏浪费 \(127\times 32\times 7168\times 2\approx 55\) MiB；SM100 的 \(a=256\) 翻倍到约 111 MiB。解码时 token 少，多数专家的段长远小于 \(a\)，大部分行是空隙——这就是 表 3 里最坏情况远大于平均有效行数的根源。减小 \(a\) 可以节省显存，但会破坏 GEMM 的块对齐假设：一个 tile 可能跨越专家边界，需要同时加载两套权重矩阵，DeepGEMM 不支持这种模式。因此唯一安全的 \(a\) 值是 GEMM 的 M 块大小或其倍数。

更巧的是前缀和的格式。DeepGEMM 的 M 分组连续 GEMM 接受两种分组描述：长度为 \(M\) 的“每行属于哪组”（空隙填 −1），或打开 use_psum_layout 后长度为组数的前缀和（gemm.hpp 第 212–220 行）。它的测试这样构造后者：

还有两个与展开布局相关的开关。do_zero_padding=True 会在拷贝尾声末尾把每段的对齐空隙清零：隐藏向量、权重和缩放因子都写 0（dispatch_copy_epilogue.cuh 第 232–325 行），它只能与 do_expand=True 同用（ep.hpp 第 316–317 行）。测试逐个专家检查 \([\text{psum}[i], \operatorname{align}(\text{psum}[i],a))\) 区间全为零（test_ep.py 第 430–435 行）。另一个是 deterministic=True：原子加分配的行号顺序取决于 warp 的到达先后，每次可能不同；打开后会在尾声之后按源 token 的全局编号对每个专家段内部重新排序，并相应改写 recv_src_metadata[:, 2:]（ep.py 第 174–205 行）。

do_cpu_sync：用一次 CPU 等待换精确的张量大小

dispatch 结束前，接收端并不知道自己会收到多少行，而 PyTorch 张量必须在分配时给出形状。do_cpu_sync 决定这个矛盾怎么解（README 第 162 行）。

打开时（默认），主内核的 notify warp 把每个源 rank 发来的 token 数和每个本地专家的对齐计数写进一块映射到 GPU 地址空间的锁页主机内存（dispatch.cuh 第 222–229 行），CPU 在尾声里忙等这些值就绪，然后按精确大小分配输出。关闭时，CPU 不等，直接按最坏情况分配：

} else if (do_cpu_sync) {
    // ...
    pybind11::gil_scoped_release release;
    // ...
    const auto start_cpu_time = std::chrono::high_resolution_clock::now();
    while (true) {
        // ...
        if (std::chrono::duration_cast<std::chrono::seconds>(now - start_cpu_time).count() > context->num_cpu_timeout_secs)
            throw EPExceptionWithLineInfo("Dispatch CPU wait", get_buffer_info());
    }

    num_recv_tokens = num_max_tokens_per_rank * context->num_ranks;
    num_expanded_tokens = context->num_ranks * num_max_tokens_per_rank * std::min(num_topk, num_local_experts);
    num_expanded_tokens += (expert_alignment - 1) * num_local_experts;

}

CPU 同步的代价有三部分。一是 CPU 线程被阻塞到对端的计数到达为止，期间不能继续向 GPU 排后面的内核；代码在忙等前释放了 GIL，注释说这是为了不卡住其他 Python 线程（例如 KV 传输）。二是它要求一次真实的主机–设备往返，这与 CUDA graph 捕获不相容——我们的理解是，这正是解码路径要关掉它的主要原因，README 只说“解码时用 GPU 端计数”。三是超时：默认 300 秒等不到就抛异常并打印各计数的当前值，便于排查卡住的 rank。

最坏情况的公式也有道理：每个源 rank 最多发来 \(T\) 个 token，一个 token 到一个 rank 只会到一次（发送端已按 rank 去重），到达后最多展开成 \(\min(k,E_\ell)\) 行，每个专家段最多再补 \(a-1\) 行空隙：

\[ N_{\text{exp}}^{\max} = \operatorname{align}_a\!\big(R\,T\,\min(k, E_\ell) + (a-1)\,E_\ell\big) \](2)

表 3 说明了两种模式的分工：解码时 \(T\) 小，按最坏情况多分配一百多 MiB 换来无需 CPU 往返；训练和预填充时 \(T\) 大，最坏情况要 3.6 GiB 而平均只用八分之一，CPU 同步的代价反而值得付。这也是 README 把 do_cpu_sync=True 标为“训练与预填充常用”的原因。

关掉同步后，下游怎样知道哪些行有效

CPU 不知道计数，handle 里的 num_recv_tokens 和 num_expanded_tokens 就只是上界（ep.py 第 96–98 行的注释写着“没有 CPU 同步时可能不准”），CPU 侧的 num_recv_tokens_per_expert_list 为空。唯一可信的信息在 GPU 上：

  • psum_num_recv_tokens_per_scaleup_rank[-1] 是收到的 token 总数。拷贝尾声自己就这么做：当传入的行数等于最坏值 \(R\,T\) 时，改从这个张量读真实值（dispatch_copy_epilogue.cuh 第 63–65 行）。
  • psum_num_recv_tokens_per_expert 给出每个专家段的真实终点，下游 GEMM 必须用它确定有效区间（README 第 162 行原话）。按上一节的分析，它可以原样作为 DeepGEMM PSUM 布局的输入；GEMM 只计算 \([s_i, \text{psum}[i])\) 内的行，最后一个专家段之后的大片容量既不读也不写。

竞态安全性也值得点明。psum_num_recv_tokens_per_expert 在 dispatch 主内核中被 notify warp 初始化为排他前缀和（各段起点），在拷贝尾声中被每个 token 的 atomicAdd 就地递增到最终值。两者的先后由 CUDA 流序保证：尾声内核在主内核完成后才启动（同一流上串行，或延迟模式下 wait() 先等主内核事件再在计算流上启动尾声）。下游 GEMM 在 wait() 返回后排入计算流，与尾声在同一条流上串行，因此一定能看到所有 atomicAdd 的最终结果。这就是 GPU 端计数无需额外 fence 的原因——CUDA 的同流有序执行已经提供了充分的序。

README 特意提醒：do_zero_padding=True 只清零专家之间的对齐空隙，不会让最后一段之后的未用容量变成有效数据（README 第 287 行）。那一段内存是 torch.empty 得到的，内容未定义；如果你的专家计算按整块容量做逐元素运算，又不按 psum 截断，就会读到垃圾。

接收端的拷贝尾声也不再分配行号，而是从 recv_src_metadata[:, 2:] 读出上次的展开行号（上一节摘录里的 kCachedMode 分支）。所以缓存 dispatch 产生的布局与原 dispatch 逐行相同，测试直接用 torch.equal 比较二者的接收数据、dst_buffer_slot_idx 和 psum（test_ep.py 第 441–450 行）。数据可以换——测试里缓存 dispatch 传的仍是同一个 x，但接口只要求形状一致，训练反向正是用它来发送梯度；变的只能是“发什么”，不能是“发到哪”。

为什么 topk_idx 在 handle 用完前不能改

槽位表 dst_buffer_slot_idx 只记录“发到目标 rank 的第几个槽”，并不记录目标是哪个 rank。上面的摘录里，目标 rank 号 stored_dst_rank_idx 仍由 topk_idx 现算（dispatch.cuh 第 313–322 行）；随 token 一起发出的元数据里也带着 topk_idx，接收端靠它判断该 token 属于哪些本地专家。combine 同样要用 handle.topk_idx 来决定把结果加回哪里（ep.py 第 821–835 行）。一旦 topk_idx 变了，“新的目标 rank”配上“旧的槽位”，数据会写进别的 token 的槽里，且不会报错。为此 handle 只保存引用，并在每次访问时检查 PyTorch 的版本计数器：

# `topk_idx` cannot change in the handle
self._topk_idx = topk_idx
self._topk_idx_version = None if topk_idx.is_inference() else topk_idx._version

@property
def topk_idx(self) -> torch.Tensor:
    assert self._topk_idx_version is None or self._topk_idx._version == self._topk_idx_version, \
        '`topk_idx` must not be modified while the EP handle is in use'
    return self._topk_idx

这个检查有盲区，文档自己列了出来：通过 .data 或裸指针的写入不会增加版本号；在 inference mode 下创建的张量没有版本计数器，根本不检查（ep.py 第 39–42 行）。推理服务通常整体跑在 inference mode 下，这时只能靠调用者自觉。另外，缓存模式不支持在线负载统计 cumulative_local_expert_recv_stats（dispatch.hpp 第 55–57 行），因为计数阶段被跳过了。

什么时候能复用 handle

只在“路由完全相同”时：训练里同一层前向的 handle 用于该层的两次反向通信。README 明说，新的路由决策需要一次新的 dispatch，解码本身并不会让旧的 handle 变得可复用（README 第 162 行）。

更具体地，以下任一条件成立时，上一个 handle 就不能再传给 dispatch，必须跑一次完整的（非缓存）dispatch 拿新的 handle：

  • 路由变了：新的 forward pass 产生了不同的 topk_idx——最常见的场景。每个 micro-batch 的 gate 输出通常不同，所以前向生成的 handle 只在该层的反向中用两次（发送梯度和合并梯度各一次）。
  • 形状参数变了：num_experts、expert_alignment 或 num_max_tokens_per_rank 与 handle 创建时不同。代码在缓存 dispatch 入口逐项检查并断言（ep.py 第 652–663 行）。
  • EPBuffer 被重建了：handle 内的指针（如 recv_src_metadata）指向旧 buffer 的显存，旧 buffer 销毁后这些指针悬空，缓存 dispatch 会段错误或读到垃圾。
  • 张量被原地修改：即使值没变，.data.copy_() 或裸指针写入不增加版本计数器，检查会放过——语义上 handle 已失效但代码检测不到（上文已提到这个盲区）。

延迟尾声：通信先发出去，拷贝等到 wait() 再做

每次 dispatch 都由两个内核组成：在通信流上运行的主内核（计数、发送、等数据到齐），和把接收缓冲里的 token 搬进输出张量的拷贝尾声（copy epilogue）；combine 对应的是主内核加归约尾声（reduce epilogue）。尾声之前还有主机端的工作：如果开了 CPU 同步，要先忙等计数；然后按计数分配输出张量。defer_epilogue=True 把这三件事——CPU 等待、分配、尾声内核——一起推迟到使用者调用 wait() 的那一刻：

// Defer epilogue: record the created tensors only, and return intermediately
// NOTES: CPU sync will be deferred, too
if (defer_epilogue) {
    EP_HOST_ASSERT(async_with_compute_stream);
    const auto event = stream_control_epilogue(
        tensors_to_record, compute_stream, allocate_on_comm_stream, true);
    std::function<pybind11::object()> epilogue_hook = [epilogue = std::move(epilogue)]() mutable {
        return epilogue(at::cuda::getCurrentCUDAStream(), std::nullopt);
    };
    return pybind11::make_tuple(pybind11::none(), event, epilogue_hook);
}

Python 层把这个钩子挂到返回的 EventOverlap 上（ep.py 第 749–753 行）。wait() 先让当前流等待主内核结束的事件，再调用钩子，钩子的返回值就是 dispatch 的四元组或 combine 的二元组：

注意最后一行：钩子执行一次就被清空，第二次 wait() 返回 None。README 的说法是“结果由第一次 wait 产生，请保留它”（第 287 行）。由此还能推出一个代码里没有写明的陷阱：EventOverlap 也支持 with 语法，退出时会调用同一个 current_stream_wait()（event.py 第 98–106 行），这会把延迟尾声跑掉而丢弃结果；对延迟模式的事件，应当显式调用 wait()。

图 2 画出了 README 推荐的用法在两条流上的排布：先发起通信，CPU 立刻返回去排独立的计算，等到专家计算真正需要输入时再 wait()。

和另外两种模式对比更清楚（ep.hpp 第 152–181 行、第 782–786 行）：

  • async_with_compute_stream=False：主内核和尾声都排在通信流上，然后计算流立即等待通信流。调用返回时数据可以直接用，但计算流在这期间没有可重叠的工作。
  • async_with_compute_stream=True、不延迟：主内核和尾声仍都在通信流上，返回张量和事件；使用前要 event.current_stream_wait()。若开了 CPU 同步，CPU 在 dispatch 调用内部就被卡住，等不到计数就不能去排后面的计算。
  • 延迟：只有主内核在通信流上；CPU 立即返回。到 wait() 时，如果主内核已经结束、计数已写入主机内存，CPU 的忙等会立即结束。
尾声内核以全部 SM 启动（ep.hpp 第 723–743 行的注释写着“Launch copy kernels with full SMs”），而主内核只用估算出的少量 SM（见第 6 篇）。

延迟带来的好处，代码和文档能直接证实的有两条：CPU 不必在通信调用里阻塞；combine 的 bias 可以是在通信发起之后才算出来的张量（例如共享专家的输出），因为 bias 指针直到尾声执行时才解析——代码注释说“在这里解析指针，以便在延迟尾声里保留 bias 张量”（ep.hpp 第 936–940 行，README 第 289 行）。还有一条是我们的推测：用满 SM 的尾声如果留在通信流上，会和计算流上的独立计算抢 SM；挪到计算流上、排在独立计算之后，两者就串行而不互相干扰。

previous_event 与 allocate_on_comm_stream

默认情况下，通信流在开始前等待计算流上“此刻之前”的全部工作（ep.hpp 第 122–133 行）。如果独立计算已经先排进了计算流，这种等待就把重叠吃掉了。previous_event 让通信只等一个更早的事件：在排独立计算之前用 EPBuffer.capture() 在计算流上记一个事件，再把它传进来（README 第 289 行）。这时必须同时打开 allocate_on_comm_stream：

上方几行注释给的理由是：previous_event 意味着重叠的计算内核先被排进去了，为了“不使用计算流上的内存”，必须在通信流上分配。我们对它的理解是：PyTorch 的缓存分配器按流管理空闲块，计算流上刚被释放的块可能仍被那些已排队、尚未执行的计算内核使用；通信流只等了更早的事件，若从计算流的池里拿内存，就可能与它们写同一块地址。把分配切到通信流，就避开了这种跨流复用。两个流之间的张量生命周期则靠 record_stream 维持；设置 EP_AVOID_RECORD_STREAM=1 时改为把张量挂在事件对象上，此时事件本身必须活到通信结束（ep.hpp 第 159–170 行，README 第 402 行）。

为什么成立，用一点线性代数就能看清。以展开模式为例，把全组所有 token 叠成 \(x\in\R^{N\times H}\)，把某个 rank 收到的展开行叠成 \(r\in\R^{M\times H}\)。dispatch 只做复制和搬运，不做任何算术，所以它是一个线性映射：

\[ r = S\,x,\qquad S\in\{0,1\}^{M\times N},\qquad S_{m,t}=1 \iff \text{第 } m \text{ 行是 token } t \text{ 的副本} \](3)

\(S\) 的每一行恰好有一个 1（每行来自唯一的 token），每一列有几个 1 取决于该 token 选中了本 rank 的几个专家。专家计算把第 \(m\) 行变成 \(z_m=w_m\,f_{e(m)}(r_m)\)，其中 \(e(m)\) 是该行所在段的专家、\(w_m\) 是一维 recv_topk_weights 的第 \(m\) 项——README 规定路由权重由专家计算在 combine 之前乘上，combine 只求和（README 第 279 行）。于是 combine 是

\[ y_t = \sum_{m:\ S_{m,t}=1} z_m + b_t \quad\Longleftrightarrow\quad y = S^{\top} z + b \](4)

其中 \(b\) 是可选的 bias（如共享专家输出或残差）。对线性映射求梯度，就是乘它的转置：

\[ \frac{\partial L}{\partial x} = S^{\top}\frac{\partial L}{\partial r},\qquad \frac{\partial L}{\partial z} = S\,\frac{\partial L}{\partial y},\qquad \frac{\partial L}{\partial b}=\frac{\partial L}{\partial y} \](5)

式 (5) 的左式说：一个 token 的输入梯度是它所有副本梯度之和——这正是 combine 做的事（\(S^\top\) 作用）。中式说：输出梯度要原样复制给该 token 的每个副本——这正是 dispatch 做的事（\(S\) 作用）。用图 1 的数字检查：token A 在 rank 0 上有两个副本，第 0 行（e0）和第 8 行（e1）；前向 combine 给出 \(y_A=z_0+z_8+(\text{其他 rank 上的副本})\)，于是 \(\partial L/\partial z_0=\partial L/\partial z_8=\partial L/\partial y_A\)，由 dispatch 把 \(\partial L/\partial y_A\) 送到这两行；反过来 \(\partial L/\partial x_A=\partial L/\partial r_0+\partial L/\partial r_8+\cdots\)，由 combine 把各行梯度加回 A 的原位置。

图 3 把这件事和 handle 联系起来。式 (3) 中的 \(S\) 完全由路由决定，前向 dispatch 已经把它“物化”在 handle 里：槽位表决定 \(S\) 的列怎样映射到各 rank，recv_src_metadata 决定行号。所以 combine_backward 用的是带 handle 的缓存 dispatch，不需要再计数、也不需要 CPU 同步（README 第 281 行：“缓存 dispatch 重放保存的展开布局，不再做接收计数的 CPU 同步”）；dispatch_backward 用的 combine 本来就要 handle。这也是 handle 必须在整个反向结束前保持有效、topk_idx 不能被改的根本原因。

路由权重的梯度走的是同一条路。在展开模式下，recv_topk_weights[m] 是 \(W_{t,j}\) 的一个副本，而且每个 \((t,j)\) 至多出现在一行，所以它的梯度也是“按原路送回”。README 的 dispatch_backward 把 grad_recv_topk_weights 作为 combine 的 topk_weights 传入，取回的 combined_grad_topk_weights 形状为 \([N_{\text{local}}, k]\)；测试验证了 combine 返回的权重与原始 topk_weights 逐位相等（test_ep.py 第 514–518 行），说明权重确实被一对一地送回原位置。测试注释还提醒，展开模式下 combine 要带 topk_weights 需要 allow_multiple_reduction=True（第 229–231 行）。

非展开模式的推导相同，只是 \(S\) 的粒度变成“（token, 目标 rank）”：一个 token 到一个 rank 只占一行，本地多个专家的扇出与求和由使用者在 rank 内完成，combine 再把各 rank 的部分和加起来。

两点实现上的不对称值得一提。其一，精度：反向 combine 的输入（即各副本的梯度）必须是 BF16，与前向 combine 同一条断言；反向 dispatch 则可以像前向一样发送 FP8 数据加缩放因子，README 的 combine_backward 签名接受二元组。其二，dispatch_backward 也接受 bias。按式 (4) 的形式，它会被加到 \(\partial L/\partial x\) 上；我们推测用途是把 \(x\) 经由其他路径（残差、共享专家）得到的梯度在同一个尾声里合并，README 没有展开说明。

局限与未覆盖

  • 没有实测。本文所有字节数（表 2、表 3）都是把源码公式代入示例参数算出来的，脚本为 plots/size_hint.py；没有 GPU 上的测量，也不涉及任何时延或带宽。“延迟尾声能隐藏多少时间”取决于独立计算的长短，仓库没有给出数据，本文也不给。
  • 推断与事实的界线。以下几点是我们根据代码推断的，仓库没有直接说明：解码关闭 CPU 同步与 CUDA graph 捕获的关系；DeepEP 的 psum 可原样喂给 DeepGEMM 的 PSUM 布局（两侧格式一致，但没有官方串联示例）；把尾声留到计算流上可避免与独立计算抢 SM；allocate_on_comm_stream 防止的是跨流复用缓存块；dispatch_backward 中 bias 的用途；以及对延迟事件使用 with 会丢失结果。
  • 文档与代码的细微差异。hint 对 FP8 缩放因子按每 32 元素一个包估算，偏大于 1×128 缩放的实际需要，代码注释自称近似；num_topk=0 时按 32 计算。这些都只会让 hint 偏大，不会偏小。
  • 没讲的部分。dispatch 主内核如何计数、去重、经 TMA 和 NVLink/RDMA 发送（第 2 篇）；combine 的归约顺序、多次归约与 bias 的加法细节（第 3 篇）；混合模式的转发、通道与链表（第 4 篇）；SM 数和 QP 数的估算公式（第 6 篇）；deterministic 模式的完整排序规则只点到为止。
  • 版本。本文对应 DeepEP 提交 f6aa38f（V2.5 之后）。V1 的接口和低延迟内核已被完全移除（README 第 18 行），旧文章里关于 Buffer、low_latency_dispatch 的描述不适用于这里。

小结

一个 EPBuffer 要回答的问题是：在不知道路由结果的前提下，怎样让通信既能被提前发起、又能交出分组 GEMM 直接可用的输出。DeepEP V2.5 的回答分四层。容量按最坏情况一次算定，由 dispatch 与 combine 中较大的一方决定。输出采用按专家分段、对齐的展开布局，段边界由一个兼作原子计数器的前缀和给出，格式与 DeepGEMM 的 PSUM 布局一致。要不要为精确大小付一次 CPU 等待，由 do_cpu_sync 交给使用者：训练和预填充付，解码不付而改用 GPU 端前缀和。最后，一次路由的全部信息存进 handle，供反向的两次通信原样重放；这在数学上之所以成立，是因为 dispatch 和 combine 互为转置。
