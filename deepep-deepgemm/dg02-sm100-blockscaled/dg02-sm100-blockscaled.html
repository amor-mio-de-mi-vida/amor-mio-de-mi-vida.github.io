TL;DR

  • Blackwell（SM100）用 tcgen05.mma 取代 Hopper 的 wgmma：操作数在共享内存，累加器搬进张量内存（TMEM），缩放因子也存入 TMEM 供块缩放 MMA 就地读取。
  • DeepGEMM 的 SM100 FP8/FP4 内核把线程分成四种角色——TMA 搬运、MMA 发射、UTCCP 转置、尾声写出——比 SM90 多了「UTCCP 转置」一环。
  • TMEM 列预算有限（上限 512），当累加器加缩放因子列超限时可以重叠（overlap），通过额外的 tmem_overlap_barriers 保证先读后写。
  • swap-AB 技巧把可变的 M 映射到 UMMA 的 N 维度，配合 update_instr_desc_with_umma_n 动态裁剪——这是 MoE 分组 GEMM 的关键出口。

从 SM90 到 SM100：硬件接口换了一层

上一篇讲了 Hopper（SM90）上的 FP8 GEMM：TMA 把数据搬进共享内存（SMEM），wgmma 从 SMEM 读操作数、在寄存器文件里累加。到了 Blackwell（SM100），硬件给 GEMM 的接口做了三个根本性的改变 [1]：

  • 指令换代：wgmma 变成了 tcgen05.mma（也叫 UMMA——Unified Matrix Multiply-Accumulate）。两者最大的区别是操作数来源：wgmma 可以从寄存器读 A 操作数，而 tcgen05.mma 的 A 和 B 都必须在共享内存中，用 SMEM 描述符来定位。
  • 累加器搬家：SM90 的累加器在寄存器文件里，每个 warp 直接访问自己的寄存器。SM100 引入了专用的张量内存（Tensor Memory, TMEM）——每个 SM 最多 512 列，每列 32 个 32 位元素（对应 32 个 datapath）。累加器不再占用寄存器，而是住在 TMEM 里，读写需要 tcgen05.st 和 tcgen05.ld 等专门指令。这意味着尾声（epilogue）阶段必须先从 TMEM 读出累加器再做后处理。
  • 缩放因子就地读取：块缩放 MMA（block-scaled MMA）需要 UE8M0 编码的缩放因子。SM100 要求这些缩放因子也在 TMEM 中——MMA 指令直接从 TMEM 的指定列读取 SF，不需要额外的寄存器传递。这就多出了一条数据通路：SF 先由 TMA 搬入 SMEM，再经 UTCCP（Unified Tensor Core Copy，tcgen05.cp）从 SMEM 拷入 TMEM。

这三个变化叠在一起，使得 SM100 的 GEMM 内核在线程分工、内存管理和同步模式上都与 SM90 有显著不同。DeepGEMM 实现这些变化的核心文件是 sm100_fp8_fp4_gemm_1d1d.cuh [2]——一个模板化的 CUDA 内核，同时支持 FP8×FP8、FP8×FP4 和 FP4×FP4 三种精度组合。模板参数 kGemmType 决定精度，kGemmMode 决定是普通 GEMM 还是 MoE 分组 GEMM。下面我们来逐一拆解它的核心机制。

SM90 内核用两类角色——TMA 生产者 warp 和 MMA 消费者 warpgroup。SM100 内核需要更精细的分工：缩放因子必须先在 SMEM 内转置、再经 UTCCP 拷入 TMEM，这多出了一类专职角色。完整的线程分配如 图 1 所示：

Warp 0——TMA 搬运工。它遍历所有 K 块，每一轮用 TMA 把 A tile、B tile 搬入 SMEM，再把 SFA、SFB 搬入 SMEM 中另一块区域。搬完后通过 full_barriers[stage].arrive() 通知 warp 1 可以开始消费，通过 sf_full_barriers[stage].arrive() 通知 warp 2 可以开始转置。当 kNumMulticast == 2 时，A 或 B 的 TMA 使用多播模式（multicast），一次搬运同时写入两个 SM 的 SMEM——这要求 cluster 内两个 CTA 的 SMEM 地址连续分配。

Warp 1——MMA 发射者。这是唯一执行 tcgen05.mma 的 warp，且仅在 is_leader_cta（双 CTA 时 rank 0 的 CTA）时执行。它在每个 K 块开始前等待 full_barriers，确认 TMA 搬运完毕；然后执行 UTCCP 把 SF 从 SMEM 拷入 TMEM，最后发射一连串 MMA 指令消费 A、B tile。当所有 K 块结束后，它通过 tmem_full_barriers 通知尾声 warp 累加器准备好了。

Warp 2(–3)——SF 转置。UTCCP 要求输入数据按 K-major 排列，但 TMA 载入的 SF 是 MN-major 的。Warp 2 在 sf_full_barriers 等到 SF 数据到达后，在 SMEM 内做一次 4×32→32×4 的转置（详见 UTCCP）。当 SF_BLOCK_K == 2（即每个 tile 有两组 SF）时，warp 3 也加入转置，两个 warp 各处理一组。转置完成后通过 full_barriers 的额外到达通知 warp 1。

其余 warp——尾声。尾声 warp 等待 tmem_full_barriers，确认 MMA 完成后，用 tcgen05.ld 从 TMEM 读出累加器，做类型转换（BF16 或 FP8），经 SMEM 中转后用 TMA 或直接 store 写回全局内存 D。写完后通过 tmem_empty_barriers 反馈给 warp 1，释放 TMEM 累加器空间用于下一轮 tile。

屏障初始化：6 组屏障，3 种到达模式

四种角色之间的同步靠 6 组屏障协调，全部在 SharedStorage 的 SMEM 中分配。屏障的初始化由 warp 1 的 elected leader 完成，TMEM 分配同时由 warp 2 执行——两者并行：

// Initialize barriers
if (warp_idx == 1 and cute::elect_one_sync()) {
    #pragma unroll
    for (uint32_t i = 0; i < kNumStages; ++ i) {
        // Arrive at all CTAs

        smem.empty_barriers[i].init(1);
        // Arrive only at the leader CTA

SM90 内核的 warp 分工只有「TMA 生产者」和「MMA 消费者」两种。SM100 把消费者进一步拆成 MMA、转置和尾声三种角色，本质上是因为 TMEM 引入了额外的数据搬运步骤（UTCCP）和额外的同步约束（overlap barriers）。

四种角色的线程总数也与 SM90 不同。SM90 的 FP8 内核用 1 个 TMA warp + 1 个 MMA warpgroup（128 线程）= 160 线程。SM100 内核用 1 个 TMA warp + 1 个 MMA warp + 1–2 个转置 warp + 若干尾声 warp，总线程数随 kNumEpilogueWarps 变化，典型配置约 192–256 线程。尾声 warp 的数量由 BLOCK_N / 32 决定——每个尾声 warp 处理 TMEM 的 32 列，BLOCK_N = 128 时需要 4 个尾声 warp，BLOCK_N = 256 时需要 8 个。

TMEM 列预算与 overlap 屏障

TMEM 每个 SM 最多 512 列。内核需要为三类数据分配列空间：

  1. 累加器：UMMA_N × kNumEpilogueStages 列。kNumEpilogueStages 默认为 2（双缓冲），使得一份累加器被 MMA 写入时，另一份可以被尾声读取。
  2. SFA 列：存放 A 的缩放因子，列数为 ceil(SF_BLOCK_M × SF_BLOCK_K, 32)——因为每列 32 个 32 位元素，每个 uint32 装 4 个 UE8M0 字节。
  3. SFB 列：存放 B 的缩放因子，列数为 ceil(SF_BLOCK_N × SF_BLOCK_K, 32)。

具体的计算在内核的编译期常量中（图 2 给出了两个典型算例）：

关键在第 121 行的 kNumOverlappedTmemCols：它等于 max(总列数 − 512, 0)。当累加器加 SF 的总需求不超过 512 列时，三者各占各的地址，互不干扰，overlap 为零。但一旦总需求超过 512——比如 BLOCK_N = 256 时，仅累加器就需要 \(256 \times 2 = 512\) 列——SF 列就只能和累加器列的尾部共用同一片 TMEM 地址。

当出现 overlap 时，同一片 TMEM 地址既是累加器的一部分，又是 SF 的存放处。这就带来了读写冲突：尾声需要读累加器（包括重叠区域），而 MMA warp 的 UTCCP 需要往 SF 列写入新的缩放因子。如果 UTCCP 在尾声读完之前就覆盖了重叠区域，结果就会出错。

为此，内核引入了 tmem_overlap_barriers。尾声在读完重叠区域后到达该屏障（sm100_store_cd_swap_ab.cuh 第 113–122 行）；MMA warp 在下一轮 tile 的首个 K 块 UTCCP 之前等待这个屏障：

if constexpr (kNumOverlappedTmemCols > 0) {

        ptx::tcgen05_before_thread_sync();

        smem.tmem_overlap_barriers[preceding_stage_idx].wait(preceding_phase_idx);

注意这里的巧妙之处：overlap 屏障不是在每个 K 块都等，而是只在首个 K 块 UTCCP 之前等一次（k_block_idx == 0）。原因是同一 tile 内的所有 K 块共享同一组累加器列——SF 只在第一个 K 块的 UTCCP 时写入重叠区域，后续 K 块的 SF 写入的 TMEM 地址不变。这就允许 UTCCP 与前一轮尾声的后半段在时间上部分重叠，而不是严格串行。

TMEM 分配由 warp 2 执行（第 185–188 行），释放由 warp 0 在最后一轮同步后执行（第 566–567 行）。分配器 Allocator2Sm 在双 CTA 时使用，确保两个 CTA 的 TMEM 不冲突。此外，get_num_aligned_tmem_cols（common/utils.cuh 第 43–50 行）将列数向上对齐到 32/64/128/256/512 之一——实际分配的列数可能比计算值更多。

块缩放 MMA：两种指令、两种粒度

SM100 的块缩放 MMA 用 UE8M0 编码的缩放因子对操作数做分块反量化。UE8M0 是一种 8 位纯指数格式——没有尾数位，只有指数，表示 \(2^{e-127}\) 的缩放系数（详见 dg03）。DeepGEMM 用到两种 tcgen05.mma 指令变体 [1]：

  • kind::mxf8f6f4.block_scale——支持 FP8×FP8、FP8×FP6、FP8×FP4 等混合精度组合。每步 MMA 的 K 维度为 UMMA_K=32，即一次消费 32 个 K 方向的元素。对应地，每 32 个元素有一个 UE8M0 缩放因子。
  • kind::mxf4.block_scale.block32（需要 CUDA 12.9 或更新版本）——FP4×FP4 专用。由于 FP4 精度更低、吞吐更高，UMMA_K 翻倍到 64。旧版编译器（CUDA < 12.9）写作 scale_vec::2X——含义是每步消耗两组 SF（每组 32 个 K 元素）。

这两种指令都通过 SMEM 描述符读取 A、B 操作数，通过 TMEM 地址读取缩放因子（tmem_sfa、tmem_sfb）。关键区别在于 SF id 的选择——它决定了每步 MMA 用 SF 列中的哪一个缩放因子。在主循环中（第 414–426 行），SF id 的计算有两种模式：

  • 粒度 32（kGranKA == 32，即每 32 个 K 元素一个 SF）：sf_id = (offset % 128) / 32。一个 128-K 子块里有 4 个 SF，每步 MMA 消费 32 个 K，sf_id 从 0 到 3 递增。这种模式下缩放粒度更细，量化误差更小。
  • 粒度 128（kGranKA == 128）：sf_id = sfa_stage_in_group_idx。整个 128-K 子块共用一个 SF，id 由更外层的 stage 索引决定。粒度更粗，但 SF 的存储和搬运开销更小。
MXF4 的 scale_vec::2X / block32 含义是每步 UMMA_K=64 消耗两组 32 元素的 SF（sf_id 以步长 2 递增）；block_scale 本身指的是每个 block（32 或 64 个元素）共享一个标量 SF，与 per-element scaling 相对。

在 swap-AB 模式下（见 swap-AB），A 和 B 的角色互换：指令描述符中 sfa_id 和 sfb_id 也相应翻转（第 427–429 行），以保证缩放因子与实际操作数的对应关系正确。

UTCCP：把缩放因子从 SMEM 搬进 TMEM

缩放因子（4 个 UE8M0 值打包成一个 uint32）先由 TMA 搬入 SMEM，但 MMA 要求它们在 TMEM 里。UTCCP（tcgen05.cp，即 Unified Tensor Core Copy）负责这段从 SMEM 到 TMEM 的拷贝。

但 UTCCP 有一个布局要求：输入数据必须按 K-major 排列。而 TMA 载入 SMEM 的 SF 是 MN-major 的——128 个 SF 值按 M（或 N）方向连续存放。因此在 UTCCP 之前，warp 2(–3) 需要在 SMEM 内做一次转置：

            values[i] = ptx::ld_shared(smem_ptr + i * 32 + lane_idx);
        __syncwarp();
        ptx::st_shared(smem_ptr + lane_idx * 4, values[0], values[1], values[2], values[3]);
    };

源码：deep_gemm/include/deep_gemm/impls/sm100_fp8_fp4_gemm_1d1d.cuh 第 458–470 行（节选）

转置函数 utccp_required_smem_warp_transpose（在 SM100_UTCCP_4x32dp128bit 中定义）把 128 个 uint32 按 4×32 的布局（4 行 × 32 个 lane）读入寄存器：每个 lane 读取 4 个间隔 32 的值。然后以 32×4 的布局写回同一块 SMEM——每个 lane 把 4 个值连续写到 lane_idx × 4 的位置。经过这次 shuffle，SMEM 中的数据就从 MN-major 变成了 UTCCP 要求的 K-major 布局。转置是就地完成的（读写同一块 SMEM），需要在读完后、写回前插入一次 __syncwarp()，防止 warp 内某些 lane 的写入覆盖其他 lane 尚未读取的位置。这个转置操作每个 K 块执行一次（或两次，当 SF_BLOCK_K == 2 时），开销约为 128 个 SMEM 读 + 128 个 SMEM 写 + 1 次 warp 同步——相对于 MMA 指令的计算开销而言很小，但仍然是 SM100 相比 SM90 多出的固有延迟。

每 128 个 SF 元素发一条 cute_utccp_t::copy，底层对应 cute::SM100_UTCCP_4x32dp128bit_1cta（单 CTA）或 _2cta（双 CTA）变体。TMEM 的列步长为 4——因为 128 个 SF 值分布在 4 列 TMEM 上（每列 32 个 32 位元素，每个元素装 4 个 UE8M0 值，排列方式由 UTCCP 的 atom 大小决定）。SF 描述符由 make_sf_desc 构造：指定 K-major 布局、atom 大小 8×128 bit、SBO（Swizzle Base Offset）=128 字节、LBO=0。

值得注意的是同步模型：UTCCP 在 full_barriers 等到 A/B 的 TMA 完成后才执行——它与 A/B 的 MMA 消费在同一个 warp 中串行。内核注释（第 446–448 行）指出 tcgen05.commit 隐含 fence::before_thread_sync，因此 UTCCP 完成到 MMA 开始之间无需显式 fence。这个设计简化了 MMA warp 内部的同步逻辑——不过它依赖的是 PTX ISA 的隐含语义，而非显式的屏障。

双 CTA MMA：两个 CTA 共享一份累加器

当 kNumMulticast == 2 时，内核使用 cluster 包含两个 CTA。两个 CTA 运行在同一个 GPC（Graphics Processing Cluster）的两个相邻 SM 上，可以通过 TMA multicast 把同一份 A 或 B 数据同时分发给两个 SM 的 SMEM，从而把全局内存带宽需求减半。但双 CTA 模式对 MMA 和 TMEM 管理有几个特殊要求：

  1. TMEM 分配必须协调：用 Allocator2Sm（第 49 行）替代普通分配器。分配前需要一次 cluster 同步（第 131 行：cluster_sync_with_relaxed_arrive()），确保两个 CTA 都准备好后再分配，避免 TMEM 地址冲突。
  2. MMA 只由 leader CTA 发射（第 299 行：is_leader_cta）。tcgen05.mma 带 cta_group::2 后缀时，一条指令就消费两个 SM 的 SMEM 数据——leader CTA 发一条就够了，follower CTA 的 warp 1 什么也不做。这避免了重复发射导致的结果错误。
  3. 屏障到达计数翻倍：两个 CTA 的 TMA warp 和转置 warp 都会到达同一组屏障。例如 full_barriers 的初始计数是 kNumMulticast × (1 + 32 × SF_BLOCK_K)（第 172 行）——其中 1 是 TMA warp 的到达，32 × SF_BLOCK_K 是转置 warp 的每线程到达数。
  4. MMA 指令用 cta_group::2——例如 SM100_MMA_MXF8F6F4_2x1SM_SS。这告诉硬件：两个 SM 共同完成一个更大的 MMA，等效的 UMMA_M 翻倍到 \(128 \times 2 = 256\)。
cluster_sync_with_relaxed_arrive 由 cute::cluster_arrive_relaxed() 加 cute::cluster_wait() 实现（comm/barrier.cuh 第 26–31 行）。relaxed 意味着到达操作没有内存序保证（不刷新 store buffer），但 cluster_wait 提供了充分的同步语义。相比 cute::cluster_sync()（带 acquire 语义），relaxed 版本在不需要全局可见性时更高效。

总结一下双 CTA 的收益：TMA multicast 让 A（或 B）只搬一份、两个 SM 共享，全局内存带宽减半；MMA 的 cta_group::2 让两个 SM 的 Tensor Core 联合计算，等效算力翻倍。代价是 TMEM 分配需要额外同步，且屏障逻辑更复杂。DeepGEMM 的启发式（sm100.hpp）在 tile 够大时自动启用双 CTA。具体来说，启发式会在 BLOCK_N ≥ 128 且总 SM 占用率足够时选择双 CTA——因为当 tile 太小时，multicast 节省的带宽不足以抵消 cluster 同步的开销（每次 tile 迭代至少需要一次 cluster_sync_with_relaxed_arrive）。双 CTA 模式还有一个约束：两个 CTA 必须调度到同一个 GPC 内的相邻 SM 上，这限制了硬件调度器的灵活性——如果 GPC 负载不均衡，可能导致某些 SM 空闲而另一些过载。

swap-AB 尾声：让 MoE 的不齐 M 不再是问题

MoE（Mixture of Experts）的分组 GEMM 中，每个专家分到的 token 数 M 不同、不对齐，而且在推理时每 batch 都在变化。标准 GEMM 的 tile 沿 M 方向固定大小（比如 BLOCK_M=128），对不齐的 M 要么 padding 浪费算力，要么用 mask 降低 Tensor Core 利用率。

swap-AB 的思路是：把 A 和 B 互换，让原来的 M 维度映射到 UMMA 的 N 维度。这样做的好处是，tcgen05.mma 允许动态修改指令描述符中的 N 维度——

CUTLASS_DEVICE void update_instr_desc_with_umma_n(
    cute::UMMA::InstrDescriptorBlockScaled& desc, const uint32_t& umma_n) {
    desc.n_dim_ = umma_n >> 3;
}

源码：deep_gemm/include/deep_gemm/mma/sm100.cuh 第 150–153 行（节选）

——内核在每个 tile 的开头调用 update_instr_desc_with_umma_n，把 umma_n 设成该 tile 实际有效的 M 值（第 351–354 行）。如果这个 tile 只覆盖了 60 个 token（而非满额的 128），umma_n 就设为 60，多余的列不会被计算也不会被写入。这正是 swap-AB 能高效处理 MoE 不齐 M 的关键——完整的分组 GEMM 调度逻辑见 dg04。

启发式中，三种 M 分组 GEMM（GroupedContiguous、GroupedMasked、GroupedMaskedV2）一律启用 swap-AB：

源码：csrc/jit_kernels/heuristics/sm100.hpp 第 34–45 行——M 分组一律启用 swap-AB

swap-AB 下，UMMA_N = BLOCK_M（第 67 行）——注意是 BLOCK_M 而不是 BLOCK_N，因为原来的 M 现在是 UMMA 的 N。这个维度映射的本质是利用了矩阵乘法的结合律：\(D = A \cdot B\) 等价于 \(D^\top = B^\top \cdot A^\top\)，交换输入后的累加器里存的恰好是 \(D^\top\)（转置的结果矩阵）。尾声在写回全局内存前必须把数据转置回来。转置在 SMEM 层面完成：BF16 输出用 SM90_U32x4_STSM_T（sm100_store_cd_swap_ab.cuh 第 155 行），FP8 输出用 SM100_U8x8_STSM_T（第 172 行）——这两条 STSM 指令在从寄存器存入 SMEM 时自带转置。对应地，TMEM 读取也换成了 16dp256b1x 形状（第 99–103 行），因为 STSM 的 b16/b8 布局要求与标准尾声的 32dp32b 不同。
