TL;DR

  • BucketBuffer 提供 all-gather、reduce-scatter、all-reduce 三种集合通信；数据住在 NCCL Gin 注册的对称缓冲区里，一次调用可以操作多个“桶”（同一缓冲区内的不连续区域）。
  • all-gather 在 NVLink 和 hybrid 路径上完全由复制引擎（CE）驱动，SM 使用量为零；仅纯 RDMA 路径需要 SM 内核来发射 put。
  • reduce-scatter 和 all-reduce 的节点内归约通过 multimem.ld_reduce 一条 PTX 指令完成——NVSwitch 把每张卡同一偏移的数据就地求和，不需要先搬到本地再累加。
  • hybrid 路径把每次操作分成等大的 chunk，用一个双项代价模型自动选取 chunk 数，SM 数量也由带宽公式自动计算，最终只需 4–8 个 SM。
  • BucketSession 上下文管理器允许用户对未注册张量做集合通信，内部自动分配缓冲区并拷贝。

前置知识

了解 ep05 的 NCCL Gin 与对称内存，以及 bg02 的 NVLink/复制引擎概念。本篇新引入：BucketBuffer 接口、CE 驱动的 all-gather、multimem.ld_reduce 归约、hybrid 双项代价模型。

前六篇讲的 EP dispatch 和 combine 解决的是 all-to-all：每个 token 按路由去到不同的专家。但训练与推理还有另一类通信需求——参数同步、梯度聚合、权重预取——它们是标准的集合通信：all-gather、reduce-scatter、all-reduce。DeepEP [1] 为此提供了一个独立的 BucketBuffer，与 EPBuffer 共用 NCCL Gin 后端和对称内存（见第 5 篇），但接口和内核完全不同。

BucketBuffer 的设计目标是最小化 SM 占用。all-gather 能做到 0 个 SM（纯靠复制引擎），reduce-scatter 和 all-reduce 也只需个位数的 SM。本文围绕 CHECKLIST 6a–6e，逐一拆解这三种操作在不同拓扑（NVLink、RDMA、hybrid）上的实现。

BucketBuffer：多桶、多组、一块缓冲

BucketBuffer 在初始化时分配一块对称存储（storage），并向一个或多个通信组（ProcessGroup）注册。三种集合操作的输入张量必须位于这块存储内，每个张量就是一个“桶”（bucket）。一次调用可以操作多个桶，内部用一个固定大小的 BucketList（最多 64 个桶）描述每个桶在缓冲区内的偏移和字节数。

all-gather：复制引擎全权负责

all-gather 是三种操作中最简单的：每个 rank 持有一个分片，目标是让所有 rank 都拿到完整数据。BucketBuffer 的关键设计决定是不用 SM 内核做数据搬运，而是把 GPU 的复制引擎（copy engine，CE）当成一条独立的 DMA 流水线来用。

纯 NVLink 路径

最简单的情况：所有 rank 在同一个 NVLink 域内。每个 rank 用 CE 把自己的分片推送到域内所有对等 rank 的对称缓冲区中（push 语义，不是 pull），用一对 copy_engine_sync 调用做前后屏障。整个过程不启动任何内核——0 个 SM。

host 端的 launch_all_gather 构造了三个平行数组——dst_ptrs（对端缓冲地址，通过 get_sym_ptr 映射）、src_ptrs（本地分片地址）和 sizes（每个桶的字节数）——覆盖 \((R-1) \times B\) 次拷贝（\(R\) 个 rank、\(B\) 个桶）。CE 操作分三步发射：第一个 copy_engine_sync 等待所有对端发出的就绪信号（确认它们的缓冲区可以被写入），然后 copy_engine_push 批量提交所有拷贝描述符到 CE 队列，最后第二个 copy_engine_sync 在本地写入完成后向所有对端发出完成信号。

信号本身也在对称缓冲区的 workspace 中：每个 rank 有 \(R\) 个 uint64_t 信号槽，第 \(i\) 个槽位由 rank \(i\) 写入。write_signals 指向对端的信号槽（通过 get_sym_ptr 拿到 NVLink 可达地址），wait_signals 指向本地的信号槽。increase_seq_idx 生成递增的序列号——CE 在 wait 时检查信号 \(\geq\) 目标值才放行，在 write 时写入新值。这比 GPU 内核的原子屏障便宜得多：CE 的 signal/wait 完全在硬件复制引擎内部完成，不占用任何 SM 周期。

hybrid 路径：SM 发射 RDMA，CE 做 NVLink 转发

hybrid 拓扑的例子：2 个 RDMA 节点 × 8 个 NVLink rank，共 16 个 rank。NVLink 域内用 CE，跨节点用 RDMA。

当拓扑同时包含 NVLink 和 RDMA 两个域时，CE 负责 NVLink 域内的推送和转发，但跨节点的 RDMA put 必须由 SM 内核通过 NCCL Gin 发射——这是唯一需要 SM 的地方，而且 SM 内核在发完 put 后立即退出，不等完成。

具体流程分三层（图 1）：

  1. SM 内核：每个 RDMA 对等节点分配一个 CTA，每个 CTA 内 8 个 warp 分别绑定一个 QP（kNumQPsPerChunk = 8）。每个 warp 按 chunk 顺序把本 rank 的分片用 gin.put 推到对端，每推完一个 chunk 通过 WeakVASignalInc 递增远端的 tail 信号。所有 chunk 发完后 SM 内核退出。
  2. CE 流：先把本 rank 的分片推到 NVLink 域内每个对等 rank（与 SM 内核并行）。然后逐 chunk 等待 RDMA 到达（copy_engine_wait 检查 tail 信号是否达到阈值），再把到达的 chunk 转发到 NVLink 域内每个对等 rank。
  3. 屏障：wait() 时启动一个 1-SM 的屏障内核确认所有数据到位。

chunk 数的自动选取

hybrid all-gather 把每个分片切成若干等大的 chunk。chunk 太少，CE 要等最慢的 RDMA 到达才能开始转发；chunk 太多，每个 chunk 带来 10 μs 的 CE 启动开销，且单个 QP 的数据量太小影响网卡效率（代码要求每个 chunk 至少 4 MiB）。源码用一个双项代价模型来选取最优 chunk 数：

// Choose the number of chunks by estimating the single-stream CE timeline: the CE pushes the local shard, then
// forwards each chunk wave (one chunk from every RDMA peer) once it lands, paying a launch gap per wave.
// The chunk is floored so that each QP puts at least 512 KiB, where the NIC efficiency is stable
constexpr int kNumMinChunkBytes = 4 * 1024 * 1024;
const auto push_t = num_shard_bytes * (context.num_nvl_ranks - 1) / nvl_bandwidth;
const auto rdma_t = num_shard_bytes * (context.num_rdma_ranks - 1) / rdma_bandwidth;
const auto forward_t = push_t * (context.num_rdma_ranks - 1);
int num_best_chunks = 1;
float best_t = std::numeric_limits<float>::infinity();
for (int i = 1; i <= std::min<int64_t>(64, num_shard_bytes / kNumMinChunkBytes); ++ i) {
    // CE-bound: forward all waves after the local push or the first wave; RDMA-bound: forward the last wave
    // NOTES: `10e-6` is CE overhead
    const auto t = std::max(std::max(push_t, rdma_t / i) + forward_t + i * (10e-6f), rdma_t + forward_t / i);
    if (t < best_t)
        best_t = t, num_best_chunks = i;
}

代价模型有两项，取较大者（图 2 展示了一组示例参数下的代价曲线）：

  • CE 受限项：CE 先完成本地推送或等第一波 RDMA 到达（取较大者），然后串行转发所有 chunk 波次，每波次一个 CE 启动开销。公式：\(\max(\text{push}_t,\;\text{rdma}_t / i) + \text{forward}_t + i \times 10\,\mu\text{s}\)。
  • RDMA 受限项：RDMA 传完所有数据后，CE 只需转发最后一波。公式：\(\text{rdma}_t + \text{forward}_t / i\)。

纯 RDMA 路径

当 NVLink 域只有一个 rank 时（num_nvl_ranks == 1），用 SM 协作内核完成 all-gather：所有 SM 做入口屏障确认本地分片就位，然后每个 warp 负责一批目标 rank，用 gin.put 推送。这是 all-gather 中唯一需要多个 SM 的路径，但 SM 只做发射，不做计算。

NVLink multimem 归约：一条指令读八张卡

reduce-scatter 和 all-reduce 的核心计算是归约（求和），而 BucketBuffer 在 NVLink 域内的归约方式与 NCCL 的 ring / tree 算法截然不同：它使用 NVIDIA NVSwitch 的多播归约读（multicast reduction load）[2]——ptx::multimem_ld_reduce_add_f32。

图 3 画出了这一过程。指令的前提是缓冲区注册了 NCCL 的多播对象（buffer_multimem），它把每张卡上同一偏移映射到同一个多播地址。发起者读这个多播地址时，NVSwitch 自动从每张卡取数据、做 FP32 加法、把和返回。整个域内归约只需一次读+一次写，而不是 \(N-1\) 步的 ring。这种硬件加速归约的延迟优势在小消息场景下最为显著：ring 算法的延迟正比于 \(N-1\)（步数），而 multimem 归约的延迟与参与 rank 数无关——NVSwitch 在一跳内完成所有卡的数据聚合。对于 8 卡 NVLink 域，ring 需要 7 步，而 multimem 只需 1 步。当然，multimem 的前提条件更严格：它要求所有参与缓冲区在对称内存中注册，且 NVSwitch 必须支持多播归约（第三代 NVSwitch 以上）。

reduce-scatter：从 multimem 到 RDMA ring

reduce-scatter 的语义是：每个 rank 持有完整数据的一份副本，归约后每个 rank 只留下自己负责的那个分片。BucketBuffer 按拓扑分三条路径。

纯 NVLink 路径

最直接的用法：屏障确认数据就位后，每个 SM 读 buffer_multimem 上自己分片偏移处的数据——multimem_ld_reduce_add_f32 一条指令完成域内求和——写回本地缓冲。代码只需一个简洁的 iterate_ld_st 循环：

hybrid 路径：multimem + RDMA ring 的三阶段流水线

hybrid reduce-scatter 的 chunk 大小固定为 32 KiB（kNumChunkBytes = 32 * 1024），不像 all-gather 的 chunk 大小需要动态计算。

当拓扑同时包含 NVLink 和 RDMA 时，hybrid reduce-scatter 在每个 SM 内启动三组不同角色的 warp，组成一条三阶段流水线（图 4）：

  1. 阶段 ① · multimem warp（8 个 warp，分 2 组，每组 4 个）：对每个目标 RDMA 节点的每个目标 NVLink rank，在本节点内做 multimem 归约——把发往该 rank 的分片在本节点各卡上的副本求和，写回本地缓冲。这一步的输出是“每个 RDMA 目标节点的分片”的节点内归约结果。
  2. 阶段 ② · issue warp（每个 multimem 组配 1 个）：等 named barrier 收到 multimem 组的完成通知后，用 gin.put 把归约后的 chunk 推到目标 RDMA 节点的环形槽位（ChunkView2D），并用 StrongVASignalAdd 递增对端的 tail 计数。发送前先检查 head 信用——如果槽位还没被消费就等，防止覆盖未读数据。
  3. 阶段 ③ · reduce warp（2 个，各 64 KiB 共享内存）：等 tail 达到目标值后，用 TMA 把到达的 chunk 从临时存储读入共享内存，再通过 tma_store_reduce_add_f32（即 cp.reduce.async.bulk）加到本地输出分片上。消费完毕后给发送方回 head 信用（via gin.signal）。

环形信用机制保证了流水线的正确性：tail 表示已到达的 chunk 数，head 表示已消费的 chunk 数。发送方在 head 达标前不会写入同一个槽位，接收方在 tail 达标前不会读取。槽位数由 ChunkStorage::kNumBytes / kNumChunkBytes / kNumRDMARanks 决定，固定为 256 MiB 除以每 chunk 32 KiB 除以 RDMA rank 数。

纯 RDMA 路径

当 NVLink 域只有一个 rank 时，没有 multimem 归约。内核直接分成 issue warp 和 reduce warp 两组：issue warp 把本 rank 数据的每个 chunk 推到所有对端，reduce warp 从所有对端接收并累加。流水线结构与 hybrid 的后两阶段相同，只是少了 multimem 阶段。

all-reduce：归约加广播

all-reduce 的语义是每个 rank 持有同样大小的数据副本，归约后每个 rank 都拿到完整的归约结果。BucketBuffer 同样分三条路径实现。

纯 NVLink 路径

hybrid 路径：四种 warp 角色

hybrid all-reduce 是最复杂的路径，在一个 SM 内核里同时运行四种 warp 角色，实现 reduce-scatter + all-gather 的融合：

  1. multimem warp：做节点内 multimem 归约（与 reduce-scatter 相同）。
  2. RS issue warp：把归约后的 chunk 沿 rail 发 RDMA put，完成跨节点的 reduce-scatter 阶段。
  3. reduce warp：接收远端 chunk 并累加，完成归约。
  4. broadcast warp：归约完成后，用 multimem.st（通过 TMA 的 multimem_cp_async_bulk）把结果广播回所有 RDMA 节点，完成 all-gather 阶段。

这四组 warp 通过 named barrier 和 tail/head 信号流水线协作。broadcast warp 的数量随 RDMA rank 数扩展（kNumBroadcastWarps = align(issue_warps + reduce_warps + ceil_div(rdma_ranks, 32), 4) - issue_warps - reduce_warps），以保证有足够的 lane 覆盖所有远端 rank。

纯 RDMA 路径

类似 reduce-scatter 的纯 RDMA 路径：issue warp 和 reduce warp 两组协作。与 reduce-scatter 不同的是，all-reduce 的 reduce warp 在累加完所有远端 chunk 后还需要把结果广播回所有远端——这一步通过 reduce warp 自身的 put 完成。

session：为未注册张量打开一扇门

BucketBuffer 要求输入张量位于注册的对称缓冲区内。这个限制在实际使用中不方便——用户可能有分散在不同位置的张量需要做集合通信。BucketSession 就是为此设计的上下文管理器。

class BucketSession:
    """A session in which collective methods can accept unregistered tensors"""

    def __init__(self, buffer: 'BucketBuffer'):
        self.buffer = buffer

进入 session 时，它把 BucketBuffer 的 all_gather、reduce_scatter、all_reduce 三个方法替换成包装版本（_collective_func）。包装版本的工作是：

  1. 检查输入张量是否已在缓冲区内；如果不在，从缓冲区的空闲空间分配一块，把数据拷贝过去。
  2. 调用原始的集合操作。
  3. 如果输出位置与缓冲区内的目标不同，在 wait() 的 hook 里把结果拷回。

session 还提供 allocate() 方法，让用户直接在缓冲区内分配张量：

with buffer.session() as session:
    # 在缓冲区内分配，已注册
    x = session.allocate((num_ranks, hidden), group=group)
    x[rank_idx].copy_(my_shard)
    result = buffer.all_gather(x[rank_idx], group=group).wait()

有一个特殊情况：纯 NVLink 的 all-gather 支持 out-of-buffer 输入（accept_unregistered_src = True），因为 CE 可以从任意 CUDA 地址做 push。此时 session 跳过拷贝，直接传原始张量。session 的拷贝开销取决于张量大小和 HBM 带宽：对于 1 GiB 的权重张量，一次 D2D 拷贝在 H800 上约需 0.5 毫秒（HBM 带宽约 2 TB/s）。在训练中每步都做多次集合通信的场景下，这个额外拷贝可能积少成多。因此，对于频繁参与集合通信的张量，建议直接在 BucketBuffer 的对称存储中分配（通过 session.allocate()），避免反复拷贝。

BF16 通信精度

reduce_scatter 接受 comm_precision="bf16" 参数，但仅限纯 RDMA 路径（num_rdma_ranks > 1 and num_nvl_ranks == 1）。启用后，内核增加了 cast warp：

  • 发送端的 cast warp 把 FP32 数据转成 BF16 后再发 RDMA，通信量减半。
  • 接收端的 reduce warp 收到 BF16 数据后转回 FP32 再累加。

在 reduce-scatter launcher 中，BF16 路径的 chunk 大小加倍（kNumCommBytesPerChunk 是通信字节数，kNumBytesPerChunk = 2 * kNumCommBytesPerChunk），因为同样数量的 FP32 元素在 BF16 下只占一半通信带宽。

为什么只有 RDMA-only reduce-scatter 支持 BF16？multimem 归约在硬件层面只支持 FP32 加法（multimem_ld_reduce_add_f32），所以涉及 NVLink multimem 的路径无法降到 BF16。all-reduce 没有 BF16 变体——源码中的断言 (comm_precision != "bf16" or (num_rdma_ranks > 1 and num_nvl_ranks == 1)) 明确了这一限制。

SM 使用量的解析估算

get_theoretical_num_sms 根据操作类型和拓扑，用 NVLink / RDMA / HBM 带宽计算所需 SM 数。核心思路是：SM 归约的瓶颈在 HBM 读写带宽，需要的 SM 数等于“目标归约带宽 ÷ 每 SM 读（或写）带宽”的上取整。

def get_theoretical_num_sms(self, op: str, group: Optional[dist.ProcessGroup] = None) -> int:
    context_idx = self.get_context_idx(group)
    context = self.contexts[context_idx]
    num_rdma_ranks, num_nvl_ranks = context.get_physical_domain_size()

    if op == 'reduce_scatter':
        # NVLink
        if num_rdma_ranks == 1 and num_nvl_ranks > 1:
            dst_gbs = get_nvlink_gbs() / num_nvl_ranks
            num_sms = max(dst_gbs / get_sm_read_gbs(), dst_gbs / get_sm_write_gbs())
            return align(max(6, math.ceil(num_sms)), 2)
# ...
        # Hybrid
        if num_nvl_ranks > 1 and num_rdma_ranks > 1:
            dst_gbs = min(get_nvlink_gbs() / num_nvl_ranks,
                          get_rdma_gbs() * num_rdma_ranks / (num_rdma_ranks - 1))
            # Multimem and local reduction each require one read and one write.
            num_sms = max(2 * dst_gbs / get_sm_read_gbs(),
                          2 * dst_gbs / get_sm_write_gbs())
            return align(max(8, math.ceil(num_sms * 1.2)), 2)
# ...
    if op == 'all_reduce':
        # Hybrid
        if num_rdma_ranks > 1 and num_nvl_ranks > 1:
            dst_gbs = min(get_nvlink_gbs() / num_nvl_ranks,
                          get_rdma_gbs() * num_rdma_ranks / (2 * (num_rdma_ranks - 1)))
            # Multimem reduction, RDMA reduction and broadcast each require one read and one write.
            num_sms = max(3 * dst_gbs / get_sm_read_gbs(),
                          3 * dst_gbs / get_sm_write_gbs())
            return align(max(6, math.ceil(num_sms)), 2)
# ...

    if op == 'all_gather':
        return 0

    raise NotImplementedError

关键观察：

  • all-gather 恒返回 0——不需要 SM 做计算，CE 就够了。
  • reduce-scatter NVLink：目标带宽 = NVLink 带宽 / rank 数，SM 数由读或写的较大者决定。
  • reduce-scatter hybrid：因为同时做 multimem 归约和本地归约，读写量翻倍（2 * dst_gbs），再乘 1.2 的余量。
  • all-reduce hybrid：比 reduce-scatter 多一步广播写回（3 * dst_gbs），目标带宽的分母也翻倍。

表 1 列出了各操作在不同拓扑下的估算 SM 数。这些数字远低于典型 GPU 的 SM 总数（如 H800 的 132 个）。与 NCCL 的集合通信相比，BucketBuffer 把绝大多数 SM 留给了计算内核。值得注意的是，该估算模型做了几处保守简化：带宽参数用的是 NVLink 和 RDMA 的理论峰值而非实测值，且没有考虑片上缓存命中对有效带宽的提升。因此实际所需 SM 数可能更少，这里的结果是一个安全的上界。

SM 估算公式的另一个隐含假设是所有 SM 的利用率相同。但在 hybrid reduce-scatter 中，multimem warp、issue warp 和 reduce warp 三种角色的负载并不均衡——multimem 归约受限于 NVSwitch 吞吐，issue warp 受限于 RDMA 延迟，reduce warp 受限于 TMA 写带宽。当某一阶段成为瓶颈时，其余 warp 会处于等待状态。代码通过在 SM 估算中取读写带宽的较大者（max(read_sms, write_sms)），并乘以 1.2 的余量系数来部分补偿这种不均衡。

局限与未覆盖

  • 数据类型：源码中所有集合操作的输入只支持 FP32（torch::kFloat）。BF16 仅限 RDMA-only reduce-scatter 的通信路径。
  • 缓冲区限制：输入张量必须位于 BucketBuffer 的对称存储内（session 减轻了这一限制，但增加一次拷贝）。
  • ChunkStorage 固定 256 MiB：hybrid 路径的环形槽位从这块空间分配，可能限制大规模通信的并发度。
  • 带宽参数：get_theoretical_num_sms 使用的 NVLink / RDMA 带宽来自环境变量（envs.py），是估计值而非实时测量。
  • 本文未覆盖的内容：
    • BucketBuffer 的 barrier 方法和 BufferAllocator 的分配计划。
    • EventOverlap 的 hook 机制与计算-通信重叠的具体用法。
    • hybrid all-reduce 的 broadcast warp 内部实现细节。
    • 本文没有任何实测性能数字——本地无 GPU。
  • 关于 multimem：multimem_ld_reduce_add_f32 只支持 FP32 加法。如果 NVSwitch 未来支持 BF16 multimem，NVLink 路径的 reduce-scatter 和 all-reduce 可能也能降到 BF16——但这是推测，当前源码中没有相关实现。
