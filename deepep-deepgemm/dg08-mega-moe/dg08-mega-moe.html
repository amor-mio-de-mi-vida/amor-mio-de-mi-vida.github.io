TL;DR

  • Mega MoE 把 EP dispatch（NVLink 拉取）、Linear1（FP8×FP4 / FP8×FP8 / BF16 GEMM）、SwiGLU 与 FP8 再量化、Linear2、combine 写回六个阶段融合进一个持久化内核，通信与计算在同一组 SM 上交替执行。
  • 通信不走 NCCL，而是用 PyTorch 对称内存（torch.distributed._symmetric_memory）开出跨 rank 可见的缓冲区，内核自己通过 NVLink 上的远程指针完成拉取和写回。
  • 环形缓冲区（ring buffer）限制了同一时刻存活的 token 块数，使中间激活不需要按最坏情况分配。调度器用 L1 预热再转 L1/L2 交替的两阶段策略保证无死锁。
  • 权重需要预变换：L1 的 gate/up 权重按 8 行一组交错排列，两层的 UE8M0 缩放因子按 UTCCP 128 元素粒度转置。

把整层 MoE 塞进一个内核：省掉五次 HBM 往返

一层 MoE 的传统前向包含六步：EP dispatch（all-to-all）把 token 送到持有对应专家权重的 rank，做 Linear1（FP8×FP4 GEMM），做 SwiGLU 激活并重新量化到 FP8，做 Linear2（FP8×FP4 GEMM），再通过 combine（all-to-all）把结果写回各 token 来源的 rank。每步是一次独立的内核启动，中间激活至少写一次全局内存（HBM）。

Mega MoE 把这六步压进一个持久化内核。README 的用法示例展示了它的调用方式：先分配对称缓冲区和变换权重，再调用一个函数完成整层。

## Interfaces

#### Notices

This library provides optimized GEMM kernels for NVIDIA GPUs with a naming convention: `D = C + A @ B`. The input shape layout is NT (non-transposed A, transposed B). While the SM90 implementation supports only the NT memory layout (row-major, col-major), the SM100 implementation supports all memory layouts (NT, TN, NN, TT). For example, `fp8_gemm_nt` will do a `D = C + A @ B.T`

For both architectures, the LHS scaling factor is required to have a TMA-aligned and transposed layout. And the data format for the scaling factor of SM90 and SM100 is different:

- SM90 requires scaling factors in FP32 format.
- SM100 requires scaling factors in packed [UE8M0](https://docs.nvidia.com/cuda/parallel-thread-execution/#alternate-floating-point-data-formats) format, which packs 4 UE8M0 into a single `torch.int`.

融合的好处有两个。第一，中间激活——Linear1 的输出、SwiGLU 的输出——不再写到 HBM 再读回来，而是留在片上的 ring buffer 里直接传给下一步。以 hidden = 7168、inter = 18432、4096 个 token 为例，传统流程中 Linear1 输出（BF16）就有 4096 × 18432 × 2 ≈ 144 MiB 需要写入再读出 HBM；融合后这 144 MiB 完全留在 ring buffer 的共享内存中，只有最终的 combine 输出才写回全局内存。第二，NVLink 通信（dispatch 的拉取和 combine 的写回）与张量核计算可以在同一组 SM 上交替执行，通信延迟被藏在计算后面。图 1 对比了传统流程和 Mega MoE 的时间线。

对称缓冲区：不走 NCCL，内核自己做 NVLink 搬运

Mega MoE 的通信不使用 NCCL 或 DeepEP 的通信底座，而是直接使用 PyTorch 提供的对称内存（symmetric memory）原语。对称内存的核心语义是：每个 rank 分配同样大小的一块 GPU 内存，PyTorch 底层让所有 rank 的这块内存对彼此可见——rank 0 可以通过 NVLink 直接读写 rank 1 的对称内存，不需要显式的 send/recv。

Python 端的 SymmBuffer 类封装了这个机制。分配时，单 rank 用普通 torch 分配，多 rank 用 symm_mem.empty() 加 symm_mem.rendezvous()。

# Allocate or reuse a symmetric buffer
num_bytes, slice_input_buffers = _C.get_symm_buffer_size_for_mega_moe(

    num_max_tokens_per_rank, num_topk,

    mma_type, activation,
    num_shared_experts

if base is None:

rendezvous() 返回的 handle 携带所有 rank 的 buffer 指针列表（buffer_ptrs）。在 C++ 侧，这些指针被传入 SymBuffer 结构体：

template <uint32_t kNumRanks = kNumMaxRanks>
struct SymBuffer {
    int64_t base;
    int64_t offsets[kNumMaxRanks];
    uint32_t rank_idx;

    DG_STATIC_ASSERT(kNumRanks <= kNumMaxRanks, "Too many ranks");

    SymBuffer() = default;

    template <typename Container>
    explicit SymBuffer(const Container& c, const uint32_t& rank_idx): rank_idx(rank_idx) {
        const auto size = static_cast<uint32_t>(c.size());
        base = c[rank_idx];
        for (uint32_t i = 0; i < kNumMaxRanks; ++ i)
            offsets[i] = i < size ? (c[i] - base) : 0;
    }

#if defined(__CUDA_ARCH__) or defined(__CLION_IDE__)
    template <typename ptr_t = void*>
    CUTLASS_DEVICE ptr_t get_base_ptr() const {
        return reinterpret_cast<ptr_t>(base);
    }

    template <typename ptr_t>
    CUTLASS_DEVICE ptr_t map(const ptr_t& ptr, const uint32_t& dst_rank_idx) const {
        if constexpr (kNumRanks == 1)
            return ptr;

        int64_t mapped_ptr = offsets[dst_rank_idx] + reinterpret_cast<int64_t>(ptr);
        return *reinterpret_cast<ptr_t*>(&mapped_ptr);
    }
#endif

源码：deep_gemm/include/deep_gemm/layout/sym_buffer.cuh 第 9–44 行（节选）

SymBuffer 只存一个 base（本 rank 的基址）和每个 rank 相对于 base 的 offsets。map(ptr, dst_rank_idx) 把一个本地指针映射到另一个 rank 的对应位置——只要加上那个 rank 的偏移量。这个偏移加法发生在内核内部的每一次跨 rank 读写中。最多支持 72 个 rank（kNumMaxRanks）。

MegaMoEBuffer：对称缓冲区里装什么

对称缓冲区被切成多个区域，由 MegaMoEBuffer 结构管理。布局从低地址到高地址大致如下：

  1. workspace：包含 MegaMoESignals（全局同步计数器、NVLink barrier、各 locality domain 的 L1/L2 任务计数、combine 就绪标记、每个专家的收发 token 计数）以及每个专家的 token 元数据（TokenSrcMetadata：rank_idx、token_idx、topk_idx，用于 combine 时写回正确位置）。
  2. 输入缓冲：x（token 数据）、x_sf（scale factor）、topk_idx、topk_weights——调用方在启动内核前把当前 rank 的 token 写到这里，别的 rank 通过 NVLink 来拉。
  3. 共享专家缓冲：shared_l1_acts、shared_l2_acts 及其 SF。
  4. 环形激活缓冲（ring buffer）：l1_token、l1_sf、l1_topk_weights（Linear1 的输入，从远端拉来）、l2_token、l2_sf（Linear1 的输出，SwiGLU + quant 后写入）、combine_token（Linear2 的 BF16 输出，待 combine 写回）。

环形缓冲区的容量不是"所有可能的 token"，而是一个有限的 num_ring_tokens。它由调度器的活跃块数上界（get_num_max_live_pool_blocks）乘以 block_m 计算得到。这使得内存分配与最大 token 数成正比，而不是与最坏情况下的 token 总量成正比。

SwiGLU 融合：epilogue 里的完整计算

SwiGLU 的 SiLU(gate) × up 并非一个单独的 warp 或内核，而是直接嵌在 L1 任务的 epilogue 循环里（sm100_fp8_fp4_mega_moe.cuh 第 1058–1235 行）。8 个 epilogue warp 分成 2 个 warpgroup，每个负责 BLOCK_M / 2 行。对 L1 的每个 N 块，一个 warpgroup 的步骤是：

  1. 从 TMEM 读累加器：用 SM100_TMEM_LOAD_16dp256b1x 每次读 8 行，读入寄存器 raw_values。因为 gate/up 权重已交错（见权重变换一节），相邻行就是一对 (gate, up)。
  2. 转 BF16 并可选钳位：FP32 累加结果转为 BF16，如果配置了 kActivationClamp（≠∞），用 __hmin2/__hmax2 钳位。
  3. SiLU(gate) × up × weight： 
    gate = bf16_to_fp32(gate_row)
silu_gate = gate / (1 + exp(-gate))   // 或 fast_rcp 版
activation = silu_gate × up × topk_weight
    其中 topk_weight 是 dispatch 阶段从远端拉来的路由权重，存在 ring buffer 的 l1_topk_weights 中。
  4. Amax 归约（线程 → warp → warp 对）：每 8 行的最大绝对值先在 4 个 lane 内归约，再通过共享内存与相邻 warp 交换，得到 8 行的全局 amax。这是 FP8 量化所需的逐块缩放因子的来源。
  5. 量化到 FP8 E4M3：用 amax 算出 UE8M0 缩放因子，除以它后转为 __nv_fp8x4_e4m3，用 STSM 写入 SMEM。
  6. TMA 写出到 L2 buffer：SM90_TMA_STORE_2D 把 SMEM 中的 FP8 数据写到 ring buffer 的 l2_token 区域。SF 直接写到 l2_sf_buffer。
  7. 信号推进：L2KBlockDependency::arrive 翻转 l2_full_mask 的对应位，同时 red_add(l1_empty_count) 通知 dispatch 可以复用这个 ring 槽位。

L2 任务的 epilogue 更简单：从 TMEM 读 FP32 累加器，转 BF16，写入 SMEM，然后读取 TokenSrcMetadata（包含 rank_idx、token_idx、topk_idx），通过 sym_buffer.map 把 BF16 结果直接写到源 rank 的 combine_token 缓冲区——这就是 combine 的"写回"阶段。全部 L2 N 块完成后，epilogue warp 进入 combine 归约循环：每个 warp 负责一部分 token，从各 topk 对应的 combine_token 读 BF16 值做加权和，写回最终输出 y。

调度器：L1 预热保证无死锁

Mega MoE 把 Linear1 和 Linear2 交替调度到同一个 MMA warpgroup 上。调度器（MegaMoEScheduler）维护四种任务阶段：Linear1、Linear2、SharedLinear1、SharedLinear2。每个阶段的任务按 locality domain 分组，调度器优先从本域的原子计数器领取任务。当本域计数器耗尽时，调度器可以"窃取"另一个域的任务——但有一个保护条件：kNumMinStealWaves（默认为 2）定义了窃取的最低波数阈值，当目标域剩余任务不足 2 波时禁止窃取，以避免跨局部性域读取权重带来的额外延迟拖慢目标域的最后几波任务。SM 的域归属由 sm_locality_domain_idx 确定，它来自 probe_sm_locality_domains 的探测结果（见第 5 篇），在内核启动时通过 __clusterid() 或设备拓扑信息传入。

L1 和 L2 之间有一个关键的依赖关系：L2 的每个 K 块需要读 L1 的输出，但 L1 的输出按 N 块写入——L1 的一个 N 块完成后，所有 L2 任务中对应 K 范围的那个 K 块才能读取。代码用 L2KBlockDependency 追踪这个依赖：一个 64 位 bitmask，每个 L1 N 块完成时用原子 XOR 翻转对应的位，L2 在读取前用 ld_acq_gpu 检查位是否就绪。

L2KBlockDependency：64 位 bitmask 的精细依赖追踪

L2KBlockDependency 结构体用一个 64 位 bitmask 追踪 L1 → L2 的依赖——每个 L1 N 块占一位。当一个 L1 N 块的 MMA 完成时，epilogue 线程调用 arrive，用 ptx::red_xor_rel（release 语义的原子 XOR）翻转那一位。L2 的 MMA 线程在读取每个 K 块之前调用 wait，用 ptx::ld_acq_gpu（GPU-scope acquire load）读 mask，检查当前 K 块对应的那几位是否就绪：

// Each finished L1 N block toggles its bit in `l2_full_mask`, so L2 K blocks can start as soon as they are fed
// NOTES: the mask parity per ring generation relies on the ring capacity, see `get_num_max_live_pool_blocks`
template <uint32_t L1_SHAPE_N, uint32_t BLOCK_N, uint32_t BLOCK_K>
struct L2KBlockDependency {
    static constexpr uint32_t kNumL1BlockNs = L1_SHAPE_N / BLOCK_N;
    static constexpr uint32_t kNumL1BlockNsPerL2KBlock = BLOCK_K / (BLOCK_N / 2);
    static constexpr uint64_t kFullMask = kNumL1BlockNs == 64 ? ~0ull : (1ull << kNumL1BlockNs) - 1;
    DG_STATIC_ASSERT(kNumL1BlockNs <= 64, "Too many L1 N blocks for the L2 readiness mask");
    DG_STATIC_ASSERT(BLOCK_K % (BLOCK_N / 2) == 0, "Invalid L1/L2 shape relationship");

    const uint64_t* mask_ptr;
    uint64_t expected_mask, pending_mask = kFullMask;

    CUTLASS_DEVICE L2KBlockDependency(const uint64_t* mask_ptr, const uint32_t& generation_idx):
        mask_ptr(mask_ptr), expected_mask(generation_idx & 1 ? 0ull : kFullMask) {}

    CUTLASS_DEVICE static void arrive(const uint64_t* mask_ptr, const uint32_t& n_block_idx) {
        ptx::red_xor_rel(mask_ptr, 1ull << n_block_idx);
    }

    // Re-read the mask only when the K block is not fed yet
    CUTLASS_DEVICE void wait(const uint32_t& k_block_idx) {
        const auto k_block_mask = ((1ull << kNumL1BlockNsPerL2KBlock) - 1) << (k_block_idx * kNumL1BlockNsPerL2KBlock);
        while (pending_mask & k_block_mask)
            pending_mask = ptx::ld_acq_gpu(mask_ptr) ^ expected_mask;
    }
};

源码：deep_gemm/include/deep_gemm/scheduler/mega_moe.cuh 第 140–166 行（L2KBlockDependency 的 arrive/wait 机制）

这里有一个奇偶代（generation）的技巧：因为 ring buffer 会被复用，同一个 pool block 的下一代 L1 写入又会翻转同一位。构造函数根据 generation_idx & 1 设置 expected_mask——奇数代期望全零、偶数代期望全一。pending_mask = ld_acq_gpu(mask_ptr) ^ expected_mask 让 wait 只关心当前代有没有完成。这要求 ring buffer 的容量是偶数块——get_num_max_live_pool_blocks 保证了这一点。

另一个细节是 k_block_mask 的粒度。L1 的每个 N 块经过 SwiGLU 后输出宽度是 BLOCK_N/2，而 L2 的每个 K 块需要 BLOCK_K 宽的输入——因此一个 L2 K 块依赖 kNumL1BlockNsPerL2KBlock = BLOCK_K / (BLOCK_N/2) 个连续 L1 N 块。wait 在 spin loop 中只检查这几位：k_block_mask = ((1 << kNumL1BlockNsPerL2KBlock) - 1) << (k_block_idx * kNumL1BlockNsPerL2KBlock)，这样 L2 可以在部分 L1 N 块完成时就开始处理已就绪的 K 块，实现 L1/L2 的流水线重叠。

TaskInfo 与 4 阶段调度

调度器给 MMA warpgroup 的每个任务用 TaskInfo 结构体描述。它是一个 16 字节对齐的 8 字段 POD，包含 block_phase（Linear1/Linear2/SharedLinear1/SharedLinear2）、local_expert_idx（本 rank 上的专家编号）、m_block_idx（M 方向分块索引）、n_cluster_idx（双 CTA 中的 N 方向成对索引）、pool_block_idx（ring buffer 中的槽位）、valid_m（有效 token 数，尾块可能不满）、shape_n 和 shape_k。is_valid() 检查 block_phase != None——调度器在无任务可取时返回空 TaskInfo，MMA warpgroup 轮询直到拿到有效任务。

如果 L2 任务被调度得太早，它可能等不到 L1 的输出，整个内核就死锁了。调度器的解决方案是 L1 预热（warmup）：在 L1/L2 交替开始之前，先纯跑若干波 L1 任务。预热的波数由 get_num_l1_warmup_waves 计算：

// Get minimal L1 warmup waves to ensure no L1 -> L2 deadlock
// constexpr func, no runtime overhead in kernel
CUTLASS_HOST_DEVICE constexpr
int get_num_l1_warmup_waves(
    const int& num_total_m_blocks,
    const int& num_clusters,
    const int& num_l1_n_clusters,
    const int& num_l2_n_clusters) {
    // The first L2 wave may touch multiple M blocks; all their L1 N tasks must be issued first.
    const int num_first_l2_wave_m_blocks = math::constexpr_ceil_div(num_clusters, num_l2_n_clusters);
    const int num_l1_warmup_clusters_for_first_l2_wave = math::constexpr_ceil_div(
        num_first_l2_wave_m_blocks * num_l1_n_clusters, num_clusters);

    // When each M block has more L1 tasks than L2 tasks, the interleaved schedule
    // leaves `(num_l1_pair_n_blocks - num_l2_pair_n_blocks)` extra L1 tasks behind
    // per M block. To avoid deadlock, no L2 task for an M block should be scheduled
    // before that block's L1 tasks have been issued. The last M block is the
    // bottleneck: it needs its own `num_l1_pair_n_blocks` L1 tasks, and the preceding
    // `num_total_m_blocks - 1` M blocks accumulate
    // `(num_total_m_blocks - 1) * (num_l1_pair_n_blocks - num_l2_pair_n_blocks)`
    // pending L1 tasks, so we issue them during the warmup phase. Add one extra
    // CTA-pair wave to cover partial-wave rounding.
    const int num_interleave_cluster_diff_per_m_block =
        num_l1_n_clusters > num_l2_n_clusters ? num_l1_n_clusters - num_l2_n_clusters : 0;
    const int num_warmup_waves_for_interleave_schedule = math::constexpr_ceil_div(
        num_l1_n_clusters + (num_total_m_blocks - 1) * num_interleave_cluster_diff_per_m_block,
        num_clusters) + 1;

    // TODO: may delay combine NVLink
    return cute::max(num_l1_warmup_clusters_for_first_l2_wave, num_warmup_waves_for_interleave_schedule);

源码：deep_gemm/include/deep_gemm/scheduler/mega_moe.cuh 第 15–45 行（节选）

这个函数考虑两种约束，取两者的最大值（mega_moe.cuh 第 15–44 行）：

  1. 第一波 L2 约束：第一波 L2 可能涉及 \(\lceil C_{\text{all}} / C_{\text{L2,N}}\rceil\) 个 M 块（\(C_{\text{all}}\) 是 cluster 总数，\(C_{\text{L2,N}}\) 是 L2 的 N 方向 cluster 数），这些 M 块的全部 L1 N 任务必须先完成。预热波数 \(= \lceil \text{M\_blocks} \times C_{\text{L1,N}} / C_{\text{all}} \rceil\)。
  2. 交替调度约束：若 \(C_{\text{L1,N}} > C_{\text{L2,N}}\)，每个 M 块在 L1/L2 交替中积压 \(C_{\text{L1,N}} - C_{\text{L2,N}}\) 个多余的 L1 task。\(M_{\text{total}} - 1\) 个前序 M 块的积压加上当前块自己的 \(C_{\text{L1,N}}\)，除以 \(C_{\text{all}}\) 再加 1 波的余量。

ring buffer 容量也是调度器决定的

get_num_max_live_pool_blocks 计算 ring buffer 需要容纳的最大同时存活 M 块数（mega_moe.cuh 第 48–79 行）：

\[ R = \min\!\Bigl(M_{\text{total}},\; \underbrace{\bigl\lceil\frac{W_{\text{warmup}} \cdot C_{\text{all}}}{C_{\text{L1,N}}}\bigr\rceil}_{\text{预热后存活块}} + \underbrace{M_{\text{total}} \cdot \frac{C_{\text{L2,N}} - C_{\text{L1,N}}}{C_{\text{L2,N}}}}_{\text{前沿增长（仅当 L2>L1 时）}} + \underbrace{\bigl\lceil\frac{C_{\text{all}}}{\min(C_{\text{L1,N}},C_{\text{L2,N}})}\bigr\rceil}_{\text{波余量}}\Bigr) \](1)

第一项：预热结束时有多少个 M 块的 L1 已发出但 L2 还没消费（因此占着 ring 槽位）。第二项：当 \(C_{\text{L2,N}} > C_{\text{L1,N}}\) 时，交替调度中 L2 消费得比 L1 快，存活块的"前沿"在 M 方向膨胀。第三项：覆盖偏波和流水线延迟的余量。最终 num_ring_tokens = R × BLOCK_M。

CUTLASS_HOST_DEVICE constexpr int get_num_max_live_pool_blocks(
    const int& num_total_m_blocks,
    const int& num_sms,
    const int& hidden,
    const int& intermediate_hidden) {
    constexpr int kMegaMoEBlockN = 128;
    constexpr int kNumCTAsPerCluster = 2;

    DG_UNIFIED_ASSERT((intermediate_hidden * 2) % (kNumCTAsPerCluster * kMegaMoEBlockN) == 0);
    DG_UNIFIED_ASSERT(hidden % (kNumCTAsPerCluster * kMegaMoEBlockN) == 0);
    const int num_clusters = num_sms / kNumCTAsPerCluster;
    const int num_l1_n_clusters = intermediate_hidden * 2 / (kNumCTAsPerCluster * kMegaMoEBlockN);
    const int num_l2_n_clusters = hidden / (kNumCTAsPerCluster * kMegaMoEBlockN);
    const int num_l1_clusters = num_total_m_blocks * num_l1_n_clusters;
    const int num_l1_waves = math::constexpr_ceil_div(num_l1_clusters, num_clusters);
    const int num_min_l1_warmup_waves = get_num_l1_warmup_waves(
        num_total_m_blocks, num_clusters, num_l1_n_clusters, num_l2_n_clusters);
    const int num_l1_warmup_waves = cute::min(num_min_l1_warmup_waves, num_l1_waves);
    const int num_l1_warmup_clusters = cute::min(num_l1_warmup_waves * num_clusters, num_l1_clusters);
    const int num_live_blocks_after_warmup = math::constexpr_ceil_div(num_l1_warmup_clusters, num_l1_n_clusters);

    // Conservative closed-form bound for the L2/L1 alternating tail. If L1 advances faster in
    // M-block space (B1 < B2), live blocks can grow by about total_m_blocks * (B2 - B1) / B2.
    // Add one global-wave margin to cover partial waves / pipeline lag.
    // This is slightly larger than the tight bound, but cheaper and simpler.
    // TODO: refactor here
    const int frontier_growth = num_l2_n_clusters > num_l1_n_clusters ?
        math::constexpr_ceil_div(
            num_total_m_blocks * (num_l2_n_clusters - num_l1_n_clusters), num_l2_n_clusters) : 0;
    const int wave_margin = math::constexpr_ceil_div(
        num_clusters, cute::min(num_l1_n_clusters, num_l2_n_clusters));
    return cute::min(num_total_m_blocks, num_live_blocks_after_warmup + frontier_growth + wave_margin);

NVLink 通信与计算的重叠

dispatch warpgroup 在拉取 token 时，MMA warpgroup 可以同时在计算已经拉到 ring buffer 里的上一批 token。两者交替进行：dispatch 填满一个 ring 槽位后翻转 l1_full_count，MMA 看到信号就开始算这个槽位的 L1；MMA 算完 L1 后 epilogue 做 SwiGLU + quant，写入 L2 ring 槽位并翻转 l2_full_mask（这是一个 64 位 mask，每个 L1 N 块对应一位）；MMA 再取 L2 任务算完后，epilogue 做 combine 写回。

全局同步通过 MegaMoESignals 中的信号完成。这个结构体占据对称缓冲区的最前端，128 字节对齐，内含五组信号：


struct alignas(128) MegaMoESignals {

    static constexpr uint32_t kNumMaxExperts = 2048;
    static constexpr uint32_t kNumMaxExpertsPerRank = 512;
    static constexpr uint32_t kNumMaxRingBlocks = 1u << 20;  // 20 MiB for the ring signals
    static constexpr uint32_t kNumMaxSharedL2Blocks = 1u << 15;  // 128 KiB

    // Grid and NVLink synchronization
    uint32_t grid_sync_count[kNumMaxGridSyncCounters];
    uint32_t nvl_barrier_counter;
    int nvl_barrier_signals[2];

    // Task scheduling
    uint32_t l1_task_count[kNumDeviceLocalityDomains];
    uint32_t l2_task_count[kNumDeviceLocalityDomains];
    uint32_t shared_l1_task_count[kNumDeviceLocalityDomains];
    uint32_t shared_l2_task_count[kNumDeviceLocalityDomains];

    // Combine readiness: `combine_ready_grid_idx[peer] == own grid index` means the peer's L2 writes into this
    // rank are done; grid indices are unique per launch, so no reset is needed. Peers push theirs during dispatch.
    alignas(128) uint64_t combine_ready_grid_idx[kNumMaxRanks];
    alignas(128) uint64_t peer_grid_idx[kNumMaxRanks];

    uint32_t l1_empty_count[kNumMaxRingBlocks];
    uint64_t l2_full_mask[kNumMaxRingBlocks];

源码：deep_gemm/include/deep_gemm/layout/mega_moe.cuh 第 53–89 行（MegaMoESignals 的完整布局）

第一组是全局同步：grid_sync_count（4 个 grid 级计数器）、nvl_barrier_counter 加两相 nvl_barrier_signals，保证所有 rank 的 dispatch 完成后才开始计算。第二组是调度计数器：每个 locality domain 各有 L1、L2、SharedL1、SharedL2 四个原子计数器，调度器用 atomicAdd 领取任务。第三组是 combine 就绪标记：combine_ready_grid_idx[peer] 存的是 peer rank 的 grid index——每次 launch 的 grid index 唯一递增，所以不需要重置。第四组是专家粒度的 token 计数（send/recv/recv_sum），dispatch warpgroup 用来知道每个专家收了多少 token。第五组是 ring buffer 的四路信号：l1_full_count（dispatch 填好，MMA 可读）、l1_empty_count（MMA 读完，dispatch 可复用）、l2_full_mask（L1 的 64 位完成 bitmask，L2 做 K 块级等待）、l2_empty_count（L2 读完，ring 槽位可回收）。

这五组信号的内存布局经过精心对齐。结构体最外层按 128 字节对齐（alignas(128)），combine_ready_grid_idx 和 expert_send_count 各自也有 128 字节对齐。这保证了不同信号组落在不同的缓存行上，避免了跨 rank 原子操作之间的伪共享。kNumMaxRingBlocks 设为 2^{20}（约 100 万个条目），是信号数组（l1_full_count、l1_empty_count、l2_empty_count 等）的编译期索引上界，而非 ring buffer 数据区域的实际容量。运行时只使用前 num_ring_tokens / block_m 个条目——这个值由 get_num_max_live_pool_blocks 决定，通常只有几十到几百。

信号的生产-消费协议采用单调递增计数器而非布尔标志。以 l1_full_count 为例：dispatch 线程填满第 i 个 ring 槽位后把 l1_full_count[i] 加 1（release 语义）；MMA 线程在取第 i 个槽位前轮询 l1_full_count[i] 直到它等于预期的代数（acquire 语义）。因为 ring buffer 会被循环复用，计数器的值每绕一圈加 1，所以 MMA 线程总是知道自己等的是第几代。同理，l1_empty_count 由 MMA 推进、dispatch 等待，形成了一个经典的有界缓冲区生产者-消费者模型。

l2_full_mask 比较特殊：它是 64 位 bitmask 而非计数器，因为 L2 需要做 K 块级的细粒度等待——一个 L1 N 块完成后只翻转一位，L2 可以在其他 K 块还没就绪时先处理已就绪的部分。这种设计让 L2 的 MMA 可以尽早开始消费已完成的 K 块，而不是等到同一 pool block 的所有 L1 N 块全部完成。在典型配置中 L1 可能有 8–16 个 N 块，如果 L2 要等全部完成才能开始，流水线就会出现明显的气泡。bitmask 的逐位等待把这个气泡缩小到单个 N 块的延迟，对整体吞吐有可观的提升。

权重变换：gate/up 交错 + UTCCP scale 转置

Mega MoE 要求权重在第一次使用前做一次预变换。transform_weights_for_mega_moe 对 FP8/FP4 权重做两件事，对 BF16 权重只做第一件：

def transform_weights_for_mega_moe(
    l1_weights: Union[torch.Tensor, Tuple[torch.Tensor, torch.Tensor]],
    l2_weights: Union[torch.Tensor, Tuple[torch.Tensor, torch.Tensor]],
    activation: str = 'swiglu'
) -> Tuple[Union[torch.Tensor, Tuple[torch.Tensor, torch.Tensor]],
           Union[torch.Tensor, Tuple[torch.Tensor, torch.Tensor]]]:
    assert activation == 'swiglu', f'Only `swiglu` activation is supported, got `{activation}`'
    if isinstance(l1_weights, tuple):
        # FP8/FP4: interleave gate/up for weight and SF, then transpose L1 SF for UTCCP
        l1_w = _interleave_weights(l1_weights[0])
        l1_sf = _transpose_sf_for_utccp(_interleave_weights(l1_weights[1]))
        l1_transformed = (l1_w, l1_sf)
        # L2: only transpose SF for UTCCP
        l2_transformed = (l2_weights[0], _transpose_sf_for_utccp(l2_weights[1]))
    else:
        # BF16: L1 interleave gate/up, L2 unchanged
        l1_transformed = _interleave_weights(l1_weights)
        l2_transformed = l2_weights
    return l1_transformed, l2_transformed

gate/up 交错

_interleave_weights 把 L1 权重从 [gate | up] 的拼接排列变成 [gate:0..7, up:0..7, gate:8..15, up:8..15, ...] 的交错排列。

def _interleave_weights(t: torch.Tensor, gran: int = 8) -> torch.Tensor:
    # [gate: 0..7, up: 0..7, gate: 8..15, up: 8..15, ...] instead of [gate | up]
    # Unsqueeze for 2D
    assert t.dim() in (2, 3)
    squeeze_group_dim = t.dim() == 2
    if squeeze_group_dim:
        t = t.unsqueeze(0)

    # Transpose
    g, n, *rest = t.shape
    half = n // 2
    gate = t[:, :half].reshape(g, half // gran, gran, *rest)
    up = t[:, half:].reshape(g, half // gran, gran, *rest)
    result = torch.empty_like(t).copy_(torch.stack([gate, up], dim=2).reshape(g, n, *rest))
    return result.squeeze(0) if squeeze_group_dim else result

源码：deep_gemm/mega/__init__.py 第 112–126 行（节选）

为什么要交错？SwiGLU 的定义是 SiLU(gate) * up，epilogue 线程需要同时读到一对 gate 和 up 行来做激活。如果 gate 和 up 各自连续存放，epilogue 就要跳到相距 N/2 行的地方读取另一半；交错后，第 2i 行是 gate、第 2i+1 行是 up（在 8 行粒度内），读取是局部的。图 2 画出了变换前后的排列。

UTCCP scale 转置

_transpose_sf_for_utccp 对两层权重的 UE8M0 缩放因子做转置。它把 (mn, packed_sf_k) 中每 128 行视为 (-1, 4, 32, packed_sf_k)，然后交换 dim 2 和 dim 3，结果是 (-1, 32, 4, packed_sf_k)。

def _transpose_sf_for_utccp(sf: torch.Tensor) -> torch.Tensor:
    # Unsqueeze for 2D
    assert sf.dtype == torch.int and sf.dim() in (2, 3)
    squeeze_group_dim = sf.dim() == 2
    if squeeze_group_dim:
        sf = sf.unsqueeze(0)

    # Transpose
    num_groups, mn, packed_sf_k = sf.shape
    assert mn % 128 == 0
    result = (sf.reshape(num_groups, -1, 4, 32, packed_sf_k)
                .transpose(2, 3)
                .reshape(num_groups, mn, packed_sf_k))
    result = torch.empty_like(sf).copy_(result)
    return result.squeeze(0) if squeeze_group_dim else result

源码：deep_gemm/mega/__init__.py 第 129–143 行（节选）

这个转置是 SM100 块缩放 MMA 的要求。UTCCP（Unified Tensor Core Copy）把缩放因子从全局内存搬入 TMEM（张量内存），搬运的粒度是 128 个元素。转置后，TMA 按行读入的 SF 数据恰好按照 UTCCP 期望的顺序排列在 TMEM 里。对 L1 权重，先做 gate/up 交错再做 SF 转置；对 L2 权重，只做 SF 转置（L2 不涉及 gate/up 拆分）。

SM100 BF16 与 FP8/FP4：两条 MMA 路径的差异

Mega MoE 有两套 SM100 实现：sm100_bf16_mega_moe.cuh 用于 BF16 前向路径，sm100_fp8_fp4_mega_moe.cuh 用于 FP8/FP4 量化路径。两者共享 Mega MoE 的整体架构——对称缓冲、ring buffer、三类线程组、L1 预热调度——但 UMMA 配置和缩放因子处理有关键差异。

差异总结：

  1. UMMA 粒度翻倍：UMMA_K = 32（BF16 是 16）、UMMA_BLOCK_K = 128（BF16 是 64）。低精度元素尺寸更小，tcgen05 每条指令打包更多数据。
  2. 权重支持 FP8 或 FP4：weight_dtype_t 可以是 float_e4m3_t（FP8）或 float_e2m1_unpacksmem_t（FP4）——前者是路由专家用 FP8 权重，后者用 FP4。激活和共享专家权重固定为 FP8 e4m3。
  3. UTCCP 4×32 转置：transform_sf_token_idx lambda 把每 128 个元素的线性索引映射为 (idx & 31) * 4 + ((idx >> 5) & 3)——与 权重变换 一节中 _transpose_sf_for_utccp 在 Python 端做的 4×32 转置对应，内核端用它来定位转置后的 SF 行。此外，FP8/FP4 路径需要额外的 TMA 描述符来搬运 A、B、共享 B 各自的缩放因子。

局限与未覆盖

  • Mega MoE 只有 SM100（Blackwell）实现。它依赖 tcgen05/UMMA、TMEM、UTCCP 和 2-CTA cluster，这些都是 SM100 的新特性。在 SM90（Hopper）上无法实现同等的融合度。这意味着对于 Hopper 集群，MoE 层仍需分解为独立的 dispatch、GEMM、combine 三步调用，中间结果要写回 HBM，而 Mega MoE 把这些全部融合进一个持久化内核，省去了中间的全局内存往返——wgmma 不支持 cta_group::2，累加器在寄存器而非 TMEM 中（无法跨 warpgroup 共享），且缺少对称内存的原生 NVLink 指针机制。
  • 本文没有实测性能数字。本地没有 GPU，仓库文档中也没有提供 Mega MoE 的 benchmark 数据。
  • BF16 路径与 FP8/FP4 路径的 MMA 配置差异已在上一节展开，但两条路径的epilogue 实现细节（BF16 路径的 SwiGLU 直接写出 vs FP8 路径的 SF 打包）没有逐行对比。BF16 路径在 epilogue 阶段可以直接把 SwiGLU 的结果写到全局内存，因为输出精度和计算精度一致；FP8 路径则需要额外一步量化和缩放因子的打包写出，这使得其 epilogue 的寄存器压力和共享内存用量都更高。两条路径在调度器层面共享相同的 L1/L2 信号机制和持久化 tile 分配逻辑，差异仅在 MMA 配置和尾声处理上，这使得两条路径可以共享大部分调度器和通信代码，降低了维护负担，也方便了后续对新数据类型（如未来可能出现的更低精度格式）的扩展支持，也便于独立测试和调试各条路径。
  • 共享专家路径（SharedLinear1、SharedLinear2）使用了独立的输入缓冲区和信号（如 shared_l2_full_count），本文只做概述，没有深入分析共享专家的调度。
  • Mega MoE 与 DeepEP 的集成——特别是 DeepEP 的 deferred epilogue 接口——不在本文范围。Mega MoE 自己包含了 dispatch 功能，可以独立于 DeepEP 使用。
  • 内核内部的 UMMA 流水线（TMA → TMEM → UMMA → 累加器 → 输出）细节和 Mega MoE 的 warp 特化内部实现没有展开。dg02（Blackwell GEMM）覆盖了 SM100 GEMM 的通用结构。
  • 调度器中局部性域亲和与工作窃取的条件判断（"当本域剩余任务过少时禁用窃取"等边界条件）没有逐行展开。
