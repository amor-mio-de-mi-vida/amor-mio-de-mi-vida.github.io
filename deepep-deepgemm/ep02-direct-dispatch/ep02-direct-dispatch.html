直连模式的 dispatch：
计数、布局、收发与拷贝尾声

dispatch 内核先用通知 warp 数清每个 rank 和专家要收多少 token，再用发送 warp 把数据经 NVLink 或 RDMA 搬到对端缓冲区；拷贝尾声通过 PDL 接力，把缓冲区中的 token 展开到专家对齐的输出张量里，并零填充对齐间隙。

TL;DR

  • dispatch 内核分成通知 warp 和发送 warp 两组：通知 warp 在全部 SM 上做两级归约计数，再经 NVLink 或 RDMA 与对端交换；发送 warp 逐 token 把 hidden、SF 和元数据打包成对齐的记录，直写对端缓冲区。
  • token 记录的内存布局把 hidden（32B 对齐）、缩放因子（32B 对齐）和元数据（32B 对齐）三段拼在一起，整条记录再对齐到 64B 以满足 RDMA 要求。
  • 拷贝尾声通过 PDL（程序化依赖启动）零开销接力，按专家前缀和把 token 展开到输出张量，并用 TMA store 零填充每个专家区间的对齐间隙。
  • FP8 缩放因子作为 token 记录的一部分随数据传输，发送端用 cp.async 而非 TMA 加载（因为输入 SF 可能有非连续步幅），接收端带步幅逐元素写出。

dispatch 内核在做什么

上一篇介绍了 EPBuffer 的 Python 接口和展开布局（expanded layout）概念。这一篇拆开直连模式（num_scaleout_ranks == 1）下 dispatch 的两个 CUDA 内核，看它们怎么把 token 数据搬到正确的 rank 上。

dispatch 的工作可以概括为一句话：把本 rank 的 token，按其 top-k 专家选择，发送到拥有这些专家的 rank 的接收缓冲区里。如图 1 所示，这件事拆成两个内核依次执行：

  1. dispatch_impl——主内核。通知 warp 数清每个 rank/专家会收到多少 token，交换计数并计算布局偏移；发送 warp 负责把数据搬到对端缓冲区。
  2. dispatch_copy_epilogue_impl——拷贝尾声。通过 PDL（Programmatic Dependent Launch）接在主内核之后零开销启动，把对端写来的 token 从缓冲区展开到最终输出张量里。
直连模式指所有 rank 之间都可以直接通信（NVLink 或 RDMA），不需要混合模式的转发 warp。混合模式见第 4 篇。

这两个内核的分工在 dispatch.hpp 的 launch_dispatch 函数中决定：当 num_scaleout_ranks == 1 时选择直连模式的 dispatch_impl，否则选择混合模式的 hybrid_dispatch_impl。通知 warp 固定为 4 个（kNumNotifyWarps = 4），发送 warp 数由共享内存预算决定——每个发送 warp 需要一个 TMA 缓冲槽位，所以 warp 数 = min((smem - 通知区) / 每槽字节数, 32 - 4)。

两组 warp 的并行时序

notify warp 和 send warp 在初始 gpu_barrier 之后完全并行执行——两者之间没有任何同步点。Notify warp 只与自身同步（named_barrier<kNumNotifyThreads>），send warp 只与同 warp 的 mbarrier 同步。两组在最终 gpu_barrier（含 TMA store flush）处汇合（dispatch.cuh 第 72–405 行）：

两组之间没有数据依赖：notify warp 计算接收端的全局计数（"你将收到多少 token"），send warp 通过独立的 scaleup_atomic_sender_count[R] 分配槽位索引（"这个 token 放在接收缓冲区的哪个位置"）。两组计数器完全独立，所以 send warp 可以从第一条 token 就开始发送，无需等 notify warp 完成。最终的 gpu_barrier tag1 保证：当尾声内核启动时，所有 rank 的数据已全部到达。

这个并行设计的内存序值得点明。两组 warp 之间不共享任何数据，因此不需要 st.release/ld.acquire 配对。跨 rank 的序由 gpu_barrier tag1（阶段 5）提供：它内部先执行 tma_store_arrive_fence 确保本 rank 所有 TMA store 到达远端的可见性屏障，再通过 BarrierSignals 的两阶段翻号协议等待所有 rank 到达同一点。对端的屏障信号通过 NVLink 的 gin.put_value 写入（NVLink 保证单一 QP 内的写入按序可见）或 RDMA 的 gin.put 发出（IB 规范保证同一 QP 的 RDMA Write 按序完成）。当 tag1 屏障通过时，所有 rank 的所有 token 记录和所有计数都已在接收端可见——这就是拷贝尾声可以安全读取缓冲区的前提。通知 warp 的计数交换则靠更细粒度的序：发送端的 gin.put_value 在接收端的 ld_volatile 轮询循环中用"编码负数"区分"未到达"和"到达且为零"，不需要额外的 fence——volatile 读保证每次从全局内存取值，而 NVLink/RDMA 写到达后对 volatile 读可见。完整的内存序原语表见第 5 篇。

通知 warp 的三步：本地计数、全网格归约、对端交换

在发送任何数据之前，每个 rank 必须知道自己会收到多少 token——这是分配缓冲区槽位的前提。通知 warp（4 个 warp，128 个线程）分三步完成这件事。

第一步：本地计数

每个 SM 的通知 warp 各扫描一部分 token。对于每个 token 的 top-k 专家选择：

  • 专家计数：直接对共享内存中的 expert_count 数组做 atomicAdd_block——因为专家选择不会重复（同一 token 不会选同一个专家两次）。
  • Rank 计数：先用 ptx::deduplicate 在 warp 内去重（同一 token 的多个 top-k 选择可能映射到同一个 rank），只有"主 lane"执行 atomicAdd_block，避免重复计数。
// Atomic add on shared memory
EP_STATIC_ASSERT(kNumTopk <= 32, "Insufficient lanes");
const auto global_warp_idx = warp_idx * kNumSMs + sm_idx;
for (int i = global_warp_idx; i < num_tokens; i += kNumNotifyWarps * kNumSMs) {
    // Expert choice can not be redundant
    // NOTES: no assertions here as they are expensive
    const auto dst_expert_idx = lane_idx < kNumTopk ?
        static_cast<int>(__ldg(topk_idx + i * kNumTopk + lane_idx)) : -1;
    if (dst_expert_idx >= 0)
        atomicAdd_block(expert_count + dst_expert_idx, 1);

    // Rank choice should do deduplication here
    const auto dst_rank_idx = dst_expert_idx >= 0 ? dst_expert_idx / kNumExpertsPerRank : -1;
    if (ptx::deduplicate(dst_rank_idx, lane_idx) and dst_rank_idx >= 0)
        atomicAdd_block(rank_count + dst_rank_idx, 1);
}
ptx::named_barrier<kNumNotifyThreads>(kNotifyBarrierIndex);

源码：deep_ep/include/deep_ep/impls/ep/dispatch.cuh 第 91–107 行（节选）

这里的去重（deduplicate）是关键：如果 top-k = 8 且其中 3 个专家属于同一个 rank，rank 计数应该只加 1（表示向该 rank 发送 1 个 token），但专家计数应该加 3。ptx::deduplicate 用 warp 级 match 指令（__match_any_sync）找到所有持有相同值的 lane 的位掩码，再用 get_master_lane_idx（底层是 bfind.u32，即取最高位）选出"主 lane"——最高编号的匹配 lane。只有主 lane 执行后续的 atomicAdd，其余 lane 跳过。注意 __match_any_sync 是全 warp 广播操作，不要求输入有任何排列顺序。

第二步：全网格归约

每个 SM 有自己的局部计数，需要求和得到全局计数。DeepEP 用了一个巧妙的打包编码：

// Do full-grid reduction
#pragma unroll
for (int i = thread_idx; i < kNumRanks + kNumExperts; i += kNumNotifyThreads) {
    const int64_t counter = (1ll << 32ll) | rank_expert_count[i];
    ptx::red_add(workspace_layout.get_notify_reduction_workspace_ptr() + i, counter);
}

源码：deep_ep/include/deep_ep/impls/ep/dispatch.cuh 第 109–114 行（节选）

把到达计数器（高 32 位）和实际计数（低 32 位）打包成一个 int64_t，用一次 ptx::red_add（全局原子加）同时更新两者。SM 0 等待高 32 位等于 kNumSMs 时，就知道所有 SM 都已写完，可以安全读取低 32 位的总和。这避免了显式的网格同步。

SM 0 读取到总和后，还需要用 encode_decode_positive 编码再写回：


template <typename dtype_t>
__forceinline__ __device__ __host__ bool is_decoded_positive_ready(const dtype_t& value) {
    return value >= 0;
}

template <typename dtype_t>
__forceinline__ __device__ __host__ dtype_t encode_decode_positive(const dtype_t& value) {
    return -value - static_cast<dtype_t>(1);

源码：deep_ep/include/deep_ep/common/math.cuh 第 24–32 行（正数编码与就绪检查）

编码规则是 -value - 1：0 变成 -1，3 变成 -4，依此类推。它是自身的逆——再调用一次就恢复原值。为什么需要这一步？因为计数交换后，对端需要区分"计数还没到达"和"计数到达了但值为 0"——两者在普通编码下都是 0。编码后，"未到达"仍是 0（初始值），"到达且值为 0"变成 -1；接收端通过 is_decoded_positive_ready(value)（即 value >= 0）判断是否就绪，就绪后再调用 encode_decode_positive 解码得到原始计数。SM 0 在使用完归约区域后立即清零（workspace[i] = 0），为下一次 dispatch 调用恢复初始状态。

第三步：与对端交换计数

SM 0 拿到本 rank 发给每个对端的 token 数后，需要告诉每个对端"你将收到多少"。NVLink 和 RDMA 的交换方式不同：

  • NVLink：逐元素用 gin.put_value 写到对端的 workspace。因为 NVLink 可以直接访问对端内存，每次写一个 int64_t 就够了。
  • RDMA：先把本 rank 的专家计数写到本地 send buffer（workspace 里），再用 gin.put 批量发送到对端。RDMA 的建连开销高，批量发送更高效。

交换完成后，SM 0 等待收到所有对端的计数，然后：

  1. 归约每个本地专家的接收 token 数，向上对齐到 kExpertAlignment。
  2. 计算 rank 维度的包含前缀和（inclusive prefix sum）和专家维度的排他前缀和（exclusive prefix sum）。
  3. 如果启用了 CPU 同步（kDoCPUSync），把计数写到映射的 host workspace，让 CPU 端可以读到。

前缀和用 warp 级的 ptx::warp_inclusive_sum 实现：warp 0 算 rank 前缀和，warp 1 算专家前缀和——两个 warp 并行工作。

token 记录与工作缓冲区

dispatch 把每个 token 的所有信息打包成一条token 记录（token record），作为通信的最小单元（图 2）。记录的布局由 TokenLayout 定义：

struct TokenLayout {
    int num_hidden_bytes, num_sf_bytes;
    // NOTES: the top-k index is always 32-bit
    bool with_metadata;
    int num_topk, num_metadata_bytes;
// ...
    __forceinline__ __device__ __host__
    TokenLayout(const int& num_hidden_bytes, const int& num_sf_bytes,
                const int& num_topk, const bool& with_metadata, void* base = nullptr) :
        num_hidden_bytes(num_hidden_bytes),
        num_sf_bytes(num_sf_bytes),
        // Metadata includes: top-k indices, weight and source rank/token index
        with_metadata(with_metadata),
        num_topk(num_topk),
        num_metadata_bytes(num_topk * (sizeof(int) + sizeof(float)) +
                           (with_metadata ? (1 + num_topk) * sizeof(int) : 0)),
        base(base) {
        EP_STATIC_ASSERT(sizeof(int) == sizeof(float), "Invalid size assumption");
        EP_UNIFIED_ASSERT(num_hidden_bytes % kNumTMAAlignmentBytes == 0);
    }
// ...
    __forceinline__ __device__ __host__ dtype_t get_num_bytes() const {
        const auto num_data_bytes = math::align<int>(
            math::align(num_hidden_bytes, kNumTMAAlignmentBytes) +
            math::align(num_sf_bytes, kNumTMAAlignmentBytes) +
            math::align(num_metadata_bytes, kNumTMAAlignmentBytes), kNumRDMAAlignmentBytes);
        const auto num_bytes =
            num_data_bytes + math::align<int>(kWithMBarrier ? sizeof(ptx::mbarrier) : 0, kNumTMAAlignmentBytes);
        return static_cast<dtype_t>(num_bytes);
    }

源码：deep_ep/include/deep_ep/layout/ep/token.cuh 第 10–42 行（节选）

对齐规则反映了硬件约束：kNumTMAAlignmentBytes = 32 是 TMA（Tensor Memory Accelerator）的最小传输粒度，kNumRDMAAlignmentBytes = 64 是 RDMA 传输的对齐要求。这两个常量贯穿整个通信层。选择 64 字节而非更小的 RDMA 对齐值是为了兼容不同厂商网卡的最优传输粒度——InfiniBand 和 RoCE 的 DMA 引擎在 64 字节对齐时可以避免跨缓存行的拆分读写，从而达到最高吞吐。对于 hidden = 7168、FP8 精度的典型配置，hidden 段占 7168 字节（已是 32B 对齐），SF 段占 224 字节（56 个 4 字节包），metadata 段占 68 字节（top-k=8 时：索引 32B + 权重 32B + src_idx 4B），整条记录约 7460 字节，对齐到 64B 后为 7488 字节。

metadata 字段包含：

  • topk_idx（\(k \times 4\)B）：这个 token 的 top-k 专家索引。
  • topk_weights（\(k \times 4\)B）：对应的门控权重。
  • src_token_global_idx（4B）：源 token 在全局中的位置（rank_idx * T + token_idx），供 combine 回传时使用。
  • linked_list_idx（\(k \times 4\)B）：混合模式下的链表索引（直连模式不使用）。

通信缓冲区由 BufferLayout 管理：接收缓冲区分为 R 个 rank 区域，每个区域最多容纳 T 个 token 记录；发送缓冲区只有 1 个区域（本 rank 发出的 token 的临时副本，仅 RDMA 路径使用）。

工作区（workspace）则由 EPSignals 承载所有信号和计数器：

发送 warp：装载、发送与两条路径

发送 warp 的数量由共享内存预算决定：每个 warp 独占一个 smem TMA 缓冲槽位（包含完整的 token 记录 + mbarrier）。典型配置下有十几到二十几个发送 warp。

每个发送 warp 以 warp 级步幅遍历所有 token，对每个 token 执行以下流水线：

装载：TMA + cp.async

// Issue data TMA
if (ptx::elect_one_sync()) {
    ptx::tma_load_1d(tma_buffer.get_hidden_ptr(), math::advance_ptr(x, token_i64_idx * kNumHiddenBytes),
                     mbarrier_ptr, kNumHiddenBytes);
}
// ...
// Issue SF TMA or cp.async
if constexpr (kNumSFPacks > 0) {
    EP_STATIC_ASSERT(sizeof(sf_pack_t) % 4 == 0, "Unaligned SF element type");
    const auto gmem_src_ptr = math::advance_ptr<sf_pack_t>(sf, token_i64_idx * sf_token_stride * sizeof(sf_pack_t));
    const auto smem_dst_ptr = tma_buffer.get_sf_ptr();

    constexpr auto kNumFullIters = kNumSFPacks / 32;
    #pragma unroll
    for (int k = 0; k < kNumFullIters; ++ k) {
        ptx::cp_async_ca(gmem_src_ptr + (k * 32 + lane_idx) * sf_hidden_stride,
                         smem_dst_ptr + k * 32 + lane_idx);
    }
    if (kNumFullIters * 32 + lane_idx < kNumSFPacks) {
        ptx::cp_async_ca(gmem_src_ptr + (kNumFullIters * 32 + lane_idx) * sf_hidden_stride,
                         smem_dst_ptr + kNumFullIters * 32 + lane_idx);
    }
    ptx::cp_async_mbarrier_arrive(mbarrier_ptr);
    __syncwarp();
}

hidden 数据用 TMA 1D load 搬到 smem（一次搬完全部 kNumHiddenBytes）；SF 用 cp.async 逐 pack 搬运——这是因为输入 SF 张量可能有非连续步幅（sf_hidden_stride），而 TMA 要求连续内存。cp.async_mbarrier_arrive 让 SF 的完成信号合并到同一个 mbarrier，与 hidden 的 TMA load 形成一个统一的等待点。

随后加载 top-k 索引和权重到 smem（从全局内存用普通 __ldg 读取），并写入源 metadata（rank_idx * T + token_idx）。写完 metadata 后执行 tma_store_fence——这条围栏确保后续的 TMA store 能看到 smem 里的所有更新。

槽位分配与去重

每个 token 可能有多个 top-k 选择指向不同的 rank，但只需要向每个目标 rank 发送一次完整的 token 记录（因为记录里包含了所有 top-k 的 metadata）。所以发送前需要跨 lane 去重：

// Deduplicate ranks and assign slots
int stored_dst_slot_idx = -1;

        const auto value = stored_dst_slot_idx >= 0 ?
            rank_idx * kNumMaxTokensPerRank + stored_dst_slot_idx : -1;
        dst_buffer_slot_idx[token_idx * kNumTopk + lane_idx] = value;
    }
}

两种模式：

  • 首次 dispatch（kReuseSlotIndices = false）：用 ptx::deduplicate 在 warp 内去重目标 rank，主 lane 用 atomicAdd 从全局计数器分配槽位索引，并保存到 dst_buffer_slot_idx 供后续 combine 重用。
  • 缓存 dispatch（kReuseSlotIndices = true）：直接读取上次保存的槽位索引，跳过去重和分配。这对应 ep01 介绍的 cached dispatch 模式。

NVLink 与 RDMA 两条路径

等待 TMA load 和 cp.async 都完成后，根据连接类型选择发送方式：

  • NVLink：通过 gin.get_sym_ptr 获取对端缓冲区的对称内存指针，用 TMA store 直接写到对端——整条 token 记录一次搬完，延迟极低。
  • RDMA：先 TMA store 到本地 send buffer（L360-364），等本地写完成后（tma_store_wait<1>），再用 gin.put 发起 RDMA 传输。对于 NVLink 可达的 rank（混合拓扑中），即使走 RDMA 路径也会跳过（L384: dst_ptr == nullptr）。

所有 token 发完后，一个全局屏障（gpu_barrier）确保所有 rank 的数据都已到达，最后 cudaTriggerProgrammaticLaunchCompletion 触发拷贝尾声内核。

拷贝尾声：展开、填充与 PDL

拷贝尾声（dispatch_copy_epilogue_impl）的任务是把接收缓冲区里按 rank 排列的 token 展开到按专家排列的输出张量里。它通过 PDL（Programmatic Dependent Launch）启动，用 cudaGridDependencySynchronize 等待主内核完成——这比独立 launch + event 等待的开销更低，因为 PDL 在调度器级别做依赖。

PDL 是 CUDA 12.x 引入的机制：尾声内核的 grid 可以在主内核还在运行时就被调度器加载，主内核结束后立即开始执行，省去了 CPU 端 launch 的延迟。

尾声内核遍历所有接收到的 token（总数由 rank 前缀和的最后一个元素给出）。对每个 token：

  1. 从接收缓冲区 TMA load 整条记录到 smem。
  2. 读取 topk_idx，过滤出属于本 rank 专家范围的索引。
  3. 根据模式计算目标位置 dst_tensor_idx。

如图 3 所示，目标位置的计算有三种情况：

// Calculate target indices in the tensor
constexpr int kMetadataStride = 2 + kNumTopk;
int dst_tensor_idx = -1;
if (not kDoExpand and ptx::elect_one_sync()) {
    dst_tensor_idx = i;
} else if (kDoExpand and kCachedMode and lane_idx < kNumTopk) {
    // Cached expand mode: read pre-computed dst_tensor_idx from metadata
    dst_tensor_idx = recv_src_metadata[i * kMetadataStride + 2 + lane_idx];
} else if (kDoExpand and not kCachedMode and dst_expert_idx >= 0) {
    dst_tensor_idx = atomicAdd(psum_num_recv_tokens_per_expert + dst_expert_idx, 1);
}
__syncwarp();

// Wait for TMA arrival

  • 不展开（kDoExpand = false）：dst = i，token 按接收顺序紧密排列。这是 combine 的反向（backward）使用的模式。
  • 缓存展开（kCachedMode = true）：从之前保存的 metadata 中直接读取预计算的位置。
  • 首次展开（默认）：对专家前缀和做 atomicAdd，原子地分配展开位置。这正是展开布局的构建过程。

零填充

展开布局中每个专家的 token 数被向上对齐到 kExpertAlignment，对齐间隙里的数据必须清零——后续的 MoE GEMM 会读到这些位置。零填充阶段：

  1. 用 ptx::st_bulk 把 smem 中的 hidden 区域清零（一条指令清整块内存），然后 tma_store_fence。
  2. 遍历每个专家的 padding token，用 TMA store 把全零 hidden 写到输出。
  3. 同时把对应位置的 topk_weights 和 SF 也清零。

遍历 padding 的算法比较精巧：它在 warp 内用前缀和和 __ballot_sync 定位每个 pad token 属于哪个专家，一个 while 循环跨所有专家的所有 padding，用 wave 索引跳转到正确位置。零填充不仅保证了后续 GEMM 内核读到的数据是确定的（全零），还避免了 NaN 或 denorm 值意外参与 Tensor Core 的累加——对 FP8 模式尤其重要，因为 FP8 E4M3 只有一个 NaN 表示（0x7F），padding 区域如果残留来自上一轮的随机数据，有约 1/128 的概率命中 NaN，会导致整个 Tensor Core 累加器被"感染"为 NaN。零填充还保证了 SF 的对齐间隙也是零——如果 SF 残留非零值，反量化后会产生非零的伪数据参与归约，造成静默的精度偏差。

FP8 缩放因子如何随数据一起传输

当 dispatch 的输入是 FP8 格式时，每个 token 除了 hidden 数据外还携带缩放因子（scaling factor, SF）。DeepEP 把 SF 作为 token 记录的一部分传输，不走独立的通信通道。

SF 的传输有几个值得注意的细节：

  • 发送端加载：SF 用 cp.async（而非 TMA）从全局内存搬到 smem。原因是输入 SF 张量可能有非连续的 sf_hidden_stride（例如 DeepGEMM 的列主序布局），cp.async 可以按步幅逐元素加载，而 TMA 1D load 要求源内存连续。
  • 打包类型：SF 以 sf_pack_t 为单位存储，这是一个联合体，可以容纳一个 float（per-token 缩放因子）或四个 UE8M0 字节（per-128 块缩放因子）。
  • 在记录中的位置：SF 紧跟在 hidden 之后，两者之间有 TMA 对齐填充。kNumSFPacks 是模板参数，当值为 0 时（例如 BF16 dispatch），所有 SF 相关代码被编译期消除。
  • 接收端写出：拷贝尾声把 SF 先读到寄存器，再用显式的逐 lane 全局内存写（不是 TMA store）写到输出 SF 张量。这是因为输出 SF 也可能有步幅（recv_sf_hidden_stride），需要带步幅写出。遍历所有有效的 dst_tensor_idx lane（通过 mask 和 __ffs），对每个有效位置执行带步幅的 SF 写入。

对比 combine：combine 的 token 记录不携带 SF（num_sf_bytes = 0），因为 MoE 的输出精度是 BF16，不需要额外的缩放因子。

SF 的打包格式取决于上游量化方式。如果是 per-token FP32 缩放（DeepGEMM 的 FP8 模式），kNumSFPacks = 1，每个 token 携带一个 4 字节 float。如果是 per-128-element UE8M0 块缩放（SM100 的 MXFP8/MXFP4），kNumSFPacks 等于 ceil(hidden/128) 个 4 字节包，每包含 4 个 UE8M0 字节——例如 hidden = 7168 时需要 56 个包、224 字节。两种格式的通信开销差异显著：per-token 模式下 SF 只占记录总大小的 0.05%（4 / 7460），而 per-128 块缩放模式下 SF 占约 3%（224 / 7488）——对于大规模通信来说仍然很小，但在 RDMA 带宽受限的场景下不可忽略。这个模板参数在 DeepJIT 编译时根据实际 SF 尺寸确定，不同的 SF 尺寸会生成不同的内核实例。值得注意的是，SF 在记录中的位置经过对齐填充（kSFPadding），确保 TMA store 的起始地址满足 16 字节或 128 字节的对齐要求——不对齐的 TMA 操作会在某些硬件配置上静默产生错误数据。
