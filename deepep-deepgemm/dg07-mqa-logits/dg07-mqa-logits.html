TL;DR

  • 索引器的分数是“每个头的点积先过 ReLU，再按查询自己的头权重加权求和”；所有查询头共用一个 K 头，所以内核把 128 个 (token, 头) 行拼成 GEMM 的 N 维，KV token 作 M 维。
  • 连续版的输出是压缩的：第 i 行第 c 列对应 KV 下标 ks[i] + c，每行都从第 0 列开始，有效区间以外的列内核不写。
  • SM90 用 FP8 加每 token 一个 FP32 缩放，由于 ReLU 正齐次，这个缩放可以留到加权求和之后再乘；SM100 用 MXFP4/MXFP8 加每 32 维一个 UE8M0 缩放，只能交给块缩放 MMA 在张量核里处理。
  • 分页 KV cache 的形状写成 [.., D′+4]，但一页里实际是先放全部 token 的数据、再放全部 4 字节缩放。
  • 稀疏版只给每个查询选中的 8 或 16 token 小块打分；相邻两个查询的块列表合并去重后共享一次 KV 搬运，再按槽位写回各自的压缩行。

索引器只要一张分数表，DeepGEMM 按 KV 的取法给了四个入口

DeepSeek-V3.2 提出的 DeepSeek 稀疏注意力（DeepSeek Sparse Attention，DSA）[1] 在主注意力之前加了一个轻量的打分器：对每个查询 token，它给前文中每个候选 KV token 打一个分，后续再按分数挑出要真正参与注意力的 token。DeepGEMM 的 README 把为它准备的内核称为 “lightning indexer” 的打分内核，并写明它算的是“加权 ReLU 的 MQA logits”[2]。DeepGEMM 只负责算分数；按分数挑 token 的那一步不在这个仓库里。

“MQA”指多查询注意力（multi-query attention）：一个查询 token 有 \(H\) 个头，但只对应一个 K 头。对打分内核来说，这意味着 KV 侧每个 token 只是一条 \(D\) 维向量，而查询侧每个 token 是一个 \(H \times D\) 的小矩阵。

这个打分在不同阶段的访问方式差别很大。预填充时，一批新 token 各自看一段连续的 KV 区间；解码时，KV 存在分页的缓存里，要查块表；如果上游已经把候选范围缩到一些小块，就只需要给这些块打分。csrc/apis/attention.hpp 为此注册了四个打分函数和四个配套的元数据函数（第 445–476 行），表 1 把它们并排放在一起。README 只描述了前两种（非分页用于预填充、分页用于解码），稀疏的两种只在更新日志里以 “Sparse Indexer” 出现，它们的语义要从代码注释和测试里读出来。

打分是一次 GEMM 加一个按头求和的尾声

公式：先 ReLU，再按头加权

README 用四行 PyTorch 给出了每个 \((i, j)\) 的参考计算：先把 KV 反量化，再和 \(H\) 个查询头分别做点积，过 ReLU，乘上这一行的头权重，最后对头求和。

kv_j = kv[0][j, :] * kv[1][j].unsqueeze(1)  # [head_dim]
out_ij = q[i, :, :] @ kv_j  # [num_heads]
out_ij = out_ij.relu() * weights[i, :]  # [num_heads]
out_ij = out_ij.sum()  # Scalar

源码：README.md 第 99–110 行（参考语义）

写成公式，第 \(i\) 个查询对第 \(j\) 个 KV token 的分数是

\[ \begin{gathered} \mathrm{logit}_{i,j} = \sum_{h=1}^{H} w_{i,h}\,\mathrm{ReLU}\!\left(\hat q_{i,h}\cdot \hat k_{j}\right), \\ ks_i \le j < ke_i, \end{gathered} \](1)

其中 \(\hat q_{i,h} \in \R^{D}\) 和 \(\hat k_j \in \R^{D}\) 是反量化后的查询头向量和键向量，\(w_{i,h}\) 是逐 token、逐头的权重（形状 \([S, H]\)）。有两点值得注意：ReLU 作用在每个头的点积上，而不是最终分数上；权重 \(w\) 可以为负（测试里用 torch.randn 生成），所以最终分数也可以是负数。

举一个能手算的例子：\(H = 2\)、\(D = 4\)，查询的两个头是 \(q_1 = (1, -2, 0.5, 1)\)、\(q_2 = (0.5, 1, -1, 2)\)，权重 \(w = (0.75, -0.5)\)。对 \(k_0 = (1, 0, 2, 1)\)，两个点积是 \(3\) 和 \(0.5\)，都为正，分数为 \(0.75 \times 3 - 0.5 \times 0.5 = 2.0\)。对 \(k_1 = (-1, 1, 0, 0.5)\)，点积是 \(-2.5\) 和 \(1.5\)，第一个头被 ReLU 截成 0，分数为 \(-0.5 \times 1.5 = -0.75\)。这两个数由 plots/common.py 中按 README 语义写的 NumPy 参考实现复核过。

GEMM 视角：KV 当 M，(token, 头) 当 N

式 (1) 里最贵的是点积 \(\hat q_{i,h}\cdot \hat k_j\)。把一批查询 token 的所有头摊平成行，它就是一个矩阵乘：\(K \in \R^{T\times D}\) 乘以 \(Q^\top \in \R^{D \times (\text{token}\cdot H)}\)。SM100 内核让 Q 分块固定覆盖 128 个 (token, 头) 行，所以每块装多少个 token 由头数决定：

// The Q tile always covers 128 (token, head) rows
static int get_mqa_logits_block_q(const int& num_heads) {
    DG_HOST_ASSERT(num_heads > 0 and num_heads <= 128 and num_heads % 4 == 0);
    return 128 / num_heads;
}

源码：csrc/jit_kernels/impls/sm100_mqa_logits.hpp 第 20–24 行（节选）

以 \(H = 32\) 为例，一个 Q 分块是 \(128/32 = 4\) 个 token，正好是一次 UMMA 的 N 维。KV 侧每次取一个 384 token 的“split”（kMQALogitsSplitKV），由 3 个数学 warpgroup 各算 128 行，每个 warpgroup 对应 TMEM 里的一个累加器 stage。UMMA（Blackwell 的 tcgen05.mma）和 TMEM（张量内存，MMA 累加器所在的片上存储）的基础见 第 2 篇。图 1 画出了其中一个 128 行的 KV 分块。

这个摆法让按头求和变成线程内的循环：TMEM 的每个 lane 归一个线程，线程用 tmem_load_32dp32b 把自己那一行里某个 token 的 \(H\) 列读进寄存器，就能直接求和，不需要跨线程归约。代码没有说明为什么选这个方向，上面是我们从数据流读出的效果。尾声的核心是下面两个 lambda：

// Reduce both bf16x2 halves and store the low half only for valid KV columns
const auto store_token = [&](const uint32_t& i, const uint32_t& kv_offset,
                             const nv_bfloat162& sum_0, const nv_bfloat162& sum_1) {
    const auto sum = __hadd2_rn(sum_0, sum_1);
    const auto result = __hadd2_rn(__low2bfloat162(sum), __high2bfloat162(sum));
    if (seq_k_start[i] <= kv_offset and kv_offset < seq_k_end[i])
        ptx::st_global_low_bf16(output_bases[i] + kv_offset, result);
};
const auto reduce_pairs = [&](const float* chunk, const nv_bfloat162* chunk_weights, const uint32_t& num_heads,
                              nv_bfloat162& sum_0, nv_bfloat162& sum_1) {
    #pragma unroll
    for (uint32_t head_offset = 0; head_offset < num_heads; head_offset += 4) {
        const auto accum_pair_0 = make_float2(chunk[head_offset], chunk[head_offset + 1]);
        const auto accum_pair_1 = make_float2(chunk[head_offset + 2], chunk[head_offset + 3]);
        sum_0 = __hfma2(ptx::cvt_relu_bf16x2_f32(accum_pair_0), chunk_weights[head_offset / 2], sum_0);
        sum_1 = __hfma2(ptx::cvt_relu_bf16x2_f32(accum_pair_1), chunk_weights[head_offset / 2 + 1], sum_1);
    }
};

源码：deep_gemm/include/deep_gemm/impls/sm100_mqa_logits.cuh 第 472–489 行（节选）

reduce_pairs 每次处理 4 个头：cvt_relu_bf16x2_f32 用一条 cvt.rn.relu.bf16x2.f32 指令把两个 FP32 累加值同时做 ReLU 并转成 BF16，再用 __hfma2 乘上 BF16 权重累加到两个 BF16 部分和里。store_token 把两个部分和相加、再把 bf16x2 的高低两半相加，只在 \(ks_i \le j < ke_i\) 时写出。也就是说，SM100 上按头求和是在 BF16 里完成的，最后的分数也是 BF16。SM90 版本则全程 FP32，下一节会对比。

输出被压缩成 [S, L]：每行从自己的 ks 开始

如果按稠密方式存，输出应该是 \([S, T]\)，\(T\) 是 KV 总长。但每一行真正有效的只是 \([ks_i, ke_i)\) 一段，在把多个请求打包进一次预填充时，大部分格子都是无效的。README 规定输出被压缩成 \([S, L]\)，第 \(i\) 行把自己的有效区间从第 0 列开始存放 [2]。于是第 \(i\) 行第 \(c\) 列对应 KV 下标 \(ks_i + c\)。图 2 用一个两个请求的玩具例子对比了两种视角。

分配输出的代码说明了两件事：底层存储的行数按 Q 分块对齐、行跨度按 KV 分块和 1024 字节对齐，返回给调用方的是切片；注释明确说有效区间之外的元素“不清理”（not cleaned）。

// Allocate output: compressed logits only, the entries beyond a row's valid span are not cleaned
DG_HOST_ASSERT(max_seqlen_k > 0);
const int block_q = get_mqa_logits_block_q(num_heads);
const int block_kv = arch_major == 10 ? kMQALogitsSplitKV : 256;
const int aligned_seq_len = align(seq_len, block_q);
// Logits row stride must be 1024-byte aligned
const int stride_logits_alignment = 1024 / static_cast<int>(c10::elementSize(out_dtype));
const int stride_logits = align(align(max_seqlen_k, block_kv), stride_logits_alignment);
auto logits = torch::empty({aligned_seq_len, stride_logits}, q_fp.options().dtype(out_dtype));
logits = logits.index({torch::indexing::Slice(0, seq_len), torch::indexing::Slice(0, max_seqlen_k)});

源码：csrc/apis/attention.hpp 第 108–117 行（节选）

所以 \([S, L]\) 里 \(c \ge ke_i - ks_i\) 的格子内容未定义，调用方要按 \(ke_i - ks_i\) 自己掩掉。测试也是这么做的：它先用 ke - ks 构造掩码，再把压缩结果按 tmp[i, ks[i]:ke[i]] = logits[i, :ke[i]-ks[i]] 展开回稠密形状，和参考实现比较（test_attention.py 第 171–189 行）。写入时，SM100 内核把每行的输出基址预先减去 \(ks_i\)（output_bases[i] = logits + 行偏移 - seq_k_start[i]），这样同一个 KV 下标可以直接当列偏移用（第 454–458 行）。

\(ks_i, ke_i\) 不必是“从 0 到当前位置”的因果前缀。测试里有一个上下文并行（context parallel）的例子：一个 rank 持有序列的两个不相邻分片，前一半行和后一半行的 \(ke_i\) 落在差得很远的位置上（第 106–121 行）。只要每行给出一个区间，内核就能处理。

非 MX 缩放可以最后再乘，MX 缩放必须进张量核

当前提交里，缩放方式和架构是绑定的：SM90 走非 MX 路径，SM100 走 MX 路径。两者共用的检查函数把这一点写成了断言：

const bool is_fp4 = q_fp.scalar_type() == kPackedFP4;
const bool is_mx_sf = q_sf.has_value();
DG_HOST_ASSERT(not is_fp4 or is_mx_sf);
// ...
// Check SF Q (SM100 uses MX scale factors, SM90 per-token float KV scales)
DG_HOST_ASSERT(is_mx_sf == (arch_major == 10));
if (is_mx_sf) {
    DG_HOST_ASSERT(q_sf->sizes() == q_fp.sizes().slice(0, q_fp.dim() - 1));
    DG_HOST_ASSERT(q_sf->is_contiguous());
    DG_HOST_ASSERT(q_sf->scalar_type() == torch::kInt32);
}
// ...
DG_HOST_ASSERT(weights.stride(1) == 1 and (weights.stride(0) * weights.element_size()) % 16 == 0);
DG_HOST_ASSERT(weights.scalar_type() == (arch_major == 10 ? torch::kBFloat16 : torch::kFloat32));

源码：csrc/apis/attention.hpp 第 18–44 行（节选）

第一条断言说 FP4 一定带 MX 缩放；第二条说“有 Q 缩放”当且仅当架构是 SM100。Q 缩放的形状是 Q 去掉最后一维，即每个 (token, 头) 一个 int32。表 2 汇总了两条路径的数据类型。

SM90：缩放能提到求和外面

SM90 上 Q 直接是 FP8（测试里就是 q.to(torch.float8_e4m3fn)，没有缩放），KV 每个 token 带一个正的 FP32 缩放 \(s_j\)（由 amax / 448 得到）。因为 ReLU 是正齐次的，即对 \(s > 0\) 有 \(\mathrm{ReLU}(s x) = s\,\mathrm{ReLU}(x)\)，所以

\[ \begin{aligned} &\sum_{h} w_{i,h}\,\mathrm{ReLU}\!\left(q_{i,h}\cdot s_j k_j\right) \\ &\quad = s_j \sum_{h} w_{i,h}\,\mathrm{ReLU}\!\left(q_{i,h}\cdot k_j\right). \end{aligned} \](2)

内核正是按式 (2) 右边算的：WGMMA 直接用 FP8 的 \(q\) 和 \(k\) 得到 FP32 点积，尾声里先对头做加权 ReLU 求和，最后才乘上这个 KV token 的缩放：

const auto transform = [&](const uint32_t& j) {
    return fmaxf(shifted_accum[j], 0) * weights[i][(j / 4) * 2 + (j & 1)];
};

// Intra-thread reduction
float sum[4] = {transform(0), transform(1), transform(2), transform(3)};
#pragma unroll
for (uint32_t j = 1; j < kNumHeads / 8; ++ j) {
    #pragma unroll
    for (uint32_t k = 0; k < 4; k ++)
        sum[k] += transform(j * 4 + k);
}
float v_0 = (sum[0] + sum[1]) * scale_kv_0;
float v_1 = (sum[2] + sum[3]) * scale_kv_1;

源码：deep_gemm/include/deep_gemm/impls/sm90_fp8_mqa_logits.cuh 第 279–311 行（节选）

每个线程持有两个 KV token（v_0、v_1）的部分和，再用两次 __shfl_xor_sync 在 4 个线程间归约。整个过程是 FP32，输出也是 FP32。同一性质也说明，如果调用方想给 Q 一个每 token 的正缩放，可以把它折进 \(w_{i,h}\)；这只是数学上的推论，仓库里没有展示调用方怎么做。

SM100：每 32 维一个缩放，提不出来

MX 格式（这里指 MXFP4/MXFP8）给每 32 个连续元素一个 UE8M0 缩放，即一个只有指数的 8 位数，值为 \(2^{e}\)；格式细节见 第 3 篇。设 \(g\) 是维度分组，\(a_g\)、\(b_g\) 是查询和键在第 \(g\) 组的指数，点积变成

\[ \hat q\cdot\hat k \;=\; \sum_{g=0}^{D/32-1} 2^{\,a_g + b_g} \sum_{d \in g} q_d\, k_d . \](3)

每组的系数不同，无法像式 (2) 那样整体提出，反量化只能发生在点积内部。SM100 的块缩放 MMA 正好提供这个能力：缩放因子先由 UTCCP 拷进 TMEM，MMA 指令读数据的同时按组乘上缩放（UTCCP 的细节见第 2 篇）。打包方式由测试里的量化函数确定：每 token（或每 (token, 头)）的 \(D/32\) 个缩放字节拼成一个 int32，\(D = 128\) 时正好 4 个；\(D = 64\) 或 \(32\) 时不足 4 个，用 \(2^0\) 补齐，注释说这些补位“内核不会读”（utils/math.py 第 115–124 行）。

FP4 与 FP8 在 SM100 上共用一个内核模板，差别由类型参数 qk_dtype_t 推出：

using mma_op_t = cute::conditional_t<kIsFP4, ptx::SM100_MMA_MXF4_SS, ptx::SM100_MMA_MXF8F6F4_SS>;
// ...
constexpr uint32_t kPackFactor = get_smem_pack_factor<qk_dtype_t>();
constexpr uint32_t kQKSwizzleMode = kHeadDim / kPackFactor;
constexpr uint32_t kNumUMMAK = kHeadDim / UMMA_K;
// Advance descriptor low words by each stage's fixed offset
const auto instr_desc = cute::UMMA::make_instr_desc_block_scaled<
    qk_dtype_t, qk_dtype_t, float, cutlass::float_ue8m0_t,
    UMMA_M, UMMA_N, cute::UMMA::Major::K, cute::UMMA::Major::K>();
// ...
uint64_t runtime_instr_descs[kNumUMMAK];
#pragma unroll
for (uint32_t k = 0; k < kNumUMMAK; ++ k)
    runtime_instr_descs[k] = mma::sm100::make_runtime_instr_desc_with_sf_id(instr_desc, k * kPackFactor, k * kPackFactor);

源码：deep_gemm/include/deep_gemm/impls/sm100_mqa_logits.cuh 第 372–389 行（节选）

FP4 选 kind::mxf4 的 MMA，每条 MMA 吃 \(K = 64\) 个元素；FP8 选 kind::mxf8f6f4，每条吃 32 个（同一函数第 92 行的 UMMA_K）。make_runtime_instr_desc_with_sf_id 在第 \(k\) 条 MMA 的指令描述符里填缩放 id \(k \cdot \text{kPackFactor}\)，FP4 的打包因子是 2、FP8 是 1。按测试的打包顺序（字节 \(g\) 管第 \(g\) 组 32 维），这正好让每条 MMA 用上它覆盖的那几组缩放字节。主机侧的 MQALogitsConfig 还按 FP4/FP8 选了不同的流水深度：Q 2 级或 3 级、KV 8 级或 3 级（sm100_mqa_logits.hpp 第 128–139 行）。

两条路径的精度也不同。SM90 的求和和输出都是 FP32；SM100 在 BF16 里累加各头，输出 BF16。测试对两种格式用了不同的误差阈值（第 74–75 行），这里不对它们的精度差做任何量化判断。

分页版：一页先放全部数据，再放全部缩放

解码时 KV 在分页缓存里。分页接口的主要输入是：查询 q，形状 [batch, next_n, H, D]；融合了数据和缩放的 kv_cache，uint8，形状 [num_blocks, block_kv, 1, D′+4]；每行的上下文长度 context_lens，形状 [batch, next_n]（目前只支持二维）；块表 block_table，第 \(r\) 行列出第 \(r\) 个序列依次用到的物理页号；还有预先算好的 schedule_meta。缓存只有一个 KV 头（断言 num_heads_kv == 1），这就是“MQA”的那一个 K 头。

两种架构对“行”的理解不同。SM90 固定 next_n 为 1 或 2，每个序列的 next_n 个查询 token 共用一行块表，页大小只能是 64。SM100 要求 next_n = 1，改用 indices 把扁平的查询行归到请求：相邻且 indices 相同的行属于同一个请求，每行有自己的上下文长度，页大小可以是 32、64 或 128（attention.hpp 第 199–240 行）。举一个具体例子：假设一个 batch 有 3 个请求，请求 0 只有 1 个新 token，请求 1 有 3 个，请求 2 有 2 个，那么扁平的查询张量有 6 行，indices = [0, 1, 1, 1, 2, 2]，context_lens = [500, 800, 800, 800, 300, 300]（同一请求内各行的上下文长度相同）。调度器看到 indices 从 1 变到 2 时知道请求 1 结束了。测试里同一请求的几个 token 看到逐个增长的前缀，最后一个看到全长；调度器也依赖这一点，用请求最后一个 token 的长度代表整个请求（sm100_paged_mqa_logits.cuh 第 29–39 行）。

分页稀疏内核的访问器给出了第三份独立证据。它按物理块号算出页基址，数据指针是“页基址 + 页内 token 序号 × \(D'\)”，缩放指针是“页基址 + PAGE_KV × \(D'\) + 页内 token 序号 × 4”：

图 3 画出了这一布局。以 64 token 一页、\(D = 128\) 为例：MXFP4 每 token 数据 64 字节，一页是 \(64 \times 64 + 64 \times 4 = 4352\) 字节；FP8 或 MXFP8 每 token 128 字节，一页是 \(8192 + 256 = 8448\) 字节。两者都等于 block_kv × (D′+4)，所以形状上的 “+4” 记的是总账。

为什么这样排？代码没有给理由。一个合理的推测是：数据部分对 TMA 来说就是一个规整的 [block_kv, D′] 二维块，缩放部分是一段连续的 block_kv 个 4 字节，各用一次 TMA 就能取完。SM100 的分页内核正是用三维 TMA 描述符（维度为 \(D'\)、页内 token、页号）取数据，用二维描述符取缩放，并在能凑够 4 页时用 tma_gather4 一次取 4 页的缩放。tma_gather4 是 SM100 新增的 TMA 指令变体：普通 TMA 一次取一个连续块，gather4 一次给出 4 个不同的坐标（这里是 4 个物理页号），硬件在一条指令里把 4 份缩放数据收集到共享内存的连续区域。前提是 4 个页的缩放布局在页内偏移上完全一致（分页缓存的缩放区域正好满足这一点），且描述符的维度配置允许 gather 模式。当不足 4 页时退回逐页的普通 TMA（sm100_mqa_logits.cuh 第 183–221 行）。主机侧还要求页间距是 4 的倍数，否则缩放视图的行跨度不是整数个元素（kv_cache_stride_bytes % sf_bytes == 0）。

分页版的输出是 [batch·next_n, max_context_len]，列号就是请求内的绝对 KV 位置，因为每行的区间都从 0 开始。底层行跨度按 split 和 1024 字节对齐（第 257–264 行）。SM100 内核只写 \([0, \text{context\_len})\) 内的列；SM90 分页内核对它处理到的整页无条件写出，源码注释自己也写着 “we have redundant writes here”（第 325–328 行）。因此调用方应按 context_lens 掩掉多余的列，测试对两种架构都是这样比较的。

元数据内核把不等长的工作切给各个 SM

四种形态都启动“每个 SM 一个 CTA”的持久化内核（grid 维度是 SM 数），所以要回答同一个问题：每个 SM 从哪里开始、做多少。答案由一个独立的元数据内核在打分之前算好，写进一块整数缓冲。不同形态的调度粒度和代价模型不同，下面分三种看；稀疏版的元数据放到下一节。

连续版（SM100）：带启动代价的前缀和切分

连续版的元数据是可选的。不传时，SM \(s\) 依次处理第 \(s, s+N_{\text{SM}}, s+2N_{\text{SM}}, \dots\) 个 Q 分块（grid-stride，第 240–268 行）；SM90 的连续版也是这样轮转（第 119–124 行）。SM90 连续版内部每个 CTA 有一个数学 warpgroup 和一个 TMA warp：TMA warp 用 cp.async.bulk 把 Q 和 KV 搬进共享内存，数学 warpgroup 做 WGMMA；只有一个缩放因子（每 token FP32），所以缩放可以留到求和之后再乘，不需要 SM100 那样的分组处理（第 80–118 行）。每个 Q 分块要扫的 KV 范围是它所有行区间的并：起点取最小的 \(ks\) 并向下对齐到 4，终点取最大的 \(ke\)，再按 384 token 切成若干 split（第 37–54 行）。

如果各 Q 分块的 split 数差不多，但分块数只比 SM 数多一点，轮转就会让一部分 SM 多做一整块。get_mqa_logits_metadata 改为按代价切分。它给每个 Q 分块记代价“每个 split 2 个单位，非空分块另加 3 个单位的启动代价”，主机代码的注释解释了这个比例：启动一个 Q 分块大约相当于 1.5 个 split（sm100_mqa_logits.hpp 第 11–17 行）。然后在一个 256 线程的 CTA 里对代价做前缀和，把总代价等分成 \(N_{\text{SM}}\) 份，用二分查找把每个切点落到“第几个 Q 分块的第几个 split”上：

分页版（SM100）：以请求为单位，按 split 和查询数估代价

分页版的元数据是必需的，SM100 上它返回 [N_SM + 1, 2] 的起点表：第 \(s\) 项是 SM \(s\) 的起点（请求第一个查询 token 的行号、KV split 号），第 \(s+1\) 项就是它的终点。元数据内核先成对扫描 indices，找出每个请求的起止行（所以主机断言 indices 指针 8 字节对齐），再给每个请求算代价：

代价等于 split 数乘以“每个 split 的代价”，后者有两项：KV 搬运和 MMA 随 Q 分块数增长（2 · BLOCK_Q · ⌈n/BLOCK_Q⌉），尾声随有效 token 数增长（\(n\)）。元数据内核里 BLOCK_Q 固定为 4，注释写着“为 H32 调过，其他头数的调度可能略欠均衡”（sm100_mqa_logits.hpp 第 31–32 行）。如果代价超出 32 位，内核会退回只按“split 数 × token 数”估算（第 114–141 行）。之后同样是等分总代价、二分找切点，只是切点只能落在“某个请求的某个 split”上。

打分内核按“请求 → 最多 8 个 split 组成的块段（chunk）→ 请求内的各个 Q 分块”的顺序取任务（第 220–251 行）。同一请求的多个 Q 分块连续处理同一段 KV，第二个及以后的任务标记 kv_shared_with_prev；如果这一段的 split 数正好等于 KV 流水的级数，生产者就直接复用环形缓冲里已有的 KV，不再重新加载（sm100_mqa_logits.cuh 第 150–153 行）。FP4 的 KV 流水是 8 级，等于块段长度；FP8 是 3 级，只有恰好 3 个 split 的块段才能复用。

分页版（SM90）：只数 split

SM90 的分页元数据由一个 warp 完成：每个序列的工作量是 \(\lceil \text{context\_len}/256 \rceil\) 个 split（用该序列最后一个查询 token 的长度），做前缀和后把总 split 数平均分给各 SM，余数分给最后几个 SM（sm90_paged_mqa_logits.cuh 第 47–126 行）。它不区分启动代价和尾声代价。打分内核里每个 split 是 4 个 64 token 的页，由 4 个数学 warpgroup 和 4 个各自配对的 TMA warp 分头处理（sm90_fp8_paged_mqa_logits.cuh 第 92–106 行）。

稀疏版：只给选中的小块打分，两个查询共享一次搬运

“稀疏”指什么

稀疏版的“稀疏”在 KV 一侧：每个查询 token 额外给一行块下标 sparse_kv_block_indices，形状 \([S, n]\)，每个下标指一个 \(B = 8\) 或 16 个 token 的小块，内核只给这些块里的 token 打分。主机代码的注释规定了这行下标的含义：

// Each sparse-index row starts with the valid blocks inferred from its KV length. This prefix must
// contain unique, strictly increasing absolute block indices within the corresponding KV range.
// With unaligned ks, block i starts at i * sparse_block_kv + ks % sparse_block_kv.

源码：csrc/apis/attention.hpp 第 303–305 行（节选）

也就是说，每行有效的块数不是单独传入的，而是由这一行的 KV 长度推出来：\(\min\!\big(n,\ \lceil (ke_i - ks_i)/B \rceil\big)\)（元数据内核第 222–229 行）。这一前缀必须严格递增且不重复。若 \(ks_i\) 不是 \(B\) 的倍数，可以打开 use_unaligned_ks，此时第 \(m\) 块从 \(m \cdot B + (ks_i \bmod B)\) 开始。分页稀疏版里没有 \(ks\)，块下标就是请求内的逻辑块号，再经块表换成物理页。

输出形状是 \([S,\ n \cdot B]\)：第 \(s\) 个槽位（下标行里的第 \(s\) 项）对应的 \(B\) 个 token 写到第 \(s\cdot B\) 到 \(s\cdot B + B - 1\) 列。这也是一种压缩布局，只是列按“选中的块”排而不是按区间排。测试把稀疏版的结果和完整连续版在同一组 token 上的结果对比，要求逐位相等（test_attention.py 第 653–669 行）。

上游如何产生这些块下标，不在本仓库中。从接口看，它适合在已经缩小的候选块集合上再打一次分；这是我们对用途的推测。

两个查询一组：合并块列表

稀疏内核的 Q 分块固定是 2 个 token（kBlockQ = 2），头数最多 32、头维度只能是 128（layout/sparse_mqa_logits.cuh 第 11–17 行）。相邻两个查询选中的块往往重叠，元数据内核于是把两行下标做一次有序归并：256 个线程用 merge-path 做并行归并——每个线程在两列已排序的块下标上二分搜索，找到自己负责的起点（merge-path 的核心思想：线程 \(t\) 要找使 \(A[i] + B[j] = t \cdot \text{work\_per\_thread}\) 的对角线交叉点），然后从该点开始顺序归并自己的那一段；相同的块只保留一次，每个合并后的块记下它在两个查询中各自的槽位，不属于某个查询时记 0xFFFF（第 273–325 行）。合并结果按每个 split 能装的块数打包：MXFP4 的 split 是 640 个 token、MXFP8 是 512 个（sm100_sparse_mqa_logits.hpp 第 15–18 行），即每个 split 装 80 或 64 个 8-token 块、40 或 32 个 16-token 块。图 5 用一个缩小的例子演示这个过程。

元数据里每个 split 有一个头部（Q 分块起始行、块数、两个查询的槽位基址）和每块一个 KVBlockInfo（物理块号、两个 16 位槽位偏移）。打分内核的尾声用它们把结果写回：

尾声的其余部分和连续版一样：ReLU 转 BF16、乘 BF16 权重、对头求和（同一文件第 600–626 行）。MMA 的 N 维是 \(2H\)，M 维仍是每个数学 warpgroup 128 个 KV token。

搬运：能用 TMA 就用 TMA，否则逐块收集

合并后的块一般不连续，所以 KV 默认由若干个拷贝 warp 用 16 字节的 cp.async 逐块收集，并在写入共享内存时自己做 swizzle。元数据内核会检查每个 split：如果它装满了、并且块号首尾相接（连续版、对齐 \(ks\) 时），就打上 kContiguousFlag，打分内核改由一个线程发一次 TMA 取整个 split（第 436–458 行）。最后一个块越过 KV 末尾时打 kPartialTailFlag，走带零填充的拷贝路径。分页稀疏版通过前面那个访问器取页，只走逐块收集。

调度与工作区

稀疏元数据由多个 CTA 并行构建（最多 \(4N_{\text{SM}}\) 个），每个 CTA 处理若干 Q 分块，用全局原子计数器为自己的 split 预留位置；最后一个完成的 CTA 负责排程（第 443–472 行）。连续版把全部 split 平均分给各 SM，在 Q 分块边界处再切开；分页版把每个 Q 分块拆成不超过 8 个 split 的条目，按 \(N_{\text{SM}}\) 一波排成若干波，每波内按条目大小排序后错位轮换（第 37–161 行）。排程表按 [波][SM] 存放，头部记下生成时的 SM 数，打分内核会断言它与当前 SM 数一致。

元数据内核需要一块按 CUDA 流缓存的工作区，存放计数器和每个 Q 分块的 split 范围。它在第一次使用时清零，此后由最后一个 CTA 负责复位。主机代码要求这一次清零不能发生在 CUDA graph 捕获期间，否则清零会被录进图里重放（第 284–301 行），所以要在捕获前先在该流上调用一次。

提交 1fc9c66：页间距对齐从 512 字节放宽到 128 字节

提交 1fc9c66（“Update FP8 epilogues and paged sparse MQA alignment”，#471）的说明里有一句 “accept 128-byte paged sparse KV strides”。对应的改动只有三处：主机断言和设备断言里的 stride(0) % 512 改成 % 128，测试里的页间距从按 512 字节向上取整改为按 128 字节。当前版本的断言见 attention.hpp 第 426–433 行。按图 3 的公式算，64 token 一页、\(D = 128\) 时，MXFP4 的紧凑页长是 4352 字节，MXFP8 是 8448 字节；两者都是 128 的倍数，但都不是 512 的倍数。按旧断言，紧凑排布的缓存会被拒绝，页必须补到 4608 或 8704 字节；改动之后可以不补。这些字节数由 plots/common.py 计算。

局限与未覆盖

  • 没有性能数据。本地没有 GPU，所有内核都没有运行过。测试脚本会打印 TFLOPS、带宽等，但本文没有、也不会引用任何这类数字。README 的这一节也没有给出性能数字。
  • 调度复现只是代码层面的。plots/common.py 是对调度器源码的逐行 Python 改写，只在“各 SM 的 split 总数守恒”上做了自检，没有和 GPU 上真实生成的元数据逐字节对比。图 4 的纵轴是内核自己的代价模型，不是耗时；32 个 SM 是假设值，例子是为展示轮转的尾部不均而挑选的。
  • 推断与事实。“KV 作 M 维是为了让按头求和留在线程内”、“分页布局是为了让数据和缩放各用一次 TMA”、“稀疏版适合在候选块上再打分”这三条是我们从代码推出的解释，代码和文档没有说明设计动机。
  • 仓库之外的部分。按分数挑选 token、由谁产生稀疏块下标、DeepSeek 推理系统如何组合这几个 API，都不在本仓库中。DSA 的整体设计以 DeepSeek-V3.2 报告为准 [1]，本文只讨论 DeepGEMM 里的打分内核。
  • 文档与代码的差异。README 只描述了非分页和分页两种形态，其伪代码 kv[0][j, :] * kv[1][j] 只对 SM90 的 FP32 缩放字面成立；MX 路径的缩放是打包的 int32，要按式 (3) 理解。本文以代码为准。
  • 没展开的细节。寄存器重配置、PDL（cudaGridDependencySynchronize）、TMEM 列分配、UTCCP 之前的共享内存转置、稀疏内核各 warp 的完整分工、SM90 分页内核中已被 static_assert 禁掉的 varlen 分支等，本文都没有讲。SM100 上 BF16 累加对分数精度的影响也没有量化。

小结

Lightning Indexer 的打分在 DeepGEMM 里归结为一个内核骨架。KV token 作 MMA 的 M 维，128 个 (token, 头) 作 N 维，尾声里逐行做 ReLU、乘权重、对头求和，结果按 \(j - ks_i\) 写进压缩行。缩放方式随架构切换：SM90 的每 token FP32 缩放可以留到求和之后再乘，SM100 的每 32 维 UE8M0 缩放交给块缩放 MMA。四种形态的差别在三处：KV 从连续张量、分页缓存还是选中的小块里取；结果写到区间列、绝对位置列还是槽位列；以及元数据内核按什么代价把不等长的工作切给各 SM。分页缓存的“\(D'+4\)”是一页内“全部数据 + 全部缩放”的总账，这一点由主机代码、测试和稀疏访问器三处互相印证。
