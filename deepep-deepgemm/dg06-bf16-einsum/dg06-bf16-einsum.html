没有 scale 的那一半：BF16、批量收缩、
einsum 与 cuBLASLt 兜底

把缩放因子拿掉，GEMM 内核就只剩一个累加器。DeepGEMM 用这条简化路线撑起 BF16 GEMM、两种完全不同的“批量”、四条硬编码的 einsum 表达式，以及一个在 JIT 时拼进模板的 epilogue 体系——而最常见的 BF16 矩阵乘，默认先问 cuBLASLt。

TL;DR

  • BF16 内核和 FP8 内核的骨架一样，差别是没有缩放因子的 TMA、也没有 promotion：WGMMA 的累加器一路累加到 K 末尾。
  • 少了 scale，反而多了两样能力：A/B 可以是 MN-major，C/D 可以是 FP32 并支持累加。
  • DeepGEMM 里有两种“批量”：batch 当第三个坐标（3D TMA），和 batch 当被收缩的维度（split-K 加原子累加）。
  • einsum 只认四条硬编码表达式，每条的实现都是把张量 permute 成 (batch, M, N, K) 再调已有内核。
  • 普通 BF16 GEMM 的默认路径是 cuBLASLt；只有开了确定性模式、调小过 SM 数，或要用自定义 epilogue，才落到自己的内核。
  • epilogue 是设备端的一个模板类；host 侧的 EpilogueClass 只交出三样东西：类型名、内核实参、编译选项。

前置知识

了解 dg01 的 SM90 GEMM 流水线骨架。本篇新引入：BF16 去 scale 后的 stage 合并、split-K 原子累加、einsum 四条硬编码表达式、cuBLASLt 回退策略、epilogue 模板类。

前五篇讲的都是带缩放因子的内核：FP8、FP4、UE8M0 的打包与转置、分组 GEMM 的 PSUM 布局。这一篇讲剩下的那一半——不带 scale 的部分。它们在仓库里占的篇幅不小：两个架构各一个 BF16 GEMM、两个批量收缩内核、一个只认四条表达式的 einsum、一整套 cuBLASLt 封装，以及一个被所有 SM100 内核共用的 epilogue 体系。

本篇不重复讲 SM90 的流水线骨架（warp 特化、full/empty mbarrier、TMA 多播、两级累加），见第 1 篇；也不重复 SM100 的 tcgen05/UMMA 与张量内存（TMEM），见第 2 篇。

把这些放在一起讲是有理由的：它们回答同一个问题——当“缩放”这件事从内核里消失后，剩下的结构长什么样，以及 DeepGEMM 在什么情况下干脆不自己算。符号沿用全系列：\( D = C + A B^\top \)，M、N、K 是 GEMM 的三个维度，BK 是 K 方向的块宽。

去掉 scale，内核就少了一级累加

第 1 篇里 SM90 的 FP8 内核有两组累加寄存器：accum 只装一个 128 宽的 K 块，每块算完乘上两个 scale 加进 final_accum。BF16 不需要 scale，于是 final_accum 整个消失了：

float accum[WGMMA::kNumAccum * (BLOCK_M / WAVE_BLOCK_M)] = {0};
// ...
for (uint32_t local_idx = 0; local_idx < BLOCK_M / WAVE_BLOCK_M; ++ local_idx) {
    auto shifted_accum = accum + WGMMA::kNumAccum * local_idx;
    for (uint32_t k = 0; k < BLOCK_K / WGMMA::K; ++ k) {
        // ...
        WGMMA::wgmma(a_desc, b_desc, shifted_accum, 1);

源码：sm90_bf16_gemm.cuh 第 230–271 行（节选）。

注意最后那个实参 1：它是 WGMMA 的 scale_d，为真时指令用 ScaleOut::One，即累加进累加器。FP8 内核传的是 K 方向的循环变量（第 0 条 WGMMA 清零），BF16 内核恒传 1，所以同一组寄存器从第一个 K 块累加到最后一个。图 1 把两条路径并排画出来。

少一级累加换来的是寄存器和指令数。但更有意思的是 BF16 内核多出来的两样能力，它们都是 FP8 路径做不到的。

第一，A 和 B 的主序（major-ness）可以不是 K-major。FP8 内核在 host 侧就断言 major_a == Major::K and major_b == Major::K，而 BF16 内核把两个主序做成了模板参数 kMajorA、kMajorB：TMA 的两个坐标按它们对调（sm90_bf16_gemm.cuh 第 188–199 行），WGMMA 的共享内存描述符也按它们生成（第 219–222 行）。这就是 README 说 SM90 只支持 NT 布局、SM100 支持四种布局时没说清的一层：在 SM90 上，BF16 内核本身是支持 MN-major 操作数的，只是 FP8 路径不支持 [1]。K 分组的 BF16 内核甚至要求两边都是 MN-major（sm90_bf16_gemm.hpp 第 272 行）。

第二，C/D 可以是 FP32，而且支持累加。内核静态断言 cd_dtype_t 是 float 或 bfloat16_t，再按 kWithAccumulation 在编译期选 TMA 指令：

using cute_tma_t = cute::conditional_t<kWithAccumulation,
                                       cute::SM90_TMA_REDUCE_ADD_2D, cute::SM90_TMA_STORE_2D>;
cute_tma_t::copy(&tensor_map_cd, smem_ptr,
                 n_block_idx * BLOCK_N + in_block_n_offset, m_idx);

源码：sm90_bf16_gemm.cuh 第 380–385 行（节选）。

BF16 输出走 STSM 写共享内存，FP32 输出走 st.shared 写 float2——和 FP8 的两个变体是同一套取舍。另外这个内核还藏了一个小优化：当启发式给出的 stage 数 ≥ 10、且是 NT 的普通 GEMM、且只有一个数学 warpgroup 时，它把若干个 stage 合并成一个更大的 BLOCK_K，注释说是为了摊薄 warpgroup_wait<0>() 的开销（sm90_bf16_gemm.cuh 第 45–56 行）。阈值 10 大概来自经验：stage 越多说明每 stage 的 SMEM 越小、BK 越窄，此时 WGMMA 的发射/等待开销占比上升；合并两三个 stage 成一个更宽的 BK 后，一次 WGMMA 处理更多 K 元素，等待点减半到三分之一，但 stage 数也相应减半——合并后仍保证至少 5 个 stage，确保流水线深度足以隐藏 TMA 延迟。

SM100 的 BF16 内核是另一份代码（sm100_bf16_gemm.cuh），结构按第 2 篇讲的 tcgen05 路线：UMMA 指令、TMEM 累加器、可选的 swap-AB 尾声。它和 SM90 版本的接口差别只有一个——多一个 epilogue 类的模板参数，这是本篇最后一节的内容。两个架构的 host 包装都在 bf16_gemm_nt 里按 arch_major 分派（gemm.hpp 第 525–534 行），SM90 那一支还要额外断言“alpha 和自定义 epilogue 需要 SM100”。

两种批量：第三个坐标，和被收缩的维度

“批量 GEMM”在 DeepGEMM 里指两件完全不同的事，分清它们比记住函数名重要。

第一种：batch 是第三个坐标。GemmType::Batched 走的还是普通 GEMM 内核，只是 TMA 描述符从 2D 变成 3D，batch 下标由调度器的 current_group_idx 提供，每个 batch 独立算一个 \( [M,N] \) 输出。FP8 侧是 sm90_fp8_bmm（复用 1d2d 内核，sm90_fp8_gemm_1d2d.hpp 第 283–352 行），BF16 侧是 sm90_bf16_bhr_hdr_bhd 这类 einsum 专用包装。它们的共同点是 batch 维不参与收缩。

第二种：batch 是被收缩的维度。表达式 bmk,bnk->mn 要算 \( D_{mn} = \sum_{s}\sum_{k} A_{smk} B_{snk} \)，batch 维 s 和 k 一样要被求和掉。于是 \( s \times K \) 个元素构成一条很长的收缩链，一个 CTA 算不完也不该独占，代码把它切成 split-K：

const int num_sms = runtime->get_num_sms();
const int num_mn_blocks = ceil_div(m, block_m) * ceil_div(n, block_n);
const int num_sk_blocks = s * (k / block_k);
const int split_factor = ceil_div(num_sk_blocks, std::max(num_sms / num_mn_blocks, 1));

源码：sm90_bmk_bnk_mn.hpp 第 32–35 行。

先算输出被切成多少个 MN 块，再看每个 MN 块能分到几个 SM，然后把 \( s \cdot K/\mathrm{BK} \) 个“切片块”均分给它们；grid 大小就是 MN 块数乘以 \( \lceil \text{切片块数} / \text{split\_factor} \rceil \)。代入一组测试里的形状（tests/test_einsum.py 用 \( s = 4096 \)、\( M = 128 \)、\( N = 384 \)、\( K = 128 \)）：block 是 128×128×64，MN 块数为 \( 1 \times 3 = 3 \)，切片块数为 \( 4096 \times 2 = 8192 \)；若设备有 132 个 SM，每个 MN 块分到 44 个 SM，于是 split_factor = ⌈8192/44⌉ = 187，grid = \( 3 \times \lceil 8192/187 \rceil = 3 \times 44 = 132 \)。这是按公式手算的，没有在 GPU 上验证。

切片算完各自得到一份部分和，谁来合并？SM90 版本直接用 atomicAdd 把寄存器里的值加到全局内存的 FP32 输出上：

const auto row = m_block_idx * BLOCK_M + warp_idx * 16 + lane_idx / 4;
const auto col = n_block_idx * BLOCK_N + (lane_idx % 4) * 2;
for (uint32_t i = 0; i < WGMMA::kNumAccum / 4; ++ i) {
    if (col + i * 8 >= SHAPE_N)
        break;
    if (row < SHAPE_M) {
        atomicAdd(reinterpret_cast<float2*>(d + (row + 0) * SHAPE_N + col + i * 8),
                  make_float2(accum[i * 4 + 0], accum[i * 4 + 1]));
    }
    // ...
}

源码：sm90_bmk_bnk_mn.cuh 第 160–174 行（节选）。

SM100 版本做同一件事，但用的是 TMEM 加 SM90_TMA_REDUCE_ADD_2D：先把累加器从张量内存取回寄存器、经共享内存，再由 TMA 把整块加回去（sm100_bmk_bnk_mn.cuh 第 243–257 行）。两者都要求输出是 FP32，因为累加必须在 FP32 上做。图 2 画出这个结构。

这也解释了接口上的一个约束：这个表达式的输出若是 BF16，bmk_bnk_mn 会先申请一块 FP32 的 workspace、memset 清零、递归调用自己做累加，最后用 d.copy_(workspace) 隐式转成 BF16（einsum.hpp 第 25–39 行）。FP32 输出则必须把 C 指向 D 本身——因为内核是原子累加进去的，而不是写进去的。

einsum 只认四条表达式，每条都是一次坐标重排

DeepGEMM 的 einsum 不解析表达式，它只是比较字符串：

if (expr == "bmk,bnk->mn") {
    bmk_bnk_mn(a, b, d, c);
} else if (expr == "bhr,hdr->bhd") {
    bhr_hdr_bhd(a, b, d, c, epilogue_class);
} else if (expr == "bhd,hdr->bhr") {
    bhd_hdr_bhr(a, b, d, c, epilogue_class);
} else if (expr == "bhd,bhr->hdr") {
    bhd_bhr_hdr(a, b, d, c);
} else {
    DG_HOST_UNREACHABLE(std::format("Unsupported einsum expression: {}", expr));
}

源码：csrc/apis/einsum.hpp 第 166–178 行（节选，省略两行断言）。文件里标着 // TODO: support any expression。

四条表达式里，后三条都是同一种形状：b 是 token 维、h 是头数、d 和 r 是两个特征维。它们对应 HyperConnection 一类按头分组的小矩阵乘：bhr,hdr->bhd 是 MHA 的前向投影（每个头把 r 维特征映射到 d 维），bhd,hdr->bhr 是反向梯度，bhd,bhr->hdr 是对投影矩阵的权重梯度——b 是 token 被收缩掉的。FP8 版本 fp8_einsum 的实现就是把张量 permute 成 fp8_bmm 要的 (batch, M, N, K) 次序，再交给批量 GEMM——代码里每条都写了注释说明映射关系。表 1 把四条表达式的去向列齐。

最后一条 bhd,bhr->hdr 值得注意：它的 batch 维 b 同样是被收缩的（这是一个 wgrad 形状），输出是 FP32 且必须带累加。BF16 版本没有自有内核，直接调 cuBLASLt，代码旁边留着 // TODO: investigate cuBLAS determinism.（einsum.hpp 第 146–147 行）——也就是说，开了确定性模式也挡不住这条路径走 cuBLAS，这一点在仓库里是个已知的待办。

fp8_bmm 还有一个接口细节：它的 D 可以是一个普通张量，也可以是一个 (d, sfd) 对——后者是“输出直接量化成 FP8”的简写，等价于传一个不裁剪的 FP8CastWithClamp epilogue。这要求 d.stride(0) == n 且 n % 128 == 0，因为所有 batch 的 scale 列被拼成一个二维视图，一个打包的 4-scale 字不能跨 batch 边界（einsum.hpp 第 218–227 行）。

cuBLASLt 不是失败路径，而是 BF16 的默认路径

“兜底”这个词容易让人误解。看 bf16_gemm_nt 的分派顺序：

// Dispatch into different implements; cuBLASLt only covers a plain store, optionally alpha-scaled
if (not heuristics_runtime->get_deterministic_algorithms() and runtime->is_cublaslt_available()
    and epilogue_alpha.has_value()) {
    cublaslt_gemm(a, b, d, m, n, k, major_a, major_b, c.has_value(), epilogue_alpha.value());
    return;
}

源码：csrc/apis/gemm.hpp 第 518–523 行。

cuBLASLt 在前面。普通的 BF16 矩阵乘，只要三个条件都成立就交给 cuBLASLt，自有内核反而是例外路径。三个条件各有含义：

  • get_deterministic_algorithms()：用户调 deep_gemm.use_deterministic_algorithms(True) 时置位（heuristics/runtime.hpp 第 20–26 行）。开了就不走 cuBLASLt——因为 cuBLAS 可能选 split-K 之类的归约方案，逐位结果不保证可复现。测试里正是用这个开关来回切换两条路径做对比。
  • is_cublaslt_available()：它的定义是 get_num_sms() == jit->device.get_num_sms()（runtime.hpp 第 89–91 行）。也就是说，只要用户用 set_num_sms 把可用 SM 数调小过（为了和通信内核抢资源时常这么做），cuBLASLt 就被判定为“不可用”——DeepGEMM 自己的内核能按 SM 数开 grid，cuBLASLt 的 SM_COUNT_TARGET 不被当作同等可靠的限制手段。
  • epilogue_alpha.has_value()：epilogue 类的 get_alpha() 只在”这个 epilogue 就是一次普通写回、最多乘一个 alpha”时返回数值，其余情况返回 nullopt（见下一节）。FP8 量化输出、随机舍入这类 epilogue 因此自动排除 cuBLASLt。

图 3 把这条判定链画成流程图。注意默认状态下三问全否——确定性模式默认关、SM 数默认等于设备 SM 数、默认 epilogue 是 Identity——所以一次不带参数的 bf16_gemm_nt 调用走的确实是 cuBLASLt。

封装层本身只有一个文件，二百多行。调用序列是教科书式的 cuBLASLt 用法：cublasLtMatmulDescCreate 建描述子，SetAttribute 设 TRANSA/TRANSB/SCALE_TYPE、把 SM_COUNT_TARGET 设成 DeepGEMM 的 SM 数、FP8 操作数时显式关掉 FAST_ACCUM；cublasLtMatrixLayoutCreate 建三个布局（批量时再设 BATCH_COUNT 与 STRIDED_BATCH_OFFSET）；cublasLtMatmulPreferenceSetAttribute 限制 workspace 大小、并用 REDUCTION_SCHEME_MASK 只允许 NONE 与 COMPUTE_TYPE 两种归约；cublasLtMatmulAlgoGetHeuristic 取一个算法并断言确实取到了；最后 cublasLtMatmul。

最后这一步有个必须看懂的细节：cuBLASLt 用列主序，而 DeepGEMM 的 D 是行主序，于是两个操作数被换了位置——

// Call: D = alpha * (A @ B) + beta * C
const float beta = accumulate ? 1.0f : 0.0f;
DG_CUBLASLT_CHECK(cublasLtMatmul(handle,                                // Light handle
                                 desc,                                  // Operation description
                                 &alpha,                                // Alpha
                                 b.data_ptr(), layout_a,                // A
                                 a.data_ptr(), layout_b,                // B
                                 &beta,                                 // Beta
                                 d.data_ptr(), layout_d,                // C
                                 d.data_ptr(), layout_d,                // D
                                 &heuristic.algo,                       // Algorithm
                                 workspace.data_ptr(), workspace_bytes, // Workspace
                                 stream));                              // Stream

源码：smxx_cublaslt.hpp 第 93–105 行。

传给 cuBLASLt 的 A 是 DeepGEMM 的 B、传给它的 B 是 DeepGEMM 的 A，布局也相应交换——按列主序解读这次乘法，算出来的正是所求行主序结果的转置，也就是所求的结果本身。C 和 D 传同一个指针，beta 为 1 即实现累加。

workspace 固定 16 MiB，注释给了理由：超过 16 MiB 时 cuBLAS 在某些形状（例如 m = 128、n = 7168、k = 16384）上会选到更差的启发式。handle 默认自己创建而不用 PyTorch 的，因为 at::cuda::getCurrentCUDABlasLtHandle 在某些 PyTorch 版本上 CPU 开销大（两处注释见 runtime.hpp 第 24–51 行）。

除了兜底，这个文件还提供了三样 DeepGEMM 自己没有内核的运算：cublaslt_nvfp4_gemm（NVFP4 配方，16 元素一组的 UE4M3 scale，通过 A_SCALE_MODE/B_SCALE_POINTER 传入），以及 batched_syrk（\( D = A A^\top \)）和 batched_symm（A 按约定对称），两者都被实现成普通的 strided-batched GEMM（gemm.hpp 第 796–833 行）。

epilogue 是一个模板参数，JIT 时才拼进内核

前面反复出现的 epilogue_class 是什么？它是 DeepGEMM 让用户替换“尾声那一步”的机制：GEMM 算完后，在把结果写出去之前，可以对累加值做一次变换。SM100 的每个 GEMM 都带且只带一个 epilogue 类——头注释写明“它们不组合”（epilogue_class.hpp 第 18–20 行）。

host 侧的基类只有四个虚函数，每个都对应一件要交给 JIT 的东西：

    virtual std::string get_epilogue_operator_type() const = 0;
    virtual EpilogueOperatorArgs make_epilogue_operator_args(const int& m, const int& n) const { return {}; }
    virtual deep_jit::cuda::CompilerOptions compiler_options() const { return {}; }
    // ...
    virtual std::optional<float> get_alpha() const { return std::nullopt; }
    virtual std::optional<torch::Tensor> output_sfd() const { return std::nullopt; }
};

源码：epilogue_class.hpp 第 21–41 行（节选，省略 public:、析构函数与 check() 的函数体）。

第一个函数返回一个字符串，内容是设备端类型的名字，例如 "epilogue::operators::CastToFP8WithClamp"。这个字符串被直接格式化进 JIT 要编译的那段源码里：

三样东西各走各的路：类型名作为模板实参进入 __instantiate_kernel 里那串 sm100_bf16_gemm_impl<...>；compiler_options() 作为编译选项传给 JIT；make_epilogue_operator_args(m, n) 返回的结构体作为普通内核实参传给 launch。图 4 把这条路径画出来。

仓库现在提供四个 epilogue 类（apis/epilogue_class.hpp 第 13–31 行），每个都能看出这套接口的设计意图：

  • Identity：什么都不做，get_alpha() 返回 1.0——于是 cuBLASLt 可以接手。设备端它还兼任基类，提供默认的 BF16 转换钩子 cast_bf16。
  • Alpha：把累加值乘上一个常数，设备端是 ScaleByAlpha::apply_values，用 __fmul2_rn 成对处理。注释说明了为什么不支持任意 beta：那需要另一条加载 C 的路径，不属于这个“只改值”的算子（operators.cuh 第 36–51 行）。
  • FP8CastWithClamp：把输出量化成 E4M3 加 UE8M0 scale，可选裁剪，还能把被裁剪的元素个数异步写回一个标量张量。它的 check() 要求 D 必须是 float8_e4m3fn，output_sfd() 返回 SF 张量（空问题时用来清零）。注释特别说明：累加值先舍入成 BF16 再求 amax、算 scale、转 FP8，这样结果和“先出 BF16、再跑独立的 per-token cast 内核”逐位一致（operators.cuh 第 112–120 行）。
  • BF16StochasticRounding：随机舍入到 BF16。设备端用 PTX 的 cvt.rn.satfinite.rs.bf16.f32 指令——.rs 后缀表示 stochastic rounding，硬件为每个元素独立生成随机位决定向上还是向下舍入（per-element，非 per-block）。它是 compiler_options() 唯一的用户——cvt.rs 指令要求具体架构（如 sm_100a）而不是族架构，于是这个类把编译目标改掉（epilogue_class.hpp 第 122–126 行）。

最后，三种指定方式（epilogue 对象、裸 alpha 参数、FP8 的 (d, sfd) 输出对）是互斥的，由 resolve_epilogue_class 统一归一化：断言三者至多一个、没给就用 Identity、最后用 check() 核对 D 的类型（epilogue_class.hpp 第 137–153 行）。于是“alpha”和“输出 FP8”这两个看起来像普通参数的东西，在内部其实就是两个 epilogue 类。

局限与未覆盖

  • 零性能数字。本文不含任何实测或引用的性能数值。tests/test_bf16.py 和 tests/test_einsum.py 会打印 TFLOPS 与“相对 cuBLASLt 的倍数”，但那需要 GPU；本地无 GPU，不跑、也不猜。唯一的算术是 split-K 那段 split_factor 的手算，参数（132 个 SM）是假设值，不是实测。
  • cuBLASLt 内部不展开。它选了哪个算法、nvjet 内核长什么样、REDUCTION_SCHEME_MASK 具体排除了哪些实现，都在闭源库里。本文只讲 DeepGEMM 调了哪些 API、传了什么属性。测试里按内核名 nvjet 抓时间这一点可以旁证它确实落到了 cuBLAS 的内核上，但我们没有验证过。
  • SM100 的两条路线只讲接口。sm100_bf16_gemm.cuh 与 sm100_bmk_bnk_mn.cuh 的 UMMA/TMEM 细节、swap-AB 尾声的布局，属于第 2 篇；本文只对比了它们与 SM90 版本在接口和归约方式上的差别。
  • 推断与事实。“is_cublaslt_available 用 SM 数相等来判断，是因为不把 SM_COUNT_TARGET 当作同等可靠的限制手段”是我们的推测，仓库里只有那一行代码，没有注释说明理由。“MN-major 的 BF16 内核在 SM90 上可用”是从模板参数和 TMA 分支读出来的事实，但我们没有在 GPU 上跑过这些配置。
  • 没讲的部分：einsum 的 FP8 版本如何与 HyperConnection 对接（第 9 篇）、epilogue 在 SM100 尾声里具体被调用的位置（epilogue/sm100_store_cd.cuh 与 swap-AB 变体）、EpilogueOperatorArgs 的字段全集，以及 FP8CastWithClamp 里那套 CUDA graph 安全的计数器初始化（clamp_count_ready 用 grid id 做标记）。
