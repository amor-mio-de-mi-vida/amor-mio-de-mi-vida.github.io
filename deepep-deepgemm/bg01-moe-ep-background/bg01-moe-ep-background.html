TL;DR

  • MoE 把 Transformer 的稠密 FFN 拆成几百个专家，每个 token 只激活其中 \(k\) 个——参数量大，单 token 计算量不变。
  • 专家并行（EP）把专家分散到多块 GPU 上。一个 token 选中的 \(k\) 个专家可能分布在不同 GPU 上，因此需要两次全对全通信：dispatch 把 token 送到专家所在的 GPU，combine 把结果送回来。
  • DeepEP 负责 dispatch/combine 通信，DeepGEMM 负责专家计算（GEMM），两者合在一起覆盖 MoE 层从搬运到计算的完整路径。
  • 本篇和下一篇（GPU 硬件速查）是后续 17 篇精读的前置知识。

MoE：用稀疏换容量

标准 Transformer 的每一层有一个 FFN（Feed-Forward Network），所有 token 过同一组权重。MoE（Mixture of Experts）把这个 FFN 换成 \(E\) 个"专家"——每个专家是一个独立的小 FFN——再加一个门控网络（gate），为每个 token 选出 \(k\) 个最相关的专家。只有被选中的 \(k\) 个专家参与计算，其余 \(E - k\) 个不动。

这样做的好处直接：模型总参数量正比于 \(E\)（每个专家都有自己的权重矩阵），但每个 token 的计算量只正比于 \(k\)。当 \(E = 256\)、\(k = 8\) 时，参数量是单专家的 256 倍，计算量只有 8 倍——实际还不到 8 倍，因为门控和通信的开销远小于 FFN 本身。这就是"用稀疏换容量"的核心思想：模型可以很大，但推理和训练的 FLOPS 与一个小得多的稠密模型相当。

更具体地说，一个 MoE 层对 token \(x\) 的计算是：

\[ y = \sum_{i \in \text{top-}k} w_i \cdot \text{Expert}_i(x) \]

其中 \(w_i\) 是门控网络给第 \(i\) 个专家的权重（归一化后的概率），\(\text{Expert}_i\) 是第 \(i\) 个专家的 FFN。门控通常是一个线性层 \(x W_g\) 加 softmax（或 DeepSeek 用的 sqrtsoftplus + bias 排名），输出 \(E\) 个分数，取最大的 \(k\) 个。

专家并行：256 个专家装不进一块 GPU

问题出在参数量。以 DeepSeek-V3 为例：256 个路由专家，每个专家是一个两层 FFN（up projection + down projection），隐藏维 \(H = 7168\)，中间维 \(H_{\text{ffn}} = 2048\)。单个专家的权重量约 \(2 \times H \times H_{\text{ffn}} = 2 \times 7168 \times 2048 \approx 29\text{M}\) 参数；256 个合计 \(\sim\)7.5B 参数，BF16 下占 \(\sim\)15 GB。加上注意力层、KV cache 和激活值，单块 GPU 的 80 GB 显存装不下整个模型。

专家并行（Expert Parallelism, EP）的做法很直接：把 \(E\) 个专家均分到 \(R\) 块 GPU 上，每块 GPU 持有 \(E/R\) 个"本地专家"。8 块 GPU 时，每块持有 32 个专家的权重。

但这引入了一个通信问题。一个 token 选中的 \(k = 8\) 个专家可能分布在不同 GPU 上。GPU 0 上的 token \(x\) 选中了专家 5（在 GPU 0）、专家 37（在 GPU 1）和专家 200（在 GPU 6），那么 \(x\) 的副本必须被发送到 GPU 1 和 GPU 6，让它们各自用本地专家做计算，再把结果送回 GPU 0。这就是 MoE 层的通信核心：dispatch（发送 token 到专家所在的 GPU）和 combine（把计算结果送回 token 原来的 GPU）。

一次 MoE 前向的完整步骤

把以上串起来，一次 MoE 层前向传播的步骤是：

  1. 门控路由：对每个 token 做一次线性变换 + 打分，选出 top-\(k\) 个专家和对应的权重 \(w_i\)。
  2. dispatch：按路由结果，把每个 token 发送到它选中的专家所在的 GPU 上。一个 token 如果选了分布在 3 块 GPU 上的专家，它的数据就要被复制 3 份分别发出去。这是一个"多对多"（all-to-all）通信模式。
  3. 专家计算：每块 GPU 收到一批来自各处的 token，按专家分组后做 GEMM（矩阵乘法）。这一步是计算密集的——也是 DeepGEMM 覆盖的部分。
  4. combine：每块 GPU 把计算结果按原路送回 token 所在的 GPU，由原 GPU 按 \(w_i\) 做加权求和。combine 在数据流上恰好是 dispatch 的转置。

步骤 2 和 4 的通信量取决于两个因素：token 数 \(T\) 和隐藏维 \(H\)。每次 dispatch 搬运的数据量约为 \(T \times k \times H \times \text{dtype\_size}\)，训练时（BF16，\(T=4096, k=8, H=7168\)）单个 rank 发出约 470 MB，8 个 rank 合计 \(\sim\)3.7 GB——这在 NVLink（\(\sim\)900 GB/s 双向）上只要几毫秒，但在 RDMA（\(\sim\)50 GB/s）上就成了瓶颈。

这也是为什么需要一个专门的通信库：通信模式不是简单的 all-reduce 或 broadcast，而是一种按路由结果动态决定目标的 all-to-all。每个 token 的目标 GPU 在每一步都可能不同，通信量在各 GPU 间分布不均匀，需要精心调度才能充分利用互联带宽。

DeepSeek-V3 的 MoE 配置

本系列以 DeepSeek-V3（及 V3.2）的 MoE 层为背景。了解具体配置有助于理解后续各篇中的参数选择和设计权衡。

参数值含义
路由专家数 \(E\)256每层可选的专家总数
共享专家数 \(S\)2所有 token 都经过的固定专家
每 token 选中数 \(k\)8top-k 路由
隐藏维 \(H\)7168token 的表示维度
专家中间维 \(H_{\text{ffn}}\)2048单个专家 FFN 的中间宽度
EP 组大小 \(R\)8–64参与专家并行的 GPU 数
NVLink 域大小8一个节点内 GPU 数

"共享专家"是 DeepSeek 的设计：除了路由选出的 \(k\) 个专家外，每个 token 还固定经过 \(S\) 个共享专家。共享专家不参与路由决策，所有 token 都用它们——这相当于给每个 token 一个"保底"的容量，防止路由的稀疏性导致某些信息丢失。在通信上，共享专家不需要跨 GPU 搬运（每块 GPU 都持有共享专家的副本），所以它们不增加 dispatch/combine 的通信量。

另一个关键设计是冗余专家（redundant experts）：高频使用的路由专家被复制到多个 GPU 上，减少通信热点。gate 的物理映射表（to_physical_map）负责把逻辑专家编号映射到物理副本上，并通过散列分散负载。

DeepEP 与 DeepGEMM：各管一半

回到系列的两个主角：

DeepEP（通信）
负责 MoE 的 dispatch 和 combine。支持两条路径：所有 GPU 在同一 NVLink 域时走"直连模式"（一跳），跨域时走"混合模式"（RDMA + NVLink 两跳）。还提供基于复制引擎的集合通信（all-gather、reduce-scatter），用于非 MoE 的参数同步。
DeepGEMM（计算）
负责 MoE 的专家计算——即 dispatch 之后、combine 之前的那一步 GEMM。在 Hopper（SM90）和 Blackwell（SM100）上提供 FP8/FP4/BF16 的高性能内核，支持"分组 GEMM"（一次调用处理多个专家的不等长输入）。还包括更大的融合内核：Mega MoE 把一整层 MoE（包括通信）塞进一个内核。

两者的交汇在三处：DeepEP dispatch 的输出直接是 DeepGEMM masked GEMM 的输入；Mega MoE 内核里直接用 NVLink 对称缓冲区做 dispatch/combine；两仓共用同一个运行时编译子模块 DeepJIT。这三个交汇点分别在 dg04↔ep02、dg08↔ep07、dg05↔ep06 中展开。

一个 token 的完整旅程

下面用一条时间线串起本系列 17 篇覆盖的内容。一个 token 从进入 MoE 层到出来，经过的步骤和对应的篇目是：

  1. 门控路由：gate 网络算出 top-k 专家和权重。→ dg09（Mega Gate 融合了 GEMM + 打分 + top-k）
  2. EPBuffer 分配：按最坏情况预留通信缓冲区。→ ep01
  3. dispatch：计数→布局→发送→拷贝尾声。→ ep02（直连）、ep04（混合）、ep05（底层通信原语）
  4. 专家 GEMM：按专家分组做 FP8/BF16 矩阵乘。→ dg01–dg06（GEMM 内核各篇）、dg04（分组模式）
  5. combine：结果按原路送回，加权求和。→ ep03
  6. HyperConnection：多路残差混合 + RMSNorm。→ dg09（Mega mHC）

推理解码时，Mega MoE（dg08）把步骤 3–5 融合成一个持久化内核，内核内部用 NVLink 对称缓冲区直接做 dispatch 和 combine，省掉独立的 EP 内核调用。这是本系列中最复杂的单一内核。
