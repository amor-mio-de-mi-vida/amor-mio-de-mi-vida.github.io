TL;DR

  • GPU 把几千个线程组织成 warp（32 线程）→ warpgroup（4 warp = 128 线程）→ CTA（thread block）→ cluster；每层有不同的同步和共享内存能力。
  • Hopper（SM90）三件套：TMA（硬件异步搬运引擎）、WGMMA（warpgroup 级矩阵乘）、mbarrier（异步屏障）——构成"生产者-消费者"流水线的基础。
  • Blackwell（SM100）新增：TMEM（张量内存，累加器搬出寄存器）、UTCCP（缩放因子搬运通路）、tcgen05.mma（统一 MMA）、dual-CTA（两个 CTA 协作一次 MMA）。
  • GEMM 分块的本质是把大矩阵乘切成小块，让每块 fit 进片上内存；accumulator（累加器）、epilogue（尾声）、Split-K 是后续各篇反复出现的概念。
  • NVLink 提供节点内 \(\sim\)900 GB/s 双向带宽，RDMA 跨节点 \(\sim\)50 GB/s——两者量级差 18 倍，决定了 DeepEP 的直连/混合两条路径。

GPU 线程层级：从 thread 到 cluster

NVIDIA GPU 的执行单元叫 SM（Streaming Multiprocessor）。一块 H100 有 132 个 SM，一块 B200 有 160 个。每个 SM 可以同时运行多个 CTA（也叫 thread block），具体多少取决于寄存器和共享内存的占用。

线程的组织层级从小到大：

层级线程数共享什么同步机制在源码中怎么出现
thread1自己的寄存器—每个 CUDA 线程
warp32隐式锁步执行__syncwarp、__shfl_syncwarp_id = threadIdx.x / 32
warpgroup128（4 warp）同一 SM 的寄存器文件warpgroup_arrive/waitWGMMA 和 tcgen05.mma 的执行单位
CTA / block可配置（通常 256–1024）共享内存（SMEM）__syncthreads、mbarriergrid 中的一个 block
cluster多个 CTA（通常 2）可以读对方的 SMEMcluster barrierHopper 新增，用于 TMA 多播

关键要点：warp 是 GPU 调度的最小单位——32 个线程同时执行同一条指令（SIMT）。__shfl_sync 让 warp 内的线程直接交换寄存器值，不经共享内存——DeepGEMM 的 top-k 选择和 Sinkhorn 归一化全靠它。warpgroup 是 Hopper 引入的概念，WGMMA 指令需要整个 warpgroup 协作发射。

内存层级：寄存器 → 共享内存 → L2 → HBM

GPU 的内存层级决定了内核的数据搬运策略：

存储容量（H100 单 SM）带宽量级延迟用途
寄存器65536 × 32b = 256 KB~20 TB/s~1 cycle累加器、循环变量
共享内存（SMEM）最高 228 KB~12 TB/s~30 cycleTMA 搬入的 tile、barrier
TMEM（SM100）512 列 × 32 × 4B = 64 KB专用通路~few cyclesMMA 累加器（Blackwell）
L2 cache50 MB（全芯片共享）~12 TB/s~200 cycle跨 SM 复用的权重
HBM80 GB（H100）3.35 TB/s~400 cycle权重、激活值、缓冲区

"搬运"是 GPU 编程的核心主题。GEMM 内核的大部分工程就是在安排数据搬运：用 TMA 从 HBM 搬到 SMEM，用 WGMMA 从 SMEM 读到累加器，用尾声把累加器写回 HBM。DeepEP 的 dispatch 内核也在做同样的事——只不过搬运的目标是另一块 GPU 的 HBM。

Hopper（SM90）：TMA + WGMMA + mbarrier

Hopper 对 GEMM 流水线引入了三个关键硬件特性：

TMA（Tensor Memory Access）

TMA 是一个独立于 SM 的硬件搬运引擎。发一条 TMA 指令后，SM 可以继续做别的事——搬运在后台完成。TMA 用一个"描述符"（descriptor）来定义搬运的源地址、形状、步幅和 swizzle 模式，一次搬一个多维 tile（比如 128×64 的 BF16 块）进共享内存。

TMA 的优势是零 SM 占用。传统的 cp.async 搬运需要多个线程协作计算地址和发射拷贝指令，TMA 只需一个线程发一条指令。这就是 DeepGEMM 里"TMA 生产者 warp"只用一个 warp 就能喂饱多个"MMA 消费者 warpgroup"的原因。

TMA 还支持多播（multicast）：同一份数据同时拷贝到 cluster 内多个 CTA 的共享内存。DeepGEMM 用 2-CTA cluster + 多播来共享 B 矩阵的 tile，让两个 CTA 各自算不同的 M 块但共用同一份 B。

WGMMA（Warpgroup Matrix Multiply-Accumulate）

WGMMA 是 Hopper 的张量核指令，需要整个 warpgroup（128 线程）协作发射。一条 WGMMA 指令从共享内存读操作数，在寄存器文件里做矩阵乘累加。

在 FP8 GEMM 的上下文中，WGMMA 每次处理 K = 128 列（这是 FP8 的缩放粒度）。一条 WGMMA 产出一个 \(M \times N\) 的 FP32 部分和，存在寄存器里——这就是 dg01 中 accum 寄存器数组的来历。

WGMMA 有一个 .scale_d 字段：值为 1 时做 \(D = D + A \times B\)（累加到已有结果上），值为 0 时做 \(D = A \times B\)（覆盖）。第一个 K 块用 0，后续的用 1。

mbarrier（异步屏障）

mbarrier 是共享内存中的硬件屏障，支持"相位"（phase）机制：生产者完成搬运后调 arrive，消费者调 wait 等待当前相位完成。TMA 搬运完成时会自动在指定的 mbarrier 上做 arrive——这就把"搬运完成"和"可以开始计算"直接关联起来，不需要全局同步。

DeepGEMM 用 full/empty 两组 mbarrier 构成环形缓冲：full barrier 表示"这个 stage 的数据已搬好"，empty barrier 表示"这个 stage 的数据已被消费、可以覆盖"。生产者和消费者交替推进相位——这就是后续各篇中"N 级流水线"的基础机制。

Blackwell（SM100）：TMEM、UTCCP 与 dual-CTA

Blackwell 在 Hopper 的基础上做了四个影响内核结构的改变：

特性Hopper（SM90）Blackwell（SM100）对内核的影响
MMA 指令wgmmatcgen05.mma（UMMA）操作数必须都在 SMEM
累加器寄存器文件TMEM（张量内存）尾声需先从 TMEM 读出
缩放因子寄存器中手动乘TMEM 中 MMA 自动读取需要 UTCCP 搬运通路
CTA 协作可选 cluster 多播dual-CTA MMA（两个 CTA 共用 TMEM）M 维加倍
barrier 组2 组（full/empty）6 组（TMA A/B、UTCCP A/B、full/empty）同步更精细

TMEM（Tensor Memory）是 SM100 新增的专用存储，每个 SM 有 512 列。MMA 的累加器直接写入 TMEM 而不是寄存器文件——这释放了大量寄存器给其他用途，但尾声必须用 tcgen05.ld 指令把结果从 TMEM 读出到寄存器再写回全局内存。

UTCCP（Unified Tensor Core Copy，tcgen05.cp）是专门把缩放因子从 SMEM 拷入 TMEM 的指令。SM100 的块缩放 MMA 要求缩放因子（UE8M0 编码）预先放在 TMEM 的指定列——UTCCP 完成这一步。这比 SM90 多了一个搬运环节，DeepGEMM 因此引入了"UTCCP 转置 warp"这个新角色。

Dual-CTA：SM100 允许同一 SM 上的两个 CTA 共享同一块 TMEM 做联合 MMA。其中一个是 leader CTA（负责发射 MMA），另一个提供额外的 SMEM 空间。两个 CTA 合作时 M 维加倍（比如各贡献 64 行，合成 128 行）。

GEMM 分块：为什么要切小块

矩阵乘 \(D = A \times B^\top\)（M×K 乘 N×K）的计算量是 \(2MNK\) FLOP。H100 FP8 张量核的峰值算力约 1979 TFLOPS，但 HBM 带宽只有 3.35 TB/s——如果每个 FP8 元素都从 HBM 读一次，实际吞吐会被带宽卡死在几十 TFLOPS。

分块（tiling）的核心思想：把 A 和 B 切成 BM×BK 和 BN×BK 的小块，先搬进 SMEM（快），然后在 SMEM 中反复重用——一块 BK=128 的数据被 BM×BN 个输出元素共用，摊薄了搬运代价。这就是"计算密度"或"算术强度"（arithmetic intensity）的来源。

后续各篇反复出现的三个概念：

累加器（accumulator）
存放部分和的寄存器数组。每处理一个 BK 块，MMA 把结果累加进去。K 维遍历完后，累加器里就是最终的 M×N 输出块。在 SM90 上是寄存器，在 SM100 上是 TMEM。
尾声（epilogue）
K 维遍历完成后的后处理：从累加器读出结果、做类型转换（FP32→BF16/FP8）、乘缩放因子、应用偏置（bias）、写回全局内存。DeepGEMM 的 Mega Gate 和 Mega mHC 把整个门控逻辑或归一化逻辑塞进了尾声。
Split-K
当 M 和 N 不够大、不足以占满所有 SM 时，把 K 维也拆开：多个 CTA 各算一段 K 的部分和，最后做一次全局归约合并。代价是多了归约开销和 workspace 内存，好处是把空闲的 SM 都用上。Mega mHC 和 Mega Gate 都用 Split-K。

NVLink 与 RDMA：节点内 vs 节点间

MoE 的 dispatch/combine 需要 GPU 间通信。两种主要互联：

互联范围双向带宽（H100）延迟编程接口
NVLink同节点 8 卡~900 GB/s<1 μs对称指针直写、TMA store
RDMA（InfiniBand）跨节点~50 GB/s数 μsNCCL Gin put/get/signal

NVLink 的特殊之处是对称内存窗口（symmetric memory）：同一 NVLink 域的 8 块 GPU 在相同的虚拟地址偏移处分配一段内存，拿到对端的指针后可以像访问本地内存一样读写——SM 发出一条 store 指令，NVLink 硬件把数据送到对端 GPU 的 HBM。这就是 ep05 中 get_sym_ptr 返回的那个指针。

RDMA 没有这种透明的指针访问。跨节点通信需要经过 NIC（网卡），用消息传递接口（DeepEP 中是 NCCL 的 Gin API）显式发送和接收。延迟更高、带宽更低，但这是跨节点的唯一选择。

这两种互联的带宽差（18×）直接决定了 DeepEP 的架构：同节点走"直连模式"（一跳 NVLink），跨节点走"混合模式"（RDMA 到代理节点 + NVLink 转发）。ep04 详细拆解这两条路径。
