NVLink 加 RDMA：混合模式的转发路径

当 EP 组跨越多个 NVLink 域时，dispatch 把 token 先用 RDMA 送到目标域的代理节点，再由转发 warp 经 NVLink 直通指针写进最终接收缓冲；三种 warp 角色、两层去重、批量 tail 发布与 per-channel 链表构成了一条完整的混合转发路径。

TL;DR

  • 当 EP 组跨越多个 NVLink 域时，DeepEP 用混合模式：scale-out warp 经 RDMA 把 token 送到目标域的代理节点，forward warp 再经 NVLink 直通指针写进最终接收缓冲——两跳完成一次跨域 dispatch。
  • block 内三种 warp 角色各司其职：notify warps 做两级计数归约，scale-out warps 做 RDMA 发送，forward warps 做 NVLink 转发。去重在两层分别发生：发送端按 scale-out 域，转发端按 scale-up rank。
  • tail 发布以 kScaleoutUpdateInterval = 6 为间隔批量进行，per-channel 链表和 token_metadata_at_forward 让 combine 能沿 dispatch 的原路"反向重放"。

前置知识

了解直连 dispatch 的计数-布局-发送流程（ep02）和 NVLink/RDMA 的带宽量级（bg02）。本篇新引入：scale-out/scale-up 域、notify/scale-out/forward 三种 warp 角色、两跳转发、反向重放。

为什么需要混合模式

第 2 篇介绍的直连模式假设所有 rank 在同一个 NVLink 域内，dispatch 内核可以用 gin.put 或 TMA 直写把数据一步送达目标 rank。但实际的大规模训练集群中，一个 EP 组往往横跨多个 NVLink 域（scale-up domain），域间只有 RDMA 可达。一个 token 要从 scale-out 域 0 的 rank 0 到达 scale-out 域 1 的 rank 3，就需要两跳：先经 RDMA 到域 1 的某个 rank（"代理节点"），再经 NVLink 分发到域内的最终目标。

DeepEP 用一个简单的编码区分两个域：

const auto rank_idx = scaleout_rank_idx * kNumScaleupRanks + scaleup_rank_idx;

源码：deep_ep/include/deep_ep/impls/ep/hybrid_dispatch.cuh 第 60–61 行（节选）

全局 rank 由 scaleout_rank_idx * kNumScaleupRanks + scaleup_rank_idx 得出。相应地，专家到域的映射有两个除数：kNumExpertsPerScaleout = kNumExperts / kNumScaleoutRanks（scale-out 域内的专家数）和 kNumExpertsPerRank = kNumExperts / kNumRanks（每个 rank 的专家数）。一个 token 的 topk_idx 先除以 kNumExpertsPerScaleout 判断它属于哪个 scale-out 域，再除以 kNumExpertsPerRank 判断域内的哪个 rank。

一个 token 的路由决策因此分三种情况：

  1. 目标专家在本 rank：token 不参与跨 rank 通信，直接在本地计算。
  2. 目标专家在同一 NVLink 域的其他 rank：scale-out warp 执行本地旁路（local bypass，下文第 425 行），TMA 直写入本域的 scaleout_recv_buffer；forward warp 用 NVLink 对称指针将数据转发到域内目标 rank。单跳，延迟在微秒级以下。
  3. 目标专家在另一 NVLink 域：scale-out warp 经 RDMA gin.put 发送到目标域的代理节点；目标域的 forward warp 用 NVLink 转发到域内最终 rank。两跳，延迟为 RDMA 往返（数微秒）加 NVLink 转发（亚微秒）。

三种情况在同一个 token 的不同 top-k 选择中可以同时发生——比如 top-8 中 3 个专家在本域、5 个在两个远端域，那么 scale-out warp 会为本域做一次旁路、为两个远端域各做一次 RDMA put。去重保证每种目标只发一份数据。

Notify 阶段：两级归约

notify warps 的工作与直连模式类似（见第 2 篇的三步归约），但多了一层 scale-out 归约——因为跨域的计数需要经 RDMA 广播到所有 scale-out 对端，再由对端的 SM 0 分发到域内各 rank。整个 notify 阶段对延迟极其敏感：它在关键路径上——发送 warp 必须等 notify 完成才能获得准确的目标槽位偏移。流程如下：

  1. 共享内存本地计数：每个 SM 的 notify warps 遍历本地 token，对 expert_count 做 atomicAdd_block（按专家编号），对 rank_count 先做 ptx::deduplicate 去重再累加。
  2. 全网格归约：用 ptx::red_add 把打包的 (1<<32)|count 写入 notify_reduction workspace（第 140-143 行）。SM 0 轮询等待所有 SM 到达，解码并写入 scaleout_rank_expert_count 发送缓冲。
  3. RDMA 广播：SM 0 的线程向每个 scale-out 对端发送两次 gin.put——分别是 per-rank 计数和 per-expert 计数（第 179-188 行）。
  4. NVLink 分发：SM 0 等待所有 scale-out 对端的计数到达，归约后写入域内各 scale-up peer 的 rank 级和 expert 级计数器。rank 级用 gin.put_value（一次性写入完整值），expert 级用 gin.red_add_rel（原子加，因为多个 scale-out 域可能同时写同一个 rank 的同一个专家）。
  5. 前缀和：warp 0 做 per-rank inclusive prefix sum，warp 1 做 per-expert exclusive prefix sum。

Scale-out warps：TMA 加载与 RDMA 发送

如图 2 所示，每个 scale-out warp 是一个独立的 channel，负责把自己分到的 token 发送到对端 scale-out 域。一个 token 的发送流程：

  1. TMA 载入：从全局内存载入 hidden（tma_load_1d）和 SF（cp_async_ca）到共享内存的 TMA buffer。
  2. 按 scale-out 域去重：用 ptx::deduplicate(stored_dst_scaleout_rank_idx, lane_idx) 去重——一个 token 可能被 top-k 选到属于同一 scale-out 域的多个专家，但只需要发送一份数据。
  3. TMA 存入 send buffer：如果目标不全是本地域，先写入 scaleout_send_buffer（第 426-428 行）。本地域直接 bypass——TMA 直写入 scaleout_recv_buffer（第 433-436 行）。
  4. gin.put RDMA 发送：对远端 scale-out rank 发起 gin.put<ncclTeamTagRail>（第 446-451 行），同时预载入下一个 token 以重叠 TMA 与 RDMA 操作。

去重、slot 分配与本地旁路

scale-out warp 的每次迭代处理一个 token 的所有 top-k 目的地。由于一个 token 可能有多个 top-k 专家映射到同一个 scale-out 域，不去重会发出冗余的 RDMA 写。去重和 slot 分配在一条 warp 管线中完成：

// Deduplicate ranks and assign slots
int stored_dst_slot_idx = -1;
const auto stored_old_slot_idx = ptx::exchange(

    stored_dst_slot_idx = stored_old_slot_idx;

// Update scale-out tail
const auto scaleout_rank_mask = ptx::reduce_or(stored_dst_scaleout_rank_idx >= 0 ? (1u << stored_dst_scaleout_rank_idx) : 0u);
stored_scaleout_tail += (scaleout_rank_mask >> lane_idx) & 1;

// ...
// Local rank can be bypassed
if (stored_dst_slot_idx >= 0 and stored_dst_scaleout_rank_idx == scaleout_rank_idx) {

第 410–411 行用 ptx::exchange 获取每个 lane 所指向的 scale-out 域当前的 tail 值——这是 __shfl_sync，lane 用目标 scale-out rank 做索引读取另一个 lane 保存的计数器。第 412 行 ptx::deduplicate 找到同一 scale-out 域的最高 lane，只有它拿到 slot（stored_dst_slot_idx），其余 lane 为 -1。第 416–417 行用 warp-level reduce_or 算出本轮涉及哪些 scale-out 域的位掩码，然后 popcount 推进 tail。

第 425 行的本地旁路（local bypass）是一个重要优化：如果 scaleout_rank_mask 中除了本地域没有其他位被置位，就不需要写 send buffer——因为本地域的数据不走 RDMA，直接从 TMA buffer 复制到 recv buffer（第 433–436 行）。只有当 token 要发往远端域时才写 send buffer（第 426–428 行），RDMA gin.put 从 send buffer 读取。这样在大部分 token 都目标本地域的场景下，可以跳过 send buffer 的 TMA store，减少一次显存写操作。

ptx::deduplicate 的三步流水线

上面的 ptx::deduplicate 调用在 ptx.cuh 中由三条 PTX 指令组成：

__device__ __forceinline__ unsigned match(const int& value) {
    return __match_any_sync(0xffffffff, value);
}
// ...
__device__ __forceinline__ int get_master_lane_idx(const unsigned& mask) {
    // Equivalent to `31 - __clz(mask)`
    int highest_idx;
    asm volatile("bfind.u32 %0, %1;" : "=r"(highest_idx) : "r"(mask));
    return highest_idx;
}
// ...
__device__ __forceinline__ bool deduplicate(const int& value, const int& lane_idx) {
    return get_master_lane_idx(match(value)) == lane_idx;
}

源码：deep_ep/include/deep_ep/common/ptx.cuh 第 519–546 行（match → bfind → deduplicate 三级流水线）

整个流程：

  1. match(value)（第 519 行）：封装 PTX match.any.sync.b32。在全部 32 个 lane 之间做广播比较——返回一个 32 位掩码，bit i 为 1 当且仅当 lane i 持有与调用者相同的 value。单条 PTX 指令，延迟约 2 个周期，不涉及共享内存。
  2. get_master_lane_idx(mask)（第 537 行）：封装 PTX bfind.u32，返回掩码中最高位的位置（等价于 31 - __clz(mask)）。为什么选最高位而不是最低位？答案是实现简洁性——bfind.u32 是单周期 PTX 指令，直接返回零基 MSB 索引；若用 __ffs 取最低位则返回值需减 1 才得到零基索引。两者在去重正确性上完全等价，bfind 只是更自然的原语选择。
  3. deduplicate(value, lane_idx)（第 544 行）：组合前两步——match 找出所有持有相同值的 lane 集合，get_master_lane_idx 取编号最高的 lane 作为 master，只有 master == lane_idx 的 lane 返回 true。其余同值 lane 返回 false，后续 stored_dst_slot_idx 保持 -1，TMA store 和 RDMA put 的条件判断自然跳过。

以 top-8 场景为例：假设 lane 0、2、5 指向 scale-out rank 1，lane 1、3 指向 rank 2。match(1) 在前三个 lane 上返回掩码 0b...00100101（bit 0、2、5），bfind 取最高位得 5——只有 lane 5 获得发送权并拿到 slot。整个去重只需三条 warp-level 指令（match.any.sync + bfind.u32 + 比较），不涉及共享内存原子操作，总延迟不超过 10 个周期。

TMA 与 RDMA 流水线重叠

scale-out warp 的性能关键在于 TMA 加载与 RDMA 发送的重叠。在第 442 行发出 RDMA gin.put 后，紧接着预加载下一个 token（preload_next_token(token_idx + kNumChannels)，第 442 行）——tma_load_1d 是异步操作，与 RDMA 发送并行执行。这意味着当 NIC 在发送当前 token 时，DMA 引擎已经在从全局内存加载下一个 token 到共享内存。每个 channel 的 TMA buffer 只有单缓冲（不是双缓冲），所以预加载只能在上一个 token 的 TMA store 和 RDMA put 都完成之后才开始——这限制了 overlap 的深度，但在 RDMA 延迟较高的场景下仍然有效。

批量 tail 发布

forward warp 需要知道 recv buffer 里有多少新到达的 token。scale-out warp 通过 scaleout_channel_signaled_tail 发布进度，但 st.release.sys（system-scope release store）代价很高，因此不是每发一个 token 就发布一次，而是每隔 kScaleoutUpdateInterval = 6 个 token 批量发布：

const auto update_scaleout_tail = [&](const bool& finish_flag = false) {
    if (lane_idx < kNumScaleoutRanks and
        (stored_scaleout_tail >= stored_old_scaleout_tail + kScaleoutUpdateInterval or finish_flag)) {
        const auto signaled_tail = math::pack2<int, int64_t>(finish_flag, stored_scaleout_tail);
        const auto ptr = workspace_layout.get_scaleout_channel_signaled_tail_ptr(channel_idx, scaleout_rank_idx);
        const auto old_signaled_tail = math::pack2<int, int64_t>(0, stored_old_scaleout_tail);

        // NOTES: the "release" scope will be `sys` for the local rank (we may involve NVLink so not `gpu`)
        // For RDMA requests, "release" is ensured by "atomic"
        gin.red_add_rel<ncclTeamTagRail>(ptr, signaled_tail - old_signaled_tail, lane_idx);
        stored_old_scaleout_tail = stored_scaleout_tail;
    }
    __syncwarp();
};

Forward warps：NVLink 直通转发

forward warp 的核心循环是一个 while 循环，用 wip_mask（work-in-progress mask）追踪还有哪些 scale-out 对端有未处理的数据：

  1. 轮询 tail：用 ptx::ld_acquire_sys 读取 scaleout_channel_signaled_tail，解包得到 (finish_flag, tail_idx)。
  2. Round-robin 选 rank：在 wip_mask 中轮转选择下一个有数据的 scale-out rank，避免饥饿。具体做法是：以当前 recv_scaleout_rank_idx + 1 为起点，先看 wip_mask 中起点以上的最低位（ptx::ffs(hi_mask)），如果没有就回绕到 wip_mask 的最低位。这保证了每轮循环都从上次停下的位置开始扫描，不会总是优先处理编号最小的 rank。每次只处理一个 chunk（最多 kNumSlotsPerForwardChunk = 6 个 token），然后切换到下一个 rank。chunk 的大小是一个折中：太大会让某个 rank 长时间独占 warp 导致其他 rank 的数据排队，太小会增加轮询开销。6 个 token 恰好对应一次 kScaleoutUpdateInterval 的发布粒度。
  3. TMA 载入：从 scaleout_recv_buffer 载入到达的 token 到共享内存。
  4. 按 scale-up rank 去重：用 ptx::deduplicate(stored_dst_scaleup_rank_idx, lane_idx)——这是第二层去重。一个 token 的多个 top-k 专家可能属于域内的同一个 scale-up rank，同样只需要转发一份。
  5. NVLink 直通写出：这是关键步骤——forward warp 不使用 gin.put，而是通过 gin.get_sym_ptr<ncclTeamTagLsa> 获取目标 scale-up rank 上的接收缓冲的 NVLink 直通指针，然后 TMA 直写：
if (stored_dst_slot_idx >= 0) {
    const auto dst_ptr = gin.get_sym_ptr<ncclTeamTagLsa>(
        scaleup_buffer.get_token_buffer(stored_dst_slot_idx).get_base_ptr(),
        stored_dst_scaleup_rank_idx);
    ptx::tma_store_1d(dst_ptr, tma_buffer.get_base_ptr(), tma_buffer.get_num_bytes<false>());
    ptx::tma_store_commit();
}

源码：deep_ep/include/deep_ep/impls/ep/hybrid_dispatch.cuh 第 590–596 行（节选）

这就是 NVLink 的性能优势所在：forward warp 拿到的是对端 GPU 内存的直接映射地址，TMA store 不经过 Gin 协议栈，延迟更低、带宽更高。与 scale-out warp 的 RDMA 路径相比，NVLink 直写省掉了 Gin 的 WQE 入队、NIC 固件调度和远端 PCIe 写入开销，在 8 卡 NVLink 域内的单次写入延迟通常在微秒级以下，而 RDMA 路径的往返延迟则在数微秒量级。

forward warp 的循环退出条件（wip_mask）也值得分析。每个 lane 对应一个 scale-out 对端（lane_idx < kNumScaleoutRanks），只要 stored_scaleout_tail_idx > stored_scaleout_old_tail_idx（还有未处理的 token）或 stored_finish_flag == 0（对端还没结束），该 lane 的 bit 就为 1。当所有 lane 都完成后 wip_mask 清零，循环退出。在循环内部，ptx::exchange（即 __shfl_sync）让每个 lane 能读到任意其他 lane 的状态——这是 warp 级协调的核心：forward warp 的 32 个线程不是各自独立轮询，而是共享所有对端的进度信息，通过 wip_mask 和 round-robin 协同决策下一步处理哪个 rank。

Metadata 与链表

forward warp 在转发时记录两组元数据，供 combine 阶段反向重放：

  • token_metadata_at_forward：形状 [kNumChannels, N+1, 2+2*kNumTopk]，记录每个转发 token 的 src_token_global_idx、是否为 chunk 末尾 token、每个 top-k 的目标 scale-up rank 和 slot index。以 src_token_global_idx = -1 作终止符（第 634-635 行）。
  • channel_linked_list（通过 transform_linked_list_idx）：per-channel、per-scaleup-rank 的链表。dispatch 结束后，channel_scaleup_tail 存储每个 (channel, scaleup_rank) 对的链表终止位置。

Hybrid combine：反向重放

如图 3 所示，hybrid_combine_impl 结构上也是两路 warp：scale-up warps 和 forward warps。

Scale-up warps

scale-up warps 的任务是沿着 dispatch 阶段建立的链表，遍历本 channel 的所有 token：

  1. 从 channel_linked_list 读取 token index（第 160-167 行）。
  2. 根据 src_metadata 确定 token 的源信息（scaleout rank、slot index）。
  3. 从 scaleup_buffer 经 NVLink 对称指针读取 BF16 数据；如果多个 top-k 指向同一 rank，调用 combine_reduce 做本地归约。
  4. TMA 写入 send buffer，并通过 st_release_sys 发布 channel_scaleup_tail（同样以 kNumScaleupUpdateInterval = 3 间隔批量更新）。

Forward warps（重放）

forward warps 按照 token_metadata_at_forward 的顺序依次处理每个 token：

  1. 读取 metadata：src_token_global_idx、is_token_last_in_chunk、per-topk 的 src_scaleup_rank_idx 和 src_slot_idx。
  2. 等待 tail 到达：对每个涉及的 scale-up rank，用 ld_acquire_sys 轮询 channel_scaleup_tail。
  3. 归约：从 scaleup_buffer 按 slot index 读取各 scale-up peer 的数据，调用 combine_reduce 归约到 smem。
  4. 回送 RDMA：TMA 写入 send buffer，然后 gin.put<ncclTeamTagRail> 发回源 scale-out rank。

forward warps 之所以能重放 dispatch 的路径，关键在于 dispatch 阶段的 forward warps 记录了完整的路由元数据：

            const auto metadata_ptr = token_metadata_at_forward +

每处理一个 token，dispatch 的 forward warp 记录 kNumForwardMetadataDims = 2 + 2*kNumTopk 个 int：前两个是 src_token_global_idx（源 token 全局索引，由 scale-out warp 在发送时嵌入 token buffer 的 metadata 区）和 is_token_last_in_chunk（是否为 chunk 末尾，控制 RDMA 的 AggregateRequests 聚合标志）；随后是 per-topk 的目标 scale-up rank 和 slot 位置。整个数组以 src_token_global_idx = -1 作为终止哨兵（第 634 行）。

combine 的 forward warps 按同样顺序逐 token 遍历这个数组（hybrid_combine.cuh 第 392 行起），但增加了两个关键步骤。第一步是等待 scale-up tail：对当前 token 涉及的每个 scale-up rank，forward warp 用 ld_acquire_sys 轮询 channel_scaleup_tail，直到 scale-up warps 的归约进度追上当前 token。这是两路 warp 之间的唯一同步点——scale-up warps 每隔 kNumScaleupUpdateInterval = 3 个 token 发布一次 tail，所以 forward warp 最多空等 2 个 token 的处理时间。第二步是再次去重（ptx::deduplicate），语义与 dispatch 不同：dispatch 去重防止"同一 scale-up rank 重复转发"，combine 去重防止"同一 scale-up rank 的数据被 combine_reduce 重复累加"。

combine forward warp 还有两条代码路径。当 kAllowMultipleReduction = true（第 496-572 行）时，forward warp 对同一 token 的多个 scale-up peer 数据调用 combine_reduce 归约到共享内存的 TMA buffer，然后一次 TMA store + RDMA put 发回源 rank——这减少了跨域 RDMA 次数。当 kAllowMultipleReduction = false（第 454-495 行）时，每个 top-k 的 scale-up 数据被逐一 TMA load → TMA store → RDMA put，不做归约——这在 topk 值较小时可能更高效，因为避免了归约的寄存器压力和同步开销。选择哪条路径由编译时的模板参数决定。

循环结束后，forward warps 还需要等待所有 scaleout 对端的 combine 完成：发送 tail signal，然后等待对端的 tail signal 到达（第 590-620 行），确保 recv buffer 数据完整后才能进入下一次 combine。

hybrid combine 的一个微妙之处是数据类型的变化。dispatch 时，hidden 数据是 FP8（或 BF16），scale factor 跟随其后。但 combine 阶段的数据一律是 BF16——因为专家计算的输出已经是 BF16 精度。这意味着 combine 的 per-token 字节数比 dispatch 大（FP8 dispatch 时翻倍），scale-up 和 scale-out buffer 的 slot 大小也需要相应调整。DeepEP 的缓冲区大小计算（第 1 篇的 calculate_buffer_size）取 dispatch 和 combine 所需的最大值，因此 BF16 combine 经常成为缓冲区大小的决定因素。

hybrid combine 与直连模式 combine 的另一个关键差异在于路径复杂度。直连模式的 combine 只需一跳——接收端遍历缓冲区中各 rank 的数据做归约即可。hybrid combine 需要两跳：scale-up warps 先从域内各 rank 收集 BF16 数据做本地归约，写入跨域 send buffer；forward warps 再沿 dispatch 时记录的路径反向传输，经 RDMA 回到源域。这意味着 hybrid combine 至少经历两跳传输延迟（scale-up 归约 + scale-out 回送），路径比直连模式多一跳——而且 forward warps 的每一步都要等 scale-up warps 的 tail 信号，两跳之间无法完全流水。设计者通过 kNumScaleupUpdateInterval = 3 的批量 tail 发布来平衡延迟与信号开销：粒度为 3 意味着 forward warp 最多空等 2 个 token 的时间，但避免了每个 token 一次 st.release.sys 的高代价。

此外，hybrid combine 的 forward warps 在结束后还需要执行一轮跨域的完成握手（第 590–620 行）。这是因为缓冲区在下一次 dispatch 时会被覆盖——如果源 rank 还没读完上一轮的 combine 数据就开始新一轮 dispatch，数据就会被损坏。完成握手确保所有 scale-out 对端都已读取完毕，才允许释放接收缓冲区。直连模式通过 gpu_barrier 一步完成这个同步；hybrid 模式需要跨域的 Gin signal 往返，延迟更高。

域的区分：team 与 rank 映射

ncclTeamTagLsa 的 "LSA" 即 Local Switch Attached，NVLink 域内的节点。

混合模式的正确性取决于精确地区分"NVLink 可达"和"RDMA 可达"。DeepEP 通过 NCCL 的 team 机制实现：

  • ncclTeamTagLsa：NVLink 域（scale-up 域），is_nvlink_accessible 恒返回 true。get_sym_ptr 返回 NVLink 直通指针。
  • ncclTeamTagRail：RDMA 域（scale-out 域），is_nvlink_accessible 恒返回 false（同一 RDMA rank 除外）。只能走 Gin 操作。
  • ncclTeamTagWorld：全局域，按 team_rail.rank * team_lsa.nRanks <= dst < (team_rail.rank + 1) * team_lsa.nRanks 判断是否在本域内。

这套 team 映射在通信层是统一的——gin.put<team_t>、gin.red_add_rel<team_t>、gin.get_sym_ptr<team_t> 的行为都由 team 类型决定。混合 dispatch 中：scale-out warps 用 ncclTeamTagRail 走 RDMA，forward warps 用 ncclTeamTagLsa 走 NVLink，notify warps 两者都用。屏障也分为两级：scale-up barrier 和 scale-out barrier 可以并行执行（由 gpu_barrier 调度，详见第 5 篇）。

两次去重的意义

一个 token 的 top-k 选择可能映射到多个专家，而多个专家可能位于同一目标域或同一 rank。如果不去重就会产生冗余传输。混合 dispatch 在两层分别去重：scale-out warps 按 scaleout_rank_idx 去重（一个 token 到同一域只发一份），forward warps 按 scaleup_rank_idx 去重（域内同一 rank 只转发一份）。两层去重都使用 __match_any_sync，不依赖输入顺序。直连模式只需要一层去重（只有 scale-up rank）。

此外，forward warps 检查 kScaleoutUpdateInterval（固定为 6）来决定何时从 scale-out 缓冲区拉取新数据。这个间隔不是随意选择的——它平衡了两个矛盾目标：间隔太短会导致 forward warp 频繁检查（浪费 SM 周期在空轮询上），间隔太长会增加 scale-out 数据在缓冲区中的驻留时间，推迟 NVLink 转发的启动时机。实际效果是 forward warp 每处理 6 个本地 token 就检查一次远端数据是否到达，这在 DeepSeek 的 8 卡 NVLink 域配置下大致对应一轮 scale-out RDMA 传输的延迟。

局限与未覆盖

  • 2+2+4 拓扑未支持：代码中有 TODO(NCCL): some ranks may be connected by NVLink, e.g., "2 + 2 + 4"（handle.cuh 第 56-58 行），说明当前 ncclTeamTagRail 假设 rail 内不存在 NVLink 连接——如果存在非对称的 NVLink 拓扑（如两个 2-GPU NVLink 域和一个 4-GPU NVLink 域组成一个 8-GPU 组），现有分派逻辑可能不正确。在这种拓扑下，部分 rail 对端之间有 NVLink 直连，理应走 NVLink 而非 RDMA，但 is_nvlink_accessible 对 rail team 恒返回 false，导致白白浪费 RDMA 带宽。
  • 去重不依赖输入排序：ptx::deduplicate 的底层是 __match_any_sync——它在整个 warp 内广播比较，返回所有持有相同值的 lane 的位掩码。这意味着去重对 topk_idx 的排列顺序没有任何要求：无论 top-k 选择以什么顺序排列，__match_any_sync 都能正确找到所有指向同一 scale-out 域的 lane。代码中没有对 topk_idx 做预排序——Python 包装 dispatch 中的 deterministic_sort 只用于输出的确定性排列，不影响内核的去重逻辑。
  • 模板参数爆炸：hybrid_dispatch_impl 有 16 个模板参数（加上默认计算的更多），每种配置需要 JIT 编译一份内核。代码注释 TODO(NCCL): so many params, plans to optimize? 说明开发者意识到这一问题。
  • copy epilogue 未展开：dispatch 结束后的 dispatch_copy_epilogue_impl（负责从 scaleup_buffer 构建展开布局、零填充等）在第 2 篇已详细讨论，此处不再重复。混合模式下 copy epilogue 通过 PDL（cudaTriggerProgrammaticLaunchCompletion）与 dispatch 内核衔接。
