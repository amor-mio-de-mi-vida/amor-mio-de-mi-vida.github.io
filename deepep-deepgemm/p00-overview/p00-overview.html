TL;DR

  • DeepEP（V2.5）是 DeepSeek 的专家并行通信库，实现 MoE 的 dispatch/combine；DeepGEMM 是配套的 FP8/FP4/BF16 GEMM 内核库。两者合在一起覆盖了 MoE 层从通信到计算的完整路径。
  • 本系列 17 篇精读分两卷：DeepEP 8 篇（接口 → 直连 → combine → 混合 → 通信底座 → 资源估算 → bucket 集合 → 冗余专家），DeepGEMM 9 篇（SM90 FP8 → SM100 FP8/FP4 → SF 格式 → 分组 GEMM → 启发式/JIT → BF16/einsum → MQA logits → Mega MoE → Mega Gate/mHC）。
  • 两卷的交汇点是三处：masked GEMM 吃 DeepEP dispatch 输出（dg04 ↔ ep02）、Mega MoE 把 EP 通信搬进 GEMM 内核（dg08 ↔ ep07）、DeepJIT 同时被两仓使用（dg05 ↔ ep06）。
  • 每篇独立可读，单个 HTML 文件可离线打开，所有代码链接指向固定提交。
  • 不熟悉 MoE 或 GPU 微架构？先读两篇背景：bg01（MoE 与 EP）和 bg02（GPU 硬件速查）。

DeepEP 和 DeepGEMM 各管什么

在 MoE 模型的一个前向步中，每个 token 被路由到若干专家，数据要在持有不同专家的 GPU 之间搬运（dispatch），然后计算（GEMM），最后搬回去归约（combine）。DeepEP 负责"搬运"，DeepGEMM 负责"计算"。

DeepEP（V2.5）实现了两套 EP 通信原语：

  • dispatch/combine：把 token 按 top-k 专家选择发送到目标 rank（dispatch），MoE 计算后归约并送回（combine）。支持纯 NVLink（直连）和 NVLink+RDMA（混合）两条路径。
  • bucket 集合通信：all-gather、reduce-scatter、all-reduce——用复制引擎驱动，SM 占用降至零或几个。

DeepGEMM（提交 5081f85）提供了一组高性能 GEMM 内核：

  • SM90（Hopper）和 SM100（Blackwell）上的 FP8/FP4 块缩放 GEMM。
  • MoE 分组 GEMM：contiguous、masked、K-grouped 三种分组模式。
  • 融合大内核：Mega MoE（一整层 MoE 融合进一个持久化内核）、Mega Gate、Mega mHC。
  • 所有内核通过 DeepJIT 运行时编译，从 Python 层按需生成。

两卷的交汇点

DeepEP 和 DeepGEMM 不是完全独立的两个库。它们在三处交汇：

  • masked GEMM ↔ dispatch 输出：DeepEP dispatch 产出的 per-expert token 列表直接成为 DeepGEMM M-grouped masked GEMM 的输入，后者不需要事先知道每个专家分到多少 token。（dg04 ↔ ep02）
  • Mega MoE ↔ bucket 通信：Mega MoE 把一整层 MoE（包括通信）塞进一个持久化内核，内核里直接用 NVLink 对称缓冲区做 dispatch 和 combine，省掉了独立的 EP 内核调用。（dg08 ↔ ep07）
  • DeepJIT：两仓共用同一个运行时编译子模块。DeepEP 用它按拓扑配置编译 EP 内核（ep06），DeepGEMM 用它按 GEMM 形状和硬件编译 GEMM 内核（dg05）。
