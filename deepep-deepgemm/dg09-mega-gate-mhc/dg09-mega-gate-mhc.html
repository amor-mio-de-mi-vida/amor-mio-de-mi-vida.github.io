TL;DR

  • Mega Gate 把 BF16 的 gate GEMM（x @ weight^T）与 sqrtsoftplus 打分、bias 排名、top-k 选择、权重归一化和冗余专家的物理映射融合在一个内核里，输出就是 dispatch 需要的 (topk_idx, topk_weights)。
  • Mega mHC（多路 HyperConnection）把 4 路残差混合、新残差计算、Fn 矩阵乘（TF32，Split-K）、Sinkhorn 归一化、RMSNorm、以及可选的 FP8 E4M3 量化全部融合在一个持久化内核里。
  • TF32 HC prenorm GEMM 是一个特化的 \(D = A \cdot B^\top\) 内核，A 为 BF16、B 为 FP32，输出 FP32 的 D 和逐行平方和 sqr_sum，服务于 HyperConnection 的预归一化阶段。
  • 提交 5081f85 修复了 Mega mHC 和 Mega Gate 在 CUDA graph 重放时 split barrier 被重新清零的问题：把 barrier 的分配提到 graph 捕获之前，每条流只做一次。

Mega Gate：一个内核完成门控路由

在 MoE 的前向传播中，gate 的职责是：把每个 token 的隐藏表示乘以门控权重矩阵得到 logits，对 logits 打分，选出 top-k 个专家，归一化权重，最后把逻辑专家编号映射到物理专家编号。传统做法需要一次 GEMM 加上若干 PyTorch 操作。

Mega Gate（bf16_mega_gate）把这些全部融合在一个 SM100 内核里。它的完整签名展示了融合了哪些功能：

/**
 * Fuse the BF16 gate GEMM with the MoE top-k gate.
 *
 * Args:
 *     x                              [T,H]               BF16
 *     weight                         [E,H]               BF16
 *     num_topk                       int
 *     use_shared_as_routed           bool
 *     num_shared_experts             int
 *     routed_scaling_factor          float
 *     ep_rank                        int
 *     scoring_func                   "sqrtsoftplus"
 *     mask                           [T] bool | None
 *     bias                           [E] FP32 | None
 *     image_bias                     [E] FP32 | None
 *     image_token_mask               [T] bool | None
 *     fix_routing_mask               [T] bool | None
 *     to_physical_map                [E+S, dup] int32 | None
 *     logical_count                  [E+S] int32 | None
 *     unmapped_topk_idx              [T,K] int64 | None
 *     force_random                   [T] bool | None
 *     out                            ([T,K'] int64, [T,K'] FP32) | None
 *
 * Returns:
 *     (topk_idx, topk_weights)
 *
 * Notes:
 *     S = num_shared_experts when use_shared_as_routed, else 0; K' = K + S.
 *     The kernel ranks experts on score + bias, while the emitted weights are the
 *     unbiased scores normalized over the top-k sum and scaled by routed_scaling_factor.
 *     unmapped_topk_idx receives the logical top-k indices, and for tokens with fix_routing_mask
 *     set it is also read as the routing to keep (so fix_routing_mask requires it).

源码：csrc/apis/mega_gate.hpp 第 28–59 行（节选）

输入是 x [T, H]（BF16）和 weight [E, H]（BF16），输出是 topk_idx [T, K']（int64）和 topk_weights [T, K']（FP32），其中 \(K' = K + S\)（\(S\) 是当共享专家作为路由专家使用时的共享专家数）。图 1 画出了完整的融合流程。

打分函数与排名

代码中唯一支持的打分函数是 sqrtsoftplus：先对 logit 做 softplus（log(1 + exp(x))），再取平方根。选择 sqrtsoftplus 而非标准 softmax 的原因在代码中没有注释说明（推测有数值上的好处：softmax 在专家数很多时会出现概率极度稀疏的问题，而 sqrtsoftplus 的输出是非归一化的正数，值域更宽，更适合后续的 bias 排名和 top-k 选择——但这是推测，不是代码或文档的陈述）。排名时使用的是"分数加 bias"的增强分数，但最终输出的权重是不含 bias 的原始分数，归一化方式是 top-k 个原始分数之和除以 routed_scaling_factor。代码中的断言确认了这一点：

DG_HOST_ASSERT(num_topk > 0 and num_topk <= num_routed_experts);
DG_HOST_ASSERT(ep_rank >= 0);
DG_HOST_ASSERT(std::isfinite(routed_scaling_factor));
DG_HOST_ASSERT(scoring_func == "sqrtsoftplus");

if (use_shared_as_routed) {
    DG_HOST_ASSERT(num_shared_experts == 1 or num_shared_experts == 2);
    DG_HOST_ASSERT(num_topk % num_shared_experts == 0);
    DG_HOST_ASSERT(num_routed_experts % (num_topk / num_shared_experts) == 0);

最多支持 512 个路由专家（kNumMaxRoutedExperts），专家数必须对齐到 4（kNumExpertsPerLaneVector）。

内核结构

内核由两类 warpgroup 组成：MMA warpgroup（128 线程，kNumNonEpilogueThreads）做 BF16 GEMM，把 x @ weight^T 的结果写到 TMEM；gate warpgroup（最多 7 个 warpgroup）从 TMEM 读出 logits 后做打分和排名。gate warpgroup 的数量由启发式决定：每个 warpgroup 从 TMEM 转置 8 列，每轮对 4 个 token 排名。

GEMM 使用 Split-K 策略：每个 token block 的计算由 num_expert_groups * num_mma_ctas * num_split_k 个 CTA 合作完成。split 之间的同步通过一个全局的 score barrier 数组实现，大小为 [kNumMaxTokenBlocks, 128B]（128 字节对齐，每行一个 barrier）。

TMEM 分数转出与 top-k 选择

MMA warpgroup 把 x @ weight^T 的结果写进 TMEM 后，gate warpgroup 需要把 logits 从 TMEM 搬到寄存器里做打分和排名。sm100_store_tmem_scores_to_global 完成这一步：

template <bool kScoreOnStore, uint32_t kScoreTokenStride,
          uint32_t UMMA_M, uint32_t kNumMmaCtas, uint32_t kNumGateWarps>
CUTLASS_DEVICE bool sm100_store_tmem_scores_to_global(float* scores, const uint32_t& tmem_base_addr,
                                                      const uint32_t& effective_umma_n,
                                                      const uint32_t& expert_base_idx,
                                                      const uint32_t& mma_cta_rank,
                                                      const uint32_t& gate_warp_idx) {
    // NOTES: with `UMMA_M == 128` on a CTA pair, the 64 experts of a CTA are spread over the two lane halves,
    //        so warps 0/1 and 2/3 of a warpgroup see the same experts for the two token halves
    constexpr uint32_t kNumTmemFragmentRows = 8;
    constexpr bool kPartitionedTokenPaths = UMMA_M == 128 and kNumMmaCtas == 2;
    constexpr uint32_t kNumExpertsPerCta = UMMA_M / kNumMmaCtas;
    const auto warp_idx_in_wg = gate_warp_idx % 4;
    const auto wg_idx = gate_warp_idx / 4;
    constexpr uint32_t kTokenStep = kNumGateWarps / 4 * kNumTmemFragmentRows;
    const auto num_token_cols = kPartitionedTokenPaths ? effective_umma_n / 2 : effective_umma_n;
    const auto token_base_idx = kPartitionedTokenPaths ? warp_idx_in_wg / 2 * num_token_cols : 0u;
    const auto expert_atom_idx = kPartitionedTokenPaths ? warp_idx_in_wg % 2 : warp_idx_in_wg;
    const auto global_expert_idx = expert_base_idx + mma_cta_rank * kNumExpertsPerCta +
                                   expert_atom_idx * 32 + ptx::get_lane_idx();
// ...
    for (auto token_idx = wg_idx * kNumTmemFragmentRows; token_idx < num_token_cols; token_idx += kTokenStep) {
        uint32_t values[kNumTmemFragmentRows];
        ptx::tmem_load_32dp32b<kNumTmemFragmentRows>(tmem_base_addr + token_idx, values);
        cutlass::arch::fence_view_async_tmem_load();
        const auto row_base_ptr = scores + static_cast<uint64_t>(token_base_idx + token_idx) * kScoreTokenStride +
                                  global_expert_idx;
        #pragma unroll
        for (uint32_t row_idx = 0; row_idx < kNumTmemFragmentRows; ++ row_idx) {
            auto score = __uint_as_float(values[row_idx]);
            if constexpr (kScoreOnStore)
                score = sqrt_softplus(score);
            scores_are_finite = scores_are_finite and isfinite(score);
            row_base_ptr[row_idx * kScoreTokenStride] = score;
        }
    }
    return scores_are_finite;

源码：deep_gemm/include/deep_gemm/epilogue/sm100_mega_gate.cuh 第 39–78 行（TMEM 分数转出：tmem_load 与 sqrt_softplus 打分）

关键操作是第 64 行的 ptx::tmem_load_32dp32b：它从 TMEM 地址一次取出 kNumTmemFragmentRows = 8 行的数据到寄存器数组。由于 2-CTA cluster 中 UMMA_M = 128，每个 CTA 的 64 个专家分布在两半 lane 上（kPartitionedTokenPaths），warp 0/1 和 warp 2/3 分别处理两个 token 半区的相同专家集合。如果 kScoreOnStore 为真（第 71–72 行），分数在写入全局内存前就地做 sqrt_softplus 变换。

拿到全局内存中的分数后，top-k 选择分两步。第一步是每个 lane 用一个 5 次比较的排序网络对自己的 4 个专家排序：

CUTLASS_DEVICE uint32_t sort4_best_first(float& score_0, float& score_1, float& score_2, float& score_3) {
    int idx_0 = 0, idx_1 = 1, idx_2 = 2, idx_3 = 3;
    compare_swap_best_first(score_0, idx_0, score_1, idx_1);
    compare_swap_best_first(score_2, idx_2, score_3, idx_3);
    compare_swap_best_first(score_0, idx_0, score_2, idx_2);
    compare_swap_best_first(score_1, idx_1, score_3, idx_3);
    compare_swap_best_first(score_1, idx_1, score_2, idx_2);
    return static_cast<uint32_t>(idx_0 | idx_1 << 2 | idx_2 << 4 | idx_3 << 6);
}

源码：deep_gemm/include/deep_gemm/epilogue/sm100_mega_gate.cuh 第 97–105 行（4 元素排序网络）

第二步是 select_warp_topk：每轮迭代，32 个 lane 各自提出当前未消费的最佳候选（通过一个 3 位游标 packed_cursors 索引排序后的列表），调用 warp_reduce_best 在 warp 内选出全局最优，只有赢家那个 lane 推进游标。重复 \(K\) 轮即得到 top-\(K\) 个专家及其权重。warp_reduce_best 内部先用 ptx::reduce_max_sync 找最大分数，再用 __reduce_min_sync 在分数相同的 lane 中选最小的专家编号——相同分数时取最小编号保证了确定性：无论 warp lane 的物理排列如何、无论在多少个 GPU 上运行，同分数的专家总是做出相同的选择，避免了分布式训练中的跨 rank 不一致。这个做法避免了全局排序：32 个 lane 各 4 个候选 = 128 个专家中选 \(K\) 个，复杂度正比于 \(K \times 32\)（每轮一次 warp reduce）。

冗余专家的物理映射与负载分散

当系统使用冗余专家（redundant experts）时，一个逻辑专家可能被复制到多个物理专家上。Mega Gate 通过 to_physical_map [E+S, dup] 和 logical_count [E+S] 两张表完成映射。store_topk_token 在拿到 top-k 的逻辑编号后，执行以下转换：

    auto physical_expert_idx = selected_expert_idx;
    if constexpr (kHasPhysicalMap) {
        if (lane_idx < num_physical_topk) {
            const auto logical_expert_idx = static_cast<uint32_t>(selected_expert_idx);
            // The SMEM cache only covers the routed experts
            const auto num_duplicates = static_cast<uint32_t>((lane_idx < kNumTopk ? routed_logical_count : args.logical_count)[logical_expert_idx]);
            DG_TRAP_ONLY_DEVICE_ASSERT(num_duplicates > 0 and num_duplicates <= args.num_duplicate_experts);
            // Spread the tokens of a logical expert over its duplicates, differently on every rank
            const auto duplicate_idx = (args.rank_idx + global_token_idx * 23333u) % num_duplicates;
            physical_expert_idx = args.to_physical_map[logical_expert_idx * args.num_duplicate_experts + duplicate_idx];
        }
    }

    // The smallest shuffle width covering the routed lanes, the other lanes hold zero
    constexpr uint32_t kSumWidth = kNumTopk <= 8 ? 8 : (kNumTopk <= 16 ? 16 : 32);
    const auto topk_sum = math::warp_reduce_sum<kSumWidth>(selected_unbiased_score) + 1e-20f;
    const auto selected_weight = lane_idx < kNumTopk ? selected_unbiased_score / topk_sum * args.routed_scaling_factor : 1.0f;
    store_token_outputs<kNumTopk, kHasUnmappedTopkIdx>(args, global_token_idx, lane_idx,
                                                       physical_expert_idx, selected_weight, selected_expert_idx);
}

源码：deep_gemm/include/deep_gemm/epilogue/sm100_mega_gate.cuh 第 187–216 行（store_topk_token：物理映射与权重归一化）

代码的关键在第 205 行的散列分散：(rank_idx + global_token_idx * 23333) % num_duplicates——不同 rank 和不同 token 通过两个互质因子的线性组合，把负载均匀地分散到同一个逻辑专家的所有物理副本上。常量 23333 是一个质数，保证在 num_duplicates 较小时散列的均匀性。权重归一化在第 212–213 行完成：先用 warp_reduce_sum 求 top-k 原始分数之和（宽度由 kSumWidth 选取最小的覆盖 2 的幂，避免浪费 shuffle 带宽），再除以总和乘以 routed_scaling_factor。共享专家的 lane（lane_idx ≥ kNumTopk）权重固定为 1.0。

随机路由：force_random

对于标记了 force_random 的 token，内核跳过正常的打分-排名流程，改用 store_random_topk_token 做无权重的随机专家采样。它的做法并非排序后截断，而是一种 warp 协同的 Fisher-Yates 变体：

template <uint32_t kNumTopk, bool kHasUnmappedTopkIdx, bool kHasPhysicalMap>
CUTLASS_DEVICE void store_random_topk_token(const RoutingArgs& args, const uint32_t& global_token_idx, const uint32_t& lane_idx) {
    const auto num_physical_topk = kNumTopk + args.num_shared_experts;
    auto num_physical_experts = args.num_routed_experts + args.num_shared_experts;
    if constexpr (kHasPhysicalMap) {
        auto local_count = 0u;
        for (uint32_t logical_expert_idx = lane_idx; logical_expert_idx < num_physical_experts; logical_expert_idx += 32)
            local_count += static_cast<uint32_t>(args.logical_count[logical_expert_idx]);
        num_physical_experts = __reduce_add_sync(0xffffffff, local_count);
    }
    DG_TRAP_ONLY_DEVICE_ASSERT(num_physical_experts >= num_physical_topk);

    // Sample `num_physical_topk` distinct experts: lane `i` draws from `n - i`, then ranks below every earlier draw
    // that is not larger shift up by one
    curandStatePhilox4_32_10_t rng_state;
    curand_init(args.rank_idx, global_token_idx * 32 + lane_idx, 0, &rng_state);
    const auto random_weight = curand_uniform(&rng_state);
    constexpr uint32_t kInvalidIdx = 0xffffffffu;
    auto candidate_idx = lane_idx < num_physical_topk ?
        curand(&rng_state) % (num_physical_experts - lane_idx) : kInvalidIdx;
    auto selected_expert_idx = kInvalidIdx;
    for (uint32_t output_idx = 0; output_idx < num_physical_topk; ++ output_idx) {
        const auto min_candidate_idx = __reduce_min_sync(0xffffffff, candidate_idx);
        const auto min_lane_idx = __reduce_min_sync(0xffffffff, candidate_idx == min_candidate_idx ? lane_idx : kInvalidIdx);
        if (candidate_idx != kInvalidIdx) {
            if (min_lane_idx == lane_idx) {
                selected_expert_idx = candidate_idx;
                candidate_idx = kInvalidIdx;
            } else if (candidate_idx >= min_candidate_idx and min_lane_idx < lane_idx) {
                ++ candidate_idx;
            }
        }
    }
    store_token_outputs<kNumTopk, kHasUnmappedTopkIdx>(args, global_token_idx, lane_idx,
                                                       static_cast<int64_t>(selected_expert_idx), random_weight, -1);
}

源码：deep_gemm/include/deep_gemm/epilogue/sm100_mega_gate.cuh 第 218–253 行（随机路由：warp 协同的无重复采样）

每个活跃 lane（lane_idx < num_physical_topk）用 curand 从 [0, n-i) 中抽一个候选编号。然后 num_physical_topk 轮迭代中，每轮用 __reduce_min_sync 选出当前最小的候选，赢家固定选择，其余 lane 如果候选 ≥ 赢家且优先级更低则加 1——等效于把已选的编号从剩余池中移除。最终每个 lane 得到一个不重复的物理专家编号，权重为均匀随机数。这个分支在正常推理中不触发，推测是为调试或负载测试保留的。

元数据缓存：4 KiB SMEM

Mega Gate 在共享内存中预留了 4 KiB 的 metadata_cache，用于缓存 bias、image_bias 和 logical_count 三张表。是否缓存 logical_count 由编译期的 caches_logical_count 函数决定：

CUTLASS_HOST_DEVICE constexpr bool caches_logical_count(const uint32_t num_routed_experts, const bool has_bias,
                                                        const bool has_image_token_mask, const bool has_physical_map) {
    const auto num_bias_cache_bytes = num_routed_experts * ((has_bias ? 1u : 0u) + (has_image_token_mask ? 1u : 0u)) *
                                      static_cast<uint32_t>(sizeof(float));
    return has_physical_map and num_bias_cache_bytes + num_routed_experts * static_cast<uint32_t>(sizeof(int)) <= kNumMaxMetadataCacheBytes;
}

源码：deep_gemm/include/deep_gemm/layout/mega_gate.cuh 第 46–51 行（metadata_cache 容量判断）

只有当 bias 和 image_bias 占用的字节数加上 num_routed_experts × sizeof(int) 不超过 4 KiB 时，才会把 logical_count 也放入缓存。典型的 256 个路由专家场景下，两个 bias（各 256×4 = 1 KiB）加 logical_count（256×4 = 1 KiB）共 3 KiB，可以全部缓存；但如果专家数达到 512 且同时启用 image_bias，则总需 512×12 = 6 KiB，超出限制，logical_count 只能走全局内存。缓存命中时，排名的 warp reduce 循环中每次读 bias 都是 SMEM load（~30 cycle），避免了全局内存的高延迟。

全局 workspace 布局

Split-K 的中间结果存放在全局 workspace 中，由 Workspace 结构体管理。布局为 [num_token_blocks × block_tokens, kNumSplits, kNumExperts]，每个 token 在每个 split 下有一整行专家分数。score barrier 数组单独分配，每个 token block 一条 128 字节的 barrier line。每条 line 只用前 8 字节做实际的生产者-消费者同步，epoch 和 exit count 复用同一 line 尾部的 64 字节和 72 字节偏移——这也是 CUDA graph 修复需要 per-stream 管理 barrier 的原因：line 内的状态在调用之间是有记忆的。

Mega mHC：把 HyperConnection 的全部步骤焊死

HyperConnection（HC）是 DeepSeek-V3 引入的多路残差连接机制。在标准 Transformer 里残差就是 x + sublayer(x)；HyperConnection 把残差拓展成 4 路（kNumRoutes = 4），每层用一组可学习的混合系数把 4 路残差加权组合，再做一次矩阵乘来更新混合系数。

传统实现至少需要：一次逐元素残差混合、一次矩阵乘（生成新的 mix）、sigmoid 和 Sinkhorn 归一化、一次加权合并、一次 RMSNorm，可能还有一次 FP8 量化。Mega mHC（mega_mhc）把这些全部装进一个持久化内核。图 2 画出了融合的完整管线。

融合了什么

API 注释给出了完整语义：

/**
 * Execute shifted or normal mHC, generate the next mixes, and apply RMSNorm
 * with optional FP8 E4M3 casting.
 *
 * Args:
 *     x                              [T,H]                             BF16
 *     residual                       [T,hc_mult,H]                     BF16
 *     shifted_prev_mix               [T,hc_mult,1] FP32 | None
 *     post_mix                       [T,hc_mult,1]                     FP32
 *     comb_res_mix                   [T,hc_mult,hc_mult]               FP32
 *     fn                             [hc_mult*(hc_mult+2),hc_mult*H]   FP32
 *     mix_scales                     [3]                               FP32
 *     mix_bases                      [hc_mult*(hc_mult+2)]             FP32
 *     hc_mult                        int
 *     hc_norm_eps                    float
 *     hc_pre_eps                     float
 *     hc_post_scale                  float
 *     sinkhorn_eps                   float
 *     num_sinkhorn_iters             int
 *     rmsnorm_weight                 [H]                               BF16
 *     rmsnorm_eps                    float
 *     rmsnorm_scale                  float

 *     None

 */

内核按顺序执行以下步骤：

  1. 残差混合：new_residual = x * post_mix + comb_res_mix @ residual，逐 token 的混合操作（post_mix [T, 4, 1]、comb_res_mix [T, 4, 4]）。
  2. TF32 GEMM（Split-K）：mixes = new_residual @ Fn^T，其中 Fn [24, 4*H] 是 FP32 的混合生成矩阵。N 维 = 24（kNumHCOutputs），等于 4 路残差的 \(4 \times (4+2) = 24\) 个输出系数。
  3. Mix 生成：从 24 个输出中切分出 prev_mix、post_mix、comb_res_mix，先做 sigmoid，再做 Sinkhorn 归一化（交替行/列归一化，迭代数由 num_sinkhorn_iters 控制，测试中为 10）。
  4. Norm 输入计算：shifted 模式下 norm_input = new_residual @ prev_mix（上一步生成的 prev_mix 是偏移来的），normal 模式下直接用 new_residual。
  5. RMSNorm + 可选 FP8 量化：y = RMSNorm(norm_input)，可以同时输出 BF16 和/或 FP8 E4M3（附带 UE8M0 缩放因子，每 32 维一个，4 个打包成一个 int32）。

BLOCK_M = 64，BLOCK_K = 64，N 维固定为 24（不分块，因为只有 24 个输出列）。内核用 6 个 warpgroup，每个 4 warp，共 768 线程（kNumThreads = 6 × 4 × 32）。流水线有多个独立的 stage 组：IO（residual 和 x）4 级、Fn 2 级、A（残差混合后的中间结果）4 级、Accum 和 Coeff 各 2 级。

共享内存的布局反映了 5 条独立流水线的缓冲需求：

  • residual [4][4][64×32]（BF16×2）：IO 阶段搬入的 4 路残差，4 级流水线，route-major 排列保证每次 TMA 搬运的 64×64 块是连续的。
  • x [4][64×32]（BF16×2）：当前层输入，4 级流水线。
  • fn [2][2][4][24×32]（FP32）：Fn 混合权重矩阵的两个 K-atom，2 级流水线。每个 TMA 把一个 32 元素的 TF32 swizzle 原子搬入 SMEM。
  • pre_coeff / post_coeff [2][64][4]、comb_coeff [2][64][16]：上一步生成的混合系数，2 级流水线，保留 TMA 原生的 per-token 布局。
  • hc_norm_sqr_sums [2][64]、x1_sqr_sums [2][64]、normal_scratch [64]：Post worker 和 Normal worker 的局部统计量，双缓冲。

每对 full/empty barrier 连接一组生产者和消费者。具体的生产者→消费者映射：IO barrier（Producer WG0 → Post workers WG1/2 和 Normal worker WG5）、Fn barrier（Producer WG0 → Workspace epilogue WG3）、A barrier（Post workers WG1/2 → Producer WG0 的 MMA）、Accum barrier（Workspace epilogue WG3 → Mix worker WG4）、Coeff barrier（Mix worker WG4 → Normal worker WG5）、Stats barrier（Normal worker WG5 的平方和 → Post workers WG1/2 的 RMSNorm）、Mix arrival barrier（Mix worker WG4 → Normal worker WG5 的系数广播同步点）。总共 5 对 stage barrier 加 1 对 stats barrier 和 1 个 mix arrival barrier。这些 barrier 全部是 Cutlass 的 ClusterTransactionBarrier（底层是 mbarrier），角色在编译期写死，运行时无分支判断。这种精确的 barrier 拓扑保证了无死锁：每对 barrier 只有一个生产者和一组消费者，不存在循环依赖。

WG 0 是 producer：负责 TMA 搬运（residual、x、Fn 矩阵、混合系数）和 UMMA 的 MMA 计算。WG 1–2 是两个 Post worker：各自处理一个 token 的"后处理"——在 Shifted 模式下读取 X1（上一层的 BF16 中间输出）、加权混合残差、做 RMSNorm、可选 FP8 量化。WG 3 是 workspace epilogue：把 MMA 累加器从 TMEM 搬到全局 workspace（split 部分和与 HC norm 平方和）。WG 4 是 Mix worker：归约 split 部分和、做 Sinkhorn 归一化、输出混合系数。WG 5 是 Normal worker：融合 Mix + Pre + RMSNorm，处理非 Shifted 模式的 token。6 个 warpgroup 共 768 线程，每个 SM 只跑一个 CTA——这意味着单个 SM 的寄存器文件（SM100 上为 65536 个 32 位寄存器）被 768 个线程均分，每线程只有约 85 个寄存器。为了避免寄存器溢出，代码中大量使用 __launch_bounds__ 和手动的变量复用来压缩寄存器占用。

这条数据依赖链—— WG0(IO) → WG1/2(Post) → WG0(MMA) → WG3(Epilogue) → WG4(Mix) → WG5(Normal) ——是 Mega mHC 的关键路径。回路出现在 WG0：它先做 IO（TMA 搬运），等 Post worker 算完混合残差后（A barrier），再做 MMA。这个环可以重叠：WG0 在等待当前 tile 的 A 时，可以 prefetch 下一个 tile 的 IO——这就是 IO 和 A 各有 4 级流水线的原因。WG1/2 分别处理不同 token（各覆盖 BLOCK_M/2 = 32 个），形成 token 级的并行。WG4 和 WG5 的 Coeff barrier 让 Normal worker 在 Mix 完成之前阻塞；Stats barrier 让 Post worker 在 Normal worker 的平方和就绪前阻塞——两个反向依赖防止了未就绪数据的读取。整个拓扑无环（WG0↔WG1/2 通过不同 barrier 对交替角色，不构成死锁环），这是 7 对 barrier 设计的核心不变量。

Sinkhorn 归一化：warp-level 的行列交替

Mix worker 的核心是 run_mix_task 中的 Sinkhorn 归一化。4 路残差的混合系数组成一个 4×4 矩阵（Comb 部分），需要行列交替归一化使其逼近双随机矩阵。Sinkhorn 算法（也叫 Sinkhorn-Knopp 迭代）的思路很简单：给定一个非负矩阵，先把每行除以该行之和使行和为 1，再把每列除以该列之和使列和为 1，如此交替重复；Sinkhorn 定理保证对严格正的矩阵，这个过程收敛到一个双随机矩阵（行和与列和同时为 1）。这里的"softmax"只是归一化除法——每个元素除以其行/列之和——而非带 exp 的 softmax。代码用 warp shuffle 做行归约和列归约：

const auto sinkhorn_normalize = [&](float value) {
    // Comb logits occupy a row-major route x route region after Pre and Post.
    value = is_comb_lane ? value : 0.0f;
    const float row_max = math::warp_reduce_max<kNumRoutes>(value);
    value = __expf(value - row_max);
    float row_sum = math::warp_reduce_sum<kNumRoutes>(value);
    value = value * math::fast_rcp(row_sum) + mix_args.sinkhorn_eps;

    const auto get_col_sum = [](const float& element) {
        // For four routes, these XORs combine adjacent rows, then the two row pairs.
        float sum = element + __shfl_xor_sync(0xffffffff, element, kNumRoutes);
        sum += __shfl_xor_sync(0xffffffff, sum, 6 * kNumRoutes);
        return sum;
    };

    value *= math::fast_rcp(get_col_sum(value) + mix_args.sinkhorn_eps);
    #pragma unroll 1
    for (uint32_t iteration = 1; iteration < mix_args.num_sinkhorn_iters; ++ iteration) {
        row_sum = math::warp_reduce_sum<kNumRoutes>(value);
        value *= math::fast_rcp(row_sum + mix_args.sinkhorn_eps);
        value *= math::fast_rcp(get_col_sum(value) + mix_args.sinkhorn_eps);
    }
    return value;
};

源码：deep_gemm/include/deep_gemm/epilogue/sm100_mega_mhc.cuh 第 63–86 行（Sinkhorn 归一化：行列交替 softmax）

Sinkhorn 的每轮迭代只有两行代码（第 81–83 行）：行归一化用 warp_reduce_sum<kNumRoutes>（每 4 个 lane 求和），列归一化用 __shfl_xor_sync 交叉求和。4 路残差对应 4×4 = 16 个 Comb lane，加上 Pre 和 Post 各 4 个，正好 24 个 lane——一个 warp 的 32 个 lane 中有 24 个活跃，余下 8 个闲置。这是 kNumHCOutputs = 24 的由来。

Split-K 选择

GEMM 的 K 维（= 4*H）通常很大而 M 维的块数不多（token 数 / 64），所以需要 Split-K 来获得足够的并行度。默认 split 数为 16；非确定性模式下，代码选择"最少的 split 数使得最长的任务最短"：

static uint32_t get_num_splits(const uint32_t num_m_blocks, const uint32_t hidden, const uint32_t num_sms) {
    if (heuristics_runtime->get_deterministic_algorithms())
        return mhc_layout::kDefaultNumSplits;

    // Fewest splits that still reach the shortest possible longest task
    const uint32_t num_k_blocks = hidden / mhc_layout::BLOCK_K;
    const uint32_t max_num_splits = cute::min(
        mhc_layout::kNumMaxSplits, cute::max(mhc_layout::kDefaultNumSplits, num_sms / num_m_blocks));
    return math::ceil_div(num_k_blocks, math::ceil_div(num_k_blocks, max_num_splits));
}

源码：csrc/apis/mega_mhc.hpp 第 15–24 行（节选）

这个公式先算出最大可用 split 数（受 kNumMaxSplits = 64 和 SM 数 / M 块数的限制），再选最小的 split 数使得每个 producer 的 K 块数相同（均分）。"均分"条件很重要：如果 K 块数不能被 split 数整除，最后一个 split 会比其他 split 少算几个 K 块，导致它提前完成并空等其他 split 到达 barrier——这种"短桶效应"在 Split-K 中是主要的效率损失来源。代码宁可选更少的 split（减少并行度）也要保证均分，是因为 SM100 的 SM 数量（128 或更多）已经提供了足够的 tile 级并行度，Split-K 只是补充手段。

SF 输出的三种模式

当输出 FP8 时，缩放因子有三种布局可选，API 注释做了区分：y_gemm_sf 是 TMA 对齐的列主序（适合后续 GEMM），y_routed_sf 是连续行主序（适合路由传输），y_shared_sf 是 Mega MoE 共享专家的特殊布局。三者互斥：要么单独给 y_gemm_sf，要么同时给 y_routed_sf 和 y_shared_sf。

TF32 HC prenorm GEMM：BF16 乘 FP32，附带平方和

在 HyperConnection 的预归一化阶段，需要计算 \(D = A \cdot B^\top\)，其中 A 是 BF16 的输入、B 是 FP32 的归一化参数矩阵，结果 D 和逐行平方和 sqr_sum 都是 FP32。这个计算由一个专用内核 tf32_hc_prenorm_gemm 完成：

源码：csrc/apis/hyperconnection.hpp 第 10–55 行（节选）

接口要求 A 和 B 都是 K-major（即按列存放 K 维），D 是 N-major（按行存放 N 维），sqr_sum 是连续的一维数组。为什么用 TF32 而不是 FP32？因为 Fn 矩阵本身就是 FP32 存储的，用 TF32（truncated FP32，尾数截断到 10 位）做 MMA 能利用张量核的吞吐，精度损失对归一化步骤可以接受。

可选的 num_splits 参数开启 Split-K：此时 D 的形状变成 [num_splits, M, N]，sqr_sum 变成 [num_splits, M]，后续由消费方归约。内核同时支持 SM90 和 SM100，是 DeepGEMM 中少数跨两代架构的内核之一。之所以能跨架构，是因为 TF32 MMA 在两代硬件上的语义基本一致（SM90 的 wgmma 和 SM100 的 tcgen05.mma 都支持 TF32 累加），且 N 维只有 24——远小于典型 GEMM 的 128 或 256——不需要利用 SM100 特有的双 CTA 或 TMEM 大容量优化，因此同一套 tile 配置在两代硬件上都能高效运行。

修复：CUDA graph 重放下的 split barrier

Mega mHC 的 Split-K 和 Mega Gate 的 score barrier 都需要一个全局的 barrier 数组来同步不同 split / CTA 之间的部分和归约。这个数组用 torch::zeros() 分配并清零，之后的内核调用通过原子操作在上面做生产者-消费者同步。

问题出在 CUDA graph 上。如果 torch::zeros() 发生在 CUDA graph 捕获期间，这个分配 + 清零操作会被录进 graph——每次 replay 都会重新清零 barrier，破坏内核调用之间需要保持的 epoch 和 exit count 状态。图 3 对比了修复前后的时序。

具体的失败表现是：第一次 graph replay 后 barrier 被清零，epoch 回到 0；但内核内部维护的 epoch 期望值已经推进到 1（或更高）——producer 在 epoch 1 上发信号，consumer 却在 epoch 0 上等待（因为清零后状态重置），两边永远不匹配，导致 consumer spin 永不退出，表现为 GPU hang 或超时错误。更隐蔽的情况是：如果 exit count 被清零但 epoch 恰好对上，部分 split 可能看到残留的旧 partial sum 被当作有效数据参与归约，导致静默的数值错误——这类 bug 在 CUDA graph 的确定性重放假设下极难定位，因为症状取决于上一次调用离开时 barrier 的具体状态。

提交 5081f85（"Fix mega_mhc split barriers under CUDA graph replay (#478)"）的修复方式很直接：把 barrier 分配做成 per-stream 的懒初始化，第一次调用时分配并清零，之后复用。关键是加了一条断言，要求分配时当前流没有在做 graph 捕获。Mega mHC 中的 get_split_barriers：

static const torch::Tensor& get_split_barriers(const torch::TensorOptions& options) {
    const auto stream = at::cuda::getCurrentCUDAStream();
    DG_HOST_ASSERT(options.device() == stream.device());
    static std::unordered_map<c10::cuda::CUDAStream, torch::Tensor> split_barriers_by_stream;
    auto& split_barriers = split_barriers_by_stream[stream];
    if (not split_barriers.defined()) {
        // Warm up each stream before capture so one-time zeroing is not replayed with the graph.
        DG_HOST_ASSERT(c10::cuda::currentStreamCaptureStatusMayInitCtx() == c10::cuda::CaptureStatus::None);
        split_barriers = torch::zeros(
            {mhc_layout::kNumSplitBarriers, mhc_layout::kNumMaxMBlocks, mhc_layout::kSplitBarrierLineBytes},
            options.dtype(torch::kByte));
    }
    return split_barriers;
}

源码：csrc/apis/mega_mhc.hpp 第 26–39 行（节选）

Mega Gate 的 get_score_barriers 使用完全相同的模式：

static const torch::Tensor& get_score_barriers(const torch::TensorOptions& options) {
    const auto stream = at::cuda::getCurrentCUDAStream();
    DG_HOST_ASSERT(options.device() == stream.device());
    static std::unordered_map<c10::cuda::CUDAStream, torch::Tensor> score_barriers_by_stream;
    auto& score_barriers = score_barriers_by_stream[stream];
    if (not score_barriers.defined()) {
        // Warm up each stream before capture so one-time zeroing is not replayed with the graph.
        DG_HOST_ASSERT(c10::cuda::currentStreamCaptureStatusMayInitCtx() == c10::cuda::CaptureStatus::None);
        score_barriers = torch::zeros(
            {mega_gate_layout::kNumMaxTokenBlocks, mega_gate_layout::kScoreBarrierLineBytes},
            options.dtype(torch::kByte));
    }
    return score_barriers;
}

源码：csrc/apis/mega_gate.hpp 第 13–26 行（节选）

两者的核心都是第 20 行（mega_mhc）和第 20 行（mega_gate）的断言：c10::cuda::currentStreamCaptureStatusMayInitCtx() == c10::cuda::CaptureStatus::None。这保证了 torch::zeros() 只在 graph 捕获开始之前执行，replay 时不会重新分配或清零。

barrier 的 epoch 和 exit count 存在 kSplitBarrierLineBytes（128 字节）的第一条 line 的尾部，偏移分别为 64 字节和 72 字节。因为 barrier line 本身是 128 字节，前 8 字节是实际的 barrier 状态，后面的空间被复用来存这些管理数据——不需要额外的全局分配。这种将元数据嵌入对齐填充区的做法在高性能 GPU 内核中很常见：它避免了额外的全局内存事务，同时利用了缓存行对齐已经占用的字节。

局限与未覆盖

  • Mega Gate 的打分函数在代码中是 hardcoded 为 sqrtsoftplus，如果传入其他字符串会触发断言失败。这可能是因为 DeepSeek-V3 目前只使用这一种打分。
  • Mega mHC 的 Sinkhorn 迭代数由调用方通过 num_sinkhorn_iters 参数控制（测试中用 10），不是内核自己决定的。
  • Mega Gate 的 TMEM 转出和 top-k 选择已在上文展开，但 CTA 间的 score barrier 同步（Split-K 归约的具体时序）没有逐行分析。
  • Mega mHC 的 6 个 warpgroup 角色、Sinkhorn 和 Normal worker 已在上文展开，但 Shifted 模式下 Post worker 读取 X1 的流水线（与 ring_pipeline.cuh 的交互）没有详细分析。
  • TF32 HC prenorm GEMM 是一个相对简单的特化 GEMM，它的 SM90 和 SM100 两个实现的差异本文没有对比。
  • 本文没有实测性能数字。本地没有 GPU，仓库文档中也没有提供这些内核的 benchmark 数据。
  • Mega Gate 和 Mega mHC 只有 SM100 实现（代码中有 arch_major == 10 的断言），TF32 HC prenorm GEMM 同时支持 SM90 和 SM100。
