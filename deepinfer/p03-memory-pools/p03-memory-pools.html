TL;DR

  • DeepInfer 把显存分成两个池：随上下文增长的压缩 KV 按 128 token 一块分页，长度有上界的滑窗 KV 与压缩累加器放进每序列一个的定长状态槽。
  • 一个块是一段 uint8 字节，4 个 KV 源层在块内各占一段，别名层不占字节；折合每 token 约 891 B。
  • 滑窗环比窗口多出 6 格，恰好容下一次验证步写入的全部位置，包括之后可能被拒的草稿。
  • 环被当成“每序列只有一页”的分页缓存，块池的 store/load 内核原样复用。
  • 状态槽里只有编码器层的滑窗需要落盘，约占整槽的 45%；其余都能重算或在落盘点为空。
  • 块数按“总量 × 利用率 − 峰值 − 2 × 状态池”估算，再在各 rank 间取平均而不是最小值。

前置知识

需要了解：分页 KV cache 的基本思想（vLLM 的 PagedAttention——把 KV 切成定长块、用块表间接寻址，避免连续显存和碎片），以及第 1 篇的三种 KV 格式与字节数。前缀复用（prefix caching）的概念在落盘一节会用到。

两种缓存，两种增长律

在 vLLM 一类系统里，“KV cache 管理”几乎等于分页（paging）：把每层的 K/V 按固定 token 数切成块，用块表（block table）把逻辑位置映射到物理块 [1]。这个抽象的前提是：每层缓存都随序列长度线性增长。DeepSeek-V4.1-Flash 打破了这个前提。按第 1 篇和第 2 篇的拆解，它的每个注意力层同时持有两类缓存：

  • 压缩 KV（compressed KV）与索引 K：每 \(r\) 个 token 合成一条（\(r\in\{1,2\}\)），历史有多长就要存多长。它会增长。
  • 滑动窗口注意力（sliding window attention, SWA）的 KV：每个查询只看最近 \(W=128\) 个 token，更早的永远不会再被读。压缩累加器（compression accumulator）只保存尚未凑满 \(r\) 个 token 的那半个窗口。两者都有上界，不会增长。

把有上界的东西也塞进分页池，按我们的理解，要么一直保留整段历史（浪费），要么随窗口滑动不断释放、再申请块（碎片与簿记开销）。我们先用配置算一笔账：如果把 43 个带 SWA 的层的滑窗 KV 也按长度保存，每 token 要 \(43 \times 528 = 22{,}704\) B；128K 上下文就是约 2.8 GiB，而真正会被读到的只有最后 134 个位置。DeepInfer 的做法是分成两个池，各用各的增长律管理：

如图 1 所示，两条曲线的形状完全不同。一个 128K token 的序列在块池里占 1,024 块、约 111 MiB；它的状态槽始终是 2.98 MiB。交点在约 3.5K token：再短的请求，状态槽反而更大。这也提示我们：状态槽的个数（而不是块数）会限制短请求的并发。

本篇依次回答四个问题：一个块里的字节怎样排（分页块池）；一个状态槽里放什么（状态池）；滑窗环为什么是 134 而不是 128（134 的推导）；两个池如何共用同一套读写内核（环即一页）。最后看落盘、容量估算和分叉（落盘、容量与分叉）。

分页块池：一块 128 token，每个源层占一段字节

块大小写死在 model_metadata_utils.py 第 134、140 行：每块 128 token，块步长按 128 B 对齐。

先问一句：为什么是 128。这个数在代码里是写死的常量，没有注释解释。但它不是随便取的——本篇和前两篇用到的几个约束同时指向它，vLLM 常用的 16 只满足其中一条（整除压缩比），其余三条都吃亏：

  • 落盘粒度要对齐。外部 KV 存储按 KVSTORE_GRAIN = 128 的边界落盘（见落盘）。块大小等于落盘粒度，一个块就正好是一个落盘单元，换入换出不必跨块拼接。
  • 压缩后仍要是整数条目。C2 层每块存 \(128/2 = 64\) 条。块大小必须被所有压缩比整除，否则一个块里会出现半条压缩条目。这一条 16 也满足（\(16/2=8\)），它不是区分 16 和 128 的理由，只是一条底线。
  • 滑窗是 128。\(W=128\) 意味着一个查询的滑窗恰好横跨一到两个块，边界情况最少；若块是 16，同一个滑窗要摸到 8–9 个块。
  • 块表要短。块表长度与块大小成反比：128K token 下，块大小 128 对应 1,024 项，块大小 16 则是 8,192 项。ZOS 下块表由 GPU 内核现场展开（第 5 篇），表越短，每步要推导和搬运的元数据越少。

代价是尾块浪费：一条序列平均浪费半个块，即 64 个 token 的空间，比 vLLM 的 8 个大。换句话说，V4.1 用更粗的粒度换取了更短的块表和更整齐的落盘单元——在每 token 只有 890 B 的前提下，这笔浪费折合约 57 KB/序列，相对 111 MiB 的块池占用可以忽略。以上是我们从几处约束反推的解读，仓库没有说明取值依据。

块池是一个二维 uint8 张量 [num_gpu_blocks, block_bytes]，没有“层”这一维。分配函数 KVCacheManager.process 按层号顺序走一遍所有注意力层，给每层在块内切一段字节区间，再用 as_strided 把这段区间看成该层自己的 [num_blocks, 128/r, 1, bytes_per_token] 缓存。规则只有四条：

  1. 压缩比为 \(r\) 的层每块只存 \(128/r\) 条。C2 层（层 2–19）每块 64 条，C1 层（层 20–39）每块 128 条。所有层共用同一张块表：第 \(j\) 条压缩 token 落在 block_table[j / (128/r)]（prepare_tensor_input_v4.cpp 第 39–61 行）。
  2. 别名层不占字节。按第 2 篇的跨层共享映射，层 3–7 复用层 2 的主 KV 和索引 K，依此类推；process 遇到这些层直接取源层的视图，不推进偏移（第 428–449 行）。层 0–1 只有 SWA，DFlash 草稿层 40–42 也只有 SWA，同样不占块池。
  3. 每段按 32 B 对齐（第 437、459 行）。
  4. 块步长对齐到 \(\operatorname{lcm}(128, 288)=1152\) B。注释给出两个理由：DeepGEMM 的索引内核要求块步长是 128 B 的倍数；主注意力要求块步长是每 token 字节数（288 B）的倍数（第 479–484 行）。内核本身在空子模块里，我们只能转述这条约束。

代入配置，真正占字节的只有 4 个源层（层 2、8、14、20），每层两段：

图 2 上半部分按字节比例画出了这个块。合计 113,920 B，向上对齐到 1152 的倍数得 114,048 B，即 \(114{,}048/128 = 891\) B/token。作为对照，如果 38 个压缩层各自持有 KV，每块要 1,321,472 B，是现在的 11.6 倍（与第 2 篇的估算一致）。表 1 也说明为什么“块”而不是“层”是分配单位：一个序列只需要一张块表，申请一块就同时拿到了 4 个源层、两种压缩比所需的全部空间。块 0 永远不分配（block_manager.hpp 第 27 行），留给填充行使用。

BlockManager：空闲列表加引用计数

BlockManager（block_manager.hpp）同时管理块池和状态池。它的核心是一个空闲列表（free list）加每块一个的引用计数。分配（allocate）从列表头弹出一个块号，释放（free）把块号还回列表尾。引用计数在分叉（fork）时加一：子序列继承父序列的块表，共享的块标记为“被多人引用”，直到所有引用者都释放，块才真正归还空闲列表。块 0 永远不分配，留给 CUDA Graph 的填充行使用。状态池也用同一个 BlockManager，区别只在于槽数和每槽大小。

状态池：每序列一个定长槽，槽内先放要落盘的

状态池是另一个二维 uint8 张量 [num_slots, slot_bytes]，一行就是一个序列的全部定长状态，类名叫 StateBlock。槽数由get_num_state_slots给出：

\[ N_{\text{slot}} = \lfloor 1.2\,N \rfloor + 1 \](1)
“多 20%”的理由代码里没有写。我们的推测：分叉时子序列先钉住（pin）父序列的槽、再复制到新槽，异步调度下已结束序列的槽要延迟释放，这些时刻占用的槽数会超过 \(N\)。

其中 1.2 来自环境变量 DEEPINFER_NUM_STATE_SLOTS_RATIO（environ.py 第 169 行）。式式 (1) 末尾的 +1 对应槽 0：状态池和块池用同一个 BlockManager，它从不分配编号 0。代码注释说明了槽 0 的用途：CUDA Graph 按固定批大小捕获，凑数的填充行落在“placeholder 的 state 0”这个 dummy 槽里（deepseek.py 第 222 行）。写缓存的参考实现里还专门处理了“多个填充 token 同时写 slot 0”的情况（store_kv_cache.py 第 112 行）。\(N=256\) 时共 308 个槽。

槽内布局在 StateBlock 里，原则写在文档字符串第一句：需要落盘的放前面（stored region），不落盘但运行时要用的放后面（dropped region）。这样落盘只需截取槽的前 state_size_to_disk 个字节。

图 2 下半部分按同样的方式画出了一个槽。表 2 里有三处值得停一下。

第一，dropped 区的滑窗有 23 层，不是 20 层。分区函数 _is_dropped_swa_layer 的判据是“运行时层号 ≥ n_prefill_layer（= 20）”，而运行时层号把 DFlash 的 3 个草稿层排在 40–42（layer_utils.py，config.py 第 146–155 行）。部署 Q&A 只说 dropped 区放“YOCO 消费层的 SWA”和压缩累加器 [2]，没有提草稿层。

第二，只有 ca_state，没有 ica_state。部署 Q&A 写的是 dropped 区里有 ca_state / ica_state 两种累加器 [2]。但代码只在索引器不走 use_kproj 路径时才分配 ica_state（第 123–127 行），而 V4.1 的配置把所有压缩层的 use_kproj 设为 True（config.py 第 122 行）。以代码为准：V4.1 的槽里没有索引累加器。C1 层不需要累加器（ratio > 1 才分配），别名的 C2 层也不重复分配，所以只有 3 份。

第三，槽总长对齐到 \(\operatorname{lcm}(32, 528)\)。注释解释了原因：每层的 swa_cache 视图的第 0 维步长继承整个槽（第 301–305 行）。下一节会看到，这正是“把环当成一页”所需要的。

134 = 128 + 6：多出的 6 格留给一次验证步

环长由 get_inference_swa_block_size 给出，回退长度 \(B\) 由 environ.py 第 136–139 行给出：

\[ \begin{aligned} R &= W + B, \\ B &= \max\!\left(B_{\text{env}},\; K + 1\right) = \max(0,\, 5+1) = 6 . \end{aligned} \](2)

式 (2) 中 \(B_{\text{env}}\) 是 DEEPINFER_MAX_BACKTRACKING_TOKENS 的显式设置（缺省按 0 处理），\(K\) 是 DEEPINFER_USE_NEXTN_DECODE（缺省 5）。要理解为什么是 \(K+1\)，先看一次推测解码（speculative decoding）的验证步往环里写了什么。

验证步写入 \(K+1\) 个位置，包括会被拒绝的草稿

设验证步开始时，位置 \(0..c-1\) 的 KV 都已在缓存里，位置 \(c\) 是上一步采样出的真实 token，位置 \(c+1..c+K\) 是 \(K\) 个草稿。调度器给这一步的查询长度是 \(1+\)草稿数，最多 \(K+1=6\)（scheduler.hpp 第 689 行，以及第 930–936 行的不变式注释）。解码时，这 6 个 token 的滑窗 KV 先按 slot_mapping_store_swa 写进环，注意力再从环里一起读出来（写槽位：第 98–108 行；读窗口：第 631–652 行）。写入发生在验证之前，所以被拒绝的草稿也已经写进去了；它们留在环里当垃圾，下一步从新的提交点重新写、把它们覆盖掉。

位置 \(p\) 的 KV 写在环的第 \(p \bmod R\) 格。写入位置 \(p\) 会覆盖位置 \(p-R\)。一个环在写指针为 \(h\) 时，保存的恰好是区间 \([h-R,\, h)\)。

代码要求的不变式：回退 \(B\) 个之后仍有完整窗口

代码里有两处注释把 \(B\) 的含义写得很直白：“要保证回退后仍然有 window size 个”（prepare_tensor_input_v4.cpp 第 354 行，model_runner.py 第 108 行）。用上面的记号，不变式是：对写指针 \(h\) 往回退不超过 \(B\) 的任意恢复点 \(h'\in[h-B,\,h]\)，它之前的完整窗口 \([h'-W,\, h')\) 都还在环里。由于环里是 \([h-R, h)\)，这等价于

\[ h-B-W \;\ge\; h-R \quad\Longleftrightarrow\quad R \;\ge\; W+B . \](3)

一次验证步把写指针从 \(c\) 推到 \(c+K+1\)。取 \(B=K+1\)，不变式就保证：即使把这一步写的 \(K+1\) 个位置全部撤销、退回到 \(h'=c\)，步前的窗口 \([c-W, c)\) 仍然完好。换句话说，环为一整步写入预留了余量。

一个数值例子

取 \(c=1000\)。验证步写入位置 1000–1005，落在环的第 62–67 格（\(1000 = 7\times 134 + 62\)）。写完后写指针 \(h=1006\)，环里是位置 872–1005，共 134 个。

对照图 3 逐一核对：

  • 查询 1000 要看 873–1000，查询 1005 要看 878–1005。本步所有查询需要的并集是 873–1005，共 133 个位置，全在环里。
  • 若 6 个位置全部接受，提交点变成 1006，下一步写 1006–1011，会依次覆盖 872–877，而这些已不在任何窗口里。
  • 若 5 个草稿全部被拒，提交点变成 1001，下一步查询 1001 要看 874–1001，也在环里；1001–1005 的垃圾会被下一步覆盖。
  • 位置 872 不被本步任何查询读到。只有当恢复点退到 \(h'=1000\)，也就是整步撤销时，窗口 872–999 才用得上它。若环长是 133，写 1005 时就已经把 872 覆盖了。
部署 Q&A 给 6 格另一个用途：解码期每跨过一个 128 边界就把窗口复制到副本区，复制位置最多越过边界 5 个 token，由这 6 格吸收 [2]。开源代码里这个复制触发是关闭的（见局限），无法核对。

所以严格说，仅就“这一步的注意力读得对”和“草稿被拒后能继续”而言，\(W+K = 133\) 格已经够了（最坏情况是退回到 \(c+1\)）。代码取 \(B=K+1\)，多给的那 1 格让环满足更强的不变式：一整步的写入都可以撤销。环境变量还允许把 \(B\) 设得更大；注释说这个上限也服务于前缀缓存（prefix cache）命中后的回退：“搜索的时候需要先回退再多轮”（第 101–110 行）。

同一个不变式也决定了压缩累加器的环长

压缩累加器的环长是 get_inference_compress_block_size：

\[ R_c = r + B - 1 = 2 + 6 - 1 = 7 . \](4)

式 (4) 和式 (3) 出自同一个推理。压缩比为 \(r\) 的层，在恢复点 \(h'\) 需要的是还没凑满一组的那几个 token，即 \([\,r\lfloor h'/r\rfloor,\; h')\)，最多 \(r-1\) 个。要求对所有 \(h'\in[h-B, h]\) 都能取到，就需要 \(h-B-(r-1) \ge h-R_c\)，即 \(R_c \ge r+B-1\)。代码取的正是等号。两个环长用同一个 \(B\)、按同一个“回退 \(B\) 仍可恢复”的条件推出，这让我们比较确信上面对 \(B\) 的解读是对的（这是我们的推导，代码没有写出这个式子）。

把环当成只有一页的分页缓存

两个池的数据结构不同，但 DeepInfer 只写了一套读写内核。关键在 process 第 406–422 行：每层的 swa_cache 是状态池上的一个跨步视图

seg = slots[:, start:start + 134 * 528]
swa_cache = seg.as_strided(
    (num_slots, 134, 1, 528),      # 形状
    (slot_bytes, 528, 528, 1))     # 步长

形状 [页数, 页内条数, 1, 每条字节] 和块池视图一模一样，只是“页”换成了“槽”、页内 134 条、页步长是整个槽（3,128,928 B）。对写入内核 store_kv_cache 来说，它只接收一个扁平的槽位号 slot，按 slot / 页长 和 slot % 页长 拆成页号与页内偏移；对读取内核 load_paged_kv_cache 来说，它只接收一串 [页号, 起, 止, 目标偏移] 段。两个池之间唯一的区别，是 C++ 侧怎样算出这些槽位号和段：

  • 块池：slot = block_table[j / t] · t + j mod t，\(t = 128/r\)；读历史时用 append_paged_range 沿块表逐块切段。
  • 环：slot = state_id · 134 + p mod 134；读历史时用 append_ring_range，页号恒为 state_id，只在 p mod 134 绕回 0 的地方切一刀。

图 4 下半部分是预填充的情形。make_swa_block_load_plan 对每个序列取已缓存长度 \(h\) 之前的 \(W\) 个位置，交给 append_ring_range，并断言总长恰好是“序列数 × \(W\)”。这一刀切下去得到的段，与块池在块边界处切出的段，格式完全相同。

这个设计还有一个顺序上的细节。预填充一个 chunk 时，它要写回环的最后 134 个位置（第 103 行只给 \(q-j \le 134\) 的 token 分配槽位，其余记 −1 不写），而这些槽位可能与刚要读出的历史窗口重叠。所以 attn.py 第 845–855 行坚持“先 load、后 store”，注释原话是“prefill must store only after the cache load”。

“滚动缓冲”并非新想法：Mistral 7B 的 rolling buffer cache 就把位置 \(i\) 存在 \(i \bmod W\) [3]。DeepInfer 的不同在于环长多出 \(B\)，并把环接到分页内核上。

好处是实在的：FP8 量化写入、按页读取并反量化的 TileLang 内核只维护一份，测试矩阵也只有一份（cache_common.py 第 403 行的注释：“Keep store and compact-range paged load on one shape matrix”；矩阵里的页长除了 64，还有非 2 的幂的 133）。解码期的 FlashMLA 也同时接收两种缓存，但它的内部实现在空子模块里，这里不展开。

落盘：只在 128 的倍数处，只存前 20 层

状态槽里哪些东西要落盘，由“丢了能不能便宜地找回来”决定。StateBlock 文档字符串和第 285 行注释给了两条理由：

  • 解码器层的滑窗可以重算。它本来就由有界重放在每次预填充时重建，注释原话是“恢复依赖 prefill 重算”。草稿层按层号归入同一组，也不落盘。
  • 压缩累加器在落盘点总是空的。“Compression windows end at KVSTORE_GRAIN boundaries, so only SWA is persisted”：落盘只发生在 128 的倍数处（KVSTORE_GRAIN = 128），128 能被 \(r=2\) 整除，此时每个压缩组都恰好凑满，没有半截状态要带走。

剩下必须落盘的只有编码器层 0–19 的滑窗环，它们是跨请求复用前缀时省不掉的状态：

\[ \begin{aligned} \texttt{state\_size\_to\_disk} &= 20 \times 134 \times 528\ \text{B} \\ &= 1{,}415{,}040\ \text{B} . \end{aligned} \](5)

式 (5) 与部署 Q&A 给出的数字一致 [2]。注意落盘的是 134 个位置而不是 128 个：恢复出来的环和推理时的环格式相同，带着同样的回退余量。

按 128 对齐的落盘与“重新成环”

落盘入口 select_state_slice_to_store 的第一件事是断言落盘位置 \(h\) 是 128 的倍数（第 787 行）。之后分两种情况：

  • 默认配置（DEEPINFER_PREFILL_STORE_EXTRA_STATE 关闭）：运行时的环就是 134 格，直接截取槽的前 1,415,040 字节（第 788–797 行）。
  • 开启 extra-state：运行时的环会加长 128 格（若开启有界重放，再加上保留长度，见第 96–110 行），因为预填充结束的位置一般不是 128 的倍数，要多存一段才能保证落盘点的窗口还在。落盘时用 select_state_slice 把 \([h-134,\, h)\) 从长环里抽出来，按 p mod 134 重新排进一个 134 格的环（state_cache.py 第 44–45 行）。

举个例子：开启 extra-state 且不开截断，长环是 262 格。一个提示长 1,100 的请求预填充完后，长环里是位置 838–1099。按 Q&A 的规则，落盘点取 \(\lfloor(1100-1)/128\rfloor\times 128 = 1024\) [2]。重排把位置 \(p\in[890, 1024)\) 从长环第 \(p \bmod 262\) 格搬到输出的第 \(p \bmod 134\) 格。无论运行时的环有多长，落盘的永远是一个“写指针为 \(h\) 的 134 格环”。读回时 load_state_to_cache 做反方向的散射（第 73–81 行）。

落盘之后去哪，开源代码没有答案。据部署 Q&A，块 KV 存在专用的 3FS 集群，滑窗 KV 只存在产生它的机器的主机内存里，由一个内存目录记录位置，跨机命中时远程拉取 [2]。完整的分层存储见导读。

容量估算与分叉：两个池怎样一起被分配

块数：先扣两倍状态池，再在各 rank 间取平均

启动时，profile_num_available_blocks 先跑一次 profile，量出峰值显存 \(P\)，再按下式求块数：

\[ N_{\text{block}} = \left\lfloor \frac{M \cdot u \;-\; P \;-\; 2\, N_{\text{slot}}\, S_{\text{slot}}}{S_{\text{block}}} \right\rfloor \](6)

式 (6) 中 \(M\) 是 GPU 总显存，\(u\) 是 gpu_memory_utilization（默认 0.90），\(S_{\text{slot}} = 3{,}128{,}928\) B，\(S_{\text{block}} = 114{,}048\) B。状态池乘 2 的注释是“state store & copy buffer，所以要开两倍大小”（第 243 行）。\(N=256\) 时，状态池是 \(308 \times 3{,}128{,}928 \approx 0.90\) GiB，两倍约 1.80 GiB，折合约 16,900 个块，也就是约 216 万个 token 的压缩 KV。

接着有两步值得注意（第 264–266 行）：

  1. 各 rank 的块数做 all-reduce 求和，再除以 world size，即取平均；
  2. 结果向下取偶数。

分析，未经实测

取平均而不是取最小值意味着：如果某个 rank 的峰值显存 \(P\) 明显高于其他 rank，平均出来的块数可能超过它自己能放下的数量，这个 rank 的实际占用就会超出 \(M \cdot u\)，余量不够时有显存溢出的风险。各 rank 的 \(P\) 在什么部署下会显著不同，仓库里没有数据。这是我们读代码得出的推断。

另一处也只能算分析：第二份状态池（copy buffer）在开源版中从未分配。CacheEngine 只分配一份 gpu_states，引擎的 copy_state 字段初始化为 None 后再无赋值（llm_engine.py 第 284 行）。因此开源版按两倍扣除，却只用了一倍，多扣的约 0.90 GiB 处于闲置。按上一段的换算，这 0.90 GiB 相当于约 8,450 个块、约 108 万个 token 的压缩 KV——在 \(N=256\) 的配置下，够再装下八条 128K 的序列。对只跑离线推理的使用者，把 DEEPINFER_NUM_STATE_SLOTS_RATIO 调小或改掉这个两倍系数是一笔直接的收益；不过这需要确认 copy buffer 确实用不到，而这一点取决于未开源的 KV 存储系统。

分叉：共享整块，复制尾块和整个槽

同一前缀派生多个分支（fork）时，块池和状态池的处理方式不同，原因还是两种增长律。fork_seq 让子序列先直接引用父序列的块表和状态槽，并把它们钉住（引用计数加一）。等子序列真正被调度时（第 398–433 行、第 602–617 行）：

  • 写满的块继续共享。新 token 只追加在已缓存长度之后，写满的块不会再被写，共享是安全的。
  • 尾块复制一份。最后一个含已缓存 token 的块（注释说它“可能写了一半”）是子序列接下来要写的地方，所以申请新块并整块复制；它之后预留的块直接丢弃引用。
  • 状态槽整槽复制。_clone_state 申请新槽，把（旧，新）记入 clone_states。之后 clone_and_zero_states_and_blocks 在 GPU 上异步复制一整行（约 3 MiB），然后释放对旧槽的钉住。

状态槽没法“写时才复制”：滑窗环每一步都会被写，累加器也是，分叉后第一步就会改动它。所以对状态池来说，复制是立即发生的；真正按写时复制（copy-on-write）做的只是块池。

这里要回到两种增长律 留下的那句话：限制短请求并发的是槽数，不是块数。图 5 把两个池各自能支撑的并发数画在一起：块池的容量随 \(L\) 反比下降，槽数是一条水平线，实际上限取两者的小者。块池的总容量取决于卡的大小和式 (6) 的余量，仓库没有定下来，所以图里扫了三个量级——但结论对三者都成立：在相当宽的长度区间里，先用尽的是槽而不是块。即便只给块池 10 GiB，也要到约 39K token 之后块池才成为瓶颈。

分叉正是这个约束最吃紧的场景。\(N=256\) 的配置下整机只有 308 个槽（式 (1)），每个分支——不管它多短——都要独占一个。一次 8 路的束搜索（beam search）就吃掉 8 个槽，而它在块池里几乎不占地方：分支共享前缀的所有写满块，只各自复制一个尾块。于是并发上限由槽数先到：38 条 8 路束搜索就把 308 个槽用尽，此时块池可能还空着大半。图 1 的交点（约 3.5K token）给的是单序列视角的分界，分叉把这个分界进一步推向槽数一侧——因为分支共享块、却不共享槽。

局限与未开源部分

  • 外部 KV 系统的钩子全是空实现。should_copy_state 恒返回 False，do_save_kvcache、pe_prepare_save_kvcache、pe_do_save_kvcache 只有文档字符串（llm_engine.py 第 811–825 行）。落盘、3FS 读写、命中查询都不在仓库里。本文关于存储去向的描述全部来自部署 Q&A。
  • 解码期的副本区复制在开源版中关闭。Q&A 说每跨过一个 128 边界就把窗口复制到副本区 [2]；代码里的 do_copy_state 在 copy_state is None 时直接返回（第 787–798 行），而它从未被赋值。
  • 零状态重算也没有触发方。clone_and_zero_states_and_blocks 支持把槽清零，但调度器从不填充 zero_states 列表；与之配合的 swa_valid_start 也只在外部系统里设置（参见第 2 篇）。
  • 文档与代码的两处差异：dropped 区没有 ica_state，却多了 3 个 DFlash 草稿层的滑窗（状态池）。
  • 没有任何测量。本文所有字节数、块数都是按配置和代码公式计算的，没有在 GPU 上跑过。我们只复现了显存布局的算术。“134 中多出的 1 格具体被哪条路径用到”“取平均的容量估算是否在实际部署中出过问题”都是读代码得出的分析，未经实测。
  • 闭源内核：FlashMLA、DeepGEMM 对块步长的对齐要求只能从注释转述，无法核对。

小结

核心结论

DeepInfer 按增长律给缓存分池：会增长的压缩 KV 进 128 token 一块的分页池，块内按源层分段、别名层零字节；不会增长的滑窗 KV 和压缩累加器进每序列一个的定长槽，槽内把需要落盘的放在最前。两个池通过“环 = 一页”的跨步视图共用同一套内核。

p01–p03 显存预算汇总表

前三篇的字节数散落在不同章节，在此统一汇总。增长律三种：O(L) 随序列长度线性增长，O(1) 常量，O(W) 随窗口大小固定。

跨层共享将持久块 KV 从 10,324 B 压到 890 B（11.6×）。这是 CSA2 跨层共享的收益：三张共享表把 38 个压缩层的块 KV 别名到 4 个源层。它与 YOCO 式的“只算一次”是两件事，共享省的是存储，YOCO 讲的是计算（第 2 篇）。块池的 891 B/token 几乎等于 890 B/token，差的 1 B 来自分页对齐的填充。

三个数字串起了整个设计。891 B/token 是块池的增长率，它来自跨层共享和 FP4。134 是环长：128 的窗口加上一次验证步的 6 个写入位置，保证整步可撤销。1,415,040 B 是每序列真正要落盘的状态，来自“只在 128 的倍数处落盘”：这时压缩累加器为空，解码器滑窗可以重算，剩下的只有编码器层的滑窗。
